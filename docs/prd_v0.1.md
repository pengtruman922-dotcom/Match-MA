日期：2026-05-28
状态：前端开发对齐草案
适用对象：产品讨论、Bolt 前端开发、后端接口联调

> 本文档沉淀当前已确认的产品范围、角色、核心流程和关键规则。若与早期讨论文档冲突，以本文档和 `frontend_ui_spec_v0.1.md` 为前端开发优先依据。

## 1. 产品定位

Match-MA 是面向内部并购咨询 / 中间方团队的并购撮合工作台。

系统不面向外部买家或卖家开放。一期重点服务内部营销顾问的日常工作：快速录入标的和买家意向、持续更新业务进展、发起双向推荐、复核 AI 自动更新结果、沉淀关系和跟进记录。

### 1.1 一期目标

- 让营销顾问可以快速建立标的项目和买家意向。
- 让业务更新从“人工拆分录入”变成“统一入口 + AI 拆解 + 自动应用 + 事后复核”。
- 让推荐从单向“为买家找标的”扩展为双向“为买家找标的 / 为标的找买家”。
- 让推荐结果通过“推荐列表”和“推荐报告”进入后续跟进，而不是在卡片上堆叠大量操作。
- 为后续 LLM、OCR、embedding、联网调研、Debug Mode 和后台 Worker 留出前端状态与交互空间。

### 1.2 一期非目标

- 不做外部买家 / 卖家门户。
- 不做复杂字段级权限。
- 不做完整数据看板，只保留入口或基础占位。
- 不在前端伪造 LLM、OCR、推荐报告等真实结果。
- 不把 Dry Run 写入一期核心 PRD；一期只保留 Debug Mode。

## 2. 用户角色

### 2.1 营销顾问

一期核心用户。

主要任务：

- 新建和维护标的项目。
- 新建和维护买家意向。
- 录入业务更新、聊天记录、截图、附件、跟进信息。
- 发起推荐：为买家找标的，或为标的找买家。
- 查看 AI 自动更新后的字段变化和关系进展。
- 对错误更新进行编辑、回退或补充说明。

核心体验原则：

```text
快速记录，不强迫等待；
后台异步处理；
AI 先自动应用，用户事后复核；
错误可以查看、编辑、回退。
```

### 2.2 管理员 / 平台运营

一期只保留必要入口和角色意识。

主要任务：

- 查看整体数据统计。
- 管理用户、部门、项目空间等权限基础字段。
- 进入 Debug Mode 查看 AI 执行细节。

### 2.3 开发测试人员

开发测试人员通过管理员账号使用 Debug Mode。

Debug Mode 的目的不是避免写入，而是展示 AI 和后台任务执行细节，包括 prompt、模型、原始输出、解析 JSON、检索过程、token、耗时、错误等。

## 3. 核心对象

### 3.1 seller_target：标的项目

标的管理的核心对象是 `seller_target`，即标的项目，不是单纯公司主体。

约 90% 的标的项目是公司本身，约 10% 是公司的一部分资产、业务线、股权包或其他交易项目。因此需要支持 `target_type`。

标的新建后默认可推荐，但如果信息缺失，应展示“信息不足”等状态。

### 3.2 seller_party：卖方主体

`seller_party` 表示卖方 / 公司主体。多数情况下 `seller_target` 和 `seller_party` 名称相同，但模型上分开。

### 3.3 buyer_party：买家主体

`buyer_party` 表示买方公司或机构主体。

买家主体不是推荐的核心工作对象，只是买家公司档案。

### 3.4 buyer_intent：买家意向

买家意向是推荐的核心对象。

一个买家主体可以有多个买家意向，但 90% 情况下一个买家只有一个主要意向。

买家意向允许不绑定买家主体，用于匿名需求或临时搜索任务。

### 3.5 buyer_seller_relation：买家意向与标的关系

`buyer_seller_relation` 的核心唯一关系是：

```text
buyer_intent_id + seller_target_id
```

推荐、已推荐、在谈、不感兴趣、尽调、终止等进展最终都应落在这个关系和关系事件中。

### 3.6 business_update：统一业务更新

统一业务更新是录入所有业务变化的入口。

用户不需要自己判断一段话是标的事实、买家反馈、关系进展还是买家意向变化。系统应由 AI 拆解并写入不同对象。

### 3.7 extracted_action：AI 拆解动作

AI 将 `business_update` 拆解为一个或多个 `extracted_action`。

一期重要变化：默认思路不是“等待用户确认后再应用”，而是“可定位、可信度足够的动作先自动应用，然后在工作台、列表和详情页显著提示用户复核”。

### 3.8 action_application_log：应用日志 / 回退依据

所有自动应用或人工编辑都必须写入 `action_application_log`，记录：

- 修改对象。
- 修改字段。
- 修改前值。
- 修改后值。
- 来源。
- 操作人 / 系统节点。
- 时间。
- 是否已复核。

后续回退能力基于该日志实现。

## 4. 全局导航与信息架构

主导航采用：

```text
工作台 | 标的管理 | 买家管理 | 智能推荐 | 数据看板 | 设置
```

一期优先级：

1. 工作台。
2. 标的管理。
3. 买家管理，默认以买家意向为核心工作列表。
4. 智能推荐。
5. 数据看板，占位或基础统计。
6. 设置，占位或基础模型配置入口。

顶部应保留全局搜索，搜索范围包括：

- 标的。
- 买家。
- 买家意向。
- 联系人。
- 推荐会话。
- 更新记录。

## 5. 工作台首页

首页名称使用“工作台”，不是 Dashboard。

工作台应从“展示板”转为“任务板”，主体是“待我处理”。

### 5.1 页面目标

用户打开系统后第一眼能看到：

- 哪些 AI 自动更新需要复核。
- 哪些解析或调研异常需要处理。
- 哪些推荐后需要跟进。
- 哪些标的或买家意向信息不足。
- 最近发生了什么重要业务变化。

### 5.2 主体结构

```text
左侧：待我处理 + 最近动态
右侧：快速操作 + 本周概览 + 最近推荐会话
```

### 5.3 待我处理分组

至少包含：

- 标的自动更新待复核。
- 买家意向自动更新待复核。
- 买家-标的关系进展待复核。
- 推荐后待跟进。
- 解析异常。
- 信息不足。

注意：由于一期采用“先自动应用，再复核”，工作台文案应避免使用“待确认”作为唯一概念。更准确的表达是：

```text
已自动更新，待复核
```

或：

```text
需复核
```

### 5.4 快速操作

快速操作至少包括：

```text
新建标的
新建买家意向
录入业务更新
发起推荐
```

“新建买家”不是最高频入口，可以放在买家管理页或新建买家意向流程中。

## 6. 标的管理

### 6.1 标的列表

标的列表采用：

```text
高密度表格 + 每行第二行摘要
```

列表主列建议包括：

- 标的名称。
- 一级行业。
- 二级行业 / 细分赛道。
- 省份。
- 城市。
- 营收。
- 利润。
- 估值。
- PE。
- 是否还卖。
- 推荐状态。
- 信息状态。
- 附件数量。
- 负责人。
- 最近更新。
- 操作。

营收、利润、估值、PE 不聚合成一个“关键字段”，必须分列展示。

### 6.2 附件列

标的列表需要附件列。

- 没有附件：显示 `0` 或空态。
- 有附件：显示附件数量。
- 点击附件数量：展开附件列表或进入详情页的“附件与证据”区域。

### 6.3 状态展示

状态要简单直接，避免过多枚举造成理解负担。

推荐状态：

```text
可推荐 / 暂不推荐
```

信息与处理状态可以用徽标展示：

```text
信息不足
需复核
解析中
调研中
解析异常
```

### 6.4 行内操作

每行主操作保持 1-2 个：

```text
推荐买家
录入更新
```

点击标的名称进入标的详情页。

点击“推荐买家”进入智能推荐页，模式为“为标的找买家”，并默认选中当前标的。

点击“录入更新”打开统一业务更新抽屉，并自动绑定当前标的。

## 7. 新建标的

### 7.1 最小输入

新建标的最小输入只有：

```text
标的名称
```

附件非必选，允许一句话建档。

负责人默认当前用户，也允许手动修改。

### 7.2 提交流程

用户提交后立即建档并返回标的列表，不等待附件解析、OCR、联网调研。

新建后默认：

```text
推荐状态：可推荐
信息状态：信息不足，视字段完整度而定
```

### 7.3 去重检查

去重检查在提交前实时做，不调用 LLM。

主要通过数据库快速匹配：

- 名称。
- 别名。
- 公司全称。
- 地区。
- 关键词。

疑似重复只展示 Top 5。

名称过短时提示：

```text
名称过短，建议补充公司全称或地区
```

如果疑似重复，用户可选择：

```text
更新已有标的
仍然新建
```

### 7.4 附件解析与联网调研

附件解析和联网调研都是异步任务。

联网调研由用户手动触发，不在新建时自动触发。

触发入口：

- 标的详情页：单个触发。
- 标的列表页：批量选择触发。

任务完成后，列表和详情页应显示状态回流与字段变化。

## 8. 标的详情页

### 8.1 页面结构

标的详情页采用：

```text
顶部摘要 + Tab + 右侧状态栏
```

### 8.2 Tab 设计

标的详情页 tab 采用：

```text
基本信息 | 附件与证据 | 关系/跟进 | 更新记录
```

注意：不单独设置“推荐记录”tab。

推荐记录本质上应拆解到“关系/跟进”中。例如用户录入：

```text
2026年5月28日推给广工
```

系统应理解为：该标的新增或更新了一个买家意向关系，该关系的进度事件是“2026年5月28日已推荐”。

因此“推荐记录”是关系事件的一种，不作为独立 tab。

“更新记录”必须放在最后一个 tab。

### 8.3 基本信息分组

基本信息按 6 组展示：

```text
身份
行业业务
财务
估值交易
风险
信息缺口
```

### 8.4 字段编辑与来源

详情页允许直接编辑核心字段。

字段值必须尽量展示：

- 来源。
- 更新时间。
- 操作日志。
- 是否已复核。

字段来源可以是：

- 用户手动输入。
- 附件解析。
- OCR。
- 联网调研。
- 统一业务更新。
- 系统计算。

高影响字段必须留痕，例如：

- 营收。
- 利润。
- 估值。
- 报价。
- PE。
- 是否还卖。
- 是否可并表。
- 是否可控股。
- 转让比例。
- 推荐状态。

### 8.5 右侧状态栏

右侧固定状态栏展示：

- 自动更新待复核。
- 信息缺口。
- 最近关系 / 跟进。
- 快捷操作。

## 9. 买家管理

### 9.1 核心对象

买家管理的核心工作列表是：

```text
买家意向列表
```

买家主体 `buyer_party` 是主数据，买家意向 `buyer_intent` 是工作对象。

### 9.2 新建买家意向

新建入口优先叫：

```text
新建买家意向
```

新建时可以选择：

- 关联已有买家。
- 新建买家。
- 不绑定买家，作为临时 / 匿名意向。

### 9.3 买家意向状态

买家意向状态用于表达是否还需要继续推荐。

一期简化为：

```text
继续推荐
暂停推荐
```

暂停推荐原因放在详情或抽屉中展示。

### 9.4 买家意向列表字段

买家意向列表建议展示：

- 意向名称。
- 买家名称。
- 联系人。
- 一级行业。
- 区域要求。
- 利润要求。
- 估值 / PE。
- 控股 / 并表要求。
- 上市状态偏好。
- 当前状态。
- 负责人。
- 最近更新。

### 9.5 买家详情页

买家详情页采用：

```text
顶部摘要 + Tab + 右侧状态栏
```

建议 tab：

```text
基本信息 | 意向 | 关系/跟进 | 更新记录
```

买家画像放在“基本信息”里。

买家意向是核心 tab。

推荐记录同样不单独设 tab，而是拆到“关系/跟进”中。

买家意向详情一期不做独立页面，采用买家详情里的展开抽屉。

## 10. 统一业务更新

### 10.1 定位

统一业务更新用于处理：

- 标的基础事实更新。
- 标的事件。
- 买家反馈。
- 买家意向变化。
- 买家-标的关系进展。
- 黑名单 / 排除信息。
- 内部备注。

用户可以输入文字、聊天截图、附件或混合材料。系统由 AI 自动拆解并应用到对应对象。

### 10.2 入口

统一业务更新入口包括：

- 工作台快捷入口。
- 标的列表 / 标的详情。
- 买家列表 / 买家详情。
- 买家意向列表 / 买家意向抽屉。
- 智能推荐结果。

不同入口自动带上下文：

| 入口 | 默认上下文 |
| --- | --- |
| 工作台快捷入口 | 不绑定，由用户选择或 AI 识别 |
| 标的列表 / 详情 | 当前标的 |
| 买家详情 | 当前买家 |
| 买家意向列表 / 抽屉 | 当前买家意向 |
| 推荐结果 | 当前推荐会话、买家意向、标的 |

### 10.3 自动应用与事后复核

一期核心原则：

```text
先自动应用，再支持查看、复核、编辑、回退。
```

含义：

- AI 能明确定位对象和字段时，系统自动应用更新。
- 自动应用后必须写入应用日志。
- 自动应用后在工作台、列表、详情页显著提示“需复核”。
- 用户复核时看到 before / after、来源、证据和 AI 解析结果。
- 如果更新错误，用户可以手动编辑；回退能力作为重要能力设计，前端应预留入口。

例外：

- 对象无法识别。
- 字段无法映射。
- 置信度明显不足。
- 多个候选对象冲突。

这类情况不自动应用，进入“需人工处理”。

### 10.4 复核页 / 抽屉

统一业务更新处理结果页应展示：

- 原始输入。
- 识别到的对象。
- 自动应用的动作。
- 未应用、需人工处理的动作。
- 字段变更 before / after。
- 来源附件 / OCR / 截图。
- 操作：标记已复核、编辑、回退、忽略、查看详情。
- Debug Trace，管理员可见。

注意：这个页面的核心动作不是“确认后才入库”，而是“复核已自动入库的变更”。

## 11. 智能推荐

### 11.1 双向推荐

智能推荐支持：

```text
为买家找标的
为标的找买家
```

入口包括：

- 智能推荐全局页面。
- 买家意向列表 / 抽屉的“推荐标的”。
- 标的列表 / 详情的“推荐买家”。

### 11.2 页面结构

智能推荐页采用：

```text
两栏布局 + 可收起条件抽屉
```

- 左栏：对话区。
- 右栏：推荐结果区。
- 顶部：模式切换、当前对象、推荐数量、已加入推荐列表数量、生成推荐报告、查看条件。
- 条件快照通过“查看条件”抽屉展示，不常驻占一整栏。

### 11.3 对话引导

首次进入推荐页且已选择对象时，对话区不能空白。

示例引导：

```text
已加载买家意向条件。您可以：
- 直接发送“开始推荐”使用现有条件
- 输入补充条件覆盖或细化
- 输入“帮我总结当前条件”查看条件快照
```

### 11.4 连续对话

推荐支持连续对话，例如：

```text
第一个不错，但不要 PE 超过 13 的。
再放宽到长三角。
排除利润未知的。
优先浙江省内。
```

系统应根据对话更新本次推荐条件和结果。

### 11.5 推荐结果保存

推荐聊天记录需要保存，方便回看。

结构化推荐结果只需要长期保存用户采纳的部分，例如加入推荐列表、生成报告、后续写入关系的内容。

匿名需求推荐后，不自动生成临时 buyer_intent。

## 12. 推荐结果卡片与推荐列表

### 12.1 卡片主操作

推荐卡片折叠态只保留一个主操作：

```text
加入推荐列表 / 已加入推荐列表
```

不在折叠态放“推荐、移除、录入反馈、查看详情”等多个按钮。

已加入状态需要强视觉区分，例如绿色实心按钮 + 对勾。

### 12.2 卡片内容

卡片折叠态需要直接展示足够判断信息：

- 名称。
- 推荐等级。
- 核心字段。
- 匹配摘要。
- 缺口摘要。
- 历史接触提示。

### 12.3 历史接触提示

为买家找标的时：

- 当前买家对该标的“不感兴趣”：硬排除，不出现在推荐结果。
- 该标的与其他买家有接触：展示灰色提示，例如 `接触：无锡某上市公司初步沟通中`。
- 已在谈不影响推荐给其他买家，只提示用户。

为标的找买家时：

- 当前买家意向对该标的不感兴趣：硬排除。
- 该买家 / 意向近期已被推荐其他标的：展示灰色提示，例如 `近30天已推荐：苏州器械、杭州医药商业；其中1个在谈`。

默认统计窗口：近 30 天。

### 12.4 生成推荐报告

顶部显示推荐企业数量和“生成推荐报告”按钮。

- 推荐列表为空：按钮可见但禁用，hover 提示“请先将推荐项加入推荐列表”。
- 推荐列表非空：按钮高亮可点击。

一期可以先做按钮和占位流程；后端未完成时不能伪造报告内容。

---

## 13. Debug Mode

### 13.1 定位

一期只保留 Debug Mode，不写入 Dry Run 作为核心需求。

Debug Mode 的含义是：

```text
展示 AI、检索、任务执行细节。
```

不是：

```text
不写入数据。
```

### 13.2 可见性

Debug Mode 只对管理员账号可见。

普通营销顾问不显示入口。

### 13.3 展示内容

管理员开启 Debug Mode 后，应能在相关页面看到：

- job 状态。
- LLM 节点名称。
- provider / model。
- prompt 版本。
- prompt 输入。
- 原始输出。
- 解析后的 JSON。
- schema 校验错误。
- 检索 / 候选池信息。
- token。
- 耗时。
- 费用。
- 错误摘要。

## 14. 前端工程约束

前端代码必须放在：

```text
frontend/
```

不允许把 Vite 项目文件直接放仓库根目录。

前端 API Base URL 使用环境变量：

```text
VITE_API_BASE_URL=https://match-ma-production.up.railway.app/api/v1
```

API 封装集中在：

```text
frontend/src/lib/api.ts
```

组件里不要散落 fetch。

后端未实现的 LLM、OCR、推荐、报告、Debug 能力可以做显式占位，但不能伪造真实业务结果。
