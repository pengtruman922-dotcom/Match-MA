## 2. 系统定位

Match-MA 定位为：

> 面向内部咨询公司 / 中间方团队的并购标的与买家需求撮合管理平台。

系统当前只服务内部用户，不直接开放给卖家或买家。

后续如需向买家展示平台资源，可以单独设计资源看板，例如：

- 覆盖多少行业。
- 覆盖多少地区。
- 标的数量。
- 买家意向数量。
- 成交量 / 活跃量。

但底层标的、买家、跟进、推荐明细均属于内部核心资产，不对外开放。

## 3. 与旧系统的关系

新系统不再以旧系统中的 `report / chunk / FastGPT knowledge base` 为中心。

新系统核心对象是：

- `seller_target`：标的项目。
- `seller_party`：卖方 / 公司主体。
- `buyer_party`：买方主体。
- `buyer_intent`：买方收购意向。
- `buyer_seller_relation`：买方与标的之间的关系状态。
- `business_update`：统一业务更新入口。
- `extracted_action`：AI 从业务更新中提取的候选动作。
- `recommendation_session`：推荐对话和推荐过程留痕。

旧系统可复用的能力或经验：

- 附件上传。
- PDF / Word / PPT / Excel 解析。
- OCR fallback。
- 联网 researcher 思路。
- LLM 调用配置经验。
- Railway 部署经验。

明确不复用：

- FastGPT push。
- FastGPT 知识库。
- FastGPT agent。
- 旧 `report_chunks` 作为主数据。
- 旧 `pipeline_v3.py` 作为新主流程。

旧数据暂不迁移。

## 4. 当前已确认的核心产品原则

### 4.1 新系统生成自己的 ID

不沿用旧系统 BD 编号。

建议 ID 类型：

- `seller_party_id`
- `seller_target_id`
- `buyer_party_id`
- `buyer_intent_id`
- `recommendation_session_id`
- `business_update_id`
- `extracted_action_id`

可以保留可选展示字段，例如：

- `display_name`
- `short_name`
- `internal_code`

但它们不作为业务主键。

### 4.2 标的是项目，不一定等于公司

标的主对象为：

```text
seller_target
```

约 90% 的 `seller_target` 是公司本身，约 10% 是某公司的一部分资产、业务线、股权包或其他交易项目。

`seller_target` 需要支持：

- `company`：公司整体。
- `equity`：股权包 / 控制权。
- `asset`：资产包。
- `business_line`：业务线 / 板块。
- `listed_control`：上市公司控制权 / 壳资源。
- `other`：其他。

### 4.3 卖方主体单独建模

卖方 / 公司主体为：

```text
seller_party
```

多数情况下，`seller_target` 和 `seller_party` 名称可能相同，但模型上分开。

### 4.4 买家按公司主体管理

买方主体为：

```text
buyer_party
```

当前不强制细分集团、平台、基金、二级公司等复杂层级。

一个 `buyer_party` 可以有多个 `buyer_intent`。

### 4.5 买家意向可以匿名存在

买家意向优先以“某次搜索任务 / 某个收购意向”为单位。

允许：

- 绑定具体买家的意向。
- 匿名需求 / 临时搜索任务。

匿名需求可以直接进入推荐流程，后续再决定是否保存为正式买家意向。

### 4.6 标的新建后默认可推荐

已确认：标的新建后默认进入“可推荐”。

同时系统需要记录：

- 信息完整度。
- 缺失字段。
- 待复核字段。
- 是否正在后台解析 / 调研补全。

如果标的信息很少，推荐时应作为低优先候选或提示信息不足，而不是默认不可推荐。

### 4.7 推荐可用状态先保持简单

一期只区分：

- `recommendable`：可推荐。
- `on_hold`：暂不推荐。

后续如有需要，再扩展为已成交、下架、归档、独家推进中等状态。

## 5. 用户角色

当前角色分三类。

### 5.1 营销顾问

一期核心用户。

主要任务：

- 标的管理。
- 买家管理。
- 买家意向管理。
- 标的-买家意向匹配推荐。
- 录入业务更新。
- 上传聊天截图、文字、材料，系统自动解析。
- 查看和处理待复核项。

核心 UX 原则：

```text
快速记录，不强迫等待；
后台异步解析；
关键变更显眼提示；
用户可以事后接受、拒绝、编辑或撤销。
```

### 5.2 管理员 / 平台运营管理人员

后续再细化。

核心任务可能包括：

- 权限配置。
- 用户管理。
- 负责人分配。
- 字典与标签管理。
- 数据统计。
- 项目进度追踪。
- 待复核项管理。

### 5.3 开发测试人员

该角色很重要，一期需要“测试模式”。

主要任务：

- 观察 LLM 配置。
- 观察 prompt 输入输出。
- 观察结构化解析结果。
- 观察 token 消耗、费用、耗时。
- 观察候选池、filter DSL、SQL、推荐证据包。
- 使用 dry run 调试流程。
- 对比模型和 prompt。

## 6. 技术方案确认

### 6.1 主检索底座

当前接受的推荐方案：

```text
PostgreSQL + pgvector
```

理由：

- Match-MA 首先是结构化买卖双方关系和交易状态管理平台，不是纯向量知识库。
- 主数据、关系状态、黑名单、推荐留痕、审计、向量索引可以放在同一个数据库。
- 一期复杂度低，适合快速验证产品闭环。
- 未来如有需要，可通过 SearchBackend 接口扩展 Qdrant / OpenSearch / Elasticsearch。

### 6.2 LLM 意向解析方案

当前接受的推荐方案：

```text
LLM 输出 filter DSL
→ 服务端校验 DSL
→ 服务端编译成参数化 SQL
→ 服务端执行 SQL
```

不采用：

```text
LLM 直接生成 SQL 并执行
```

理由：

- 安全可控。
- 字段和操作符可白名单校验。
- 能表达 hard / preference / missing policy / blacklist 等业务语义。
- 避免 LLM 把偏好误写成硬条件。
- 避免 LLM 错误排除未知字段。
- 后续表结构变化时，只需更新 DSL compiler，不需要让 LLM 直接适配数据库细节。

### 6.3 推荐职责分工

LLM 负责最终推荐 list。

但推荐流程中：

- 黑名单硬排除由服务端执行。
- “不感兴趣”硬排除由服务端执行。
- 暂不推荐标的排除由服务端执行。
- 候选池生成由服务端编排。
- LLM 基于候选池和证据包输出最终推荐 list、推荐理由、风险、信息缺口和推进建议。

## 7. 更新与反馈统一入口

已确认：采用统一业务更新入口。

不再要求用户判断自己是在：

- 更新标的。
- 记录买家反馈。
- 更新买家意向。
- 记录买家-标的关系。

用户只需要提交一条业务更新。

系统底层统一保存为：

```text
business_update
```

AI 再解析为多个候选动作：

```text
extracted_action[]
```

可能动作类型：

- `seller_fact_update`
- `seller_event_create`
- `buyer_event_create`
- `buyer_seller_relation_update`
- `buyer_intent_target_exclusion`
- `buyer_intent_update_suggestion`
- `buyer_target_blacklist_suggestion`
- `internal_note`
- `future_task`

## 8. 业务更新示例

用户输入：

```text
今天和上海启元项目方见面，对方还愿意卖，但报价从 3 亿提高到 3.5 亿。
无锡某上市公司说可以继续看，但希望确认 4 月财务。
另外浙江国资这边对启元不感兴趣，觉得利润规模太小。
```

系统应拆分为：

### 8.1 标的事实更新候选

```text
上海启元仍愿意卖。
报价从 3 亿提高到 3.5 亿。
```

处理策略：

- 属于标的核心事实。
- 默认进入待复核。
- 不直接覆盖 seller_profile。

### 8.2 标的事件

```text
今天与上海启元项目方见面。
```

处理策略：

- 高置信时可自动保存为 seller_event。

### 8.3 买家-标的关系更新

```text
无锡某上市公司继续看上海启元。
希望确认 4 月财务。
```

处理策略：

- 更新或新增 buyer_seller_relation。
- 关系状态可为 `initial_contact` / `materials_requested` / 后续枚举待定。
- 可自动应用或中低置信待复核。

### 8.4 买家意向-标的排除

```text
浙江国资对上海启元不感兴趣。
原因：利润规模太小。
```

处理策略：

- 默认挂在 `buyer_intent + seller_target`。
- 高置信时可自动应用。
- 后续推荐该 buyer_intent 时硬排除上海启元。

### 8.5 买家意向更新建议

```text
浙江国资可能偏好更高利润规模标的。
```

处理策略：

- 只生成 suggestion。
- 不自动修改 buyer_intent。
- 在显眼位置提示用户接受 / 忽略 / 编辑后接受。

## 9. 不感兴趣的层级规则

已确认：`不感兴趣` 默认挂在：

```text
buyer_intent + seller_target
```

即：

```text
buyer_intent_target_exclusion
```

规则：

- 给同一个 buyer_intent 推荐时，硬排除该 seller_target。
- 给同一买家的其他 buyer_intent 推荐时，不一定排除。
- 给其他买家推荐时，不受影响。

如果文本明确表示买家全局不看某标的，例如：

```text
这个公司我们整体不看了。
以后不用给我们推这个项目。
集团内部已经否掉了。
```

则可生成：

```text
buyer_target_blacklist_suggestion
```

一期建议谨慎处理 buyer-level blacklist：

- 默认进入待复核或显眼建议。
- 用户接受后再对该买家所有意向生效。

## 10. 待复核与建议机制

已确认：待复核和建议要放在显眼位置，尤其列表页。

### 10.1 标的核心事实默认待复核

以下字段属于核心事实，AI 提取后默认进入待复核：

- 报价。
- 估值。
- PE。
- 营收。
- 净利润。
- 资产负债率。
- 是否还卖。
- 是否可控股。
- 是否可并表。
- 交易状态。
- 推荐可用状态。
- 重大风险标签。

用户可以：

- 接受。
- 拒绝。
- 编辑后接受。
- 查看来源。
- 稍后处理。

### 10.2 买家意向规则更新默认只生成 suggestion

例如：

```text
买家多次反馈利润太小。
系统建议：是否将该意向的利润偏好从 2000 万提高到 5000 万？
```

用户可以：

- 接受修改。
- 忽略。
- 编辑后接受。
- 查看来源反馈。

### 10.3 列表页显眼展示

标的列表建议展示：

```text
待确认 3
```

买家意向列表建议展示：

```text
待建议 2
```

首页 / Dashboard 建议展示：

- 标的核心事实待确认数量。
- 买家意向建议待确认数量。
- 业务更新解析失败数量。
- 低置信关系状态数量。

## 11. 测试模式

一期测试模式采用：

```text
Trace + Dry Run
```

### 11.1 Trace

记录正式流程的详细执行轨迹，仅开发测试人员可见。

Trace 内容包括：

- LLM 输入。
- Prompt 版本。
- 模型配置。
- 原始输出。
- 结构化解析结果。
- JSON schema validation。
- token 消耗。
- 费用估算。
- 耗时。
- filter DSL。
- 编译后的 SQL。
- 候选数量。
- 候选来源。
- 最终候选证据包。
- 最终推荐 JSON。
- extracted_action 分流结果。
- 错误与重试。

### 11.2 Dry Run

Dry Run 含义：

```text
试运行，可以读取正式数据，但不写入正式业务数据。
```

Dry Run 可以用于：

- 测试业务更新解析。
- 测试买家意向解析。
- 测试候选池生成。
- 测试最终推荐。
- 对比 prompt 或模型。

Dry Run 不写入：

- seller_profile。
- buyer_intent。
- buyer_seller_relation。
- blacklist。
- 正式 recommendation_session。

Dry Run 可以写入：

- debug_run。
- model_trace。
- 临时结果。

后续二期再建设完整 Eval Dataset。

## 12. 当前收敛后的核心用户流程

当前核心用户流程收敛为 6 条：

1. 新建标的：快速建档，后台解析和调研，核心事实待复核。
2. 新建买家：创建买家主体，可轻量建档。
3. 新建 / 更新买家意向：自然语言解析，保存意向，建议显眼展示。
4. 统一业务更新：任意上下文录入文字 / 截图 / 附件，AI 分流为事实、事件、关系、建议。
5. 发起推荐：对话式输入或选择意向，候选池 + LLM 最终推荐，支持连续对话。
6. 测试模式：Trace + Dry Run。

“记录反馈”不再作为单独流程，而是并入“统一业务更新”。

## 15. 已确认流程：新建标的 v0.1

### 15.1 核心原则

```text
先建档，不等待；
附件解析后更新一轮；
联网调研后再更新一轮；
低风险字段高置信自动写入；
核心财务 / 交易字段进入待确认；
用户在列表页即可看到状态和处理入口。
```

### 15.2 最小输入

新建标的至少需要输入：

- 标的名称。

附件非必选，允许一句话建档。

可选字段：

- 负责人：默认当前用户，可手动修改。
- 行业：可选，不强制。
- 地区：可选，不强制。
- 备注 / 一句话描述：可选。
- 附件：可选。

用户只输入标的名称也允许建档。

### 15.3 实时去重

用户输入标的名称后，系统提交前实时进行去重检查。

匹配因子包括：

- 标的名称。
- 公司名称。
- 简称 / 别名。
- 统一社会信用代码，后续可用。
- 股票代码，后续可用。
- 地区。
- 行业。
- 名称相似度。

去重结果只展示 Top 5。

如果名称过短，提示：

```text
名称较短，可能返回较多相似结果。建议补充公司全称或地区。
```

如果疑似重复，用户选择：

- 更新已有标的。
- 仍然新建。

如果用户确认新建，则创建新的 `seller_target`。

### 15.4 提交后立即建档

用户提交后，系统立即创建：

- `seller_target`
- `seller_party` 初步记录
- 初始 `business_update` 或 `initial_input`
- 附件记录，若有

标的默认：

```text
recommendation_status = recommendable
owner_user_id = 当前用户
```

如果只填了名称，则处理状态为：

```text
信息待完善
```

用户提交后不等待附件解析，不等待联网调研，直接回到标的列表。

### 15.5 附件解析阶段

如果上传附件，后台异步解析。

列表状态显示：

```text
附件解析中
```

解析完成后：

- 高置信低风险字段自动写入。
- 核心字段进入待确认。
- 解析失败显示异常。

低风险字段示例：

- 行业。
- 地区。
- 产品。
- 资质。
- 官网。
- 公司简介。
- 细分赛道标签。

核心字段示例：

- 营收。
- 净利润。
- 估值。
- 报价。
- PE。
- 是否还卖。
- 是否可控股。
- 是否可并表。
- 重大风险。

### 15.6 联网调研阶段

联网调研手动触发，不默认自动触发。

入口：

- 标的详情页：单个触发。
- 标的列表页：批量选择触发。
- 筛选“信息待完善”后批量触发。

调研中显示：

```text
调研中
```

调研完成后：

- 补充公开信息。
- 生成新的低风险字段或待确认核心字段。
- 不直接覆盖人工确认或更高优先级来源。
- 显示“待确认 N”或“调研完成”。

### 15.7 列表页状态

标的列表建议列：

```text
标的名称 | 行业 | 地区 | 推荐状态 | 处理状态 | 负责人 | 更新时间
```

推荐状态一期只展示：

- 可推荐。
- 暂不推荐。

处理状态保持简单：

- 信息待完善。
- 附件解析中。
- 调研中。
- 待确认 N。
- 异常 N。
- 已完善。

示例：

```text
+--------------------------------------------------------------------------------+
| 标的名称          行业        地区      推荐状态    处理状态        负责人      |
|--------------------------------------------------------------------------------|
| 上海启元项目      医药健康    浙江      可推荐      待确认 5       张三        |
| 杭州某医药商业    -           浙江      可推荐      信息待完善     李四        |
| 苏州某器械企业    医疗器械    江苏      可推荐      附件解析中     张三        |
| 南京某能源项目    新能源      江苏      可推荐      调研中         王五        |
| 宁波某材料公司    新材料      浙江      暂不推荐    异常 1         李四        |
+--------------------------------------------------------------------------------+
```

### 15.8 待确认处理

点击 `待确认 N`，打开侧边栏或弹窗。

用户可以：

- 接受。
- 编辑后接受。
- 忽略。
- 查看来源。

待确认字段应展示：

- 字段名。
- 当前值。
- 建议值。
- 来源。
- 证据片段或附件定位。

示例：

```text
+--------------------------------------+
| 上海启元项目 / 待确认字段             |
+--------------------------------------+
| 净利润                                |
| 当前：未知                            |
| 建议：2500 万                         |
| 来源：2024审计报告.pdf 第12页         |
| [接受] [编辑] [忽略]                  |
|                                      |
| 报价                                  |
| 当前：3 亿                            |
| 建议：3.5 亿                          |
| 来源：5月26日跟进记录                 |
| [接受] [编辑] [忽略]                  |
+--------------------------------------+
```

### 15.9 不覆盖原则

来源优先级暂定：

```text
人工确认 > 最新跟进记录 > 年报 / 审计 / 公告 > 上传材料 > 公开调研 > LLM 推断
```

如果低优先级来源与高优先级来源冲突：

```text
生成待确认冲突项，不自动覆盖。
```

## 16. 已确认流程：统一业务更新 v0.1

### 16.1 核心原则

```text
一个入口，支持混合输入；
用户可选上下文；
AI 自动拆分；
默认全待复核；
用户确认后分别入库；
全程保留原文、OCR、解析、字段变化和操作记录。
```

### 16.2 入口

一期入口：

1. 首页快捷入口：`录入业务更新`。
2. 标的详情页：`新增更新`。

首页快捷入口适合：

- 零散聊天记录。
- 多个标的混合更新。
- 多个买家反馈。
- 用户不确定该归到哪个对象。

标的详情页入口适合：

- 明确与当前标的相关。
- 当前标的默认作为上下文。

### 16.3 上下文选择

提交时优先推荐选择上下文，但不强制。

可选：

- 关联标的：可多选，可不选。
- 关联买家：可多选，可不选。
- 关联意向：可多选，可不选。

没选的内容由 AI 识别。

如果从标的详情页打开，当前标的默认已选。

### 16.4 输入类型

支持：

- 文字。
- 大段聊天记录。
- 截图。
- 附件。
- 多项目、多买家混合内容。

截图处理：

```text
原图保存
→ OCR 文本保存
→ OCR 文本进入 AI 解析
→ AI 解析结果保存
```

原图、OCR 文本、AI 解析结果都要可追溯。

### 16.5 提交后立即保存

用户提交后立即创建：

```text
business_update
```

保存内容：

- 原始文字。
- 原始图片 / 附件。
- OCR 文本。
- 用户选择的上下文对象。
- 提交人。
- 提交时间。
- 来源入口：首页 / 标的详情。
- 处理状态。

状态：

```text
解析中
```

用户可以离开，不必等待。

### 16.6 AI 拆分 extracted_action

AI 解析后生成多个动作：

```text
extracted_action[]
```

一期动作类型：

- `seller_fact_update`
- `seller_event_create`
- `buyer_seller_relation_update`
- `buyer_intent_target_exclusion`
- `buyer_intent_update_suggestion`
- `buyer_target_blacklist_suggestion`
- `internal_note`
- `unresolved_item`

所有动作默认：

```text
pending_review
```

即默认全待复核。

### 16.7 确认交互

如果用户还停留在页面：

```text
解析完成后弹出侧边栏 / 确认面板
```

如果用户已经离开：

```text
标的列表 / 标的详情更新记录 tab 显示 待确认 N
```

确认面板按类型分组：

```text
本次识别到 6 项更新

[标的事实 2]
- 报价：3 亿 → 3.5 亿        高影响
  [接受] [编辑] [忽略]

- 是否还卖：未知 → 仍愿意卖  高影响
  [接受] [编辑] [忽略]

[标的事件 1]
- 今日已与项目方见面
  [接受] [编辑] [忽略]

[买家-标的关系 2]
- 无锡某上市公司：继续看，需确认 4 月财务
  [接受] [编辑] [忽略]

- 浙江国资 / 医药意向：不感兴趣，原因利润太小
  [接受] [编辑] [忽略]

[买家意向建议 1]
- 建议提高利润规模偏好
  [接受] [编辑] [忽略]
```

允许操作：

- 单条接受。
- 单条编辑后接受。
- 单条忽略。
- 批量接受本次全部动作。
- 批量忽略。
- 查看来源。
- 稍后处理。

批量接受时，高影响动作要明显提示。

例如：

```text
本次包含 2 个高影响字段：报价、是否还卖。
确认批量接受？
```

### 16.8 确认后写入位置

| action 类型 | 用户接受后写入 |
| --- | --- |
| `seller_fact_update` | `seller_profile` / `seller_fact` |
| `seller_event_create` | `seller_event` |
| `buyer_seller_relation_update` | `buyer_seller_relation` / `relation_event` |
| `buyer_intent_target_exclusion` | `buyer_intent_target_exclusion` |
| `buyer_intent_update_suggestion` | 用户接受后更新 `buyer_intent` |
| `buyer_target_blacklist_suggestion` | 用户接受后更新 buyer-level blacklist |
| `internal_note` | `internal_note` |
| `unresolved_item` | 保留为未解决项，用户后续处理 |

所有应用动作都写入：

```text
action_application_log
```

记录：

- 操作人。
- 操作时间。
- 原值。
- 新值。
- 来源。
- 是否由 AI 提取。
- 是否编辑后接受。
- 是否可回滚。

### 16.9 标的详情更新记录 tab

标的详情页增加：

```text
基本信息 | 附件 | 关系买家 | 推荐记录 | 更新记录
```

`更新记录` tab 展示该标的相关的所有业务更新。

如果一个首页快捷入口输入涉及多个标的，则同一条 `business_update` 会出现在每个相关标的的更新记录中。

卡片示例：

```text
+--------------------------------------------------------------------------------+
| [业务更新] 2026-05-26  张三                                                     |
| 来源：首页快捷录入 · 文字 + 截图                                                |
| 状态：部分应用 · 待确认 2                                                       |
| 关联：上海启元项目 / 无锡某上市公司 / 浙江国资医药意向                           |
|                                                                                |
| 字段变化：                                                                      |
| 报价：3 亿 → 3.5 亿                                                             |
| 是否还卖：未知 → 仍愿意卖                                                       |
|                                                                                |
| [展开] [处理待确认]                                                             |
+--------------------------------------------------------------------------------+
```

展开后展示：

- 原始输入。
- OCR 文本。
- AI 识别动作。
- 字段变化。
- 证据来源。
- Trace，测试人员可见。

### 16.10 列表页提醒

标的列表应体现统一业务更新产生的待处理事项。

例如：

```text
上海启元项目    医药健康    浙江    可推荐    待确认 3
```

点击 `待确认 3`：

- 可进入该标的的待确认动作。
- 可直接打开更新记录侧边栏。
- 可批量接受或逐条处理。

### 16.11 与当前平台更新记录的继承关系

当前平台更新记录的优点：

- 时间线卡片。
- 字段变更对比。
- 输入来源。
- 操作人。
- 展开详情。
- 执行步骤。

Match-MA 继续保留这些体验，但底层从：

```text
intake_logs
```

升级为：

```text
business_update
extracted_action
action_application_log
```

这样既能显示“字段从 A 到 B”，也能显示“AI 识别了哪些动作、哪些应用了、哪些还待确认”。

## 17. 已确认流程：买家管理 v0.1

### 17.1 买家主体 buyer_party

买家主体为：

```text
buyer_party
```

最小输入：

- 买家名称。

通常是公司名称。

新建买家需要去重。

去重因子可包括：

- 买家公司全称。
- 简称。
- 别名。
- 统一社会信用代码，后续可用。
- 所属集团，后续可用。
- 地区。
- 负责人。
- 历史联系人。

买家主体可以轻量建档，先不要求完整画像。

### 17.2 买家列表

买家列表建议展示：

```text
买家名称 | 负责人 | 意向数 | 继续推荐意向数 | 最近更新
```

示例：

```text
+----------------------------------------------------------------+
| 买家名称              负责人      意向数   继续推荐   最近更新 |
|----------------------------------------------------------------|
| 浙江某国资平台        张三        2        1          05-26    |
| 无锡某上市公司        李四        1        1          05-25    |
| 某能源集团            王五        3        2          05-22    |
+----------------------------------------------------------------+
```

### 17.3 买家意向 buyer_intent

买家意向为：

```text
buyer_intent
```

关系：

```text
一个 buyer_party 可以有多个 buyer_intent。
```

当前业务中，约 90% 的买家只有一个意向。因此 UI 上应避免给用户造成复杂层级感。

如果买家只有一个意向，可以在买家详情中默认展示当前主要意向。

如果买家有多个意向，再展示意向列表。

### 17.4 买家意向状态

已确认买家意向状态采用两个主状态：

| 中文展示 | 底层枚举 | 含义 |
| --- | --- | --- |
| 继续推荐 | `active` | 该意向仍有效，后续可以继续推荐标的 |
| 暂停推荐 | `paused` | 当前不需要继续为该意向推荐标的 |

可选记录暂停原因，例如：

- 已找到标的。
- 已收购。
- 暂停收购。
- 预算变化。
- 战略调整。
- 联系不上。
- 其他。

列表页只展示 `继续推荐 / 暂停推荐`，详情页再展示原因。

### 17.5 买家意向联系人

买家意向可以没有联系人。

如果有联系人，联系人应挂在具体意向上，而不是只挂在买家主体上。

原因：同一买家的不同意向可能对应不同联系人。

### 17.6 买家意向列表

买家列表和买家意向列表分开。

买家意向列表是推荐工作的重要入口。

建议展示字段：

```text
买家/意向 | 行业 | 地区 | 利润要求 | PE/估值 | 交易要求 | 状态 | 待建议 | 负责人
```

示例：

```text
+------------------------------------------------------------------------------------------------+
| 买家意向                            行业        地区      利润要求   PE/估值     状态       待处理 |
|------------------------------------------------------------------------------------------------|
| 浙江国资 / 医药健康并表需求          医药健康    长三角    2000万+    PE≤13      继续推荐   建议2  |
| 某能源集团 / 新能源控股需求          新能源      江浙      利润为正   50-100亿   继续推荐   -      |
| 某文旅平台 / 轻资产运营需求          文旅/IP     全国      未明确     未明确     暂停推荐   -      |
+------------------------------------------------------------------------------------------------+
```

买家意向详情页增加：

```text
[推荐标的]
```

点击后跳转智能推荐页，并默认：

```text
模式 = 为买家找标的
已选择 buyer_intent = 当前意向
```

### 17.7 买家详情页

买家详情页建议 tab：

```text
基本信息 | 意向 | 关联标的 | 推荐记录 | 更新记录
```

最小展示内容：

- 买家名称。
- 负责人。
- 意向列表。
- 意向对应联系人。
- 当前继续推荐 / 暂停推荐状态。
- 已推荐 / 不感兴趣 / 在谈标的摘要。

### 17.8 买家画像 buyer_profile

买家画像需要和买家意向区分。

`buyer_profile` 表示买家的长期稳定属性，例如：

- 买家类型：国资平台、产业集团、上市公司、基金等。
- 所属地区。
- 产业背景。
- 是否有上市平台。
- 资金能力。
- 决策特点。
- 历史偏好。
- 明确不看的方向。
- 已收购案例。
- 常见联系人。

`buyer_intent` 表示某个具体需求，例如：

- 行业。
- 地域。
- 利润。
- PE。
- 是否并表。
- 是否控股。
- 是否上市 / 非上市。
- 排除项。
- 当前是否继续推荐。

推荐时优先级：

```text
本次对话输入 > buyer_intent > buyer_profile > 行业模板
```

一期买家画像不需要过度结构化，可先支持：

- `buyer_profile_summary`
- `stable_preferences`
- `stable_negative_preferences`

并通过业务更新和反馈逐步生成建议。

## 18. 已确认流程：智能推荐 v0.1

### 18.1 首页主导航

首页主导航采用三个 tab：

```text
标的管理 | 买家管理 | 智能推荐
```

### 18.2 推荐模式

智能推荐支持双向推荐。

模式一：

```text
为买家找标的
```

底层枚举：

```text
buyer_to_target
```

输入为买家意向 / 买家 / 匿名自然语言需求，输出为标的推荐列表。

模式二：

```text
为标的找买家
```

底层枚举：

```text
target_to_buyer
```

输入为标的，输出为买家意向 / 买家推荐列表。

智能推荐页内可以展示：

```text
[为买家找标的] [为标的找买家]
```

或简化为：

```text
[找标的] [找买家]
```

### 18.3 推荐入口

入口 A：智能推荐页。

- 用户主动选择推荐模式。
- 可以选择买家、买家意向、标的。
- 也可以输入匿名需求。

入口 B：买家意向列表 / 详情页。

- 买家意向详情页增加 `[推荐标的]`。
- 点击后跳转到智能推荐页。
- 默认模式为 `为买家找标的`。
- 默认选中当前 buyer_intent。

入口 C：标的列表 / 详情页。

- 标的详情页增加 `[推荐买家]`。
- 点击后跳转到智能推荐页。
- 默认模式为 `为标的找买家`。
- 默认选中当前 seller_target。

### 18.4 为买家找标的

输入：

```text
buyer_intent / buyer_party / 匿名自然语言需求
```

输出：

```text
seller_target 推荐列表
```

系统使用数据：

- buyer_intent。
- buyer_profile。
- buyer_intent_target_exclusion。
- buyer_target_blacklist。
- seller_profile。
- buyer_seller_relation。
- 推荐历史。

规则：

- buyer_intent_target_exclusion 命中时，对该 buyer_intent 硬排除对应 seller_target。
- buyer_target_blacklist 命中时，对该 buyer_party 硬排除对应 seller_target。
- seller_target 暂不推荐时，全局排除。
- 已有其他买家接触 / 在谈不排除，只提示。
- 字段未知不直接排除，按 missing policy 降权或标记信息缺口。

### 18.5 为标的找买家

输入：

```text
seller_target
```

输出：

```text
buyer_intent 推荐列表 / buyer_party 推荐列表
```

系统使用数据：

- seller_profile。
- buyer_intent。
- buyer_profile。
- buyer_intent_status。
- buyer_intent_target_exclusion。
- buyer_seller_relation。
- 推荐历史。

规则：

- 已暂停推荐的 buyer_intent 不推荐。
- 某 buyer_intent 已明确不感兴趣该 seller_target，则不推荐。
- 买家已接触 / 在谈该标的时不排除，但提示。
- 买家意向缺少关键字段时，LLM 可作为潜在匹配并标记缺口。

### 18.6 匿名需求

匿名需求推荐后，不自动生成 buyer_intent。

匿名需求只保存在：

```text
recommendation_session
```

后续可以提供按钮：

```text
[保存为买家意向]
```

但不自动生成。

### 18.7 推荐结果保存

推荐结果默认保存。

保存对象：

```text
recommendation_session
```

两种模式都保存：

- `buyer_to_target`
- `target_to_buyer`

推荐 session 应记录：

- 推荐模式。
- 用户输入。
- 选中的买家 / 意向 / 标的。
- intent_snapshot。
- 候选池。
- LLM 输出。
- 最终推荐结果。
- 连续对话历史。
- 用户后续操作。

### 18.8 连续对话机制

已确认连续对话采用：

```text
LLM 生成 intent_patch / action
→ 服务端重新生成候选池
→ LLM 基于候选池重新推荐
```

LLM 不直接读全库自由判断，而是负责：

- 理解用户本轮自然语言。
- 判断是更新搜索条件、解释结果，还是提出业务动作。
- 输出结构化 `intent_patch` 或 `proposed_action`。

服务端负责：

- 应用 intent_patch。
- 重新生成候选池。
- 执行黑名单 / 不感兴趣 / 暂不推荐等硬约束。
- 构造候选证据包。

LLM 再基于候选池证据包输出推荐。

示例：为买家找标的。

用户：

```text
不要连锁药店，优先医疗器械和 IVD。
```

LLM 输出：

```json
{
  "type": "intent_patch",
  "patch": {
    "negative_sub_sectors": ["连锁药店"],
    "preferred_sub_sectors": ["医疗器械", "IVD"]
  }
}
```

服务端更新当前 session 的 `intent_snapshot`，重新生成候选池，再让 LLM 重新推荐。

示例：为标的找买家。

用户：

```text
只看还在积极找医药标的的买家，暂停的不要。
```

LLM 输出：

```json
{
  "type": "intent_patch",
  "patch": {
    "buyer_intent_status": "active",
    "industry_requirement": ["医药健康"]
  }
}
```

服务端重新查 buyer_intent 候选池。

### 18.9 推荐会写库动作

连续对话中，如果用户表达的是业务动作，例如：

```text
把第二个推荐给买家看看，其他先不用。
```

LLM 应输出 `proposed_action`，例如：

```json
{
  "type": "proposed_action",
  "action": "create_relation_from_recommendation",
  "seller_target_id": "st_xxx",
  "buyer_intent_id": "bi_xxx",
  "relation_status": "recommended"
}
```

所有会写库的动作都需要用户确认。

## 20. 已确认流程：推荐结果卡片与关系转化 v0.1

### 20.1 核心分层

推荐链路分为三层，三者不能混淆：

```text
recommendation_session
  记录系统推荐了什么

recommendation_selection / shortlist
  记录用户本次认可或移除了哪些推荐项

buyer_seller_relation
  记录真实业务推进状态
```

推荐结果本身不代表已经推荐给买家，也不自动创建买家-标的关系。

只有用户明确触发业务动作时，才创建或更新 `buyer_seller_relation`。

### 20.2 为买家找标的：标的推荐卡片

场景：

```text
输入：buyer_intent / buyer_party / 匿名需求
输出：seller_target list
```

卡片目的：帮助营销顾问判断该标的是否值得推给当前买家意向，以及下一步如何处理。

推荐卡片默认展示：

- 标的名称。
- 行业 / 地区。
- 推荐等级。
- 匹配理由。
- 风险 / 缺口。
- 关键字段。
- 已有买家接触 / 在谈提示。
- 操作按钮。

示例：

```text
+--------------------------------------------------------------------------------+
| 1. 上海启元项目                                      强推荐        匹配度：高    |
| 医药健康 / 医疗器械     浙江                         可推荐                    |
|--------------------------------------------------------------------------------|
| 匹配理由                                                                         |
| ✓ 行业匹配：医疗器械，符合医药健康方向                                           |
| ✓ 区域匹配：浙江，符合“浙江优先”                                                 |
| ✓ 利润匹配：净利润约 2500 万，超过 2000 万要求                                   |
| ? 并表：未明确，需要进一步确认                                                   |
|                                                                                |
| 风险 / 缺口                                                                      |
| - PE 根据估值和利润估算约 12.8，需确认口径                                       |
| - 是否接受控股并表尚未有明确证据                                                 |
|                                                                                |
| 已有接触                                                                         |
| - 无锡某上市公司：初步沟通中                                                     |
|                                                                                |
| [加入shortlist] [本次移除] [标记已推荐] [买家不感兴趣] [录入反馈] [查看标的]      |
+--------------------------------------------------------------------------------+
```

### 20.3 为买家找标的：卡片动作

| 操作 | 含义 | 写入影响 |
| --- | --- | --- |
| 加入 shortlist | 用户认可该标的进入本次候选清单 | 只影响当前 recommendation_session，不更新 buyer_seller_relation |
| 本次移除 | 本次推荐中移除该标的 | 只影响当前 recommendation_session，不影响后续推荐 |
| 标记已推荐 | 已将该标的推荐给当前买家 / 意向 | 创建或更新 buyer_seller_relation = `recommended`，创建 relation_event |
| 买家不感兴趣 | 当前买家意向明确不看该标的 | 创建 buyer_intent_target_exclusion，更新 buyer_seller_relation = `not_interested` |
| 录入反馈 | 录入后续聊天、截图、反馈 | 进入统一业务更新，自动带当前推荐上下文 |
| 查看标的 | 查看标的详情 | 跳转 seller_target 详情页 |

已确认：

- `加入 shortlist` 只代表本次推荐筛选，不更新 `buyer_seller_relation`。
- 只有点击 `标记已推荐`，才创建或更新 `buyer_seller_relation`。
- `本次移除` 和 `买家不感兴趣` 必须区分。
- 推荐结果中点击 `录入反馈`，进入统一业务更新，并自动带当前推荐上下文。

### 20.4 为标的找买家：买家意向推荐卡片

场景：

```text
输入：seller_target
输出：buyer_intent list / buyer_party list
```

卡片目的：帮助营销顾问判断该标的适合推给哪些买家意向。

推荐卡片默认展示：

- 买家名称。
- 意向名称。
- 意向状态。
- 联系人。
- 匹配理由。
- 风险 / 缺口。
- 历史接触情况。
- 操作按钮。

示例：

```text
+--------------------------------------------------------------------------------+
| 1. 浙江国资 / 医药健康并表需求                         强推荐      继续推荐       |
| 联系人：王总      负责人：张三                                                  |
|--------------------------------------------------------------------------------|
| 匹配理由                                                                         |
| ✓ 行业匹配：买家关注医药健康，标的是医疗器械                                     |
| ✓ 区域匹配：买家浙江优先，标的位于浙江                                           |
| ✓ 利润匹配：标的净利润约 2500 万，超过 2000 万要求                               |
| ? 并表：买家要求并表，标的是否接受并表待确认                                     |
|                                                                                |
| 历史接触                                                                         |
| - 尚未推荐该标的给此意向                                                         |
|                                                                                |
| [加入shortlist] [本次移除] [推荐给该买家] [该买家不感兴趣] [录入反馈] [查看意向]  |
+--------------------------------------------------------------------------------+
```

如果该 buyer_intent 已经不感兴趣该标的，则不应出现在推荐结果中。

如果已经接触过，不排除，但必须提示历史接触情况。

### 20.5 为标的找买家：卡片动作

| 操作 | 含义 | 写入影响 |
| --- | --- | --- |
| 加入 shortlist | 用户认可该买家意向进入本次候选清单 | 只影响当前 recommendation_session，不更新 buyer_seller_relation |
| 本次移除 | 本次推荐中移除该买家意向 | 只影响当前 recommendation_session，不影响后续推荐 |
| 推荐给该买家 | 将该标的推荐给该买家意向 | 创建或更新 buyer_seller_relation = `recommended`，创建 relation_event |
| 该买家不感兴趣 | 该买家意向明确不看该标的 | 创建 buyer_intent_target_exclusion，更新 buyer_seller_relation = `not_interested` |
| 录入反馈 | 录入后续聊天、截图、反馈 | 进入统一业务更新，自动带当前推荐上下文 |
| 查看意向 | 查看买家意向详情 | 跳转 buyer_intent 详情页 |

已确认：

- `加入 shortlist` 只代表本次推荐筛选，不更新 `buyer_seller_relation`。
- 只有点击 `推荐给该买家`，才创建或更新 `buyer_seller_relation`。
- `本次移除` 和 `该买家不感兴趣` 必须区分。
- 推荐结果中点击 `录入反馈`，进入统一业务更新，并自动带当前推荐上下文。

### 20.6 推荐结果与 business_update 的关系

推荐结果本身不是业务更新。

但推荐结果可以触发统一业务更新入口。

当用户点击推荐卡片中的：

```text
[录入反馈]
```

系统创建 `business_update`，并自动带入上下文：

- 当前 `recommendation_session`。
- 当前 `buyer_party`。
- 当前 `buyer_intent`。
- 当前 `seller_target`。

用户可粘贴文字、上传截图或附件，由 AI 拆分为 `extracted_action`，默认待复核。

### 20.7 推荐结果与 buyer_seller_relation 的关系

推荐结果默认只保存在 `recommendation_session` 中。

以下操作会创建或更新 `buyer_seller_relation`：

| 用户操作 | relation 状态 |
| --- | --- |
| 标记已推荐 / 推荐给该买家 | `recommended` |
| 买家反馈感兴趣 | `interested` 或 `initial_contact`，具体枚举后续确认 |
| 进入沟通 | `initial_contact` |
| 资料已发 | `materials_sent` |
| 约谈中 | `meeting` |
| 尽调中 | `due_diligence` |
| 买家不感兴趣 / 该买家不感兴趣 | `not_interested` + buyer_intent_target_exclusion |
| 终止 | `terminated` |

推荐结果本身可以记录：

```text
system_recommended = true
```

但不等同于已推荐给买家。

### 20.8 推荐会写库动作确认

推荐对话中，如果用户表达写库动作，例如：

```text
把第二个推荐给买家看看，其他先不用。
```

LLM 应输出 `proposed_action`，系统弹出确认。

示例：

```json
{
  "type": "proposed_action",
  "action": "create_relation_from_recommendation",
  "seller_target_id": "st_xxx",
  "buyer_intent_id": "bi_xxx",
  "relation_status": "recommended"
}
```

所有会写库的推荐动作都需要用户确认。

### 21.1 工作台首页

顶部导航采用：

```text
工作台 | 标的管理 | 买家管理 | 智能推荐 | 数据看板 | 设置
```

工作台首页从“展示板”转为“任务板”。

主体为：

```text
待我处理
```

右侧展示：

- 快捷操作。
- 本周概览。
- 最近推荐会话。

底部展示：

- 最近动态。

顶部增加全局搜索，搜索范围包括：

- 标的。
- 买家。
- 买家意向。
- 联系人。

待我处理建议分组：

- 标的事实待确认。
- 买家意向建议待确认。
- 推荐后待跟进。
- 解析异常。

其中“推荐后待跟进”后续可细化为：

- 已生成推荐报告但未记录反馈。
- 已标记推荐但超过 N 天无反馈。
- 已进入沟通但超过 N 天无更新。
- 买家要求补资料但未处理。

### 21.2 智能推荐布局

智能推荐页由原三栏调整为：

```text
两栏 + 可收起条件抽屉
```

推荐页结构：

- 顶部：模式切换、当前对象选择器、查看条件、推荐数量、已加入推荐列表数量、生成推荐报告按钮。
- 左侧：对话区。
- 右侧：推荐结果区。
- 条件快照通过 `查看条件` 抽屉展示。

推荐页两种模式共用同一页面结构：

- 为买家找标的。
- 为标的找买家。

差异体现在：

| 模式 | 当前对象 | 推荐结果 | 主语境 |
| --- | --- | --- | --- |
| 为买家找标的 | 买家 / 买家意向 | 标的列表 | 给买家推荐标的 |
| 为标的找买家 | 标的 | 买家意向列表 | 给标的寻找潜在买家 |

### 21.3 推荐卡片精简

推荐卡片折叠态只保留一个核心操作：

```text
加入推荐列表 / 取消推荐
```

原 `shortlist` 中文化为：

```text
推荐列表
```

折叠态需要展示足够判断信息：

- 名称。
- 推荐等级。
- 行业 / 地区 / 利润 / PE 等核心字段。
- 匹配摘要。
- 缺口摘要。
- 历史接触提示。
- `加入推荐列表 / 取消推荐`。

不在折叠态展示：

- 标记已推荐。
- 买家不感兴趣。
- 录入反馈。
- 查看详情。

这些动作后置到报告生成后、统一业务更新或后续跟进中处理。

### 21.4 加入推荐列表按钮状态

未加入时：

```text
[ 加入推荐列表 ]
```

建议视觉：空心按钮、低视觉权重。

已加入时：

```text
[✓ 已加入推荐列表]  取消
```

建议视觉：实心绿色背景 + 对勾 + 右侧小“取消”文字链接。

用户应能快速扫出哪些项目已被选中。

### 21.5 历史接触提示

推荐卡片中需要展示轻量历史接触提示。

该信息对撮合业务非常重要，用于判断：

- 这个标的是不是已经被其他买家推进。
- 这个买家是否近期已被推荐多个标的。
- 这个买家是否已经在谈类似标的。
- 当前标的与当前买家意向是否已有历史关系。

折叠卡片中历史接触提示最多显示 1 行。

如果多条，显示聚合摘要，例如：

```text
接触：3 个买家在跟进
```

点击或 hover 后再查看详情。

#### 21.5.1 为买家找标的

当前推荐对象为：

```text
buyer_intent → seller_target
```

展示规则：

| 情况 | 展示规则 |
| --- | --- |
| 当前买家意向与该标的无历史关系 | 不展示 |
| 当前买家意向已对该标的不感兴趣 | 不应出现在推荐中，服务端硬排除 |
| 当前买家意向已推荐过该标的 | 展示：`已给该意向推荐过：2026-05-10` |
| 当前买家意向正在沟通该标的 | 展示：`该意向已在沟通中` |
| 其他买家正在接触该标的 | 展示灰色小字：`接触：无锡某上市公司初步沟通中` |
| 多个买家正在跟进该标的 | 展示：`接触：3 个买家在跟进` |
| 有买家尽调中 / 协议中 | 展示更明显的进展提示 |

如果该标的与当前买家意向已 `not_interested`，该卡片不应出现。

#### 21.5.2 为标的找买家

当前推荐对象为：

```text
seller_target → buyer_intent
```

展示规则：

| 情况 | 展示规则 |
| --- | --- |
| 当前标的与该买家意向无历史关系 | 可不展示或展示 `尚未推荐该标的` |
| 该买家意向已对该标的不感兴趣 | 不应出现在推荐中，服务端硬排除 |
| 该标的已推荐过给该意向 | 展示：`该标的已推荐过：2026-05-10` |
| 该意向正在沟通该标的 | 展示：`该标的与该意向沟通中` |
| 该意向近期已推荐多个标的 | 展示：`近期：已推荐 3 项` |
| 该意向已有在谈项目 | 展示：`近期：已推荐 3 项，在谈 1 项` |
| 该意向已有尽调 / 协议项目 | 展示重点跟进提示 |

“近期”默认定义为：

```text
近 30 天
```

后续可配置。

### 21.7 生成推荐报告

推荐页顶部固定展示：

```text
推荐结果：12 项    已加入推荐列表：3 项    [生成推荐报告]
```

当已加入推荐列表数量为 0：

- `生成推荐报告` 按钮置灰。
- hover 提示：`请先将推荐项加入推荐列表`。

当已加入推荐列表数量大于 0：

- `生成推荐报告` 高亮可点击。

点击后弹出报告生成确认。

报告内容可包括：

- 买家需求理解 / 标的情况理解。
- 推荐标的或推荐买家列表。
- 每个推荐项的推荐理由。
- 风险与信息缺口。
- 后续建议。

报告格式可支持：

- Word。
- PDF。
- Markdown。

生成推荐报告不等于已推荐给买家，也不自动更新 `buyer_seller_relation`。

报告生成完成后，可以提供后续操作：

```text
[下载报告] [预览] [复制摘要] [标记这些项目为已推荐] [稍后处理]
```

其中 `标记这些项目为已推荐` 需要用户确认。

两种推荐模式均支持生成报告：

| 模式 | 报告语境 |
| --- | --- |

## 22. 已确认 UI 方向：标的管理、买家管理、统一业务更新 v0.1

### 22.1 标的管理页定位

标的管理页是营销顾问日常查看、筛选、更新标的的核心工作页。

页面重点不是低密度卡片，而是：

```text
信息密度较高的表格 + 每行第二行摘要
```

原因：

- 营销顾问需要快速横向比较多个标的。
- 标的字段天然适合表格筛选、排序和批量操作。
- 第二行摘要用于承载接触提示、待处理状态、负责人、最近更新等辅助信息，避免主列过宽。

标的列表不把营收、利润、估值、PE 聚合成一个“关键字段”。

这些字段应分别展开为独立列，便于：

- 快速比较。
- 排序。
- 筛选。
- 判断推荐匹配度。

建议列：

```text
标的名称 | 行业/赛道 | 地区 | 营收 | 利润 | 估值/报价 | PE | 附件 | 推荐状态 | 处理状态 | 操作
```

示例：

```text

| 上海启元项目      医药健康/器械   浙江      1.2亿     2500万    报价3.5亿     12.8    3      可推荐     待确认5  |
```

标的列表每行主操作保持 1-2 个，避免操作噪音。

已确认：

- 不等待联网调研。

如果名称过短，展示：

但不阻止新建。

#### 23.2.1 身份

- 标的名称。

- 公司全称。
- 简称 / 别名。
- 统一社会信用代码。
- 上市状态。
- 注册地。
- 实际经营地。
- 官网。
- 负责人。

- 二级行业。
- 细分赛道。
- 核心产品 / 服务。
- 主要客户。
- 主要销售区域。
- 技术壁垒。
- 资质 / 认证。
- 产能。
- 出口能力。
- 团队情况。
- 业务摘要。

已确认原则：

- 一级行业、二级行业使用相对规范字典。
- 细分赛道、产品、客户、资质采用半结构化方式，支持标准标签 + 原文标签 + 自由文本说明。

- 营收。

- 资产总额。
- 负债率。
- 毛利率。

- 数据口径说明。

- 数值。
- 单位。
- 期间。
- 口径。
- 来源。
- 可信度 / 待确认状态。

#### 23.2.4 估值交易

建议字段：

- 是否还卖。
- 推荐状态：可推荐 / 暂不推荐。
- 估值。
- 报价。
- PE。
- 转让比例。
- 是否可控股。
- 是否可并表。

- 是否接受资产收购。
- 是否接受迁址。
- 是否接受返投 / 固投。

- 交易紧迫度。

```text

```


#### 23.2.5 风险

风险字段需要结构化，不应只作为自由文本。

建议风险类型：

- 诉讼风险。
- 环保风险。
- 债务风险。
- 高负债。
- 商誉减值风险。
- 审计意见异常。
- 重大违法违规。
- 技术过时。
- 产能过剩。
- ST / 退市风险。
- 周期行业风险。
- 其他风险。

风险字段建议采用：

```text
风险类型 + 风险状态 + 风险等级 + 说明文本 + 来源
```

风险状态建议：

| 状态 | 含义 |
| --- | --- |
| `confirmed_present` | 确认存在 |
| `suspected` | 疑似存在 |
| `not_found` | 暂未发现 |
| `confirmed_absent` | 明确不存在 |
| `unknown` | 未知 |

#### 23.2.6 信息缺口

信息缺口是详情页重要区域。

示例：

```text
信息缺口：
- 是否可并表未知
- 股权转让比例未知
- 2024 年净利润来源待确认
- 是否接受浙江买家进场待确认
```

信息缺口用于：

- 提醒营销顾问补资料。
- 影响推荐置信度。
- 在推荐结果中解释为什么该标的需要进一步确认。

### 23.3 买家详情页字段布局

买家详情页中：

```text
买家画像放在基本信息里
买家意向作为核心 tab
```

买家详情页 tab：

```text
基本信息 | 意向 | 关联标的 | 推荐记录 | 更新记录
```

买家主体字段建议：

- 买家名称。
- 公司全称。
- 简称 / 别名。
- 买家类型。
- 所属集团。
- 上市状态。
- 所在地区。
- 主营业务。
- 资金实力 / 预算描述。
- 负责人。
- 常用联系人，可选。
- 买家画像摘要。

买家画像只保存长期稳定信息，例如：

- 长期偏好。
- 历史投资方向。
- 资金实力。
- 决策特点。
- 风控偏好。
- 区域偏好。
- 已知排除项。
- 历史反馈总结。

买家画像用途：

```text
当本次 buyer_intent 信息不完整时，作为背景补充。
```

推荐优先级仍然是：

```text
当前对话输入 > 当前 buyer_intent > buyer_profile > 行业默认模板
```

### 23.4 买家意向是推荐核心

已确认：

```text
买家意向 buyer_intent 才是推荐业务的核心对象。
```

买家主体 `buyer_party` 是主数据，买家意向 `buyer_intent` 是工作对象。

因此操作入口应调整为：

```text
新建买家意向 优先于 新建买家
```

工作台快捷入口建议调整为：

```text
[新建标的] [新建买家意向] [录入业务更新] [发起推荐]
```

买家管理页默认 tab 建议为：

```text
买家意向
```

买家主体 tab 中保留：

```text
[新建买家]
```

### 23.5 新建买家意向流程

推荐流程：

```text
新建买家意向
↓
输入买家名称 / 选择匿名意向
↓
系统快速查重买家主体
↓
用户选择：
  1. 关联已有买家
  2. 新建买家
  3. 暂不关联买家，作为临时意向
↓
输入或粘贴收购需求
↓
LLM 解析 hard / preference / unknown
↓
生成买家意向卡
↓
进入买家意向列表
```

买家意向详情一期不做独立复杂页面。

已确认采用：

```text
买家详情页 > 意向 tab > 点击意向卡 > 展开抽屉
```

买家意向支持三类条件展示：

| 类型 | 含义 |
| --- | --- |
| `hard` | 硬条件，原则上用于过滤或强约束 |
| `preference` | 偏好项，用于排序、推荐理由和权衡 |
| `unknown` | 未明确，需要补问或在推荐结果中标记缺口 |

### 23.6 非标字段精准检索原则

针对行业、细分赛道、产品、资质、风险等非标字段，不采用单一向量检索方案。

已确认原则：

```text
硬条件交给数据库，模糊匹配交给召回，复杂权衡交给 LLM。
```

推荐采用组合检索：

```text
结构化字段 + 标签字典 + 别名体系 + 全文检索 + 向量召回 + LLM rerank
```

各方式分工：

| 检索方式 | 适合 | 不适合 |
| --- | --- | --- |
| SQL 结构化过滤 | 利润、PE、地区、上市状态、推荐状态、排除关系 | 理解复杂自然语言 |
| 标签检索 | 行业、赛道、产品、资质、风险类型 | 判断复杂上下文 |
| 全文检索 | 精确关键词、公司名、产品名、资质名 | 泛化语义 |
| 向量检索 | 长文本语义、非标准表达、扩大召回 | 硬条件过滤、风险排除 |
| LLM rerank | 综合字段缺失、优先级权衡、生成理由 | 直接查库、直接执行硬排除 |

### 23.7 字段分类处理

#### 23.7.1 可标准化字段

必须尽量结构化。

包括：

- 行业一级分类。
- 行业二级分类。
- 地区。
- 上市状态。
- 交易类型。
- 是否可并表。
- 是否可控股。
- 推荐状态。
- 是否还卖。
- 风险类型。
- 买家-标的关系状态。

这些字段用于 SQL / filter DSL 精准过滤。

#### 23.7.2 半标准化字段

采用：

```text
标准标签 + 原文标签 + 自由文本说明
```

包括：

- 细分赛道。
- 产品。
- 客户类型。
- 资质认证。
- 技术壁垒。
- 出口能力。
- 产能。
- 产业协同。

示例：

```text
标准标签：medical_device.ivd
展示名称：体外诊断 / IVD
原文标签：体外诊断试剂、IVD、诊断试剂
来源：BP 第 12 页
置信度：0.87
```

#### 23.7.3 自由文本字段

不强制结构化。

包括：

- 业务摘要。
- 调研摘要。
- 卖方诉求。
- 风险说明。
- 历史沟通记录。
- 推荐理由。
- 买家反馈原文。

这些字段适合全文检索、向量召回和 LLM rerank。

### 23.8 行业检索策略

行业建议采用轻量行业字典。

示例：

```text
一级行业：医药健康
二级行业：医疗器械
细分赛道：IVD / 医美耗材 / 骨科耗材
```

底层可以存：

```text
industry_primary = healthcare
industry_secondary = medical_device
sector_tags = [ivd, orthopedic_consumables, aesthetic_consumables]
raw_industry_text = "医疗器械、体外诊断、医美耗材"
```

同时维护别名表：

```text
ivd:
- IVD
- 体外诊断
- 诊断试剂
- 体外诊断试剂
```

买家意向解析后输出 filter DSL，由服务端校验并转 SQL。

LLM 不直接写 SQL。

### 23.9 风险检索策略

风险字段不依赖向量语义作为硬排除依据。

例如买家要求：

```text
排除环保风险和重大诉讼
```

服务端应优先理解为：

```text
exclude risk_status in confirmed_present / suspected
where risk_type in environmental / litigation
and severity >= medium
```

如果风险未知：

- 对“排除已知重大风险”类需求，未知可保留，但标记信息缺口。
- 对“必须材料齐全 / 必须无风险证明”类需求，未知应降权，必要时不进入首批推荐。

是否把 unknown 作为排除条件，由买家意向解析结果中的：

```text
constraint_type
unknown_policy
```

共同决定。

### 23.11 当前数据库固化补充

已确认并写入 migration / schema 草案：

- `tag_dictionary` 使用 `coalesce(team_id, workspace_id)` 表达式唯一索引，支持全局默认字典和团队/空间覆盖，避免 PostgreSQL `null` unique 失效。
- `risk_type` 一期不加 check constraint，保持开放 text；P0 风险类型作为 `tag_dictionary(domain = risk)` 参考字典。
- 一级行业字典只做非穷尽种子，覆盖当前买家意向合集中的高频方向；长尾行业、二级行业、细分赛道允许原文入库或进入待归一化。
- `deal_path / payment_method / control_path` 作为 `tag_dictionary` 参考字典 seed，用于交易路径、支付方式和控制路径归一化。
- 新增 `region_alias_config`，用于“长三角、江浙沪、珠三角、沿海发达地区”等买家意向区域表达的展开。

注意：区域别名配置只辅助买家意向解析和规则判断，不改变 `seller_target` 的事实字段。标的侧仍保存注册地、总部地、经营区域、生产区域、资产区域和原始地域描述。
