## 1. 功能架构

### 1.1 产品分层

```text
登录/JWT/角色权限
        │
        ├─ V0 业务资料与推荐
        │    ├─ 标的管理（seller_target）
        │    │    ├─ 列表/筛选/分页/批量指派与删除
        │    │    ├─ 标的信息：结构化字段 + 五组“其他”补充栏
        │    │    ├─ 业务更新 → AI 抽取 → 复核/采纳/回滚 → 审计
        │    │    ├─ 附件/文本提取/OCR/证据
        │    │    └─ 标的调研 → 画像与白名单字段自动采纳
        │    ├─ 买家管理
        │    │    ├─ 买家主体（buyer_party）
        │    │    └─ 买家意向（buyer_intent）/多方案条件/解析/状态
        │    └─ 智能推荐（双向）
        │         ├─ SQL 初筛（多方案 OR + 三态）
        │         ├─ 代码打分 → LLM 深评
        │         ├─ 推荐会话/追问/选中项/报告
        │         └─ “开始推进”创建撮合关系
        │
        ├─ V1 撮合进度
        │    ├─ buyer_seller_relation（买家意向 × 标的，唯一）
        │    ├─ 九状态流水线 + relation_event 时间线
        │    ├─ 标的详情推进 / 意向详情推进 / 关系时间线
        │    └─ 全局撮合看板：分桶、折叠、筛选、责任范围、深链接
        │
        ├─ V2 管理与配置（管理员）
        │    ├─ 账号管理：创建、角色、停用/启用、重置密码、活跃度
        │    └─ 设置：AI 节点、模型与搜索/OCR、Prompt 版本（行业字典 0908 下线，不再有数据字典 tab）
        │
        └─ V3 运营与运维（管理员扩展）
             ├─ 数据看板：标的/买家省级分布、标的行业 top、营收规模
             ├─ 任务中心：队列、状态、失败、重试、忽略、归档、Trace
             └─ 隐藏调试中心：实体、业务更新、推荐会话、表统计
```

### 1.2 角色与可见性

| 角色 | 可见范围 | 可执行能力 |
|---|---|---|
| 顾问（consultant） | 自己负责的标的、买家主体/意向；参与关系对双方负责人可见 | 录入/编辑业务资料、发起推荐、创建关系、记录推进动态 |
| 管理员（admin） | 全局明细、全局关系、全库数据看板 | 账号管理、负责人指派、系统设置、任务中心、调试中心 |
| 系统账号 | 机器写入与后台任务 | 不作为业务负责人活跃度，不应冒充顾问 |

权限地板：顾问请求中即使构造其他负责人的 owner 参数，也只能得到“自身权限 ∩ 指定筛选”的结果；关系对标的负责人、意向负责人及管理员可见。

### 1.3 关键业务链路

1. **资料进入**：手动新建/编辑，或业务更新文字、图片、PDF、Office 附件。
2. **AI 处理**：`business_update` 根据 `processing_scope` 扇出 `basic_info`、`follow_up` 或两者；OCR 完成后按原范围继续处理。解析与调研共享标的原子运行锁，冲突返回 409。
3. **字段落库**：手动编辑、解析采纳、调研采纳统一经过字段写入服务，执行注册表授权、枚举/数值校验、字段来源和更新审计；支持单条或批量回滚。
4. **推荐到推进**：意向→标的或标的→意向，先 SQL 初筛、再代码打分、再异步深评/报告；推荐结果可“开始推进”创建唯一关系（初始状态“已推荐”）。
5. **推进到看板**：关系状态和动态写入同一时间线；从标的详情、意向详情、看板三处镜像可见。

## 2. 测试准备

### 2.1 账号与数据夹具

| 代号 | 数据 | 用途 |
|---|---|---|
| ADM | 管理员账号 | V2/V3、全局权限、指派和调试 |
| C1/C2 | 两个顾问账号 | owner_scope、跨负责人关系可见性 |
| T1/T2 | 两个 `active` 标的，分别填不同省份、L1/L2、营收、利润、估值、状态 | 标的、推荐、看板 |
| B1 | 一个买家主体 | 主体 CRUD、查重 |
| I1/I2 | B1 的两条不同买家意向，设置不同条件/方案 | 需求、双向推荐、关系唯一性 |
| B2/I3 | 第二个买家主体及意向 | 排他提示、候选交叉 |
| REL1 | I1 × T1 关系 | 九状态、事件、看板 |
| FAIL | 一条可控失败的解析/模型任务 | 任务中心重试/忽略 |

建议所有测试对象使用带日期的“TEST-”前缀，不直接改真实在推进项目；每条用例记录对象 ID、账号角色、浏览器和请求状态码。

### 2.2 优先级与结果口径

| 级别 | 口径 |
|---|---|
| P0 | 核心流程不可用、数据损坏、越权或敏感信息泄露 |
| P1 | 核心结果错误、异步链路丢失、审计缺失、关系重复 |
| P2 | 展示、交互、边界校验或提示问题，不阻断主链路 |
| OBS | 外部服务未配置、产品尚未决策或仅做观察，不直接判失败 |

## 4. 推荐执行顺序

```text
环境/版本确认
 → AUTH-01~07
 → TGT-01~20、BUY-01~12
 → REC-01~10
 → REL-01~12
 → USER-01~07、SET-01~09
 → DASH-01~07、TASK-01~09
 → X-01~10
```

先跑 P0，再跑 P1，最后补 P2/OBS。任何 P0 失败都先停止向后扩散（例如登录/权限失败时，不继续判定业务页面为失败）。

## 5. 执行记录模板

在表格中追加以下列即可形成实际验收表：`实际结果`、`状态（通过/失败/阻塞/未测）`、`证据链接`、`缺陷编号`、`测试人`、`测试时间`。

缺陷至少记录：用例编号、环境与 commit hash、账号角色、对象 ID、复现步骤、预期/实际、Network URL/状态码/响应体（脱敏）、截图或录屏、影响范围。

外部搜索、OCR、LLM 未配置时，对应端到端用例记为 `OBS/未测（环境原因）`；若已配置但出现代码错误、任务静默堆积、错误终态不释放或产生伪造数据，应按 P0/P1 缺陷处理。
