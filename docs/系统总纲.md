## 1. 业务与用户

**系统名称**：投资撮合管理和智能推荐平台（Match-MA）。

**业务背景**：咨询公司的投资撮合业务。顾问同时服务买卖双方——为买家寻找标的，为卖家寻找买家，并推进双方持续沟通。

**平台三大核心**：
1. 买家和卖家的信息管理与画像；
2. 智能推荐（双向）；
3. 撮合项目进度管理。

**用户与权限模型**（已实现，不需改动）：
- **顾问（consultant）**：录入信息、查看并管理自己负责的买家/卖家、发起推荐、记录进度。数据可见性 = 负责人本人 + 管理员（`owner_scope`）。
- **管理员（admin）**：全局明细可见、账号管理、系统设置（模型/prompt/搜索工具等 tab 仅管理员可见）。
- 登录：`app_user` 账号密码 → JWT；另保留共享管理员凭证作恢复通道（`auth.py`）。
- **未启用**：team/workspace 多租户（列存在、值恒为种子常量）、`visibility` 三档字段（无过滤行为）。见 §6 判决。

## 2. 领域模型

### 2.1 核心实体

```
seller_target（标的，宽表 ≈80 列）──┐
buyer_party（买家主体）             ├── buyer_seller_relation（意向×标的 = 撮合关系）
buyer_intent（买家意向，宽表 ≈53 列）┘         └── relation_event（关系时间线）
        │
        ├── entity_profile_section（五组“其他”补充栏，多修订版本）
        ├── business_update → extracted_action → action_application_log（解析与更新审计链）
        ├── attachment → parsed_document → evidence_span（附件/OCR/证据）
        └── research_proposal（调研产出）
AI 基础设施：model_provider_config / model_node_config / prompt_template / background_job / ai_trace
数据字典：industry_taxonomy（L1/L2）
```

### 2.2 两层信息结构（定型，不再争论）

- **结构化字段**（宽表列）：服务 SQL 初筛与代码打分。宽表是「初筛必须代码化」的直接代价，通常**不换成 jsonb/纵表**。唯一的受控例外是多行业事实：`industry_pairs_json` 保存已归一化的 `{l1,l2}` 对，GIN/JSONB 条件支持“任一行业命中”；`industry_l1/l2` 仅保留首对兼容投影，不再是独立事实源。加字段的成本问题由指标注册表解决（§5）。
- **定性补充五栏**（`entity_profile_section`）：`identity / business_product / tech_team / ops_quality / deal_terms`，每组标题均为「其他」，只承接结构化字段装不下的定性内容。原“产业链位置”并入“业务与产品”，原“出售诉求与风险”并入“交易属性与出售诉求”。它保留多修订与当前值；不再人为计算“画像待补”或以三态提示覆盖缺口。
- 前端合并展示为一个「标的信息」页：五组，组内先结构化字段、后「其他」补充栏，参与初筛/打分的字段带「筛」角标。信息页的全部业务事实均可编辑；手动编辑通过统一写入通道，记录操作人、时间、来源和更新记录。

### 2.3 数据字典原则

- 行业：`industry_pairs_json` 是唯一的标的行业事实源，保存一个或多个归一化的 `L1/L2` 对；筛选时任一对命中即可。`industry_l1/l2` 是为存量读路径保留的首对兼容投影，必须由该 JSON 派生，不能独立写入。原始行业表述只留在业务更新、证据和解析审计中，不设标的宽表兜底列。
- 所在地：只保留 `location_province / location_city / location_district`。LLM 按证据直接判断，无法确定的层级为空，页面显示 `-`；筛选按用户填写到的层级匹配，不设别名字典、原文列或粒度标记。
- 枚举字段的取值及中文名由指标注册表统一声明；注册表同时声明分组、筛选角色、可写来源和手动编辑权限。

### 2.4 标的状态模型

- **交易状态**只由 `lifecycle_status` 表达：`active / sold / off_market`，前端显示「在售中 / 已售出 / 已停售」。推荐初筛只认 `active`，不再把解析是否成功混进推荐闸门。
- **AI 处理**由服务端统一合并解析与调研两条流水线。运行态来自 `information_status=parsing/researching`；终态用 `last_parse_at` 与 `last_research_at` 判断最近一次操作，再结合 `parse_failed` / `research_last_outcome` 显示「解析失败 / 调研失败 / 已完成 / 未处理」。前端只渲染 API 返回的 `ai_processing_state/detail`，不复制判定表。
- 解析与调研在任务入队前原子占用同一个标的；已有任一流水线运行时，另一流水线返回 409，不允许出现“任务已入队、状态未置位”。所有成功和最终失败出口都必须释放运行态并记录对应终态时间。
- `pending_review` 不再是标的状态。未自动采纳的 `extracted_action` 自身仍可保持待复核并留痕，但不得污染 `seller_target.information_status`。
- 2026-07-27 采用两阶段生产迁移：阶段 A 的 `005 / 20260727_0052` 仅回填、规范化、增加 `last_parse_at` 和新索引；数据库旧列在 Railway 全部 API/worker 切换前保留，API 只为滚动发布计算返回兼容字段。阶段 B 才以独立 `006 / 20260727_0053` 删除旧索引、约束和列，同时移除兼容 API。禁止把两阶段合成一次 preDeploy 迁移。

## 3. 关键流程

### 3.1 信息录入与解析（买卖两侧同一机制）

```
顾问粘贴文本/上传附件 → business_update
  → LLM 解析（专用 parser 节点）→ extracted_action（带 action_type 白名单）
  → apply（人工确认或自动）→ 写实体字段/画像/跟进
  → action_application_log → 「更新记录」展示 + 可回滚
```

**字段写入规则**：手动编辑、解析采纳与调研采纳均收敛到**唯一字段写入服务**：`写入(实体, 字段, 新值, 来源, 证据)`——内部查注册表做来源授权、合法性校验与归一化 → 写列 → 记审计和字段来源。原则一句话：**来源可以多，写入通道必须只有一条。**

### 3.2 标的调研 Agent（2026-07 已按此重写）

- 架构：**主 agent + 工具**（`web_search` / `fetch_page`），模型自主规划检索词、判断结果、决定收尾；代码不做规则限制（无锚点闸门、无取证计数器、无代码侧冲突分类——否决清单见 0721 方案 §8，不再重开）。
- 时效与冲突判断在 prompt 内完成，输出带 `relation`（consistent/supplement/temporal_update/same_period_conflict）与 `sources`。
- 产出自动采纳（写画像 + 白名单内结构化字段），全部进更新记录、可回滚。
- 30 天内调研过的标的：批量发起时**显式弹窗二次确认**，不做服务器静默过滤。
- 全链路留痕：一次调研一行 `ai_trace`（完整工具调用链 + 统计元数据）。
- prompt 通过设置页版本管理发布，**不写 prompt seed 迁移**。

### 3.3 智能推荐（双向）

```
买家意向 → 标的：SQL 初筛（多方案 OR + 三态判断）→ 代码打分（乐观分）→ 深评分片（LLM）→ 推荐报告
标的 → 买家意向：同一引擎反向（recommendation_flow._candidate_intents_for_target）
```

- 初筛与打分**必须代码化**，禁止全库打包给 LLM。
- 与进度管理的接口：新候选可通过 **[开始推进]** 一键创建关系（状态=已推荐）。推荐结果按“已在推进 / 新候选”分区已列入后续优化，本轮不作为阻断项。

### 3.4 撮合进度管理（已实现）

**核心决策：进度的单元是「买家意向 × 标的」这一对（`buyer_seller_relation`），不是任何单个实体。** 每对唯一、九状态流水线、事件挂关系（`relation_event`）。"多线程且交叉"由此消解：交叉只是同一条线从两个详情页可见。

四个视图：
1. **标的详情「推进」tab**：该标的的全部关系（买家、状态、最新动态、下一步、无动态预警）；
2. **买家意向详情「推进」tab**：完全镜像；
3. **关系时间线**（点开一对）：事件流 + 状态变更 + 下一步 + 记录动态；
4. **全局看板**：只做概览 + 跳转。九状态收敛为「初步接触 / 深度交流 / 已成交」三主列和「已关闭」底部抽屉；支持按标的/按意向双视角、责任范围三态、搜索与“隐藏最近无动态”筛选，固定按最近关系动态由近到远。同列同主体的多条关系默认折叠成摞，但每张内层卡仍是一条独立关系。点击卡片通过 `?tab=progress&relation=<id>` 深链接到两侧详情并展开对应时间线。

看板取数使用 `/relations/board` 瘦端点（9 个固定字段），前端一次加载后完成分桶、折叠、筛选和计数；达到客户端上限会显式提示截断，不再静默丢数据。默认责任范围为「我参与的」，另有「全部 / 我全权的」；具体可见性仍由后端 ownership 语义和负责人权限控制。

**动态来源与路由**：当前关系由推荐「开始推进」或手动「关联对手方」两条确定性路径创建。手工动态允许修改和软删除；系统开局、状态变更和解析事件不可修改。一次录入中的事实更新、实体跟进与关系事件如何共同扇出仍是未决问题，当前不通过自由文本自动识别对手方挂关系。

**三个业务规则（2026-07-22 定稿）**：
1. **排他性**：标的与某买家进入深入推进阶段后，对其他买家的推荐里照常参与，但标注「正与其他买家深入推进」，**不透露对方是谁**。
2. **跨负责人可见性**：一条关系对双方负责人 + 管理员可见。
3. **状态集**：沿用 schema 九状态跑真实业务，之后按实际使用裁剪。

### 3.5 附件与 OCR

`attachment → OCR（外部 API）→ parsed_document → 进入 3.1 解析流程`，`evidence_span` 记录字段值在原文中的出处。OCR 的 API key 配置并入 `model_provider_config` 加密 key 体系（待做，小改动）。

## 5. 指标注册表（设计）

**问题**：一个指标今天散在五处——DB 列、`recommendation_flow` 读取、前端 `infoGroups.ts`、extracted_action apply 白名单、调研字段白名单——靠人肉同步 + 缝合测试（`test_action_type_sync` / `test_info_group_sync`）兜底。

**形态**：`backend/app/registry/indicators.py`，纯声明式：

```python
@dataclass(frozen=True)
class Indicator:
    entity: str                # "seller_target" | "buyer_intent"
    column: str                # DB 列名 = API 字段名
    label: str                 # 中文名（前端/更新记录/prompt 上下文共用）
    group: str                 # 五组之一（identity + 四个业务分组）
    kind: str                  # text | yuan | ratio | enum | date | bool3
    enum_options: tuple | None # 枚举 code 与中文名
    screening: str | None      # None | "hard" | "soft:<权重>"
    writable_by: frozenset     # {"manual", "parse", "research"} 子集
    deep_eval: bool            # 是否进入深评上下文
```

**五个消费方的接入方式**：
1. 前端：`/meta/indicators` 驱动分组、中文名、枚举、编辑权限与「筛」角标——**运行时驱动，不做代码生成**，`infoGroups.ts` 仅保留值格式化；
2. 打分器：一致性测试改为「`recommendation_flow` 读取的列 ⊆ 注册表 screening 列」，替代正则扒源码；
3. extracted_action apply 白名单 = `writable_by ∋ "parse"`；
4. 调研 `allowed_structured_fields` = `writable_by ∋ "research"`；
5. 字段写入服务用 `kind/enum_options` 做校验与归一化，并按 `writable_by` 拒绝无权来源；更新记录用 `label` 显示。

**迁移路径**：立注册表（先只覆盖 seller_target）→ `/meta/indicators` 上线 → 前端切换 → 两个白名单切换 → 缝合测试改写或删除 → buyer_intent 接入。每步可独立发版。
