## 1. 业务与用户

**系统名称**：投资撮合管理和智能推荐平台（Match-MA）。

**业务背景**：咨询公司的投资撮合业务。顾问同时服务买卖双方——为买家寻找标的，为卖家寻找买家，并推进双方持续沟通。

**平台三大核心**：
1. 买家和卖家的信息管理与画像；
2. 智能推荐（双向）；
3. 撮合项目进度管理。

**用户与权限模型**（已实现，不需改动）：
- **顾问（consultant）**：录入信息、查看并管理自己负责的买家/卖家、发起推荐、记录进度。数据可见性 = 负责人本人 + 管理员（`owner_scope`）。
- **管理员（admin）**：全局明细可见、账号管理、系统设置（模型/prompt/搜索工具等 tab 仅管理员可见）。
- 账号管理的「最近活跃」只取业务更新、未撤回的关系动态、人工字段应用和推荐提问；AI 解析/调研等机器写入使用系统账号，不以业务对象 `updated_at` 冒充负责人活跃。
- 登录：`app_user` 账号密码 → JWT；另保留共享管理员凭证作恢复通道（`auth.py`）。
- **未启用**：team/workspace 多租户（列存在、值恒为种子常量）、`visibility` 三档字段（无过滤行为）。见 §6 判决。

## 2. 领域模型

### 2.1 核心实体

```
seller_target（标的，宽表 ≈80 列）──┐
buyer_party（买家主体）             ├── buyer_seller_relation（意向×标的 = 撮合关系）
buyer_intent（买家意向，宽表 ≈53 列）┘         └── relation_event（关系时间线）
        │
        ├── entity_profile_section（五组“其他”补充栏，多修订版本）
        ├── business_update → extracted_action → action_application_log（解析与更新审计链）
        ├── attachment → parsed_document → evidence_span（附件/OCR/证据）
        └── research_proposal（调研产出）
AI 基础设施：model_provider_config / model_node_config / prompt_template / background_job / ai_trace
数据字典：industry_taxonomy（L1/L2）
```

### 2.2 两层信息结构（定型，不再争论）

- **结构化字段**（宽表列）：服务 SQL 初筛与代码打分。宽表是「初筛必须代码化」的直接代价，通常**不换成 jsonb/纵表**。唯一的受控例外是多行业事实：`industry_pairs_json` 保存已归一化的 `{l1,l2}` 对，GIN/JSONB 条件支持“任一行业命中”；`industry_l1/l2` 仅保留首对兼容投影，不再是独立事实源。加字段的成本问题由指标注册表解决（§5）。
- **定性补充五栏**（`entity_profile_section`）：`identity / business_product / tech_team / ops_quality / deal_terms`，每组标题均为「其他」，只承接结构化字段装不下的定性内容。原“产业链位置”并入“业务与产品”，原“出售诉求与风险”并入“交易属性与出售诉求”。它保留多修订与当前值；不再人为计算“画像待补”或以三态提示覆盖缺口。
- 前端合并展示为一个「标的信息」页：五组，组内先结构化字段、后「其他」补充栏，参与初筛/打分的字段带「筛」角标。信息页的全部业务事实均可编辑；手动编辑通过统一写入通道，记录操作人、时间、来源和更新记录。
- 买家需求详情的「买家信息」tab 只展示 `buyer_party` 的全局共享资料：买家名称、所属行业、所在地区、联系人、联系方式、其他；每项独立进入编辑态并写回同一主体，因此会在其所有关联需求中同步。主体所属行业/所在地描述买家自身，绝不与收购条件混用。当前需求的收购行业、目标地区和交易条件只属于 `buyer_intent` 的「需求信息」；行业复用一级/二级行业多选字典，主体所在地复用省/市选择器。

### 2.3 数据字典原则

- 行业：`industry_pairs_json` 是唯一的标的行业事实源，保存一个或多个归一化的 `L1/L2` 对；筛选时任一对命中即可。`industry_l1/l2` 是为存量读路径保留的首对兼容投影，必须由该 JSON 派生，不能独立写入。原始行业表述只留在业务更新、证据和解析审计中，不设标的宽表兜底列。
- 所在地：只保留 `location_province / location_city / location_district`。LLM 按证据直接判断，无法确定的层级为空，页面显示 `-`；筛选按用户填写到的层级匹配，不设别名字典、原文列或粒度标记。
- 枚举字段的取值及中文名由指标注册表统一声明；注册表同时声明分组、筛选角色、可写来源和手动编辑权限。

### 2.4 标的状态模型

- **交易状态**只由 `lifecycle_status` 表达：`active / sold / off_market`，前端显示「在售中 / 已售出 / 已停售」。推荐初筛只认 `active`，不再把解析是否成功混进推荐闸门。
- **AI 处理**由服务端统一合并解析与调研两条流水线。运行态来自 `information_status=parsing/researching`；终态用 `last_parse_at` 与 `last_research_at` 判断最近一次操作，再结合 `parse_failed` / `research_last_outcome` 显示「解析失败 / 调研失败 / 已完成 / 未处理」。前端只渲染 API 返回的 `ai_processing_state/detail`，不复制判定表。
- 解析与调研在任务入队前原子占用同一个标的；已有任一流水线运行时，另一流水线返回 409，不允许出现“任务已入队、状态未置位”。所有成功和最终失败出口都必须释放运行态并记录对应终态时间。
- `pending_review` 不再是标的状态。未自动采纳的 `extracted_action` 自身仍可保持待复核并留痕，但不得污染 `seller_target.information_status`。
- 2026-07-27 已按两阶段完成生产迁移设计：阶段 A 的 `005 / 20260727_0052` 仅回填、规范化、增加 `last_parse_at` 和并存索引，并在 Railway 全部 API/worker 切换后完成生产验收；阶段 B 再以独立的 `006 / 20260727_0053` 删除旧索引、约束和列，同时移除兼容 API。两个阶段禁止合并为一次 preDeploy 迁移。

## 3. 关键流程

### 3.1 信息录入与解析（买卖两侧同一机制）

```
顾问从标的/买家意向选择「更新基本信息 / 记录跟进 / 两者都更新」
  → 一份原始文字和附件落 business_update
  ├─ basic_info → 专用 update parser → extracted_action → apply
  │              → 写实体字段/画像 → action_application_log（可回滚）
  └─ follow_up → 用户先选定 buyer_intent × seller_target 关系
                 ├─ 直接写入 → 原文立即成为 relation_event.content
                 └─ AI 整理 → 先建“AI解析中” relation_event 占位
                    → relation_followup_draft_parser 整理 content/next_step
                    → worker 原位回填；最终失败则把同一事件标成可编辑/可删除的解析失败
```

**路由与提交规则（2026-08-03 更新）**：处理范围由顾问在入口显式选择，不让通用 Agent 猜测。`both` 让两个独立任务读取同一来源，任一分支失败不回滚另一分支；OCR 完成后仍按原范围扇出。跟进节点不识别或创建关系、不改推进状态、不选择动态类型；关系和动态类型由顾问选择。顾问可选择直接写入原文，或「提交并 AI 整理」后立即离开：后者在提交事务内先创建时间线占位，不依赖页面轮询或二次确认，worker 成功后自动回填，最终失败后保留原记录供删除或手工编辑。没有已有关系时先走「开始推进 / 关联对手方」。实体级旧跟进不再存在，所有跟进事实统一进入关系时间线。

**字段写入规则**：手动编辑、解析采纳与调研采纳均收敛到**唯一字段写入服务**：`写入(实体, 字段, 新值, 来源, 证据)`——内部查注册表做来源授权、合法性校验与归一化 → 写列 → 记审计和字段来源。原则一句话：**来源可以多，写入通道必须只有一条。**

**买家需求新建与主体复用**：用户提交创建时，系统自动按输入名称对全库 `buyer_party.buyer_name / aliases_json` 做转义后的 `ILIKE` 包含查重；有命中时必须列出全部疑似重复主体并二次确认。历史 `legal_name` 已迁入别名，不再单独维护。用户可跨负责人复用已有买家主体，新需求仍归当前创建人负责；复用后，主体资料会在全部关联需求详情共享。普通买家列表与编辑权限继续遵守 `owner_scope`，不会因查重复用而放宽。

**买家需求附件唯一解析链**（2026-08-03 定稿）：新建买家需求时，`business_update` 只作为附件、OCR 与证据载体；OCR 完成后只投递 `buyer_intent_parse`，由 `buyer_intent_semantic_parser → buyer_intent_normalizer` 两段式专用链解析，严禁同时投递 `business_update_extract_actions`。通用业务更新抽取仍服务业务更新入口，不是买家新建入口的第二写入者。专用解析在最终写入边界按公共条件/同名方案分别裁决：当前值为空则自动补充，归一化后相同则 no-op，仅当前非空且新值不同才进入待确认；类型不合法或作用范围/规则含义不明确的建议不得一键采纳。结构化字段已承载的描述必须从同模块「其他」中去重。

### 3.2 标的调研 Agent（2026-07 已按此重写）

- 架构：**主 agent + 工具**（`web_search` / `fetch_page`），模型自主规划检索词、判断结果、决定收尾；代码不做规则限制（无锚点闸门、无取证计数器、无代码侧冲突分类——否决清单见 0721 方案 §8，不再重开）。
- Agent 输出事实、期间与 `sources`，代码按当前值确定 `relation`（consistent/supplement/temporal_update/same_period_conflict）。文本不做语义相似或日期推断：当前为空是补充，去掉首尾空白后文字完全一致是一致，其余一律是冲突；核心财务字段仍按财务期间区分新期间更新、同期冲突与禁止旧期覆盖。
- 可追溯的补充、一致项和新期间财务信息自动采纳（写画像 + 白名单内结构化字段），冲突留在 `research_proposal.pending_review`。待确认冲突直接显示在标的信息对应字段或对应分组的「其他」栏下，支持「采纳 / 修改并采纳 / 忽略」；修改并采纳在同一事务中应用顾问最终值，同时保留原调研值并标记审计。标的列表「AI 处理」按未处理冲突建议数显示「X项待确认」，全部处理后自动消失。
- 30 天内调研过的标的：批量发起时**显式弹窗二次确认**，不做服务器静默过滤。
- 全链路留痕：一次调研一行 `ai_trace`（完整工具调用链 + 统计元数据）。
- prompt 通过设置页版本管理发布，**不写 prompt seed 迁移**。

### 3.3 智能推荐（Agent 化，2026-08-04 重构）

**主路径是「直接输入一段需求」，不再要求先建买家需求或标的。** 推荐页是一个对话页：一个输入框 +
一段可直接复制给客户的文本。施工单见 `平台优化方案/智能推荐Agent化改造施工单0804.md`。

```
一段需求原文 / 上传的需求文件
  → recommendation_agent_to_target（worker，带工具）
      ├─ search_targets     参数化 SQL 初筛，可多次调用（≤6），count_only 可低成本试探
      ├─ get_target_detail  少数候选的完整画像（累计 ≤12）
      └─ ask_user           澄清（全程 ≤1 次，默认不用）
  → 写作素材包（brief）
  → recommendation_answer_writer_to_target（API 侧 SSE，无工具，流式）
  → 一段带标的链接的正文
```

- **初筛与打分必须代码化，禁止全库打包给 LLM。** Agent 只负责编排（理解 / 决定筛几次 / 解读 /
  写话），初筛仍是 `_candidate_targets_for_intent` 那段 SQL + 打分；Agent 看到的永远是每次筛选返回的
  候选摘要。`search_targets` 的过滤器走 `OVERRIDE_FIELD_KINDS` 白名单校验，模型给的未知字段被丢弃。
- **两个方向是两套流程，不是一个流程的参数**：SQL、工具集、prompt 各自独立，会话的 `mode` 由后端强制
  不可变（`recommendations.py` 拦 mode 不匹配 → 400），前端在发出第一条消息后锁定方向。
  Agent 节点**刻意没有共用兜底节点** —— 两个方向的工具集不同，一份提示词兜不住。
- **本轮只实现正向（为买家找标的）**。反向（为标的找买家）暂时不可用，标的列表的「推荐买家」入口
  已一并移除，推荐页的反向 tab 置灰。反向 Agent 化时真正要解决的是：把一段出售需求描述解析成能驱动
  `_candidate_intents_for_target` 初筛的标的画像 —— 该 SQL 完全依赖标的的结构化字段，字段空则初筛失效。
- **数字来自代码，不来自模型**。候选行带 `facts`（净利/地区/控股/PE/营收/估值，`_target_facts`，枚举
  标签取自指标注册表），brief 组装时用 `id` 关联回代码持有的 facts；模型报了不在候选里的 id 直接丢弃。
- **标的名 → 链接由后端确定性回填**（`recommendation_answer.backfill_target_links`，按本轮候选精确
  字符串匹配，长名优先、每个标的至多一次、已链接不重复包）。模型永远不输出 id 或 URL；前端只渲染
  站内路径链接。复制按钮输出去掉链接的纯文本。
- **流式只做最后一段**。没有 Redis（队列是 Postgres 表），worker 内的流式推不到浏览器，因此编排在
  worker、写作在 API 的 SSE 端点。`llm_client.stream_openai_compatible_chat` 是独立的无工具函数，
  刻意不碰 tool_calls 的分片累积解析。写作节点未配置或调用失败时回落 `fallback_answer_markdown`
  （用同一份 facts 规则拼装），用户仍拿得到可发的文本。流可恢复：答案落库后重连直接重放，不二次计费。
- **过程必须可见**。Agent 每次调用工具就写一条 `recommendation_message`(`agent_step`) 并立即提交，
  前端 1.2 秒轮询增量渲染成「已筛选 2 次 · 正在细看 12 家」的折叠行。Agent 自行放宽条件这类决定
  必须出现在这里，否则结果的来路不可见，用户不会信任它。
- **推荐页只干推荐**：不建标的、不建买家需求、不出报告、不做推进维护。「开始推进」移到标的详情页。
  会话仍带 `temporary_filter` 标记，现有守卫继续保证它永远变不成一条撮合关系。
- 澄清默认不问：条件不全时先按现有条件出结果、在结尾提示可补充什么；只有条件空到无法收敛才调
  `ask_user`，且最多一轮、最多 3 题、每题给可点选项并留「跳过」。
- 用户端不展示数字评分、A/B/C 档或内部评分明细。分数与评级仍保留在后端用于排序、调试和审计。
- 推荐召回可跨负责人。候选摘要带负责人与「已在推进 / 正与其他买家深入推进」布尔标记，
  后者只给布尔值，不泄露另一关系的对象或阶段。
- **已下线（代码不再调用，节点定义与数据表暂留，待死表判决）**：`recommendation_reranker`、
  `recommendation_deep_eval*` 三个深评节点、`recommendation_query_parser`。推荐报告双节点、
  `recommendation_report` 表与 Word 导出**保留后端**，仅撤掉推荐页入口。
- `worker-llm` 的 stale 窗口从默认 300s 提到 1800s（两套部署已同步）：一轮 Agent 跑满工具预算会超过
  5 分钟，窗口盖不住会把还在干活的任务判死。Agent 侧另有 240 秒墙钟预算强制收尾，双保险。
- **新增节点需要在设置页建配置和 Prompt 才能工作**（不写 prompt seed 迁移）：
  `recommendation_agent_to_target`（必配，否则推荐直接失败）、
  `recommendation_answer_writer_to_target`（不配则走规则兜底文案）。

### 3.4 撮合进度管理（已实现）

**核心决策：进度的单元是「买家意向 × 标的」这一对（`buyer_seller_relation`），不是任何单个实体。** 每对唯一、九状态流水线、事件挂关系（`relation_event`）。"多线程且交叉"由此消解：交叉只是同一条线从两个详情页可见。

四个视图：
1. **标的详情「推进」tab**：该标的的全部关系（买家、状态、最新动态、下一步、无动态预警）；
2. **买家意向详情「推进」tab**：完全镜像；
3. **关系时间线**（点开一对）：事件流 + 状态变更 + 下一步 + 记录动态；
4. **全局看板**：只做概览 + 跳转。九状态收敛为「初步接触 / 深度交流 / 已成交」三主列和「已关闭」底部抽屉；支持按标的/按意向双视角、责任范围三态、搜索与“隐藏最近无动态”筛选，固定按最近关系动态由近到远。同列同主体的多条关系默认折叠成摞，但每张内层卡仍是一条独立关系。点击卡片通过 `?tab=progress&relation=<id>` 深链接到两侧详情并展开对应时间线。

标的管理与买家管理列表只展示实体自身的「更新时间」（`updated_at`，前端格式 `MM-DD HH:mm`），不在实体列表聚合或展示关系的最近跟进/推进；关系动态只在上述四个进度视图中读取。

看板取数使用 `/relations/board` 瘦端点（9 个固定字段），前端一次加载后完成分桶、折叠、筛选和计数；达到客户端上限会显式提示截断，不再静默丢数据。默认责任范围为「我参与的」，另有「全部 / 我全权的」；管理员可再按指定负责人筛选。指定负责人与责任范围是 AND，且使用独立 SQL 参数，不能覆盖或放宽负责人权限地板；顾问构造他人 owner 参数也只能看到自身权限与该筛选的交集。

**动态来源与路由**：当前关系由推荐「开始推进」或手动「关联对手方」两条确定性路径创建。手工动态（含 AI 自动回填的跟进）允许修改和软删除；系统开局和状态变更事件不可修改。录入跟进时必须先选一条已有关系；直接写入保留原文，AI 路径只整理沟通内容与下一步并自动回填同一占位事件。同一份材料需要同时更新事实时，由用户选择「基本信息和跟进都更新」，两个固定节点独立处理。系统不通过自由文本自动识别对手方或创建关系。

**三个业务规则（2026-08-03 更新）**：
1. **深入推进提示**：`due_diligence / agreement` 中的关系不排除另一侧继续参与推荐；标的侧只提示「正与其他买家深入推进」，买家需求侧只提示「正与其他标的深入推进」，**不透露对方是谁**。早期接触、已成交与关闭状态均不算“正在深入推进”。
2. **跨负责人可见性**：一条关系对双方负责人 + 管理员可见。
3. **状态集**：沿用 schema 九状态跑真实业务，之后按实际使用裁剪。

### 3.5 附件与 OCR

`attachment → OCR（外部 API）→ parsed_document → 按 business_update.processing_scope 进入 3.1 对应分支`，`evidence_span` 记录字段值在原文中的出处。OCR 是外部 HTTP 服务，不绑 AI 节点、不吃 Prompt；配置以 `provider_type='ocr'` 存入 `model_provider_config`，设置页支持新增、编辑、启停与直接录入 API Key。直接录入的 Key 经 Fernet 加密且永不回显，API 与 worker-ocr 读取同一条数据库配置；仅在没有启用的数据库配置时回落到环境变量。文本 PDF 与 Office 文件本地提取，扫描 PDF 才调用 Doc2X，图片直接进入多模态模型。

### 3.6 数据看板

数据看板定位为**库存画像**，对顾问与管理员均可见，不承载账号活跃度考核，也不展示标的或买家名称。2026-07-29 拆除原按账号活跃度表并完成正式实现，四块内容三行版面：**标的省级分布地图 / 买家省级分布地图 / （标的行业分布 top + 标的营收规模）**。页面不写标题也不写口径说明，右上角只有服务端取数时间。

- **取数**：`/stats/overview`，**全库、不分 `lifecycle_status`、不按 `owner_scope` 过滤**——回答的是「盘子长什么样」而不是「我手上有什么」，所以大屏上每个人看到的是同一张图。响应只含计数，不含任何名称。
- **底图**：DataV.GeoAtlas 省级边界，含台湾省与南海诸岛（九段线画在右下角插图框）。`scripts/build_china_map.py` 离线做 Albers 等积圆锥投影 + Douglas-Peucker 简化，产出 `frontend/src/features/dashboard/chinaMap.ts` 的 34 条 SVG 路径；**运行时不解析 GeoJSON，也不引入图表库**——前端运行时依赖仍是 5 个。底图 chunk 约 136 KB，按需加载不进主包，两张地图共用同一份。
- **着色**：固定阈值分档，不做数量编码——同一个颜色在两次打开之间含义必须不变。**分档表按指标各配一份**：标的用 1–2/3–5/6–10/11+（红），买家主体量级只有一半、单省最多 2 家，用 1/2–3/4–6/7+（金）；共用一张表会让买家图整张落在最浅档。量级整体上台阶后回来调 `distribution.ts`。
- **买家地图画的是买家主体所在地**（`buyer_party.region_province`），不是买家想买哪里。需求地域 `buyer_intent.region_scope_summary` 是自由文本（「优先考虑长三角、珠三角区域具备扩产潜力的项目」），要上地图得先有结构化地域字段，属于买家侧注册表接入的后置项。
- **行业按二级行业取 top 10**，一级行业太粗读不出赛道。两个已知失真必须在页面上说出来：一个标的可挂多个 L2 所以计数之和大于标的数；二级行业字典的同义词尚未合并（食品 / 食品制造 / 食品加工 各占一行），榜单因此偏低估——去重工单见 `平台优化方案/数据看板拆除验收单0729.md` §1.3，是二级赛道图不失真的前提。

## 5. 指标注册表（设计）

**问题**：一个指标今天散在五处——DB 列、`recommendation_flow` 读取、前端 `infoGroups.ts`、extracted_action apply 白名单、调研字段白名单——靠人肉同步 + 缝合测试（`test_action_type_sync` / `test_info_group_sync`）兜底。

**形态**：`backend/app/registry/indicators.py`，纯声明式：

```python
@dataclass(frozen=True)
class Indicator:
    entity: str                # "seller_target" | "buyer_intent"
    column: str                # DB 列名 = API 字段名
    label: str                 # 中文名（前端/更新记录/prompt 上下文共用）
    group: str                 # 五组之一（identity + 四个业务分组）
    kind: str                  # text | yuan | ratio | enum | date | bool3
    enum_options: tuple | None # 枚举 code 与中文名
    screening: str | None      # None | "hard" | "soft:<权重>"
    writable_by: frozenset     # {"manual", "parse", "research"} 子集
    deep_eval: bool            # 是否进入深评上下文
```

**五个消费方的接入方式**：
1. 前端：`/meta/indicators` 驱动分组、中文名、枚举、编辑权限与「筛」角标——**运行时驱动，不做代码生成**，`infoGroups.ts` 仅保留值格式化；
2. 打分器：一致性测试改为「`recommendation_flow` 读取的列 ⊆ 注册表 screening 列」，替代正则扒源码；
3. extracted_action apply 白名单 = `writable_by ∋ "parse"`；
4. 调研 `allowed_structured_fields` = `writable_by ∋ "research"`；
5. 字段写入服务用 `kind/enum_options` 做校验与归一化，并按 `writable_by` 拒绝无权来源；更新记录用 `label` 显示。

**迁移路径**：立注册表（先只覆盖 seller_target）→ `/meta/indicators` 上线 → 前端切换 → 两个白名单切换 → 缝合测试改写或删除 → buyer_intent 接入。每步可独立发版。
