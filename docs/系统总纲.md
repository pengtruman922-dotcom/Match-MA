## 1. 业务与用户

**系统名称**：投资撮合管理和智能推荐平台（Match-MA）。

**业务背景**：咨询公司的投资撮合业务。顾问同时服务买卖双方——为买家寻找标的，为卖家寻找买家，并推进双方持续沟通。

**平台三大核心**：
1. 买家和卖家的信息管理与画像；
2. 智能推荐（双向）；
3. 撮合项目进度管理。

**用户与权限模型**（已实现，不需改动）：
- **顾问（consultant）**：录入信息、查看并管理自己负责的买家/卖家、发起推荐、记录进度。数据可见性 = 负责人本人 + 管理员（`owner_scope`）。
- **管理员（admin）**：全局明细可见、账号管理、系统设置（模型/prompt/搜索工具等 tab 仅管理员可见）。
- 登录：`app_user` 账号密码 → JWT；另保留共享管理员凭证作恢复通道（`auth.py`）。
- **未启用**：team/workspace 多租户（列存在、值恒为种子常量）、`visibility` 三档字段（无过滤行为）。见 §6 判决。

## 2. 领域模型

### 2.1 核心实体

```
seller_target（标的，宽表 ≈80 列）──┐
buyer_party（买家主体）             ├── buyer_seller_relation（意向×标的 = 撮合关系）
buyer_intent（买家意向，宽表 ≈53 列）┘         └── relation_event（关系时间线）
        │
        ├── entity_profile_section（定性画像六栏，多修订版本）
        ├── business_update → extracted_action → action_application_log（解析与更新审计链）
        ├── attachment → parsed_document → evidence_span（附件/OCR/证据）
        └── research_proposal（调研产出）
AI 基础设施：model_provider_config / model_node_config / prompt_template / background_job / ai_trace
数据字典：industry_taxonomy（L1/L2）
```

### 2.2 两层信息结构（定型，不再争论）

- **结构化字段**（宽表列）：服务 SQL 初筛与代码打分。宽表是「初筛必须代码化」的直接代价，**不换成 jsonb/纵表**——那会让初筛 SQL 无法编写。加字段的成本问题由指标注册表解决（§5）。
- **定性画像六栏**（`entity_profile_section`）：`business_product / chain_position / tech_team / ops_quality / deal_terms / sell_intent_risk`，装结构化字段装不下的判断。多修订、三态（filled/not_found/not_applicable）、接受即当前值、进更新记录、可回滚。
- 前端合并展示为一个「标的信息」页：七组（身份地区 + 画像六栏），组内先硬字段后定性栏，参与初筛/打分的字段带「筛」角标。

### 2.3 数据字典原则

- 行业：**原文 + 归一化双存**（`industry_primary/secondary` 存 LLM 原文，`industry_l1/l2` 存 `industry_taxonomy` 归一化值，初筛只认 L1/L2）。
- 地区：省/市结构化列 + `raw_region_text` 原文 + 粒度标记。归一化由 LLM 解析时直接提取省/市完成，**不设别名字典**（`region_alias_config` 判死，见 §6.1）。
- 枚举字段的取值与中文名未来统一由指标注册表声明（§5）。

## 3. 关键流程

### 3.1 信息录入与解析（买卖两侧同一机制）

```
顾问粘贴文本/上传附件 → business_update
  → LLM 解析（专用 parser 节点）→ extracted_action（带 action_type 白名单）
  → apply（人工确认或自动）→ 写实体字段/画像/跟进
  → action_application_log → 「更新记录」展示 + 可回滚
```

**目标态（待实施）**：三个来源（手动编辑/解析采纳/调研采纳）收敛到**唯一字段写入服务**：`写入(实体, 字段, 新值, 来源, 证据)`——内部查注册表做合法性校验与归一化 → 写列 → 记审计。原则一句话：**来源可以多，写入通道必须只有一条。**

### 3.2 标的调研 Agent（2026-07 已按此重写）

- 架构：**主 agent + 工具**（`web_search` / `fetch_page`），模型自主规划检索词、判断结果、决定收尾；代码不做规则限制（无锚点闸门、无取证计数器、无代码侧冲突分类——否决清单见 0721 方案 §8，不再重开）。
- 时效与冲突判断在 prompt 内完成，输出带 `relation`（consistent/supplement/temporal_update/same_period_conflict）与 `sources`。
- 产出自动采纳（写画像 + 白名单内结构化字段），全部进更新记录、可回滚。
- 30 天内调研过的标的：批量发起时**显式弹窗二次确认**，不做服务器静默过滤。
- 全链路留痕：一次调研一行 `ai_trace`（完整工具调用链 + 统计元数据）。
- prompt 通过设置页版本管理发布，**不写 prompt seed 迁移**。

### 3.3 智能推荐（双向）

```
买家意向 → 标的：SQL 初筛（多方案 OR + 三态判断）→ 代码打分（乐观分）→ 深评分片（LLM）→ 推荐报告
标的 → 买家意向：同一引擎反向（recommendation_flow._candidate_intents_for_target）
```

- 初筛与打分**必须代码化**，禁止全库打包给 LLM。
- 与进度管理的接口：推荐结果分区展示——「已在推进(n)」（该意向与候选已有活跃关系，不参与排名，仅对照）与「新候选」；新候选带 **[开始推进]** 按钮，一键创建关系（状态=已推荐）。不隐式过滤，显式分区（与调研 30 天弹窗同一原则）。

### 3.4 撮合进度管理（设计定稿待三个规则拍板）

**核心决策：进度的单元是「买家意向 × 标的」这一对（`buyer_seller_relation`），不是任何单个实体。** 每对唯一、九状态流水线、事件挂关系（`relation_event`）。"多线程且交叉"由此消解：交叉只是同一条线从两个详情页可见。

四个视图：
1. **标的详情「推进」tab**：该标的的全部关系（买家、状态、最新动态、下一步、无动态预警）；
2. **买家意向详情「推进」tab**：完全镜像；
3. **关系时间线**（点开一对）：事件流 + 状态变更 + 下一步 + 记录动态；
4. **全局看板**：状态列 × 关系卡片，管理员全局、顾问默认只看自己。

**动态来源与路由**：手动记录之外，LLM 跟进解析识别出对手方的动态挂到关系（`relation_event`），识别不出的留在实体自身跟进（`target_follow_up` / `buyer_intent_follow_up`）。**单边信息挂实体，双边信息挂关系，由解析路由。**

**三个业务规则（2026-07-22 定稿）**：
1. **排他性**：标的与某买家进入深入推进阶段后，对其他买家的推荐里照常参与，但标注「正与其他买家深入推进」，**不透露对方是谁**。
2. **跨负责人可见性**：一条关系对双方负责人 + 管理员可见。
3. **状态集**：沿用 schema 九状态跑真实业务，之后按实际使用裁剪。

### 3.5 附件与 OCR

`attachment → OCR（外部 API）→ parsed_document → 进入 3.1 解析流程`，`evidence_span` 记录字段值在原文中的出处。OCR 的 API key 配置并入 `model_provider_config` 加密 key 体系（待做，小改动）。

## 5. 指标注册表（设计）

**问题**：一个指标今天散在五处——DB 列、`recommendation_flow` 读取、前端 `infoGroups.ts`、extracted_action apply 白名单、调研字段白名单——靠人肉同步 + 缝合测试（`test_action_type_sync` / `test_info_group_sync`）兜底。

**形态**：`backend/app/registry/indicators.py`，纯声明式：

```python
@dataclass(frozen=True)
class Indicator:
    entity: str                # "seller_target" | "buyer_intent"
    column: str                # DB 列名 = API 字段名
    label: str                 # 中文名（前端/更新记录/prompt 上下文共用）
    group: str                 # 七组之一（identity + 画像六栏）
    kind: str                  # text | yuan | ratio | enum | date | bool3
    enum_values: tuple | None  # 枚举取值与中文名
    screening: str | None      # None | "hard" | "soft:<权重>"
    writable_by: frozenset     # {"manual", "parse", "research"} 子集
    deep_eval: bool            # 是否进入深评上下文
```

**五个消费方的接入方式**：
1. 前端：新增 `/meta/indicators` 端点，前端按 API 渲染分组/中文名/枚举/「筛」角标——**运行时驱动，不做代码生成**，`infoGroups.ts` 退役；
2. 打分器：一致性测试改为「`recommendation_flow` 读取的列 ⊆ 注册表 screening 列」，替代正则扒源码；
3. extracted_action apply 白名单 = `writable_by ∋ "parse"`；
4. 调研 `allowed_structured_fields` = `writable_by ∋ "research"`；
5. 字段写入服务（§3.1 目标态）用 `kind/enum_values` 做校验与归一化，更新记录用 `label` 显示。

**迁移路径**：立注册表（先只覆盖 seller_target）→ `/meta/indicators` 上线 → 前端切换 → 两个白名单切换 → 缝合测试改写或删除 → buyer_intent 接入。每步可独立发版。

## 6. 实现判决（2026-07-22 审计，方法：写入路径/读取路径/种子/前端展示四查）

### 6.1 表级判决

**判死（baseline 不再携带）**：

| 表 | 证据 | 判决理由 |
|---|---|---|
| `seller_target_financial` | 零读零写零种子 | 多期财务从未接线；current_* 列已承担最新期。需要多期时重新设计 |

| `seller_target_tag` + `tag_dictionary` | tag 表零写；字典只有种子+1 处 meta 读 | 标签体系从未接线；行业/地区已有专表字典 |

**其余 32 表：活，保留。**（`evidence_span`、`field_value_source` 经查为活表——证据链与字段来源展示在用，此前"疑似死"的判断错误。）

### 6.3 迁移压平（2026-07-22 完成）

47 个 SQL 迁移 + 48 个 alembic 版本脚本已压成 `database/migrations/001_baseline.sql` + 单一 alembic 修订（沿用压平前的修订号 `20260722_0048`，生产部署零感知 no-op，无需 stamp）。要点：
