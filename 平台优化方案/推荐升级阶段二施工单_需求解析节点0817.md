# 阶段二施工单：需求解析节点

> 2026-08-17。方案见 `平台优化方案/推荐功能升级设计框架0805.md` 第三节。
> **不依赖指标体系那条线，也不依赖阶段一，可并行开工。**

## 一、这个阶段解决什么

现在解析和执行在同一个模型里：用户说一句话，agent 自己理解、自己筛选、自己下结论。
**没有任何地方能比对「用户说了什么」和「agent 筛了什么」**——
实测中出现过用户只说「杭州标的」，agent 自己编出「半导体 + 华东 + 净利 3000 万」去筛的事故。

拆出独立的解析节点后，**结构化条件成为一份可审计的基线**，主 Agent 只能消费不能创造。
这个问题从结构上消失，不需要额外的证据校验机制。

代价是多一次 LLM 调用（约 3–8 秒）。

## 四、设计

### 4.1 输出 schema

```json
{
  "condition_groups": [
    {
      "label": "上市公司",
      "conditions": {
        "industry_l2_json": ["机器人", "人工智能"],
        "acceptable_listed_status_json": ["listed"],
        "min_market_cap_yuan": 100000000,
        "max_pe": 15
      },
      "strength": {"min_market_cap_yuan": "required", "max_pe": "preferred"}
    },
    {
      "label": "非上市公司",
      "conditions": {
        "industry_l2_json": ["机器人", "人工智能"],
        "acceptable_listed_status_json": ["unlisted"],
        "min_revenue_yuan": 30000000
      },
      "strength": {"min_revenue_yuan": "required"}
    }
  ],
  "qualitative_requirements": ["具备地区产业优势", "有成熟的海外仓网络"],
  "exclusions": {"industries": ["房地产与建筑"]},
  "unstructured_notes": ["希望能配合做业绩承诺"],
  "raw_text": "用户原话",
  "parser_status": "ok"
}
```

四个字段各有不可替代的作用：

- **`condition_groups`** 是多方案的对话式表达。组内 AND、组间 OR，
  由主 Agent 拆成多次 skill 调用实现。**不落 `buyer_intent_scenario` 表**——
  对话链路不需要持久化多方案。
- **`strength`** 只给主 Agent 看，skill 不认。它决定 agent 先带哪些条件、
  召回不足时先去掉哪些。取值 `required` / `preferred`。
- **`qualitative_requirements`** 是深评的工作对象，筛选完全用不上，
  但必须在解析阶段抓出来——后面没有任何节点会再看用户原话。
- **`unstructured_notes`** 记录「用户说了但我没能结构化的话」。
  **这是最容易被忽略也最该保留的一项**：它让「漏掉了什么」变得可见。

### 4.2 双出口：白名单只约束 conditions

`conditions` 里的字段必须限定在可筛集合内（复用现有的 `OVERRIDE_FIELD_KINDS` 白名单
+ `_coerce_value` 类型强制），映射不上的字段直接丢弃。

**但丢弃前必须有兜底出口。** 反面教材：用户说「要经营稳定的」，
而 `operation_stability_status` 已在指标重构中被判为伪枚举删除——
如果只有白名单没有兜底，这句话就既不进条件也不进定性诉求，**静默蒸发**。

规则：

| 用户表达 | 去处 |
|---|---|
| 能映射到可筛字段 | `conditions` |
| 映射不上、但是对标的的实质要求 | `qualitative_requirements` |
| 映射不上、也不是对标的的要求（背景、偏好、流程诉求） | `unstructured_notes` |
| 明确的排除 | `exclusions` |

**白名单只作用于第一行。** 后三个出口不做字段校验，只做字符串清洗与长度截断。

### 4.3 行业：L1 进 enum，L2 走后处理匹配

两级策略不同，**这是本阶段最容易做错的地方**。

**一级行业是闭集（当前 15 项）**，直接注入 prompt 的字段清单并在归一化时严格校验。
15 个词的成本可以忽略。闭集见 `industry_taxonomy.py` 的 `DEFAULT_L1_TERMS`，
运行时以 `industry_l1_prompt_list(db)` 为准。

**二级行业是开放集，由 DB 维护。** 当前生产有 29 个取值
（半导体、汽车零部件、医疗器械、机器人、人工智能、储能……），标的侧覆盖率 69%。
不要试图把 L2 全量塞进 prompt——它会随录入增长。

做法：**让模型自由输出二级行业词，代码用现有的 `resolve_l1` / `industry_taxonomy`
的 alias 机制归一**（表里 `level='alias'` 就是为此存在的）。匹配不上的词，
**不要丢**——落进 `qualitative_requirements`，让深评去判断。

> **为什么 L2 很重要**：用户说「机器人/AI 行业」，在 L1 粒度只能映射成
> 「制造与工业 + 信息技术与通信」，这两个类目占了全库近半，等于没筛。
> 真正的区分力在 L2。所以解析节点**必须同时尝试 L1 与 L2**，
> 能给出 L2 就给，主 Agent 再决定先用哪个筛。

### 4.4 Prompt 变量

`NodeSpec.prompt_variables` 更新为：

| 变量 | 内容 |
|---|---|
| `user_message` | 本轮用户原话 |
| `history_context` | 最近 6 轮已完成对话原文（复用 `agent_history_context`） |
| `industry_l1_list` | 一级行业闭集，运行时注入（现有机制） |
| `screening_fields_json` | **可筛字段清单，从注册表生成后注入** |

`screening_fields_json` 与阶段一的 schema 生成器**必须共用同一个真源**，
否则两边必然漂移——解析节点抽出了一个 skill 不认识的字段，或者反过来。
若阶段一已交付 `screening_schema.py`，直接调用它；否则本阶段实现，阶段一复用。

`mode` 变量保留（`buyer_to_target` / `target_to_buyer`），为反向留位。

> **提示词变量只认 `{{ name }}`**（`backend/app/ai/prompting.py`）。
> 写成单花括号会渲染成字面量、全链路零报错——存提示词时已有校验会拒绝，
> 但写的时候就注意，别浪费一次往返。

### 4.5 在链路中的位置

**解析在 `recommendation_agent` job 内同步执行，不新增队列或 job 类型。**

```
worker 领到 recommendation_agent job
  → ① 调解析节点（本阶段）
  → ② 写 agent_understanding 消息并 commit（前端立刻能看到进度）
  → ③ 把解析结果作为 prompt 变量传给主 Agent（阶段四接）
  → ④ 工具循环…
```

写消息用现有的 `_insert_agent_message` 骨架，`message_type` 取 `agent_understanding`。
现有的中止（abort）机制天然覆盖这一步——在解析前后各查一次 `agent_turn_aborted` 即可。

**本阶段不需要改前端。** 业务方已确认不做条件面板；生效条件由写作节点在正文开头复述
（阶段四实现）。`agent_understanding` 消息本阶段只用于 trace 与进度显示。

### 4.6 失败要响，不能静默

现有的 `fallback_parse_result` 把整句话记成语义偏好，思路是对的，但要区分三种失败：

| `parser_status` | 触发条件 | 行为 |
|---|---|---|
| `ok` | 正常解析出结构 | 继续 |
| `fallback` | LLM 调用失败/超时 | 原话进 `qualitative_requirements`，继续跑，主 Agent 按无结构条件处理 |
| `schema_mismatch` | **LLM 返回了 JSON，但一个可识别的顶层键都没有** | 同上继续跑，但必须在 trace 与 `agent_understanding` 消息里明确标注 |

第三种是这次专门要防的：**提示词版本与代码不匹配时，必须看得见**。
上一轮吃过一模一样的亏——v0.1.0 提示词把变量写成单花括号，模型收到字面量，
输出全错但全链路零报错，只能靠人读对话记录才发现。

无论哪种失败，**都不要中断本轮**——退化成「没有结构化条件的一轮」比直接报错对用户更有用。

## 五、Prompt v0.2.0 要点

提示词全文由你撰写并通过 API 安装（**不写迁移**，见 `AGENTS.md`）。必须覆盖：

1. **输出 4.1 的 JSON 结构**，四个顶层键都要，没内容就给空数组/空对象
2. **分组规则**：只有当用户对不同类型标的提出不同要求时才分组
   （典型：上市/非上市、行业分档、规模分档）。**单一要求不要强行分组。**
3. **不要补用户没说的条件**——这是这个节点存在的全部意义
4. **行业尽量给到二级**，给不出二级再给一级
5. **`strength` 的判定**：「必须/一定要」→ `required`；
   「最好/优先/倾向」→ `preferred`；没有修饰词的定量门槛默认 `required`
6. **定性诉求原样保留用户的说法**，不要改写成系统术语
7. 变量一律 `{{ name }}`

安装命令形态（token 读 `.match-ma-local-auth.json`，必须从仓库根目录运行）：

```bash
python scripts/install_prompt.py --base https://match-ma-production.up.railway.app/api/v1 --version v0.2.0
```

## 六、验收用例

| # | 输入 | 期望 |
|---:|---|---|
| 1 | `杭州的标的` | 1 组；`region_constraints_json` 含浙江省/杭州市；无其他条件 |
| 2 | `江苏的制造业，净利1000万以上` | 1 组；行业 L1=制造与工业、地区=江苏省、`min_net_profit_yuan=10000000` |
| 3 | `机器人/AI行业，上市的市值1亿PE15，非上市的营收3000万` | **2 组**；两组的行业都含 L2 机器人/人工智能；组一 listed + 市值 + PE，组二 unlisted + 营收 |
| 4 | `浙江的制造业，最好有成熟的海外仓` | 1 组条件 + `qualitative_requirements` 含海外仓那句 |
| 5 | `要经营稳定的制造业` | 行业进 `conditions`；「经营稳定」进 `qualitative_requirements`（该字段已删，**不得静默丢弃**） |
| 6 | `不要房地产` | `exclusions.industries` 含房地产与建筑 |
| 7 | `新能源车企` | 行业能归一到字典内（L1 制造与工业，L2 能给则给）；**不得原样输出字典外的词到 `conditions`** |
| 8 | `今天天气怎么样` | `condition_groups` 为空；原话进 `unstructured_notes`；不报错、不编条件 |
| 9 | `净利要3000万以上，最好在长三角` | `min_net_profit_yuan` 的 strength=`required`，地区 strength=`preferred` |
| 10 | LLM 返回 `{"foo": 1}` | `parser_status == "schema_mismatch"`，且不抛异常、不返回伪造条件 |

用例 5、8、10 是**必须过**的三条——它们分别验证「不静默丢弃」「不编条件」「失配要响」，
每一条都对应一次真实事故。
