## 一、这个阶段解决什么

现在解析和执行在同一个模型里：用户说一句话，agent 自己理解、自己筛选、自己下结论。
**没有任何地方能比对「用户说了什么」和「agent 筛了什么」**——
实测出现过用户只说「杭州标的」，agent 自己编出「半导体 + 华东 + 净利 3000 万」去筛的事故。

拆出独立的解析节点后，**结构化条件成为一份可审计的基线**，主 Agent 只能消费不能创造。
这个问题从结构上消失，不需要额外的证据校验机制。

代价是多一次 LLM 调用（约 3–8 秒）。

## 四、设计

### 4.1 输出 schema

```json
{
  "condition_groups": [
    {
      "label": "上市公司",
      "conditions": {
        "industry_l2_json": ["机器人", "人工智能"],
        "acceptable_listed_status_json": ["listed"],
        "min_market_cap_yuan": 100000000,
        "max_pe": 15
      },
      "strength": {"min_market_cap_yuan": "required", "max_pe": "preferred"}
    },
    {
      "label": "非上市公司",
      "conditions": {
        "industry_l2_json": ["机器人", "人工智能"],
        "acceptable_listed_status_json": ["unlisted"],
        "min_revenue_yuan": 30000000,
        "max_debt_ratio": 60
      },
      "strength": {"min_revenue_yuan": "required"}
    }
  ],
  "qualitative_requirements": ["具备地区产业优势", "有成熟的海外仓网络"],
  "exclusions": {"industries": ["房地产与建筑"], "risk_flags": ["equity_frozen"]},
  "unstructured_notes": ["希望能配合做业绩承诺"],
  "raw_text": "用户原话",
  "parser_status": "ok"
}
```

各字段的作用：

- **`condition_groups`** 是多方案的对话式表达。组内 AND、组间 OR，
  由主 Agent 拆成多次 skill 调用实现。**不落 `buyer_intent_scenario` 表**——
  对话链路不持久化多方案。
- **`strength`** 只给主 Agent 看，skill 不认。它决定 agent 先带哪些条件、
  召回不足时先去掉哪些。取值 `required` / `preferred`。
- **`qualitative_requirements`** 是深评的工作对象，筛选完全用不上，
  但必须在解析阶段抓出来——后面没有任何节点会再看用户原话。
- **`unstructured_notes`** 记录「用户说了但我没能结构化的话」。
  **这是最容易被忽略也最该保留的一项**：它让「漏掉了什么」变得可见。
- **`exclusions.risk_flags`** 映射到 `unacceptable_risk_flags_json`，
  归一化直接用 `services/buyer_risk_tolerance.normalize_unacceptable_risk_flags()`。

### 4.2 双出口：用 normalize_conditions 的 ignored 做判据

```python
conditions, ignored = normalize_conditions(
    raw_group_conditions,
    industry_l1_terms=list_l1_terms(db),
    industry_l2_terms=list_l2_terms(db),
)
```

`ignored` 里每一条都是「模型提了但没能生效」的东西。**这正是兜底出口的触发信号**——
不要丢掉它，按下表分流：

| 情况 | 去处 |
|---|---|
| 归一化通过 | `conditions` |
| 被 `ignored`，且是对标的的实质要求 | `qualitative_requirements` |
| 被 `ignored`，但不是对标的的要求（背景、流程诉求） | `unstructured_notes` |
| 模型压根没往条件里放的自由描述 | `qualitative_requirements` 或 `unstructured_notes` |

**反面教材**：用户说「要经营稳定的」，而 `operation_stability_status`
已在指标重构中被判为伪枚举删除。若只有过滤没有兜底，这句话就既不进条件
也不进定性诉求，**静默蒸发**。同类的还有净利率、PS、溢价、迁址/返投/留任——
它们都是合法的业务表达，只是不进初筛。

### 4.3 行业：L1 与 L2 都是运行时闭集

**两级都注入、都严格校验**，与阶段一的 schema 保持一致：

| 用途 | 函数 |
|---|---|
| 提示词注入 | `industry_l1_prompt_list(db)` / `industry_l2_prompt_list(db)` |
| 取值归一 | `normalize_l1_values(db, ...)` / `normalize_l2_values(db, ...)` |
| 别名映射 | `resolve_l1(db, term)`（`industry_taxonomy` 表里 `level='alias'` 的行） |

匹配不上闭集的行业词**不要丢**——落进 `qualitative_requirements`，让深评去判断。

> **为什么 L2 关键**：用户说「机器人/AI 行业」，在 L1 粒度只能映射成
> 「制造与工业 + 信息技术与通信」，这两个类目占了全库近半，等于没筛。
> 真正的区分力在 L2（生产当前 29 个取值：半导体、汽车零部件、医疗器械、
> 机器人、人工智能、储能……）。解析必须同时尝试两级，**能给出 L2 就给**，
> 主 Agent 再决定先用哪个筛。

### 4.4 Prompt 变量

`NodeSpec.prompt_variables` 更新为：

| 变量 | 内容 | 来源 |
|---|---|---|
| `user_message` | 本轮用户原话 | job payload |
| `history_context` | 最近 6 轮已完成对话原文 | 复用 `agent_history_context` |
| `industry_l1_list` | 一级行业闭集 | `industry_l1_prompt_list(db)` |
| `industry_l2_list` | 二级行业闭集 | `industry_l2_prompt_list(db)` |
| `screening_fields_json` | 24 个可筛字段的名称、含义、取值范围 | **由 `SCREENING_FIELDS` 生成** |
| `mode` | `buyer_to_target` / `target_to_buyer` | 为反向留位 |

去掉 `current_conditions_json`（不再有增量语义）。

`screening_fields_json` 请写一个小函数从 `SCREENING_FIELDS` 渲染
（column + label + value_type + enum_values + unit_hint），
**不要手写一份字段清单**——手写的必然与注册表漂移，这是本项目反复吃过亏的地方。

> **提示词变量只认 `{{ name }}`**（`backend/app/ai/prompting.py`）。
> 写成单花括号会渲染成字面量、全链路零报错。存提示词时已有校验会拒绝，
> 但写的时候就注意，别浪费一次往返。

### 4.5 在链路中的位置

**解析在 `recommendation_agent` job 内同步执行，不新增队列或 job 类型。**

```
worker 领到 recommendation_agent job
  → ① 调解析节点（本阶段）
  → ② 写 agent_understanding 消息并 commit（前端立刻能看到进度）
  → ③ 解析结果作为 prompt 变量传给主 Agent（阶段四接线，本阶段只需产出并落库）
  → ④ 工具循环（阶段一已改造完）
```

写消息用现有的 `_insert_agent_message` 骨架，`message_type` 取 `agent_understanding`。
中止机制天然覆盖这一步——在解析前后各查一次 `agent_turn_aborted` 即可。

> 注意 `jobs/handlers/recommendation.py` 阶段一刚改过
> （`RECOMMENDATION_AGENT_TOOLS` → `build_agent_tools(db)`），
> 拉最新代码再动，不要基于旧版本改。

**本阶段不改前端。** 业务方已确认不做条件面板；生效条件由写作节点在正文开头复述
（阶段四实现）。`agent_understanding` 消息本阶段只用于 trace 与进度显示。

### 4.6 失败要响，不能静默

现有的 `fallback_parse_result` 思路对，但要区分三种失败：

| `parser_status` | 触发条件 | 行为 |
|---|---|---|
| `ok` | 正常解析出结构 | 继续 |
| `fallback` | LLM 调用失败/超时 | 原话进 `qualitative_requirements`，继续跑 |
| `schema_mismatch` | **返回了 JSON，但一个可识别的顶层键都没有** | 同上继续跑，但必须在 trace 与 `agent_understanding` 消息里明确标注 |

第三种是这次专门要防的：**提示词版本与代码不匹配时，必须看得见**。
上一轮吃过一模一样的亏——v0.1.0 提示词把变量写成单花括号，模型收到字面量，
输出全错但全链路零报错，只能靠人读对话记录才发现。

无论哪种失败，**都不要中断本轮**——退化成「没有结构化条件的一轮」比直接报错对用户更有用。

## 五、Prompt v0.2.0 要点

提示词全文由你撰写并通过 `/model-config/prompts` API 安装（**不写迁移**，见 `AGENTS.md`）。
必须覆盖：

1. **输出 4.1 的 JSON 结构**，顶层键都要，没内容就给空数组/空对象
2. **分组规则**：只有当用户对不同类型标的提出不同要求时才分组
   （典型：上市/非上市、行业分档、规模分档）。**单一要求不要强行分组。**
3. **不要补用户没说的条件**——这是这个节点存在的全部意义
4. **行业尽量给到二级**，给不出二级再给一级；两级都只能填闭集里的词
5. **比率类一律百分数**：负债率 60% 写 `60`，股比 51% 写 `51`
6. **`strength` 的判定**：「必须/一定要」→ `required`；
   「最好/优先/倾向」→ `preferred`；没有修饰词的定量门槛默认 `required`
7. **定性诉求原样保留用户的说法**，不要改写成系统术语
8. 变量一律 `{{ name }}`
