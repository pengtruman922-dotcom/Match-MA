## 1. 已定稿的决定

### 1.1 状态模型：三个状态收敛为两个

废弃 `recommendation_status`。标的只保留两个正交状态：

| 概念 | 存储 | UI 列名 | 取值 | 谁能改 |
|---|---|---|---|---|
| 交易状态 | `lifecycle_status`（**列名不改**） | 「状态」 | 在售中 / 已售出 / 已停售 | 人工（详情页下拉）+ 成交联动 + 解析出终局信号 |
| AI 处理进度 | `information_status` + `last_parse_at` + `last_research_at` + `research_last_outcome` | 「AI 处理」 | 见 §1.2 | 系统 |

- **新建标的默认「在售中」**，立即进入推荐候选池（符合 recall 优先取向）。
- **推荐初筛条件变为 `lifecycle_status = 'active'` 单条**。已售出/已停售天然排除——成交时 `relation_flow.mark_seller_target_sold_for_deal_closed` 会置 `sold`，解析出「已售出/已停售」时 `extracted_action_apply` 同样置 `lifecycle_status`。
- 列名保留 `lifecycle_status` 而不是改成 `status`：改列名要动迁移、索引、`update_logs` 的字段白名单和历史审计记录里的 `field_path`，收益为零。**只改 UI 标签**。

### 1.2 AI 处理状态：一列合成两条流水线

原「解析状态」列改名「AI 处理」，**一列**表达"我刚才那个操作跑完没有"，覆盖解析与调研两条异步流水线。运行中优先；终态比较 `last_parse_at` 与 `last_research_at`，由最近一次操作决定，避免旧失败覆盖新成功：

| 显示 | 判定 | 颜色 | 交互 |
|---|---|---|---|
| 解析中 | `information_status = 'parsing'` | 蓝 + spinner | — |
| 调研中 | `information_status = 'researching'` | 蓝 + spinner | — |
| 解析失败 | `information_status = 'parse_failed'` | 红 | 点击进「更新记录」 |
| 调研失败 | `research_last_outcome = 'failed'` | 红 | 点击进标的详情 |
| 已完成 | 有过解析或调研（`information_status = 'normal'` 或 `last_research_at` 非空） | 绿 | hover 显示"解析 07-26 · 调研 07-27 未找到公开信息" |
| 未处理 | 从未解析也从未调研（`insufficient` 且无 `last_research_at`） | 灰 | — |

- `research_last_outcome = 'no_public_information'` 归入**已完成**，不是失败：调研本身跑通了，只是没查到，操作是生效的。
- 「未解析」这一档消失——它本来就不是真实状态，是 `recommendation_status` 串味的产物（旧代码 `presentation.tsx:30` 用 `recommendation_status === 'recommendable'` 判断"已解析"）。

### 1.3 待复核：前端删除，后端停止写入

- 前端徽章去掉该档；后端不再把标的置为 `pending_review`。
- **DB 枚举值保留**（存量数据 + 未来通知中心可能消费），只是不再写入。存量 4 行在迁移中回填为 `normal`。
- 未能自动采纳的 `extracted_action` 照旧落库、可查询，只是不再污染标的状态。
- 后端 `GET /business-updates/{id}/review-page`（约 700 行服务代码，全系统零调用）本轮不动，等通知中心方案定了再决定复用还是删。

### 1.4 筛选器

- **地区**：三级联动（省 → 市 → 区），**单选**，选到哪级筛到哪级。选项骨架来自 `@vant/area-data` 标准行政区划，库存计数作为标注；计数为 0 的省份仍显示但置灰排后。
- **行业**：一级/二级两级联动，**单选**，数据源为行业字典（`GET /meta/industry-options`），同样附库存计数。
- **搜索框**：全字段搜索加入行业对匹配，并新增显式字段选择器。
- 多选本轮不做。

### 1.5 省市区规范化

生产数据已规范，因此：

- 迁移只做**幂等防御性回填**（trim + 省级别名补后缀），预期影响 0 行，但保留统计输出；
- 真正的价值在**写入侧**：`field_writer` 对 `location_province` 做省级字典归一化（后端内置 34 项省级别名表），市/区只做 trim。解析与调研写入的地区目前零校验，这才是未来不规范的来源。

## 4. 风险与回滚

| 风险 | 缓解 |
|---|---|
| `drop column` 不可回滚 | 两阶段部署；阶段 A 不删列并等待 API、前端和四个 worker 全部切换，阶段 B 前再次记录 `/debug/table-stats` |
| 索引重建期间列表变慢 | 61 行数据，重建瞬时完成 |
| Prompt 仍产出 `recommendation_status` | 该字段将不在 `writable_columns("parse")` 中，`_normalize_proposed_changes` 会以 `ignored_unsupported_field` 丢弃并留痕；先发版再改 prompt 是安全顺序 |
| 前端旧缓存读不到字段 | 字段是删除而非改名，`types/api.ts` 同步删除后 TS 编译即可拦截漏改 |
