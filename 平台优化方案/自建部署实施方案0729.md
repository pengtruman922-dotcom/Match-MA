# Match-MA 自建部署实施方案（Railway / 自建双轨并存）

日期：2026-07-29
状态：方案（未动代码；本文档只描述后续要新增的文件与操作，供评审）

---

## 0. 目标与硬约束

**目标**：在自建服务器上跑一套完整的 Match-MA 内部正式环境，与现有 Railway 环境**并存**。先在本地 Docker 起步验证，同一套编排文件可原样平移到阿里云 ECS。

**本次已确认的选型**：

- 基础设施：**全自建**——`pgvector` 数据库跑在容器里，附件用本地持久卷（不接阿里云 RDS/OSS）。
- 数据：**全新空库**——由 Alembic 建表 + baseline 种子，模型 API key 后续在「AI 设置」页重新录入。

**硬约束（贯穿全案）**：

1. **不改任何业务代码**——`backend/`、`frontend/src/`、迁移、prompt 都不动。
2. **不动 Railway 现有配置**——`railway.toml`、`railway.worker-*.toml`、`scripts/railway_*.py`、Nixpacks 全部保持原样。
3. **所有新增文件集中在 `deploy/` 目录**，Railway 永远扫不到 → 两条部署链路物理隔离。
4. 两套环境**共享同一份代码 + 同一套环境变量契约**（`backend/app/config.py` 本就是 12-factor 全 env 驱动），差异只体现在「谁来注入这些变量、谁来启动进程」。

## 1. 为什么几乎不用改代码

`backend/app/config.py` 里所有配置项——数据库、鉴权、加密密钥、S3/OSS、OCR——**全部从环境变量读**，且对 S3 endpoint / region / bucket / key 已经做了多别名兜底（`S3_*`、`AWS_*`、`MINIO_*`、`R2_*` 都认）。这意味着换部署平台 = 换一组环境变量，代码无感。

进程角色的区分也天然适配：

- **API** = `uvicorn backend.app.main:app`
- **Worker** = `python -m backend.app.worker --queue <llm|ocr|research>`

Railway 上是靠 `scripts/railway_start.py` 按服务名 `RAILWAY_SERVICE_NAME` **推断**角色。自建环境**不走这个脚本**，而是在 compose 里给每个服务写**显式启动命令**，从而完全绕开 Railway 专属逻辑。所以 `railway_start.py` / `railway_predeploy.py` 保持 Railway 专用、自建这边看都不看。

> 结论：本次改造的工作量 ≈ 新增一套 Docker 打包 + 编排文件，业务代码零改动。

## 2. 目标架构（自建，单机）

一台机器、一个 Docker 网络内，六类进程 + 两个持久卷：

```text
                          ┌─────────────── 对外唯一入口 ───────────────┐
   浏览器 / 内网用户  ───▶ │  caddy (前端静态 + /api 反向代理)  :80/:443  │
                          └───────────────┬───────────────────────────┘
                                          │ 同源转发 /api/* → api:8000
                     ┌────────────────────┼─────────────────────────────┐
   Docker 内网       │                    ▼                             │
   (match-ma-net)    │   api (uvicorn, 内网 8000, 无公网端口)            │
                     │   worker-llm      (--queue llm)                   │
                     │   worker-ocr      (--queue ocr)                   │
                     │   worker-research (--queue research, 可多副本)     │
                     │   migrate (一次性: alembic upgrade head, 跑完退出) │
                     │                    │                             │
                     │                    ▼                             │
                     │   db  postgres+pgvector:pg17  (内网 5432)         │
                     └────────────────────┬─────────────────────────────┘
                                          │
                    持久卷: pgdata (数据库)  ·  attachments (附件文件)
```

**队列 = 3 个 worker 就够**：代码里实际入队的 `queue_name` 只有 `llm` / `ocr` / `research` 三种（`embedding`、`rerank` 是节点类型/trace 类型，其作业默认落在 `llm` 队列，由 llm worker 消费）。这与 Railway 现在跑的 3 个 worker 完全一致。

**端口只暴露 Caddy 一个**：前端和 API 通过 Caddy 反代做成**同源**，这样前端 `VITE_API_BASE_URL` 用相对路径 `/api/v1` 即可，**彻底免掉 CORS 配置**，对外也只开 80/443 一个口，安全面最小。

## 3. 双轨并存的隔离设计（本案核心）

| 维度 | Railway（现状，不动） | 自建（新增） |
|---|---|---|
| 构建方式 | Nixpacks（`builder = "NIXPACKS"` 已在 railway.toml 锁定） | `deploy/` 下的 Dockerfile |
| 是否会误用对方配置 | 不会——builder 被显式锁死为 NIXPACKS，Railway 不会去 root 找 Dockerfile | 不会——compose 只读 `deploy/`，不读任何 `railway*.toml` |
| 进程启动 | `scripts/railway_start.py` 按服务名推断角色 | compose 里每个 service 写死显式命令 |
| 数据库迁移 | `preDeployCommand` 跑 `railway_predeploy.py` | 一次性 `migrate` 服务跑 `alembic upgrade head` |
| 健康检查 | Railway 面板配 `/api/v1/health` | compose `healthcheck` 打 `/api/v1/health` |
| 配置来源 | Railway 面板 Variables | `deploy/.env` 文件（不进 git） |
| 前端 API 地址 | 构建时烧 Railway 公网域名 | 构建时烧相对路径 `/api/v1` |

**新增文件全部落在 `deploy/`**，Railway 端零感知；同时 root 的 `railway.toml` 已把 builder 锁成 NIXPACKS，即便 `deploy/` 里有 Dockerfile 也不会被 Railway 误认。两条链路互不影响。

**必须向团队讲清楚的三个「不互通」**（这是运维认知风险，不是技术问题）：

1. **数据库各自独立**：Railway 一套库、自建一套库，业务数据**不自动同步**。哪套是「正式数据源」要先定死，避免两边各改各的。
2. **模型 API key 各自录入**：全新空库意味着自建这套要在「AI 设置」页重新填模型密钥（或用环境变量注入）。
3. **Prompt 版本各自独立**：两套都从 baseline 种子的 prompt 版本起步，之后各自在设置页维护，互不影响。

## 4. 要新增的文件清单（只增不改）

全部位于 `deploy/`（除 `.dockerignore` 和 `.gitignore` 追加项在根目录）。下面给**职责 + 关键决策**，完整内容在实施阶段落地。

### 4.1 `.dockerignore`（根目录）
排除 `node_modules/`、`frontend/dist/`、`.git/`、`__pycache__/`、`.venv/`、`storage/`、各种缓存，避免把巨大无关文件塞进构建上下文（构建上下文 = 仓库根，Dockerfile 需要 COPY `backend/`、`alembic/`、`database/`、`pyproject.toml`）。

### 4.2 `deploy/Dockerfile.backend`
后端镜像（API 和 3 个 worker **共用同一个镜像**，只是启动命令不同）。分层思路：

```dockerfile
# 参考实现（实施阶段落地）
FROM python:3.12-slim
WORKDIR /app
# psycopg[binary]/cryptography/pillow 均有 manylinux wheel，slim 无需编译工具链
COPY pyproject.toml ./
COPY backend/ ./backend/
COPY alembic/ ./alembic/
COPY alembic.ini ./
COPY database/ ./database/
COPY scripts/ ./scripts/
RUN pip install --no-cache-dir .
# 附件本地卷挂载点
RUN mkdir -p /app/storage/attachments
EXPOSE 8000
# 默认起 API；worker 在 compose 里覆盖 command
CMD ["uvicorn", "backend.app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

要点：
- Python 3.12（`requires-python >=3.11`，容器里不用本机的 3.14）。
- 只 `pip install .`，依赖来自 `pyproject.toml`，无需额外 requirements 文件。
- `alembic/` + `database/migrations/001_baseline.sql` 必须进镜像，否则迁移跑不了。

### 4.3 `deploy/Dockerfile.frontend`
前端多阶段构建：node 阶段 `npm ci && npm run build`（`VITE_API_BASE_URL` 作为 **build ARG** 注入），产物 `dist/` 交给 caddy 阶段托管。

```dockerfile
# 参考实现
FROM node:20-slim AS build
WORKDIR /app/frontend
ARG VITE_API_BASE_URL=/api/v1          # ← 关键：相对路径，同源免 CORS
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

FROM caddy:2-alpine
COPY deploy/Caddyfile /etc/caddy/Caddyfile
COPY --from=build /app/frontend/dist /srv/dist
```

要点：`VITE_API_BASE_URL` 是**构建时**烧进 JS 的，改地址必须重新 build 前端镜像。

### 4.4 `deploy/Caddyfile`
在现有 `frontend/Caddyfile`（纯静态托管）基础上**加一条反代规则**，把 `/api/*` 转给后端，实现同源：

```caddyfile
# 参考实现
:80 {
  encode gzip
  handle /api/* {
    reverse_proxy api:8000
  }
  handle {
    root * /srv/dist
    try_files {path} /index.html
    file_server
  }
}
```

> 若绑内网域名并要 HTTPS，把 `:80` 换成域名、Caddy 自动签证书（内网不可达 Let's Encrypt 时用 `tls internal` 自签）。

### 4.5 `deploy/docker-compose.yml`
编排六个服务。服务清单与关键配置：

| service | 镜像/构建 | command | 依赖 | 端口/卷 |
|---|---|---|---|---|
| `db` | `pgvector/pgvector:pg17` | 默认 | — | 卷 `pgdata:/var/lib/postgresql/data` |
| `migrate` | build backend | `alembic upgrade head` | `db`(healthy) | 跑完即退 |
| `api` | build backend | `uvicorn ... :8000` | `migrate`(completed) | 卷 `attachments` |
| `worker-llm` | build backend | `python -m backend.app.worker --queue llm --sleep 2` | `migrate`(completed) | 卷 `attachments` |
| `worker-ocr` | build backend | `... --queue ocr --sleep 2` | `migrate`(completed) | 卷 `attachments` |
| `worker-research` | build backend | `... --queue research --sleep 5 --stale-after 1800` | `migrate`(completed) | 卷 `attachments`；可 `deploy.replicas` 扩副本 |
| `caddy`(前端) | build frontend | 默认 | `api` | `80:80`（唯一对外） |

关键决策：
- **一次性 `migrate` 服务**独占迁移，`api` 和 worker 都 `depends_on: migrate: condition: service_completed_successfully`，避免多容器并发跑迁移打架。
- `db` 配 `healthcheck: pg_isready`，`migrate` 等它 healthy 再跑。
- **附件本地卷 `attachments` 必须同时挂到 api 和所有 worker**（worker 也要读写附件文件），否则 OCR/解析读不到文件。
- 所有服务从 `deploy/.env` 读环境变量（`env_file`）。

### 4.6 `deploy/.env.example`
自建环境变量模板（真实 `.env` 不进 git，见 4.8）。完整变量见第 5 节。

### 4.7 `deploy/README.md`
操作手册：一键起停命令、密钥生成、冒烟验证、更新流程、备份恢复。内容见第 9 节。

### 4.8 根目录 `.gitignore` 追加一行
```
deploy/.env
```
防止把含密钥的真实 env 提交上去。

## 5. 环境变量矩阵（落地最关键的部分）

| 变量 | 作用 | 自建生产取值 | 备注 |
|---|---|---|---|
| `APP_ENV` | 环境标识 | `production` | 会触发 `auth_strict_effective` → 缺鉴权密钥直接拒绝启动 |
| `DEBUG` | 调试开关 | `false` | 生产关掉 |
| `DATABASE_URL` | 数据库连接 | `postgresql+psycopg://match_ma:<pwd>@db:5432/match_ma` | compose 内 host 是服务名 `db`；`postgresql://` 会被自动转 `postgresql+psycopg://` |
| `AUTH_ENABLED` | 是否鉴权 | `true` | 内部正式环境必须开，否则任何请求都以 admin 身份跑 |
| `ADMIN_USERNAME` | 管理员账号 | 自定义 | — |
| `ADMIN_PASSWORD` | 管理员密码 | **强随机** | 默认值 `match-ma-admin` 会被安全检查拦截 |
| `ADMIN_TOKEN` | 脚本用的静态 token | **强随机** | 不设则由账号密码派生，可预测 |
| `AUTH_JWT_SECRET` | 登录 JWT 签名密钥 | **强随机长串** | 不设则由 admin token 派生 |
| `MODEL_SECRET_ENCRYPTION_KEY` | 加密数据库里的模型 key | **Fernet key** | ⚠️ **API 和所有 worker 必须完全一致**；全新库可新生成一把 |
| `CORS_ORIGINS` | 允许的前端源 | `*` 或留空 | 反代做成同源后基本用不到；如需跨域再收窄 |
| `ATTACHMENT_STORAGE_BACKEND` | 附件后端 | `local` | 自建用本地卷 |
| `ATTACHMENT_STORAGE_DIR` | 附件目录 | `/app/storage/attachments` | 对应 compose 卷挂载点 |
| `OCR_PROVIDER` | OCR 提供方 | `doc2x` 或 `skeleton` | 不用 OCR 就 `skeleton`（占位，不真跑） |
| `DOC2X_API_KEY` | Doc2x 密钥 | 用 OCR 时填 | `v2.doc2x.noedgeai.com`，国内可达 |
| `POSTGRES_USER/PASSWORD/DB` | 初始化 db 容器 | 与 DATABASE_URL 对齐 | 只给 `db` 服务用 |

**密钥生成命令**（放进 README）：

```bash
# Fernet 加密密钥（MODEL_SECRET_ENCRYPTION_KEY）
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
# 通用强随机串（ADMIN_TOKEN / AUTH_JWT_SECRET / ADMIN_PASSWORD）
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

> 关于 `MODEL_SECRET_ENCRYPTION_KEY`：本次全新空库，**新生成一把即可**，与 Railway 无关。只有将来想把 Railway 数据整库迁过来时，才必须复用 Railway 那把同一个 key，否则解不出已加密的模型密钥——这条现在只需知晓，不影响本次实施。

## 6. 数据库与迁移

- **镜像**：`pgvector/pgvector:pg17`。普通 `postgres` 镜像**不行**——`001_baseline.sql` 里 `create extension vector` / `vector(1024)` 列 + ivfflat 索引 + `pg_trgm` 都依赖 pgvector 镜像自带的扩展。
- **建库**：`migrate` 一次性服务跑 `alembic upgrade head`，Alembic 经 `backend/app/migration_sql.py` 的自制 splitter 应用 baseline（建表 + 种子：行业/交易路径/风险字典/区域别名/prompt 版本 + 默认 team/workspace/admin）。
- **健康与种子验证**：
  ```text
  GET /api/v1/health          → {"status":"ok"}
  GET /api/v1/health/db       → {"status":"ok","database":"reachable"}
  GET /api/v1/meta/seed-status → 确认默认 team/workspace/admin + 各字典已写入
  ```
- **`/health` 的 commit hash**：自建环境没有 `RAILWAY_GIT_COMMIT_SHA`，该字段会为空——不影响功能，若想显示版本可在构建时注入一个自定义变量（可选，非必须）。
- **备份**：`docker exec db pg_dump -U match_ma match_ma > backup.sql` 定时跑；卷 `pgdata` 一并纳入宿主机备份。

## 7. 前端构建与访问

- `VITE_API_BASE_URL` 在**前端镜像构建时**注入，本案用相对路径 `/api/v1`。
- 配合 Caddy 把 `/api/*` 反代到 `api:8000`，前端与 API **同源** → 免 CORS、对外单端口。
- 改 API 地址（如将来拆分独立域名）= 重新 build 前端镜像并传入新的 `VITE_API_BASE_URL`。

## 8. 鉴权与安全（内部正式环境必须收紧）

- `APP_ENV=production` 会让 `auth_strict_effective` 为真：**缺任一鉴权密钥直接拒绝启动**（`backend/app/main.py: enforce_startup_auth_security`）。这是保护而非障碍——把该报的错在启动时报出来。
- 因此上线前**必须**备齐：`AUTH_ENABLED=true`、强随机 `ADMIN_PASSWORD`、`ADMIN_TOKEN`、`AUTH_JWT_SECRET`、`MODEL_SECRET_ENCRYPTION_KEY`。
- `deploy/.env` 权限设 `600`，且已在 `.gitignore` 排除，**绝不进仓库**。
- 对外只开 Caddy 的 80/443；db、api、worker 全在 Docker 内网，不暴露端口。

## 9. 实施步骤（分阶段）

### Phase 0 · 准备
1. 生成全部密钥（第 5 节命令），填入 `deploy/.env`。
2. 本地/服务器装 Docker + Docker Compose v2。

### Phase 1 · 本地 Docker 验证（先在开发机跑通）
```bash
cd deploy
docker compose build
docker compose up -d
docker compose logs -f migrate   # 确认迁移成功退出
```
冒烟清单：
- [ ] `curl localhost/api/v1/health` = ok
- [ ] `curl localhost/api/v1/health/db` = reachable
- [ ] `curl localhost/api/v1/meta/seed-status` 种子齐全
- [ ] 浏览器打开 `localhost` 前端能加载、能登录
- [ ] 「AI 设置」录入模型 key，跑一次买家/标的解析（验证 llm worker + 加密 key）
- [ ] 上传一个附件（验证本地卷 + ocr worker）
- [ ] 发起一次推荐（验证 research worker + rerank）

### Phase 2 · 阿里云 ECS 平移
1. **ECS 规格**：建议 **4 核 8G 起**（research 长任务 + LLM 调用吃内存；worker 多进程）。系统盘 + 一块数据盘放卷。
2. **安全组**：只放行 80/443（和你管理用的 22）。db 端口**绝不对公网开**。
3. 装 Docker，`git clone` 仓库（或 CI 推镜像到阿里云 ACR 再拉），把 `deploy/.env` 传上去（scp，权限 600）。
4. `docker compose build && docker compose up -d`——与本地**完全相同的命令**。
5. **域名/TLS**：绑内网域名走 Caddy 自动 TLS；纯内网 IP 访问可先 HTTP。公网绑域名需 ICP 备案，纯内部访问可规避。
6. **镜像加速**：配置 docker 国内镜像源，或基础镜像走阿里云 ACR，避免拉 `python`/`node`/`pgvector` 超时。
7. **外网出口**：确认 ECS 能访问所用 LLM 厂商 API。若用海外厂商，考虑走代理或改用国内可直连的厂商；Doc2x 国内直连无碍。

### Phase 3 · 运维
- **更新**：`git pull && docker compose build && docker compose up -d`（`migrate` 会自动跑新迁移）。
- **日志**：`docker compose logs -f <service>`。
- **备份**：`pg_dump` 定时任务 + 卷快照。
- **扩容 research**：`docker compose up -d --scale worker-research=N`（stale 窗口 1800s 已够多副本互不判死）。

## 10. 阿里云特有注意点（汇总）

| 事项 | 处理 |
|---|---|
| pgvector 是否支持 | 自建容器 `pgvector/pgvector:pg17`，**不依赖阿里云 RDS 的扩展支持**，省心 |
| 镜像拉取慢 | 配 docker 国内镜像加速 / 基础镜像推到阿里云 ACR |
| LLM 厂商可达性 | 海外厂商需代理或换国内厂商；Doc2x 直连 OK |
| 域名备案 | 纯内网/IP 访问免备案；公网绑域名需备案 |
| 数据盘 | 卷 `pgdata`/`attachments` 落在独立数据盘，便于快照与扩容 |

## 11. 风险与回滚

| 风险 | 应对 |
|---|---|
| 两套库数据不同步被误当一套 | 文档明确「正式数据源」是哪套；本次自建=全新，不与 Railway 混用 |
| `MODEL_SECRET_ENCRYPTION_KEY` API/worker 不一致 | 所有服务共用 `deploy/.env` 同一变量，天然一致 |
| 迁移失败卡启动 | 查 `migrate` 容器日志；baseline splitter 相关回归由 `tests/test_migration_sql.py` 兜底 |
| 附件卷没挂到 worker | compose 中 api + 全部 worker 都挂 `attachments` 卷（清单已标注） |
| 生产误用默认密码 | `APP_ENV=production` 严格模式启动即拦截，逼出配置 |
| 回滚 | `docker compose down`（保留卷）即停服；镜像可按 git tag 重建旧版本 |
