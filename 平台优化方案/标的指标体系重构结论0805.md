## 一、三句话结论

> 2026-08-05 二轮修订：补充输入「买家真实需求问卷（上市 / 非上市各 11 项）」后，用它对全部结论做了回归校验，见 **§11**。三条结论被推翻：交易方式从否决改为采纳（§5.3 / §11.4）、预算配对从接线改为判死（§6.4 / §11.5）、毛利率从加列改为降级（§4.4 / §11.6）。下面的三句话已是修订后的版本。

1. **底稿的 77 项清单有 9 项与代码不符** —— 注册地/总部/地区粒度/地区原文/行业原文/推荐状态这 9 列已被迁移 `002` 和 `006` 删除。底稿列出的问题里有一条（P2 行业原文仍在）在标的侧已经不存在，剩在买家侧。勘误见 §2。

2. **拿真实问卷回归校验后，本轮要动的是 3 个维度，不是底稿提的 7 个新增。** 问卷 11 项里 6 项已成对进 SQL、2 项语义配对成立，要动的只有：
   - 🔴 **重大风险**（涉诉/冻结/执行/违规违法）—— 双侧新增闭集枚举。**本轮最高价值项，底稿完全没提到**；现在两侧都是自由文本，打分器只产生一句「需人工核对」，不改分、不筛选。
   - 🔴 **交易方式（多选）** —— 标的侧新增闭集枚举，买家侧 `transaction_types_json` 从自由标签改闭集。
   - ⚠️ **可接受溢价范围** —— 纯接线：`max_premium_rate` 与 `premium_rate` 两侧列都现成，打分器**一行没读**。

   另加 3 个列：`listing_exchange`、`main_products_text`、`stock_code`。底稿提的产业链方向、上市日期、毛利率列 **否决或降级**（§5.2 / §5.4 / §11.6）。

3. **比缺字段更严重的是三类存量错误**，底稿一条都没列到，而问卷 11 项里有 **3 项**直接落在上面：
   - **静默失效**：`max_premium_rate`（问卷第 3 项）、`transaction_types_json`（第 7 项）、`min_gross_margin`、`budget_min/max_yuan`、`earnout_requirement` —— 买家填得进、界面显示着、打分器根本不读。这比「缺失时当未知放行」糟得多，后者至少是已知的宽松，前者是用户以为设了条件而实际没设。
   - **枚举取值定义错误**：`earnout_requirement` 用 `required/preferred/not_required` 描述对赌 —— `required` 到底是「要求有对赌」还是「必须没有对赌」？这个字段无论怎么接线都是错的，必须先换枚举。
   - **伪枚举与零写入列**：`operation_stability_status`（取值无客观判据）、`gap_summary`（6 处读、0 处写）、`is_for_sale`（与 `lifecycle_status` 同一件事）。

## 三、归类判据（本轮定下来，后面每提一个候选指标都过这三问）

底稿给了三类，但漏了第四类，导致「指标必须成对」这条约束在清单上看起来处处违反 —— 实际是分类问题，不是缺口。

```
Q1  能不能给出一个数（金额 / 比率 / 倍数 / 日期）？
     是 → 【定量】进 SQL，gte / lte
     否 ↓
Q2  买家提这个要求时，能不能用同一个闭集把话说完？
     能 → 【可枚举定性】进 SQL，eq / in。枚举必须封闭穷尽，两侧共用同一张 code 表
     否 ↓
Q3  买家会不会提这个要求？
     会 → 【不可枚举定性】不进 SQL，进画像正文交给 LLM
     不会 → 【非指标】展示 / 核验 / 系统字段。不进指标体系，不占 screening 位，不需要对手方
```

三条配套规则：

- **Q2 的判据是「买家能不能用同一个闭集说话」，不是「我们能不能列举」。** 产业优势当然可以硬分成 8 类，它不可枚举的原因是买家侧的表达没有闭集 —— 一旦标的侧封闭而买家侧开放，解析环节就被逼着在 8 个都不合适时乱选一个。这个判据可测：**写不出买家侧的对手方枚举，就说明它不是可枚举指标。**
- **「必须成对」只约束筛选指标（Q1、Q2）。** Q3 的配对是**语义配对**（画像正文 ↔ 深评），Q4 无需配对。注册表现在只能表达 SQL 配对（`target_column` + `operator`），于是语义配对的字段一律看起来像缺口 —— 建议给 `Indicator` 加 `pairing: "sql" | "semantic" | "none"`，见 §8.1。
- **缺失时的默认策略已经存在，不必逐项发明。** `_score_target_against_intent` 是乐观三态：标的侧未知 → **按满分计**（recall 优先），同时记进 `unknown_dimensions`，候选状态降为 `possible`，排序落在信息完整的候选之后。**没有任何指标会因为缺失而被筛掉。** 下表只标注偏离这条默认的例外。

| `other_overseas` | 其他境外交易所 | overseas |
| `unknown` | 未知 | unknown |

穷尽性靠两个 `other_*` 兜底 —— 没有它们，解析遇到区域股权市场或伦交所时只能乱选一个，这正是底稿开场白警告的失败模式。

**买家对手方**：新增 `acceptable_listing_exchanges_json`（多值，`in`，`default_effect="required"`）。它**取代**现有的 `listing_board_requirement_summary`（自由文本，只能进深评）—— 该字段迁移后判死。买家侧 `listing_market_region` 保留作粗粒度表达；两者同时有值时**细的赢**（exchange 生效，region 忽略），不做交集，避免「港交所 ∩ 境内」这种空集。

**缺失怎么办**：
- `listed_status = 'unlisted'` → exchange 恒为 NULL，**该维度整个不参与打分**。冲突由 `listed_status` 维度承担；在 exchange 维度再判一次等于同一件事扣两次分。
- `listed_status = 'listed'` 但 exchange 未知 → 走乐观三态 unknown。

### 5.2 产业链方向 —— 否决

「上游 / 中游 / 下游 / 平台服务」看起来是闭集，实际不是：**离开「哪条链」的定义，上下游没有真值**。同一家做正极材料的公司，在锂电池链里是上游，在矿业链里是下游。

更关键的是买家侧：买家说的是「我做电池 PACK，想收上游材料」—— 这是**相对买家自己**的位置，是一个**关系**，不是标的的属性。把关系存成标的的列，等于把二元关系的一元投影当成事实，标注者（LLM）每换一个行业就要重新理解一次链条，一致性无法保证。过 §3 的 Q2：买家侧写不出对应的闭集枚举 → 不是可枚举指标。

**替代方案**：标的侧把「主要产品 + 在哪条链上做什么」写进 `business_product` 画像栏正文（§5.7 的 `main_products_text` 承接产品，画像栏承接链条位置）；买家侧已有 `buyer_industry_advantage_summary`；协同性判断交给深评，`buyer_party_fact_block` 已经在给深评喂买家自身业务了（`profile_sections.py:262`）。

### 5.3 投资并购形式 —— 否决**该表述**，但「交易方式」是真缺口（二轮修订）

> **修订说明**：本节否决的是底稿的**具体表述**「接受股权投资 / 接受并购 / 两者皆可」—— 那是**控股维度**（谁拿控制权）的第二处记录，与布尔三件套重复，否决成立。
> 而问卷第 7 项的「交易方式（多选）」是**交易结构维度**（老股 / 新股 / 资产 / 合并），与控股维度**正交** —— 增资扩股可以控股也可以参股，股权转让同理。**那是真缺口，采纳**，见 §11.4。
> 两个维度都要留，且不能互相派生。上一轮把二者混为一谈，是因为底稿的三选一表述读起来就是控股维度。

「接受股权投资 / 接受并购 / 两者皆可」在现有模型里可以完全表达：

| 新提法 | 现有事实 |
|---|---|
| 接受并购 | `can_control = yes` |
| 接受股权投资 | `accepts_minority_investment = yes` |
| 两者皆可 | 两者都 `yes` |

**结论：不新增列。** 它是布尔三件套的一个视图，不是新事实。新增会造成同一件事两处记录、两处都可被独立写入（解析、调研、手动编辑三个来源）→ 必然打架，而且打架时没有仲裁规则。

需要这个说法出现在界面上时，做成**前端派生的展示标签**（由两个布尔算出），不落列、不进注册表。买家侧对手方已有：`requires_control` + `accepts_minority_investment`。

同一个病在两侧还各有一个镜像，一并处理：
- 标的侧 `transfer_flexibility_type`（7 值）—— 与三个布尔重叠，`screening=False`，打分链路无读者。**保留为解析原话留存，在注册表注释里写死「不参与打分」**，防止下一个人看到 7 个漂亮的枚举值就去接线。
- 买家侧 `equity_requirement_type`（7 值）—— 同样处理。

### 5.4 上市日期 —— 否决

买家不会提「2020 年后上市的」。过 §3 的 Q3：**买家不会提这个要求 → 它不是指标**。只在标的一侧加列，等于底稿开场白说的「只在一侧加等于没加」。

需要这个信息时它属于画像正文（`identity` 或 `deal_terms` 栏），由解析/调研写进去，深评能读到。

### 5.5 技术资质 / 知识产权 —— 否决新增独立指标

「专精特新」「高新技术企业」这类**资质认定**确实是闭集（国家目录），看起来符合 Q2。但：

- 买家侧的真实说法是「最好有专精特新」「要能承接科技补贴的」—— 这是**优先项而非门槛**，且列表开放（专精特新/小巨人/单项冠军/高新/瞪羚/独角兽/各省市自己的名号…），穷尽不了；
- 「专利数 ≥ N」是定量，但买家极少这样提，提了也主要用于估值判断而非准入。

**结论**：不设独立枚举，写进 `tech_team` 画像栏正文，深评判断。若一年后发现「只看专精特新」成了高频硬门槛，**再单独加一个布尔 `is_specialized_new`（是/否/未知）** —— 单值布尔不会有「8 个都不合适」的问题，届时重开成本很低。这条留在 §9 的重开条件里。

### 5.6 官网链接 —— 否决新增列

核验展示用，不作筛选。但它不需要一个宽表列：调研 agent 产出的 `sources` 已经带 URL，画像栏 `identity` 也能装。加一个只读只写不参与任何匹配的列，是往宽表里加噪声。

**结论**：写进 `identity` 画像栏。若顾问强烈要求信息页顶部有一个可点的官网链接，那是**信息页的展示需求**，走 `metadata_json` 或画像栏，不占指标位。

### 5.7 主要产品 —— 采纳为不可枚举定性（P0）

真缺口。行业只到 L2，「做锂电池正极材料的」和「做锂电池 PACK 的」都归在同一个 L2 下。

**两条路的取舍**：受控标签字典能进 SQL，但产品词是长尾（正极材料/隔膜/电解液/PACK/BMS…），字典要覆盖全行业、维护成本无上限，且字典外的词会被丢弃 —— 这是「逼着解析乱选」的另一面（不是选错，是丢掉）。

**结论：新增 `main_products_text`（文本，不可枚举定性，`screening=False`，`deep_eval=True`，组 `business_product`）**，不建产品枚举字典。

**买家对手方**：`industry_focus_tags_json` **已经存在**（自由标签，字典外细分方向）。它不是缺口，它就是对手方 —— 只是配对通过**深评**而非 SQL。注册表现在表达不了这层关系，所以看起来像「买家能提、系统永远匹配不上」。修法是给注册表加语义配对的表达能力（§8.1），不是加一个产品枚举列。

**为什么不塞进 `business_summary`**：该字段有 300 字上限（`seller_target_parse.py:272`，防止模型回灌原文淹没列表页），主要产品塞进去会被截断。

**前置依赖**：L2 字典同义词去重（食品/食品制造/食品加工 三行并存，`数据看板拆除验收单0729.md` §1.3）。L2 本身不可靠时，产品层再加一层也救不回来。

## 六、修改项与底稿未列出的问题

### 6.1 估值时间 / 报价时间：text → date（P2，底稿已列）

注册表声明 `date`，DB 实为 `text`（`001_baseline.sql:828-829`）。后果是无法比较排序，回答不了「这个估值是不是半年内的」。

**结论：按 `financial_period_label` / `financial_period_end_date` 的现成模式改 —— 原文列 + 归一化 date 列并存**，不是简单改类型。理由：解析侧 `SELLER_TARGET_TEXT_LIMITS` 给了 80 字上限，说明模型现在会写「2024年上半年」这类无法映射到单一日期的表述，直接 `alter type` 会丢数据。

两阶段（总纲 §2.4 的先例，禁止合并成一次 preDeploy）：
- **阶段 A**：加 `valuation_as_of_date` / `asking_price_as_of_date`（`date`），回填可解析的（ISO / `YYYY-MM-DD` / `YYYY年MM月`→月末 / `YYYY年`→年末），解析不了的留 NULL；原 text 列改名语义为原文留存，双写。
- **阶段 B**：全部服务切读之后，删旧索引与兼容读路径。

**买家对手方：没有，也不该造。** 新鲜度不是买家的诉求字段（买家不会填「估值必须是半年内的」），它是**推荐链路的排序与展示信号** —— 「这个估值是 2019 年的」要出现在推荐理由里。这条正好界定了「必须成对」的边界：**成对只约束筛选指标**（§3）。

### 6.2 财务期间：只差一行（P2，底稿已列，但问题不是它说的那个）

底稿说「`financial_period_label` 是自由文本，无法判断同期可比」。实际 `financial_period_end_date` 已由迁移 `009` 落地，正是为此而生。

真问题是：**它的 `writable_by` 只有 `research`**（`indicators.py:124`）。走解析入口进来的标的，财务期间截止日永远为空 —— 而解析是标的的主要入口。于是「防止旧期覆盖新期」「同期冲突判定」这两个机制对解析写入的数据全部失效。

**结论**：`writable_by` 加 `parse`，并在解析 prompt 里要求同时给出 `financial_period_label`（展示原话）与 `financial_period_end_date`（ISO 日期）。改动一行 + 一次 prompt 版本发布。

### 6.3 买家侧行业原文：判死 `industry_primary` / `industry_secondary`（P2）

标的侧已随 `002` 删除，剩买家侧两列，且仍在注册表里（`writable_by=parse`）。

它们有一个真实读者：`_score_target_against_intent:2696` 拿 `industry_secondary` 做 **+4 加分**。这个加分与 `industry_l2_json` 的 15 分维度**重复计分**，且总纲 §3.3 已记录「`industry_secondary` 常常在一列里塞多个用『、』连起来的行业，按数组去重去不掉」。

**结论：判死。** 顺序是——迁移把值按分隔符拆分、过字典后并进 `industries_json` / `industry_l2_json`（`buyer_intent_industry.py` 已有现成的归一化政策，直接复用）→ 删打分器里的 +4 分支 → 删列。排在 P2，但必须记进图纸未决问题，否则它会一直以「兼容字段」的名义活着。

### 6.4 报价没有买家对手方，而买家有两个死列（新发现）—— **二轮撤回，改判死，见 §11.5**

> **本节结论已被问卷推翻。** 正式问卷里买家的价值诉求只有一条轴（上市问市值范围、非上市问估值），**没有独立的「预算」问项**。一个没有采集入口的字段，接了线也永远为空。
> 改判：`budget_min/max_yuan` **判死**（§7 已补入）；`asking_price_yuan` 明确为**单侧展示 / 排序字段**，不设买家对手方。
> 下面的分析保留作为判断依据的记录 —— 「报价与估值不可混轴」这条仍然成立，只是结论从「接线」变成了「两侧都不接」。

`asking_price_yuan`（报价，交易对价轴 C-b）在买家侧无对手方。而 `buyer_intent` 有 `budget_min_yuan` / `budget_max_yuan` 两列：API 收、API 发、**注册表不认、打分器不读**。

打分器的注释写得很清楚（`recommendation_flow.py:2466`）：报价与估值口径不同，绝不能混比，否则「预算 10 亿买 25% 股权」的买家会与 40 亿估值的标的判成硬冲突。**买家预算恰恰是报价的同轴对手方** —— 现在这条轴两侧都有数据，中间没有连线。

**结论**：把 `budget_min_yuan` / `budget_max_yuan` 接进注册表，`target_column="asking_price_yuan"`，`operator` 为 `gte`/`lte`，`default_effect="preferred"`。

**为什么是 preferred 不是 required**：报价常常是要价，谈判空间大，硬卡会误杀。

**缺失怎么办**：多数标的只有估值没有报价 → 走乐观三态 unknown。**不要用估值兜底报价**，这正是注释警告的混轴。

### 6.5 对赌的枚举取值本身是错的（新发现，优先级高于「补配对」）

买家 `earnout_requirement` 与标的 `earnout_dependency_status` 两侧都有列，但没有 `target_column`/`operator` —— 对赌这个维度完全不参与匹配。

补配对之前必须先修枚举：`earnout_requirement` 现在用 `_REQUIREMENT_STRENGTH`（`required` / `preferred` / `not_required` / `unknown`）。套在对赌上，**`required` 读作「要求有对赌」还是「必须没有对赌」？** 两种读法都说得通，而买家真实意思几乎总是后者。这个字段无论怎么接线都是错的。

**结论：换枚举**，改名 `earnout_tolerance`：

| code | 中文 | 对 `earnout_dependency_status` 的判定 |
|---|---|---|
| `reject` | 不接受对赌 | `none` → 匹配；`low` → 降分；`medium`/`high` → **硬冲突** |
| `low_only` | 可接受轻度对赌 | `none`/`low` → 匹配；`medium` → 降分；`high` → 降分 |
| `acceptable` | 可接受对赌 | 任何值 → 匹配 |
| `unknown` | 未提及 | 维度不参与 |

标的侧枚举不变（`none/low/medium/high/unknown`）。这条是**枚举取值定义错误**的样本 —— 比缺字段隐蔽得多，因为字段、界面、check 约束全都在，只有语义是坏的。审其余枚举时按同一把尺子过一遍。

### 6.6 标的类型无买家对手方（新发现）

`target_type`（公司/股权包/业务单元/资产包/项目/其他）是标的侧的可枚举指标，买家侧无字段。买家其实会提（「只看整体公司，不要资产包」）。

**结论：补买家侧 `acceptable_target_types_json`（多值，`in`，`default_effect="preferred"`）。** 优先级 P2 —— 它是真配对缺口但频次不高，可以和 §6.4/§6.5 一批做。若本轮不做，必须在注册表把 `target_type` 的 `screening` 标为 False 并注明「单侧、只进深评」，不能让它以「可枚举指标」的身份挂着却无人可比。

### 6.7 显式声明可接受的单侧字段（新发现）

以下字段**没有也不需要**买家对手方，本轮把这个判断写死，避免下一轮重新讨论：

| 字段 | 为什么单侧成立 |
|---|---|
| `current_assets_yuan` | 买家极少提总资产门槛；提了通常是在说规模，已由营收/市值承接 |
| `current_operating_cash_flow_yuan` | 买家的诉求已由 `acceptable_cash_flow_status_json`（枚举）承接，数值列是它的证据而非条件 |
| `valuation_date` / `asking_price_date` | 新鲜度是排序/展示信号，不是筛选条件（§6.1） |
| `pe_source_type` | 元数据，说明 PE 怎么来的，不是诉求 |
| `financial_period_label` / `financial_period_end_date` | 同期可比性是系统内部约束，不是买家条件 |
| `stock_code` / `target_name` / `target_subject_name` | 核验字段 |

### 6.8 静默失效清单（新发现，本轮必须清零）

买家填得进、界面显示着、打分器根本不读的字段。它们比「缺失时放行」危险 —— 用户以为设了条件，实际没设：

| 买家字段 | 现状 | 处理 |
|---|---|---|
| `max_premium_rate` | 无 `target_column`，标的侧 `premium_rate` 现成 | **P0（问卷第 3 项）**：补 `target_column="premium_rate"`, `lte`, preferred |
| `transaction_types_json` | 自由标签，无 `target_column`，标的侧无对手方 | **P0（问卷第 7 项）**：改闭集 + 标的侧新增枚举（§11.4） |
| `min_gross_margin` | `screening=False`，无 `target_column` | **降级为深评项**（二轮改判，§11.6）——不加标的侧列 |
| `budget_min/max_yuan` | 不在注册表 | **判死**（二轮改判，§11.5）——问卷无「预算」问项 |
| `earnout_requirement` | 无 `target_column`，且枚举语义是坏的 | 先换枚举再接线（§6.5） |
| `return_investment_multiple` | 无 `target_column`，标的侧无对手方 | **降级为深评项**，注册表注明；返投倍数是谈出来的，不是标的的既有属性 |
| `financing_stage_requirement_summary` | 自由文本，标的侧无对手方 | 保持深评项，明确不接线 |
| `listing_board_requirement_summary` | 自由文本 | 被 `acceptable_listing_exchanges_json` 取代后**判死**（§5.1） |

## 八、注册表本身要改的两处

### 8.1 加 `pairing` 字段，让语义配对可声明

现在 `Indicator` 只能表达 SQL 配对（`target_column` + `operator`）。后果是：所有靠深评完成的配对（`main_products_text` ↔ `industry_focus_tags_json`、`risk_summary` ↔ `major_risk_tolerance_summary`、各模块「其他」之间）在注册表上都长得像「只在一侧有字段」的缺口 —— 底稿把「主要产品」判成 P0 缺口正是这么来的。

```python
pairing: str = "none"   # "sql" | "semantic" | "none"
```

- `sql`：必须同时有 `target_column` + `operator`，两侧枚举必须同表
- `semantic`：声明对手方字段名但不进 SQL，供深评上下文组装与「成对性」审计使用
- `none`：非指标（展示/核验/系统），审计跳过

配套一个测试：**`pairing="sql"` 却缺 `target_column`，或 `screening=True` 却 `pairing="none"`，直接挂 CI**。§6.8 那张静默失效清单，本质上就是缺这个测试。

### 8.2 六处手写列投影是本轮的主要工作量，也该顺手收掉

注册表已经驱动了：前端信息页分组/中文名/枚举/编辑权限/「筛」角标（`/meta/indicators` + `infoGroups.ts`）、解析字段词汇表（`seller_target_context_columns()`）、解析/调研/手动三个写入白名单、调研映射的字段目录（含 `allowed_values`，`research_map.py:236`）、枚举校验。

**但 SELECT 投影仍有 6 处手写**，加一列要逐个改：

| 位置 | 用途 |
|---|---|
| `seller_targets.py:335` + 两个 Pydantic 模型 | 信息页读 + PATCH |
| `seller_target_parse.py:193` | 解析上下文 |
| `extracted_action_apply.py:614` | 采纳前读当前值 |
| `business_update_flow.py:1152` | 业务更新读当前值 |
| `recommendation_agent_tools.py:363` | Agent 取详情 |
| `recommendation_flow.py:1202` | 初筛候选行 |
| `update_logs.py:1126` | 回滚白名单 |

`common.py:664` 已经证明了正确做法（`", ".join(seller_target_context_columns())`，列名来自注册表不是外部输入，可安全拼接）。**建议本轮把这 7 处收敛到 1~2 个派生投影函数** —— 否则新增 4 个列要改 28 处，而且漏掉任何一处的表现都是「字段存进去了但某个页面/某个链路看不见」，最难查。

## 十一、按真实需求问卷回归校验（2026-08-05 二轮补充输入）

补充输入：顾问采集买家需求时实际使用的问卷，上市 / 非上市各 11 项。这是目前为止**最有价值的输入** —— 前面所有判断依据的是代码与底稿，这一份是买家真实说话的词汇表。指标体系的目的是精准找到符合买家需求的标的，那么**买家问卷里没有的问项，标的侧建了也没人填；买家问卷里有而标的侧接不住的，才是真缺口**。

### 11.1 问卷的结构本身就是一个结论

**两张表只差一个字段。** 第 2 项上市问「市值范围」、非上市问「估值」，**其余 9 项逐字相同**。

- 这说明买家需求**不是两套模型**，是一套 + 一个按上市状态切换的价值口径字段。
- 平台的 **C-a 整体价值轴已经正是这个设计**：`recommendation_flow.py:2471-2478` —— 上市看 `market_cap_yuan`、非上市看 `valuation_yuan`、两者同口径可互相兜底。问卷验证了它是对的，**不需要改**。
- 但买家注册表把 `min/max_market_cap_yuan` 与 `min/max_valuation_yuan` 暴露成**四个平行字段**，填表的人要自己判断填哪一对。建议录入界面与解析提示词按 `acceptable_listed_status_json` 决定呈现/追问哪一对；打分器不用动（它已经按**标的**的 `listed_status` 选列比对）。
- 反过来的教训：**不要因为问卷有两张表就去建两套需求模型或两条推荐流程**。已写进 §10 否决清单。

### 11.2 十一项逐条对照

| 问卷项 | 买家侧字段 | 标的侧对手方 | 现状 | 结论 |
|---|---|---|---|---|
| 1 所属行业 | `industries_json` / `industry_l2_json` / `excluded_industries_json` | `industry_pairs_json` | ✅ 成对进 SQL | 不动 |
| 2a 市值范围（上市） | `min/max_market_cap_yuan` | `market_cap_yuan` | ✅ | 不动，见 §11.1 |
| 2b 估值（非上市） | `min/max_valuation_yuan` | `valuation_yuan` | ✅ | 不动，见 §11.1 |
| 3 可接受溢价范围 | `max_premium_rate` | `premium_rate` | ⚠️ **两侧列都在，打分器零行读取** | **接线，升 P0** |
| 4 经营情况（净利润要求） | `min_net_profit_yuan` | `current_net_profit_yuan` | ✅ | 不动 |
| 5 可接受负债率范围 | `max_debt_ratio` | `current_debt_ratio` | ✅ | 不动（只需上限，没人要求下限） |
| 6 能否接受重大风险 | `major_risk_tolerance_summary`（自由文本） | `risk_summary`（自由文本） | 🔴 **只产生一句「需人工核对」，不改分、不筛选** | **双侧新增闭集，§11.3** |
| 7 交易方式（多选） | `transaction_types_json`（自由标签） | **无** | 🔴 静默失效 + 单侧 | **双侧建闭集，§11.4** |
| 8 收购方所在地区产业优势 | `buyer_industry_advantage_summary` | `business_summary` + `business_product` 画像栏 | ✅ 语义配对成立 | 标 `pairing="semantic"` |
| 9 地域区位 | `region_constraints_json` | `location_province/city/district` | ✅ | 不动 |
| 10 收购股权比例 | `desired_equity_ratio_min/max` | `transfer_ratio_max/min`（交叉配对） | ✅ | 不动 |
| 11 其他要求 | 三个模块「其他」 | 五个画像栏 | ✅ 语义配对成立 | 不动 |

**得分：6 项已成对进 SQL、2 项语义配对成立、3 项要动。**

三条附带发现：

- **第 3 项「溢价率」的口径在两张表里是两回事**：上市 = 相对二级市场价格的溢价，非上市 = 相对净资产或上一轮估值的溢价。标的侧 `premium_rate` 没有口径字段（不像 PE 有 `pe_source_type`）。**不新增口径枚举**（买家不会选口径，他们只说「溢价不超过 30%」）——口径由 `listed_status` 决定，写进 label 与解析提示词钉死即可。否则会得到又一个伪枚举。
- **第 8 项的主语是「收购方」，不是标的** —— 这是买家的自我描述，用于判断协同。它在注册表上看起来是孤儿（无 `target_column`），实际对手方就是标的的画像正文。`profile_sections.py:262` 的 `buyer_party_fact_block` 已经在给深评喂买家自身业务，正是为这个问题服务的。这是 §8.1 `pairing="semantic"` 最典型的用例。
- **第 10 项没有独立的「控股/并表要求」问项** —— 控股诉求是从股权比例推出来的。打分器现在的 `if requires_control/requires_consolidation ... elif desired_min_ratio ...` 结构（枚举优先、无枚举才看比例区间）与问卷结构一致，**不用改**。

### 11.3 新增：重大风险闭集（本轮最高价值项）

**问卷把它当准入问题问**（「能否接受」），系统现在只有两段自由文本，打分器唯一的处理是 `recommendation_flow.py:2708`：买家有风险容忍要求 **且** 标的有 `risk_summary` → 追加一句「需人工核对」的 gap，**不改分、不筛选、不出局**。等于买家答了「不接受涉诉」，系统照样把涉诉标的推给他。

而问卷已经把风险**枚举好了**：涉诉 / 冻结 / 执行 / 违规违法。过 §3 判据 Q2：标的侧可以列举，买家侧能用同一个闭集说话 → **可枚举定性**，教科书级的适配。

**标的侧** `major_risk_flags_json`（jsonb 数组 + check 约束元素取值，同 `industry_pairs_json` 的模式）：

| code | 中文 |
|---|---|
| `litigation` | 涉诉 |
| `equity_frozen` | 股权冻结 |
| `enforcement` | 被执行 |
| `violation` | 违规违法（行政处罚 / 立案） |
| `none` | 已核查，无重大风险 |

**空数组 = 未核查**，`["none"]` = 已核查无风险。**这两个状态必须分开** —— 一个字段三种状态表达完，不需要第二个字段。

**买家侧** `unacceptable_risk_flags_json`（多值，同一闭集去掉 `none`），`operator="not_overlap"`，`default_effect="required"`。

- 用「**不接受**哪些」而不是「能接受哪些」来提问，是为了复用现成的 `not_overlap` 算子（`excluded_industries_json` 已经是这条代码路径），也贴合问卷「能否接受」的问法：不接受就勾上。
- 空 = 未提及 → 该维度不参与。

**缺失怎么办（本文件唯一一处偏离乐观三态的建议）**：标的侧空数组（未核查）时，若按默认计满分放行，等于**把「没查过」当成「干净」**。这是唯一一个乐观放行会造成真实业务伤害的维度 —— 推荐一个股权已被冻结的标的，顾问是在客户面前丢人。

建议：**仍进候选**（否则存量数据全被筛掉），但强制记入 `unknown_dimensions`，并在候选摘要与推荐正文里**显式标注「风险未核查」**。不硬出局，但必须可见。

**配套三件事**：
- `writable_by` 要含 `research` —— 风险核查恰恰是调研 Agent 能自动做的（工商公开信息），这个字段给了它一个明确任务。调研链路的字段目录自动从注册表生成（`research_map.py:236`），**零改动**。
- `risk_summary` 保留为**明细载体**（哪个案子、金额多少、进展如何），枚举是它的可筛选投影 —— 与 `industry_pairs_json` / 画像栏的关系完全一致。
- 买家侧 `major_risk_tolerance_summary` 降级为「其他风险说明」，不再是唯一载体。

### 11.4 修正：交易方式是真缺口（推翻 §5.3 的否决范围）

上一轮把底稿的「投资并购形式」否决了，理由是它与 `can_control` / `accepts_minority_investment` 重复。**那个否决对底稿的表述仍然成立**，但问卷的「交易方式（多选）」是另一个东西：

| 维度 | 问的是 | 现有承载 |
|---|---|---|
| **控股维度** | 谁拿控制权 | `can_control` / `can_consolidate` / `accepts_minority_investment` ✅ |
| **交易结构维度** | 用什么形式成交 | **无** 🔴 |

两者**正交**：增资扩股可以控股也可以参股，股权转让同理。底稿的三选一表述读起来是控股维度，所以上一轮判它重复；问卷的多选是交易结构，是真缺口。

**标的侧新增** `acceptable_transaction_structures_json`（多值）：

| code | 中文 |
|---|---|
| `equity_transfer` | 股权转让（老股） |
| `capital_increase` | 增资扩股（新股） |
| `asset_purchase` | 资产收购 |
| `merger` | 吸收合并 |
| `other` | 其他 |

**买家侧** `transaction_types_json` 从自由标签**改为同一闭集**，`operator="overlap"`（两边有交集即可），`default_effect="preferred"`。

- 为什么 preferred 不是 required：交易结构通常可谈，硬卡会误杀。老股/新股之争多数时候是价格问题而不是可行性问题。
- 老列 `transaction_type`（单值 text）随之判死，值并进 json 列。

### 11.5 撤回：买家预算 ↔ 标的报价的配对（推翻 §6.4）

上一轮判断 `budget_min/max_yuan` 应接线到 `asking_price_yuan`。**问卷推翻了它**：买家的价值诉求只有一条轴（上市问市值范围、非上市问估值），**没有独立的「预算」问项**。

「报价与估值不可混轴」这条结论仍然成立，但结论从「接线到报价」变成了「**两侧都不接**」：`budget_min/max_yuan` 判死，`asking_price_yuan` 明确为单侧展示 / 排序字段。

这条同时给出了一个可复用的判据：**看到一个死列，先问问卷里有没有对应问项，再决定是接线还是判死。** 上一轮少问了这一句，就差点给一个永远填不上的字段接了线。

### 11.6 降级：毛利率不加列（推翻 §4.4）

问卷第 4 项「经营情况」的括号里只有净利润。毛利率不是标准问项 → 属长尾，走第 11 项「其他要求」。

改判：**不加 `current_gross_margin` 列**，把买家侧 `min_gross_margin` **降级为深评项**（保留字段，注册表注明不进 SQL，由深评读画像正文判断）。不对称一样解除，代价从「一次迁移 + 7 处投影 + 一版 prompt」降到**一行**。

重开条件：毛利率进入正式问卷。

### 11.7 「必须成对」其实有三条腿，第三条是问卷

底稿把成对约束定义为「标的侧 ↔ 买家侧」两条腿。本轮暴露出第三条：**买家侧的字段还必须有采集入口**。没有问项的字段永远为空，和没有这个字段是一回事 —— 只是更糟，因为它在界面上显示着，看起来像个能用的条件。

三种失配，本轮各有实例：

| 失配类型 | 实例 | 处理 |
|---|---|---|
| **有字段、无问项** | `min_gross_margin`、`budget_*`、`financing_stage_requirement_summary`、`return_investment_multiple` | 补问项，或判死 / 降级（本轮选了后者） |
| **有问项、无闭集** | 第 6 项重大风险、第 7 项交易方式 | 本轮补闭集 |
| **有需求、既无问项也无字段** | **上市交易所 / 板块** | ⚠️ 见下 |

**需要你确认的一件事**：底稿把「只看 A 股」「要港股壳」列为高频诉求并定为 P0，我据此把 `listing_exchange` 排进了施工计划（§5.1）。但**这一栏不在问卷上** —— 上市那张表问了市值范围，没问交易所。

两种可能：它一直是通过第 11 项「其他要求」进来的（那么建字段是对的，但**问卷要同步补第 12 栏**，否则字段建完仍然没人填）；或者它其实是低频的，底稿高估了。我按前者处理并把「问卷补栏」写进了施工步骤第 5 步 —— **如果实际是后者，`listing_exchange` 应该整条推迟，优先做第 4 步的两个闭集。**

**建议固化成规矩**：以后每次改指标体系，都同步过一遍需求问卷；问卷不改，买家侧的新字段就是死的。
