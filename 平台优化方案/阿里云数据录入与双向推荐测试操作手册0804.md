## 1. 目标与执行边界

本次操作用于验证阿里云完整版本的数据录入、标的调研、买家需求解析及双向推荐链路。除调研结果采纳与买家创建这一处明确的并行窗口外，阶段之间严格执行门禁；同一阶段内允许受控并发执行彼此独立的子任务。

1. 逐行创建或确认 144 个标的，并提交允许使用的原始材料；
2. 仅在 144 个标的均获得唯一平台 ID、相关解析任务全部成功后，批量发起标的调研；
3. 仅在全部调研任务结束且无任务失败后，同时启动两条分支：逐一采纳所有标的的待确认 AI 调研结果；创建 24 个差异化虚拟买家及买家需求；
4. 仅在“待确认项全部采纳”和“24 个买家需求创建、解析及检索文档构建完成”两条分支都通过门禁后，执行 5 次“买家找标的”和 5 次“标的找买家”；
5. 任一阶段发现阻断性异常，重试一次；仍失败则停止后续阶段并生成异常记录 Markdown。

### 1.1 阶段内受控并发

新建标的、标的调研、新建买家需求和推荐都按“单个对象/会话 = 一个独立子任务”执行。阶段门禁不变，但同一阶段内使用受控并发：

- 默认并发数为 3；连续 10 个子任务成功、队列无新增失败且外部模型无 429/5xx 后，可提高到 5；
- 每个子任务只操作一个唯一标的、一个唯一买家需求或一个唯一推荐会话；不得多个任务同时写同一实体；
- 每个子任务各自轮询、重试、写 manifest；所有子任务成功才算阶段通过；
- 任一子任务出现阻断异常时，停止提交新的子任务；已提交的子任务允许自然到达终态，但该阶段不能通过；
- 不以提高并发为由跳过幂等检查、回读校验、任务标记或异常记录。

本次明确不做以下操作：

- 不向 Railway 生产环境录入本批测试数据；
- 不修改服务器代码、环境变量、Prompt 或模型节点配置；
- 不在服务器上 commit 或 push；
- 调研未全部完成前不提前采纳提案；全部调研完成后，必须按本手册逐项采纳所有标的的待确认 AI 调研结果；
- 不根据“是否已交易”改变标的生命周期；本批标的一律按 `active` 创建；
- 不使用源表中的“标的编码”“标的介绍材料”“是否已交易”“负责人主属部门”“归属部门”“标的公司年度报告摘要附件”；
- 不把“推介情况”当作标的当前基本信息写入；
- 不打印、保存或写入日志任何密码、Token、模型 Key、搜索 Key、OCR Key。

## 2. 环境、访问与安全

### 2.1 固定环境

- SSH 别名：`match-ma-aliyun`
- 主机：`<ECS 公网 IP>`
- 部署目录：`/opt/match-ma`
- 外部 API：`http://<ECS 公网 IP>/api/v1`
- 服务器本机 API：`http://127.0.0.1/api/v1`

Windows OpenSSH 偶尔在命令成功后显示 `close - IO is still pending on closed socket`。只要远端命令退出码为 0 且业务输出完整，该提示不视为部署或 API 失败；判断标准必须是退出码和 API 响应。

### 2.2 推荐访问方式

自动化执行优先通过 SSH 隧道访问服务器本机 HTTP，避免管理员密码或 Token 经过公网明文 HTTP：

```powershell
ssh -o BatchMode=yes match-ma-aliyun "hostname; whoami"
ssh -N -L 18080:127.0.0.1:80 match-ma-aliyun
```

第二条命令保持一个 PowerShell 窗口占用；执行器使用：

```text
http://127.0.0.1:18080/api/v1
```

管理员账号来自服务器 `/opt/match-ma/deploy/.env`。执行器可通过 SSH 在内存中读取 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD`，随后调用 `/auth/login`；禁止把值回显到终端，禁止写入 `manifest.json`、日志或异常报告。Token 只保存在当前进程内存，进程结束即丢弃。

### 2.3 服务器规则

- 服务器只允许 `git pull` 和 Docker Compose 部署操作，不在服务器改文件；
- 本次数据录入不需要重新部署，执行前只记录当前 commit；
- 若后续开发自动化脚本，应先在本地仓库开发和测试，经用户明确授权后提交、推送，再由服务器拉取；
- 部署规则以 [deploy/README.md](../deploy/README.md) 和 [自建部署实施方案0729.md](自建部署实施方案0729.md) 为准。

## 3. 批次、运行目录与幂等恢复

### 3.1 批次号

每次执行生成唯一批次号：

```text
ALIYUN-SELLER-YYYYMMDD-HHMMSS
```

示例：`ALIYUN-SELLER-20260804-103000`。

买家主体名称、需求名称、原始需求文本及任务测试标签统一带前缀：

```text
[ALIYUN-TEST-<batch_id>]
```

### 3.2 运行文件

运行产物保存在仓库外，避免误提交：

```text
D:\Match-MA-runs\<batch_id>\
├── manifest.json
├── normalized-targets.json
├── buyer-scenarios.json
├── summary.json
├── errors.jsonl
└── 异常记录-<batch_id>.md
```

`manifest.json` 至少包含：

```json
{
  "batch_id": "ALIYUN-SELLER-YYYYMMDD-HHMMSS",
  "environment": "aliyun",
  "source_file": "清洗后卖家表0116.xlsx",
  "source_sheet": "标的库数据",
  "source_sha256": "<sha256>",
  "server_commit": "<git rev-parse HEAD>",
  "started_at": "<ISO-8601 CST>",
  "targets": [],
  "research": [],
  "buyers": [],
  "recommendation_sessions": []
}
```

每个标的记录 `source_row`、原始主体/项目名、规范化名称、数据指纹、`seller_target_id`、是否新建或复用、`business_update_id`、解析/调研任务 ID、状态、轮询时间、重试次数。所有 API 成功响应必须先原子写入 manifest，再处理下一行。

### 3.3 幂等规则

执行器必须支持从 manifest 续跑，不能因中断重复创建：

1. manifest 已有实体 ID 时，先 GET 核验实体仍存在；存在则跳过创建并继续未完成步骤；
2. manifest 无 ID 时，调用 `GET /seller-targets/dedup-check?q=<target_name>`；
3. 没有精确同名项才允许 `POST /seller-targets`；
4. 有精确同名项时，只有在主体名、项目名及已有业务更新中的 `source_file/source_row` 能确认是本源表同一行时才复用；
5. 无法证明同一实体时，记录 `DEDUP_AMBIGUOUS` 并停止 Phase 1，禁止静默复用或创建“名称(2)”；
6. 业务更新的 `metadata_json` 写入 `test_batch`、`source_file`、`source_sheet`、`source_row`、`source_sha256`，作为恢复依据；
7. 重试创建前必须重新查 manifest 和服务器，不能盲目重发 POST。

曾经手工创建的源表标的若核验为同一实体，应记为 `reused_existing`，不制造重复数据。Phase 1 的验收口径为“144 行均对应一个唯一有效标的 ID”，并分别统计 `created_count` 和 `reused_count`。

## 4. 源表读取与清洗规则

### 4.1 数据范围

- 工作表：`标的库数据`
- 有效范围：`A1:Z145`
- 表头：第 1 行
- 数据：第 2—145 行，共 144 条
- 144 条均有“标的主体”和“标的项目”；源表内不存在重复的“主体 + 项目”组合
- 126 条主体与项目同名，18 条不同名

### 4.2 缺失占位值

以下值视为缺失，不写入结构化字段，也不拼入原始材料：

- 空单元格或只含空白；
- 单元格类型为数值且值精确等于 `28`；
- 去除首尾空白后的字符串精确等于 `28`；
- 去除首尾空白后的独立值：`-`、`--`、`无`、`无官网`、`暂无`、`不详`、`未知`。

必须做“精确值”判断，不能做包含判断。例如 `28万元`、`2028年`、股票代码或正文中包含 `28` 均不能自动删除。数值 `28` 在本源表中是缺失占位符，不解释为 28 元、28 万元或真实经营数据。

### 4.3 字段取用与映射

| 源字段 | 平台字段/用途 | 规则 |
| --- | --- | --- |
| 标的项目（C） | `target_name` | 主名称；为空才回退到标的主体 |
| 标的主体（B） | `target_subject_name` | 必填来源；保留原文 |
| 标的主体 + 标的项目 | `target_type` | 同名通常为 `company`；不同名时结合描述判断 `project`、`business_unit`、`asset_package`、`equity_package` 或 `other` |
| 营业收入（元）（D） | `current_revenue_yuan` | 仅录入可解析且不等于 28 的数值；D 为权威值 |
| 估值（元）（E） | `valuation_yuan` | 仅录入可解析且不等于 28 的数值 |
| 净利润（元）（G） | `current_net_profit_yuan` | 允许负数；仅排除精确值 28；G 为权威值 |
| 行业（H） | `industry_l1/l2`、`industry_pairs_json` | 必须经平台行业字典归一；不能映射时结构化行业留空，原文进入材料并记异常，不阻断身份创建 |
| 股票代码（I） | 原始材料 | 平台无独立股票代码创建字段，不强塞其他字段 |
| 估值日期（J） | `valuation_date` | 只有 E 存在有效估值时才写入 |
| 官网等来源信息（K） | 原始材料 | 排除占位值后保留，供解析和调研核验 |
| 上市情况（L） | `listed_status` | `未上市` → `unlisted`；主板/创业板/新三板/中小板 → `listed`；其他无法识别值 → `unknown` 并记异常 |
| 标的描述（M） | `business_summary` 或原始材料 | 有实质内容时保留；可先写简要结构化摘要，同时完整原文进入材料 |
| 公司简介（N） | `business_summary` 或原始材料 | 与 M 合并时标明来源标签，不覆盖更具体内容 |
| 省/市/区 | `location_province/city/district` | 经平台地区字典规范化；区值为 28 或无效时留空，不影响省市 |
| 营业收入中文展示列（R） | 仅交叉核验 | 不作为写入源；与 D 冲突时写 D 并记异常 |
| 净利润中文展示列（S） | 仅交叉核验 | 不作为写入源；与 G 冲突时写 G 并记异常 |
| 行业标签（T） | 原始材料 | 保留为补充标签；不得绕过行业字典直接写结构化 L1/L2 |
| 推介情况（U） | 不用于本阶段 | 属于关系/推进历史，不注入标的基本信息解析 |
| 备注（Z） | 仅供核验的补充材料 | 明确加“源表备注，仅供核验”，不得直接覆盖当前结构化事实 |

以下六个用户指定字段无条件排除，即使单元格有值也不发送到 API：

1. 标的编码；
2. 标的介绍材料；
3. 是否已交易；
4. 负责人主属部门；
5. 归属部门；
6. 标的公司年度报告摘要附件。

`lifecycle_status` 统一为 `active`，`information_status` 初始为 `insufficient`。不得由已排除的“是否已交易”推断 `sold` 或 `off_market`。

## 6. Phase 1：创建 144 个标的并解析原始材料

### 6.1 预处理

一次性读取工作簿，生成 `normalized-targets.json`。每行必须保留：

- `source_row`；
- 未修改的允许字段快照（六个排除字段不进入运行产物，也不发送到 API）；
- 清洗后的 API payload；
- 原始材料文本；
- 数据指纹；
- 清洗警告和财务交叉核验结果。

先对 144 行做离线校验：名称非空、数值可解析、没有 `NaN/Infinity`、估值日期不脱离估值单独出现、结构化行业在字典中、上市状态枚举合法。离线校验失败时不调用任何创建接口。

### 6.2 逐行创建

每行严格执行：

1. 根据 manifest 和 `GET /seller-targets/dedup-check?q=...` 做幂等检查；
2. 创建时调用 `POST /seller-targets`；
3. 立即保存 `seller_target_id` 和完整响应摘要；
4. 调用 GET 回读，核对名称、主体、地区、上市状态及非空财务字段；
5. 调用 `POST /business-updates` 提交允许使用的原始材料：

```json
{
  "raw_text": "<允许字段拼装文本>",
  "input_type": "text",
  "bound_seller_target_ids": ["<seller_target_id>"],
  "processing_scope": "basic_info",
  "auto_process": false,
  "include_attachment_text": false,
  "auto_parse_linked_objects": false,
  "metadata_json": {
    "test_batch": "<batch_id>",
```

### 6.3 解析轮询

- 普通解析任务：每 10 秒查询一次 `GET /background-jobs/{job_id}`；

- 失败终态：`failed`、`canceled`、`cancelled`（兼容不同接口拼写）；

- 首次失败可通过既有重试接口或原操作安全重试一次，重试前必须确认没有仍在运行的同类任务。

解析完成后回读标的。AI 解析不得把精确值 28、推介情况或源表备注错误覆盖为当前事实；若此时产生待确认建议，先记录到 manifest，统一等全部标的调研完成后再扫描和逐项处理。

## 8. Phase 2A：逐一采纳所有标的的待确认 AI 调研结果

### 8.1 执行范围与顺序

本阶段处理所有 144 个标的在 AI 调研后显示为“待确认”的 `research_proposal`。不得只处理抽样标的，不得批量改数据库状态，也不得把“采纳”简化为仅修改 `review_status`；每一项都必须通过正式采纳接口写入标的信息和来源记录。

按 Excel 行号顺序逐个标的执行。对单个标的查询：

```http
GET /research/proposals?entity_type=seller_target&entity_id=<seller_target_id>&review_status=pending_review&limit=200
```

将查询结果完整写入 manifest，记录 `proposal_id`、字段、当前值、建议值、规范化建议值、来源、冲突类型、`is_actionable` 和 `validation_error`。单个标的内按 `created_at` 从早到晚处理，使同一字段存在多轮建议时由最新建议最终生效。

### 8.2 逐项采纳

每个待确认项依次执行：

1. 核对 `entity_type=seller_target`、`entity_id` 等于当前标的 ID、`review_status=pending_review`；
2. 核对 `is_actionable=true` 且 `validation_error` 为空；不满足时不能伪造“已采纳”，记录 `PROPOSAL_NOT_ACTIONABLE` 并阻断本分支；
3. 保存采纳前的当前字段值、来源和标的 `updated_at`；
4. 调用正式接口，不传人工改写值，直接采纳 AI 建议原值：

```http
POST /research/proposals/<proposal_id>/accept
```

5. 响应必须返回 `review_status=accepted`；
6. 回读标的对应字段、字段来源和更新记录，确认实际写入值等于接口返回的 `normalized_proposed_value`（无规范化值时对比原始 proposed value）；
7. 将采纳时间、采纳前值、采纳后值和结果写入 manifest，再处理下一项；
8. 当前标的所有项处理后重新查询 `pending_review`，必须为 0，才进入下一个标的。

“逐一采纳”包括 `conflict_kind` 为冲突的待确认项。不得因为建议值与源表值不同而跳过；冲突详情保留在审计记录中，成功采纳后继续。若接口返回 422、字段回读不一致或来源记录缺失，则停止，不得直接更新数据库绕过验证。

### 8.3 幂等、重试与并发控制

- 每次采纳前后都更新 manifest，支持断点续跑；
- 网络中断导致响应不确定时，先重新查询 proposal：已为 `accepted` 且字段回读一致则记为成功，仍为 `pending_review` 才允许重发一次；
- 409 时先回读状态；若已由本批或同一管理员采纳且值一致，可按幂等成功记录，否则记为状态冲突并停止；
- 422 不盲目重试，记录 `PROPOSAL_APPLY_VALIDATION_FAILED` 并停止；
- Phase 2A 可与 Phase 3 并行，但 Phase 2A 内部只允许一个标的、一个 proposal 顺序执行，避免多个建议同时写同一标的；
- Phase 3 不得修改卖方标的信息；两条并行分支共享故障信号，任一分支阻断后都停止发起新的操作。

### 8.4 Phase 2A 门禁

- 144 个标的均完成一次调研后待确认项扫描；
- 初始待确认总数、成功采纳总数、幂等复用数和失败数已写入 manifest/summary；
- 所有可见待确认项均逐一通过正式接口采纳，`pending_after_count=0`；
- 每项响应状态、标的回读值和字段来源记录一致；
- 不存在 `is_actionable=false`、validation error、422、未知 409 或回读不一致而被静默跳过的项目；
- Phase 2A 失败数和未处理数均为 0。

- 每 10 秒查询 `GET /recommendations/sessions/{session_id}/page-state`；
- `polling_hint.enabled=false` 且 `summary.rerank_status.status` 为成功终态后才算完成；
- 单会话最长 20 分钟；
- 候选读取 `bundle.latest_candidates`；
- 默认最多同时运行 3 个独立会话；连续 3 个会话成功且 llm 队列稳定后最多升至 5 个。每个会话仍独立轮询并完成终态校验；
- 从 page-state、后台任务或 execution trace 取得关联 job ID，并标记为测试数据；
- 网络错误采用 5、10、20、40、60 秒退避；
- 首次失败重试一次。重试必须创建新的独立 session，并将旧 session 记为失败，不能覆盖证据。

每个会话核验：

1. `mode` 与请求一致；
2. anchor ID 与请求的需求/标的 ID 一致；
3. 候选数量大于 0，候选实体类型与方向正确；
4. 候选 ID 均真实存在，且没有把 anchor 自身当候选；
5. rerank 和深评成功，无长期 `queued/running`；
6. 深评 trace 使用正确方向专属节点，不能错误启动通用节点或另一方向节点；
7. Prompt 版本非空，渲染后的关键变量 `mode`、`anchor_context`、`candidates_json` 非空；
8. `rank` 连续且不重复，分数、评级、匹配摘要、风险/缺口信息结构合理；
9. 区域、行业、营收、利润、估值、控制权、上市偏好等硬条件没有明显反向匹配；
10. 同一批输入重复出现完全相同、与 anchor 无关的理由时，记录 `RECOMMENDATION_SUSPICIOUS_DUPLICATE`。

### 10.5 Phase 4 门禁

- 5 个 `buyer_to_target` 独立会话全部成功；
- 5 个 `target_to_buyer` 独立会话全部成功；
- 10 个会话均有候选，且候选数大于 0；
- 10 个 rerank/深评任务均成功；
- 两个方向分别使用正确的方向专属节点和非空 Prompt；
- 不存在候选类型、anchor、方向或 trace 错配；
- 所有推荐结果摘要已写入 manifest 和 summary。

## 11. 轮询、重试与停止策略

| 任务类型 | 轮询间隔 | 单任务上限 | 最大业务重试 |
| --- | ---: | ---: | ---: |
| 标的基本信息解析 | 10 秒 | 15 分钟 | 1 次 |
| 买家需求两阶段解析 | 10 秒 | 15 分钟 | 1 次 |
| 标的调研及 mapper | 30 秒 | 45 分钟 | 1 次 |
| 待确认项逐一采纳 | 每项即时回读 | 每项 5 分钟 | 1 次 |
| 推荐 rerank/深评 | 10 秒 | 20 分钟 | 1 次 |

通用规则：

- HTTP 429/502/503/504 或连接错误使用 5、10、20、40、60 秒退避；
- 401/403 不重试，立即刷新登录状态或停止检查权限；
- 400/404/409/422 属于输入、实体或状态问题，不盲重试；
- 任务状态不变不代表失败，只要未超过上限继续轮询；
- 超时后不取消仍运行的任务，先停止新任务并记录；
- 任一阻断异常触发 `STOP_AFTER_<PHASE>`；并行窗口内任一分支异常会停止两条分支继续发起新操作，且不进入推荐阶段；
- 每次重试记录原始请求摘要、原任务/会话 ID、错误、重试时间和新 ID。

## 12. 异常分级

### 12.1 非阻断源数据异常

- 精确值 28、空值或占位文本；
- D/R、G/S 展示值不一致，但 D/G 有合法权威数值；
- 行业原文暂时无法映射，已留空并保留原文；
- 调研待确认项存在数据冲突，但已通过正式接口逐一采纳且回读一致。

这些异常必须记录，但在实体身份、接口和任务均正常时可继续。

### 12.2 阻断异常

- 重名实体无法确认是否同一对象；
- API 创建失败、回读失败、字段错写或 28 进入结构化字段；
- 任一后台任务失败、取消或超时且一次重试仍未恢复；
- 调研主任务成功但 mapper 子任务失败；
- 任一标的仍有未采纳的 `pending_review`、提案不可执行、采纳接口失败或采纳后字段回读不一致；
- 买家主体与需求绑定错误、解析阶段丢失或反转条件；
- 推荐零候选；
- 推荐方向、anchor、候选实体类型错误；
- 两个方向启动了错误深评节点、通用兜底节点或空 Prompt；
- 服务器健康、worker、搜索、数据库或模型配置在运行中失效；
- 源 Excel hash 在恢复执行时变化。
