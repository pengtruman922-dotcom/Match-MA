## 一、为什么做

`buyer_intent_parser`（原来的单段解析）的**字段词汇表写死在提示词正文里**，靠人记得跟
指标注册表同步 —— 这正是「营收写不进去」那个 bug 的成因（详见
`附件正文截断与调研失败静默修复0801.md`）。两段式的 normalizer 拿的是
`indicators_for("buyer_intent")` 派生的 `field_contract_json`，从注册表来，人漏不掉。

第二个理由：拆分值不值得，全系统一直**没有一次对照数据**。买家这对是现成的，
开一次就能拿到；标的解析要不要照做，等这个数据出来再定。

## 四、对照结果

### 4.1 附件全量修复得到了验证

C 的覆盖条款**两边都抽到了**（`max_debt_ratio=50`、`min_net_margin=12`、
`max_valuation_yuan=5亿`、`max_pe=12`、`min_net_profit_yuan=1000万`）。
旧代码下这段根本进不了模型 —— 0801 那次修复在真实长材料上成立。

### 4.2 两段式赢在哪

| 维度 | legacy | 两段式 |
| --- | --- | --- |
| `industry_l2_json`（参与 SQL 筛选） | **三条全空** | B `["制药","医疗器械","储能","新能源制造"]`、C `["汽车零部件","储能","半导体与集成电路","高端装备"]` |
| `acceptable_*_status_json`（现金流/盈利/上市，枚举筛选字段） | 全空 | B、C 均填 |
| `region_constraints_json`（结构化地区） | 只有一句摘要文本 | `[{"province":"江苏省","effect":"preferred"}, ...]` |
| `transaction_types_json` | 散文塞在 `transaction_type` | `["现金收购","现金+股份混合支付"]` |
| `needs_confirmation_json` / `unknown_summary` | **从未产出** | 三条全有，且指得很准（如 B 的「营收可放宽到 5000 万，基准值未明确」） |
| **多方案落库** | 0 个方案 | **B 落了 2 个方案**，各带自己的营收/估值/股比 |

多方案那条是本次最实质的收获：`buyer_intent_scenario` 此前**从未被任何管线写入过**，
legacy 提示词根本没提 scenarios。现在 B 的两个方案各自带阈值进了库，
`recommendation_flow` 的 `merge_scenario_into_anchor` 会分别筛。

### 4.4 对照途中修掉的三个真问题

**① 百分比字段被写成小数（v0.1.1 → v0.1.2）。**
C 在 v0.1.1 下输出 `max_debt_ratio=0.50`、`min_net_margin=0.12`、`min_gross_margin=0.25`、
`max_premium_rate=0.30`、`desired_equity_ratio_min/max=0.51/0.70` —— 全部差 100 倍。
而 A 在同一版下是对的（60.0 / 10.0 / 51.0）：提示词没写口径，模型每次自己猜，
**不是稳定错，是随机错**。`max_debt_ratio` 是硬筛选字段，0.5 意味着只有负债率 ≤0.5%
的标的能过 —— 等于清空候选。v0.1.2 加了 0–100 对照表与「倍数不是百分比」的区分，
C 重跑后六个字段与 legacy 完全一致。

**② 多方案写错了字段（v0.1.2 → v0.1.3）。**
v0.1.0 的提示词说「方案之间的差异写进 `condition_effects_json`」——
但那个字段是「字段 → 作用强度」的映射（`{"min_revenue_yuan":"required"}`），
`normalize_condition_effects` 只保留 `required/preferred/deep_eval`，
模型写进去的方案数组被**整段丢弃**，落库是 `{}`。
v0.1.3 改成顶层 `scenarios` 数组（`_replace_buyer_intent_scenarios` 认的正是这个形状），
B 立刻落了 2 个方案。顺带补了金额位数示例 —— v0.1.2 把「6亿」写成了 60000000。

**③ 「排除已上市」被投影成「上市状态不限」（代码，`0e9add2`）。**
两段式开始输出多值 `acceptable_listed_status_json`（C 是 `["unlisted","pre_ipo"]`，
明确排除已上市），而旧投影是 `len == 1 ? values[0] : "any"`，
于是界面上写着「上市状态：不限」—— 恰好是买家排除掉的那一项。空清单同样被投成 `any`。
改成：单值取该值，三种全收才是 `any`，其余一律 `unknown`。
规则原本在解析侧和 API 侧各有一份，现在收进 `backend/app/services/listed_status.py`。

## 六、对照途中挖出的、与两段式无关的一个 bug

**买家带附件新建时，行业字段绕开了字典校验。**

`extracted_action_apply.py` 把 `business_update_extractor` 的输出直接写进
`industries_json`，全程不碰 `industry_taxonomy`；而 `buyer_intent_parse` 会跑
`normalize_l1_values(fallback_unmapped=False)`，字典外的词一律踢进 `industry_focus_tags_json`。
**同一个封闭词表列有两个写入者、两套政策**，带附件时松的那个先写且赢。

C 的 `application_log` 实证：`extracted_action` 于 04:42:40 写入
`industries_json = ["汽车电子零部件","储能与热管理","半导体封装与测试配套","精密模具与自动化装备"]`，
四个词**没有一个在字典里**。这个列是用 `bi.industries_json ? :industry` 查的，
所以这条需求看着有行业筛选，实际筛掉全部标的。

**legacy 一样中招**，只在附件路径出现。已单独开任务，不在本单范围。
