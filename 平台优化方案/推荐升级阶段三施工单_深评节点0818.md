## 一、这个阶段解决什么

阶段二把用户的话拆成了两半：能翻译成 SQL 的进 `condition_groups`，翻译不了的进
`qualitative_requirements`——「具备地区产业优势」「有成熟的海外仓网络」「经营稳定」
「与我们现有业务有协同」。

**后一半至今无人消费。** 解析出来了，落库了，然后就停在那里。初筛不认它（本来也不该认），
主 Agent 拿不到（阶段四才接进提示词），最终答案里它就像没说过一样。

阶段三给它一个消费者：一次干净上下文的 LLM 调用，拿到全部候选的完整画像，
**逐条判定每个定性诉求，然后按匹配程度重排序**。

### 为什么是独立节点，不是主 Agent 顺手做

四个理由，缺一不可：

1. **agent 上下文不随候选数量膨胀**——40 家完整画像 3 万字，进了对话历史就再也出不去，
   后续每一轮都要重付一遍
2. **深评拿到的是干净上下文**：没有工具调用历史、没有编排系统提示词的污染
3. **编排与评估可以配不同模型**——编排要快，评估要准，本来就不该是同一个
4. 反向的「为标的找买家」可以直接复用同一个节点

## 四、设计

### 4.1 新模块，旧函数一个字都不改

`llm_client` / `profile_sections` / `screening_schema`，**不 import
`recommendation_flow` 与 `jobs.handlers.*`**，否则成环）。

`jobs/handlers/recommendation.py` 里这几个**原样保留、不要动**：

- `_run_recommendation_deep_eval`
- `_run_deep_eval_shards`
- `_interleave_shards`
- `_apply_deep_eval_results_to_candidates`
- `DEEP_EVAL_SHARD_SIZE`

它们服务 `/candidates` 旧打分链路，**阶段五整体拆除**。本阶段改它们就是越界，
而且会造成旧链路回归——旧链路虽然前端已无调用方，但接口还在、测试还在。

这与阶段二的做法一致：阶段二也保留了旧的 `parse_recommendation_message` 原封不动。

### 4.2 不分片，整体提交

框架第五节写着「分片仍保留，理由是对抗长输入的中间遗忘」。**这一条推翻。**

分档取消之后，分片就不成立了：分档时两片的结果能靠一把绝对标尺（A/B/C）合并，
**纯排序时不能**——A 片的 rank 1 和 B 片的 rank 1 谁更靠前，没有任何依据可以判断。
硬要合并就得再跑一次「合并评估」，那还不如一开始就整体提交。

预算：40 家 × 800 字符 ≈ 3.2 万字。当前模型放得下。

配套：`recommendation_deep_eval_to_target` 的 `default_timeout_seconds` 从 180 抬到 **300**
（单次调用变长了）。注意这只改注册表默认值，**已有的生产节点配置不会自动跟着变**——
部署后要在设置页确认一遍实际超时值，或由我手工改。

### 4.3 输入

| 内容 | 来源 | 为什么要 |
|---|---|---|
| 用户原话 | `snapshot["raw_text"]` | 不丢失细节 |
| 结构化条件 | `snapshot["condition_groups"]` | 告知**硬门槛已过**，不要重复判断 |
| 定性诉求 | `snapshot["qualitative_requirements"]` | **主要工作对象**，独立变量注入 |
| 排除项 | `snapshot["exclusions"]` | 已在 SQL 生效，仅供解释 |
| 未结构化残留 | `snapshot["unstructured_notes"]` | 让遗漏可见 |
| 买方自身情况 | `buyer_party_fact_block(db, party_id)` | 「与现有业务有协同」不知道买家在做什么就判不了 |
| 候选画像 | `load_profile_sections` + `render_profile_text` | 约 800 字符/家 |
| 命中组数 | 工具层（本阶段补） | 多组命中 = 强候选 |

**候选画像里要排除的字段**：PE 口径、财务期间标签、估值/报价时间。
它们对「合不合适」没有贡献，纯占位——3 万字的预算里每个字都该有用。

#### 命中组数怎么补

`RecommendationAgentTools` 加一个计数，与 `candidates_by_id` 并行维护：

```python
self.candidate_hit_counts: dict[str, int] = {}
# _search_targets 里，每次结果落袋时：
self.candidate_hit_counts[key] = self.candidate_hit_counts.get(key, 0) + 1
```

**不要改 `candidates_by_id` 的 `setdefault` 语义**——首见为准是对的，
候选内容本身在多次查询间没有差异，改成后见覆盖只会让结果不可复现。

这是本阶段唯一允许改动阶段一交付文件的地方。其余部分不要碰。

### 4.4 输出 schema

```json
{
  "ranked": [
    {
      "id": "…",
      "rank": 1,
      "qualitative_verdicts": {
        "具备地区产业优势": "符合",
        "有成熟的海外仓网络": "无法判断"
      },
      "fit_points": ["…", "…"],
      "risks": "…",
      "info_gaps": "…"
    }
  ],
  "dropped": [{"id": "…", "reason": "…"}]
}
```

**`qualitative_verdicts` 逐条判定是排序的依据，不是装饰。**
它让 LLM 做它擅长的离散判定（`符合` / `不符合` / `无法判断`），
排序成为判定的结果而非凭空的偏好——同时天然可解释：用户问「为什么这家排第一」，
答案就是三条定性诉求全部符合。

三个取值是闭集，用 JSON Schema `enum` 约束。
`qualitative_verdicts` 的**键必须来自 `qualitative_requirements` 原文**，
模型自创的键在归一化时丢弃并记进 `notes`——不要静默丢。

**不给评级、不给分数。** 上一版给 A/B/C，本版取消：
分档是绝对判断（要求模型心里有一把看不见的标尺），排序是相对判断（两两比较），
LLM 对后者稳定得多。

### 4.5 保底：不许剔成空集

模型把所有候选都放进 `dropped` 时，**保底取初筛序前 3 家**放回 `ranked`，
并在结果上标注 `fallback_reason: "all_dropped"`。

理由：「一家都没有」比「有几家但都不理想」糟糕得多——后者至少给了客户经理判断材料，
前者只会让他重新问一遍。

同理，`ranked` 里出现**不在候选集里的 id**（模型编的）一律丢弃并记进 `notes`；
候选集里**没出现在任何一边**的 id 归入 `uncovered`，按初筛序缀在 `ranked` 末尾——
漏判不等于淘汰。

### 4.6 在链路中的位置：产出并落库，不改最终答案

**与阶段二完全同构。** agent loop 跑完之后、写作素材包之前，无条件跑一次深评，
结果写成一条 `agent_deep_eval` 消息并即时提交。

**但本阶段不改最终答案**——素材包 `answer_brief_json` 保持原样，写作节点看不到深评结果。
把深评接进素材包与最终名单是**阶段四**的事。

这样切的理由：深评的质量要在真实数据上看了才知道（排序合不合理，定性判定准不准），
而在它稳定之前就让它决定用户看到的名单，出了问题连对照组都没有。
先让它跑起来、落库、可对比，是最省事的验证路径。阶段二就是这么做的，效果很好。

失败处理沿用阶段二的规矩：

- **深评调不通不中断本轮**（节点没配、超时、模型报错）——这一轮退化成「没有深评的一轮」，
  agent 的原始名单照常输出
- 但状态要如实写进消息与 trace：`deep_eval_status` ∈ `ok` / `unavailable` / `schema_mismatch`
- **`schema_mismatch` 专抓「提示词版本与代码失配」**：模型返回了东西但一个认识的键都没有。
  这是阶段二吃过的亏——v0.1.0 提示词把变量写成单花括号，模型收到字面量，
  输出全错但**全链路零报错**，只能靠人读对话记录才发现

`parser_status` 不是 `ok` 时（快照本身就是降级来的），
`qualitative_requirements` 里只有用户原话一条。**照跑**，深评仍然有意义。

## 六、验收用例

归一化逻辑用 fixture 模拟 LLM 返回做纯单测，**不要打 LLM**。

| # | 输入 | 期望 |
|---|---|---|
| 1 | 正常返回，3 家全在候选集里 | `ranked` 按 `rank` 升序，id 与候选集一一对应 |
| 2 | 模型返回的 `ranked` 里混进一个候选集没有的 id | 该条丢弃，`notes` 记一笔，其余照常 |
| 3 | 候选 5 家，模型只提到 3 家 | 另 2 家按初筛序缀在 `ranked` 末尾，`uncovered` 列出它们 |
| 4 | 模型把 5 家全放进 `dropped` | 保底取前 3 回 `ranked`，`fallback_reason = "all_dropped"` |
| 5 | `qualitative_verdicts` 的键是模型自创的 | 该键丢弃并记 `notes`，**不得静默** |
| 6 | `qualitative_verdicts` 的值是 `很符合` | 不在闭集内，归一成 `无法判断` 并记 `notes` |
| 7 | 模型返回 `{"foo": 1}` | `deep_eval_status = "schema_mismatch"`，不抛异常、不伪造排序 |
| 8 | LLM 调用抛 `LlmCallError` | `deep_eval_status = "unavailable"`，**本轮不中断**，agent 名单照出 |
| 9 | `qualitative_requirements` 为空（用户只提了硬条件） | 深评照跑，`qualitative_verdicts` 为空对象，仍产出排序 |
| 10 | 同一标的被两次 `search_targets` 命中 | `candidates_by_id` 里 1 条，`candidate_hit_counts` 为 2，且进了深评输入 |
| 11 | 节点 `recommendation_deep_eval_to_target` 未配置 | `deep_eval_status = "unavailable"`，**不得回落共用节点** |

**必须过的四条：7、8、10、11。**

- **7、8** 是阶段二那次「全链路零报错地错了一整轮」的直接复刻，两种失败都要有名字
- **10** 是本阶段唯一的新数据流，漏了不会报错、只会让深评永远看不到「强候选」信号
- **11** 是本阶段最容易做错的一条——`_get_deep_eval_node_config` 就在旁边，
  顺手复用是最自然的写法，也是错的
