# 买家管理与推荐买家优化方案（P0）

版本：v0.1
日期：2026-07-29
状态：已确认开发基线

## 一、目标与边界

P0 以“需求”为买家管理、推荐和推进的最小单元。买家主体只维护可跨需求共用的名称、联系人、主体背景和产业能力；同一买家的不同需求各占列表一行，独立维护状态、方案、推荐与推进记录。

P0 包括：

1. 公共条件与多个需求方案的展示、编辑和对比。
2. AI 解析后自动写入，人工事后复核修改。
3. 明显存疑的字段标记为“需要确认”，确认前不参加初筛和软排序。
4. 需求行业与标的行业共用同一行业字典。
5. 建立方案感知的“标的找买家”反向推荐。
6. 推荐结果解释命中方案、满足项、未知项和综合判断，支持用户最终选中。

P0 不包括：

- 不强化买家主体配置和独立管理能力。
- 不解析、拆分或提示一份材料里的多个买家或多个需求；创建流程始终假设输入为一个买家的一项需求。
- 不保存 AI 置信度。
- 不建设通用布尔规则编辑器。
- 不把含糊定性要求强行转成数值筛选条件。

## 二、产品模型

```text
买家主体（轻量共享）
└─ 需求（最小管理单元）
   ├─ 公共条件
   ├─ 方案 A
   ├─ 方案 B
   └─ 待确认事项
```

一个需求的匹配关系为：

```text
公共条件 AND（方案 A OR 方案 B OR 方案 C）
```

没有显式方案的存量需求视为只有一个默认方案，保持原有行为。

## 三、需求详情与编辑

需求详情以匹配逻辑为核心，不再只展示一张扁平摘要。

```text
+================================================================================+
| 北大健康医药并购需求                    [AI已解析·2项待确认]                   |
| 买家：北大健康    负责人：张三                       [编辑] [智能推荐]          |
+================================================================================+
| 需求摘要                                                                       |
| 围绕医药健康产业开展控股并购，上市和非上市标的采用不同要求。                   |
+--------------------------------------------------------------------------------+
| 公共条件                                                                       |
| [硬筛] 一级行业：医药与健康，任一命中                                          |
| [软排] 二级行业：医疗器械、医药流通、生物制药                                  |
| [软排] 地区：长三角，浙江优先                                                  |
| [深评] 细分方向：医疗耗材、体外诊断、医美耗材、CXO                             |
+--------------------------------------------------------------------------------+
| 方案 A：上市公司控股并购                                                       |
| [软排] 优选市值：≤50亿元                                                       |
| [硬筛] 最高市值：≤100亿元                                                      |
| [硬筛] 近三年净利润：每年≥1000万元                                             |
| [需要确认] 股比≤29.9%，同时要求控制并表                                        |
+--------------------------------------------------------------------------------+
| 方案 B：非上市公司控股并购                                                     |
| [硬筛] 上市状态：未上市                                                        |
| [硬筛] PE：≤13倍                                                               |
| [硬筛] 净利润：≥2000万元                                                       |
| [硬筛] 收购股比：≥51%                                                          |
+--------------------------------------------------------------------------------+
| 待确认事项                                                        [立即复核]   |
| 1. 上市方案股比与控制并表要求可能存在矛盾                                      |
| 2. 非上市方案没有明确绝对估值上限                                              |
+================================================================================+
```

每个条件至少包含：作用范围、字段、运算关系、值与单位、推荐角色、复核状态、原文证据和补充说明。方案支持创建、复制、启停、排序和编辑；公共条件与方案条件合并后的有效画像必须可预览。

## 四、AI 解析与复核

```text
用户创建需求
→ AI 读取原始材料和行业字典
→ 识别公共条件和方案
→ 提取字段、运算关系和规则角色
→ 标记需要确认的内容
→ 自动写入需求
→ 进入详情页人工复核
```

处理原则：

- 明确数值或枚举直接写入并生效。
- 明确偏好写入软排序字段。
- “高营收低利润，或者营收不高但利润率和利润较好”等含糊复合描述只进入深评，不生成营收、利润或利润率门槛。
- 明显矛盾、单位不清或无法确定唯一字段的内容保存为“需要确认”。
- 需要确认字段保存建议值、原因和证据，但确认前不进入初筛或软排序，只进入深评上下文。
- 不输出置信度，也不设置创建前确认页。

需求侧不显示“信息完整度百分比”，只显示“AI 已解析”“有待确认项”“已人工复核”。候选侧显示已判断项和未知项，不合成百分比。

解析器输出契约如下；正式发布时通过「Prompt 版本管理」创建并切换新版本，不使用数据库迁移写入 Prompt：

```json
{
  "fields": {
    "intent_summary": "明确、可直接生效的公共字段",
    "industries_json": ["医药与健康"]
  },
  "needs_confirmation": [
    {
      "field": "min_revenue_yuan",
      "proposed_value": 5000000,
      "reason": "原文未写明金额单位",
      "evidence": "营收至少500"
    }
  ],
  "scenarios": [
    {
      "label": "上市公司方案",
      "fields": {"preferred_listed_status": "listed", "max_market_cap_yuan": 5000000000},
      "needs_confirmation": []
    },
    {
      "label": "非上市公司方案",
      "fields": {"preferred_listed_status": "unlisted", "max_pe": 13},
      "needs_confirmation": []
    }
  ]
}
```

`needs_confirmation` 不允许输出置信度；其中的建议值不写入正式筛选字段。只有 `fields` 和方案中不在待确认列表里的字段会自动生效。

## 五、行业字典

需求与标的共用同一行业字典，但语义不同：标的行业描述企业客观归属，需求行业描述买家可接受范围。

| 字段 | 默认作用 |
|---|---|
| 一级目标行业明确限定 | 硬筛，多个值任一命中 |
| 二级关注行业 | 软排序，不命中不出局 |
| 字典外细分方向 | 深评 |
| 字典内一级/二级排除行业 | 硬排除 |
| 无法映射的排除词 | 需要确认或深评 |

AI 解析时先映射一级、二级字典；无法映射的产品、技术和场景词保留为细分关注方向，不得强行归为“其他”并参与硬筛。

## 六、正向与反向推荐

正向与反向共享同一配对语义：

```text
Accept(需求, 标的) = 需求是否接受该标的
```

但两者的查询形态不同：

- 需求找标的：固定需求条件，查询标的数据。
- 标的找买家：固定标的事实，查询哪些需求方案能够接受它。

例如标的为医药与健康、营收 800 万元、可以控股，反向初筛应保留：

```text
一级行业无硬限制 OR 一级行业包含医药与健康
AND
最低营收无要求 OR 最低营收 ≤ 800万元
AND
控股不是硬要求 OR 标的可以控股
AND
未命中明确排除行业
```

没有行业限制的需求仍可能接受标的，但排序低于明确行业命中；标的可以控股时，要求控股、不要求控股和接受少数股权的需求都可以保留，只有标的明确不可控股且需求硬性要求控股时才冲突。

反向推荐分三阶段：

1. SQL 结构化预筛：排除已知事实下明确不可能的需求方案。
2. 确定性规则复核：逐方案生成 compatible、possible、conflict、满足项、未知项和软排序结果。
3. LLM 深评：使用买家背景、需求公共条件、实际命中方案、标的完整信息、含糊要求和待确认事项进行综合判断。

若标的某项信息未知，SQL 阶段不得据此排除需求。一个需求只要有一个方案不冲突就保留，并记录最佳匹配方案；所有方案均冲突时才淘汰整个需求。

### 反向匹配画像

随着需求量增长，为每个有效方案维护一条只读匹配画像，用于索引化反向预筛：

```text
intent_id
scenario_id
hard_industry_l1
soft_industry_l2
min_revenue
min_net_profit
max_valuation
requires_control
requires_consolidation
...
```

画像只包含已生效的硬筛和软排序字段，不包含需要确认或仅深评字段。需求解析、人工编辑、方案启停后同步刷新。第一批开发先保证方案感知与结果一致性，匹配画像作为数据量增长后的性能层建设。

## 七、推荐结果

推荐结果的主对象是“买家需求”，买家主体作为辅助信息。结果优先展示：买家及需求名称、命中方案、明确满足项、未知项、软性不足、LLM 综合判断和逐字段对比，综合分数只用于排序。

```text
+================================================================================+
| 北大健康 · 医药健康产业并购                                             A档 |
| 最佳匹配方案：非上市公司控股并购                                          |
| 初筛情况：5项满足 · 2项未知 · 0项冲突                                     |
| + 明确关注医药与健康                                                      |
| + 最低营收500万元，标的营收800万元                                        |
| + 要求控股，标的可转让60%                                                 |
| ? 团队留任意愿未知                                                        |
| ? 重大风险尚未完成核验                                                    |
| AI判断：标的落入非上市控股方案的接受范围，建议优先联系。                   |
|                                                        [完整对比] [选中]   |
+================================================================================+
```

## 八、开发顺序

1. 补齐需求字段契约、待确认数据和方案 API。
2. 改造需求详情页，展示和编辑公共条件、方案与待确认项。
3. 扩展 AI 解析输出，自动落库并隔离需要确认字段。
4. 统一行业字典写入规则，二级行业默认只影响软排序。
5. 使标的找买家加载并逐一判断需求方案。
6. 深评使用实际命中方案的完整上下文。
7. 推荐结果展示方案、满足项、未知项和完整对比。
8. 数据规模需要时再建设反向匹配画像和 SQL 索引层。

## 九、核心验收

1. 营收 800 万元的标的保留最低营收 300 万、500 万和无营收要求的需求，淘汰最低营收 1000 万的需求；待确认营收条件不参与筛选。
2. 标的可以控股时，要求控股、不要求控股和接受少数股权的需求都可保留；明确不可控股时只淘汰硬性要求控股且不接受少数股权的需求。
3. 一级行业硬条件不命中时冲突；二级行业不命中只降低软排序；字典外细分方向留给深评。
4. 非上市标的可以淘汰上市方案但命中同一需求的非上市方案，最终结果显示实际命中方案。
5. 对任意确定的需求—标的配对，从需求找标的和从标的找需求得到相同的兼容状态、冲突原因和匹配方案。
