## 你要修的四件事

1. **轮询过密**。现在 1.2 秒一次、上限 300 次，一轮最多约 600 个 HTTP 请求，
   且 `setInterval(async …)` 没有单飞保护，请求会重叠。
   改成：单飞 + 前 30 秒每 3 秒 / 30 秒~5 分钟每 10 秒 / 5 分钟后每 30 秒。
2. **前端自己判超时造成假失败**。第 301 个 tick 约 361 秒就标失败，
   而生产上有一轮真实耗时 376.8 秒 —— **刚好被误杀**。
   改成：前端**永远不是**终态失败的判定者，只有后端 job 状态是。
3. **重试制造重复气泡**。模型上下文其实不重复（已用生产重试轮验证过），
   只是展示层出现两条相同用户消息。加 `retry_of_turn_id`，旧轮折叠、新轮在原位。
4. **多个澄清问题点一个就提交**。`ClarifyBlock` 每个 option 直接绑 `onPick`
   （`AgentTurnView.tsx:129`），第一题一点就创建下一轮。改成选完再统一提交。

## 五个容易做错的地方，先打预防针

1. **10 秒 / 30 秒是拍板口径，但前 30 秒要加密段。** 一轮总耗时中位数才 105 秒，
   澄清框和进度步骤如果统一等 10 秒，感知上是明显回退。前 30 秒每 3 秒，只多 8 次请求。
   **不要为了「严格照数字执行」把这个密段砍掉。**
2. **`attempts` 放慢后不再等于时间。** 所有基于 `attempts` 的判断都要改成基于
   `Date.now() - startedAt`，否则「5 分钟」会算错。这是最容易漏的一处。
3. **别把「网络暂时不可达」和「后端失败」混成一个状态。** 这是本批的核心语义分界。
   连续网络错误只能显示「暂时无法获取进度」，**绝不能引导用户重试** —— 那正是现在
   假失败 → 用户重试 → 并发开第二个付费任务的链条。
4. **失败轮折叠，但不要完全隐藏。** 留一行灰字「第 1 次尝试失败（查看详情）」。
   完全隐藏会让用户不知道自己发过，转头在别处重复发。
5. **澄清框的发送文本必须带题干。** 只发选项值，parser 会丢失题意 ——
   选项是「是 / 否」时尤其致命。正确形态：
   `上市状态：只看已上市的；净利润要求：1000万元以上`

另外：`rebuildTurns`（`Recommend.tsx:737`）在没有 brief 时直接标「这一轮没有跑完」
且不恢复轮询，重开一个后端仍在跑的会话会看到假失败 —— 这条也要一起修。

## 验收标准

| 项 | 期望 |
|---|---|
| 一轮真实推荐 | 前 30 秒进度跟得上；5 分钟后仍在跑时显示「仍在处理」而不是失败 |
| 断网 30 秒再恢复 | 显示「暂时无法获取进度」，恢复后接着走，**不出现重试按钮** |
| 后端真失败 | 出现重试按钮；点重试后旧轮折叠、新轮在原位、**只有一条新用户气泡** |
| 3 题澄清 | 三题都能选，提交后**只创建一轮**，发送文本含题干 |
| 重开运行中的会话 | 恢复轮询，不出现「这一轮没有跑完」 |
| 网络请求数 | 一轮约 30~40 次（现在约 600 次） |
| 测试 | `python -m pytest -q` 全绿；`npm run typecheck && npm run build && npm run lint` 全过 |

**光跑通测试不算完，上面前五条要在真实环境里演一遍。**
本机是 Python 3.14、无后端 venv，直接 `python -m pytest` 即可。
