## 问题一：重试

**用户原话**：

> （1）当前重试的触发机制是什么，出现的几率有点高，和多个推荐会话并行有关系吗；
> （2）点击重试后，带入的上下文会重复带入重试的吗；
> （3）当前的重试点击后是把问题新发了一遍，旧的失败的并没有删除，
> 是不是应该删除旧的那条失败的，加入新的？

**我已核实的线索**（请你验证，不要照单全收）：

**(1) 触发有两条路**：`turnStatus` 返回 `failed`，或**前端自己判超时**——
`POLL_MAX_ATTEMPTS = 300` × `POLL_INTERVAL_MS = 1200` = **360 秒**（`Recommend.tsx:18-21, 219-221`）。

**最可疑的一条**：`railway.worker-llm.toml` 的注释明写着
「**推荐 Agent 一轮跑满工具预算可以超过 5 分钟**」，所以 stale 窗口开到了 1800 秒。
而前端只等 360 秒，**并且这 360 秒是从入队开始计的**——
`startPolling` 的 `startedAt` 在 `agentTurn()` 返回后立刻取值，
**队列等待时间算在里面**。

`llm` 队列同时服务解析、深评、报告、embedding。**多个推荐会话并行时任务要排队，
排队时间直接吃掉前端的超时预算。** 所以用户问的「和并行有关系吗」，
我的判断是**大概率有**，但需要你用数据坐实：
取几个失败轮的 `background_job` 行，比较 `created_at → started_at → finished_at`，
看是等待长还是执行长。这决定了该调前端超时、还是该加 worker 副本、还是两者都要。

**(2) 上下文是否重复**：按代码看**不会**。`_agent_history_turns`
（`recommendation_flow.py:3243`）要求一轮的**问和答两半都在**才计入历史，
失败轮没有 answer，会被整轮丢掉。请实测确认一次。
但注意：`recommendation_message` 表里那条失败的 user 消息**还在**，
前端也还显示着——所以用户看到的「重复」可能是界面上的，不是模型上下文里的。
这两件事要分开回答。

**(3) 旧失败轮不删**：确认属实。`onRetry={() => void send(turn.userMessage)}`
（`Recommend.tsx:596`）——重试就是拿同一段文字**发起全新一轮**，
不复用 `turn_id`，也不删旧轮。

用户想要「替换」是合理的，但**请不要直接物理删除**：失败轮的落库痕迹
（`ai_trace`、`agent_step`、job 行）是排障依据，删了以后再出问题就查不了。
建议方向是「前端不再展示这一轮 + 后端保留全部痕迹 + 新轮记录 `retry_of` 指向旧轮」。
请评估这个方向，也可以提更好的。

## 问题二：停止之后，那个问题该不该留在上下文里

**用户原话**：

> 当前对话停止后问题是否还保留，我希望是保留。因为常见场景是用户发现提的问题要补充，
> 又不想等这个问题回答完毕再补充，所以才会停止、输入补充问题。所以应该把停止的问题
> 一并加入到上下文里，而这个停止轮的上下文相当于只有用户输入，没有 AI 输出。

**这不是 bug，是当初刻意设计的，现在要改。** 你会在
`_agent_history_turns` 的 docstring 里读到原话（`recommendation_flow.py:3244`）：

> 半轮会被模型读成「一个没回答的问题」，把下一轮拽回去重新回答它。

用户的诉求正好指向那个被担心的行为——**而且用户是对的**：
「停止 → 补充」这个场景里，被停掉的那句和补充的那句合起来才是完整需求。

所以要设计的是**「带进去，但标注清楚」**，不是简单地把中止轮当正常轮：

- 中止轮在 `history_context` 里长什么样？（例如 `<user>：…` 后面跟一个
  `（用户中止了这一轮，AI 未作答）` 的显式标注，而不是空的 `<AI>：`）
- 需求解析 Prompt 要不要相应说明「中止轮的问题是当前需求的一部分」？
  它现在拿最近 5 轮问答判断「用户现在要什么」，多一种输入形态就要多一条说明。
- `AGENT_HISTORY_MAX_TURNS = 5` 的计数口径：中止轮算不算一轮？
- 连续停止多次怎么办？会不会堆出一串没答过的问题？

请给出具体形态和涉及的改动点（含要不要发 parser Prompt 新版本）。

## 问题三：需求澄清的选择框，点一下就提交了

**用户原话**：

> 需求解析时弹出的交互选择框有问题，默认是点击了一个选项即提交。
> 明明提了多个问题，合理的交互应该是用户逐一勾选，再手动提交。

**已定位**：`AgentTurnView.tsx` 的 `ClarifyBlock`——它按
`question.questions[]` 渲染多个问题、每个问题渲染 `options[]` 按钮，
但**每个按钮都是 `onPick(option)` 立即发送**。多问一次只能答一个。

改成「多问多选 + 手动提交」是对的。请一并考虑：

- 提交后拼成的那句话**会成为下一轮的用户消息**，进 5 轮历史、被解析节点读。
  所以拼法要像人话（「只看上市的；净利 1000 万以上」），不能是 JSON 或选项编号。
- 允许某个问题不选吗？（我倾向允许——用户可能只想答一半）
- 这个框来自 agent 的 `ask_user` 工具。工具侧的 payload 形状要不要跟着改
  （比如支持「单选/多选」标记）？如果要改，那是后端 + Prompt 的事，说明清楚。

## 问题四：已经完成的对话，再打开却是黄点，而且在重新回答

**用户原话**：

> 有的对话明明已经完成了，再次打开最近推荐的列表却是又显示的黄点，
> 点击进去发现已经回到刚提问的阶段，又在重新回答。

**这一条我有一个很具体的怀疑，请优先验证它。**

正文的落库只发生在流式**全部走完之后**：`answer-stream` 端点里
`persist()` 定义在 `recommendations.py:1303` 左右，
而调用它的那一行在 `generate()` 的**末尾**。

也就是说——**客户端中途断开（关页签、切网络、甚至只是流的最后一下没收到），
Starlette 关掉生成器，`persist()` 永远不会执行，一个字都不会落库。**

后果链条完全对得上用户描述：

```
用户眼里：字都吐完了 = 完成了
服务端：没有 agent_answer 行
  → _build_recommendation_agent_status 判定 status = "writing"
  → 最近推荐列表显示黄点
  → 重新打开会话触发「补连 SSE」
  → Writer 重跑 = 「又在重新回答」
```

**验证方法**：找一个复现的会话，查它这一轮的消息类型集合——
**有 `agent_brief`、没有 `agent_answer`** 就是这条路径。
（4D 的验收记录里其实走过同一条路径，session `5813667c-...`，
但当时是「故意不连流」，被当作黄点功能的正例记下来了。
同一个机制，在用户看完正文才断开时就变成了这个 bug。）

**修的方向**：服务端在流式过程中自己累积文本，并在生成器结束时
（含 `GeneratorExit` / 客户端断开）落库，**不依赖客户端把流读完**。
请评估这个改法的边界：中止（`agent_aborted`）时**不能**落库，
这一条是 4D 用生产实测确认过的不变式，不能被这次修复破坏。

如果验证下来不是这个原因，请把真实原因查出来——另外两个可疑点是
stale 任务被重新领取，以及 `_build_recommendation_agent_status`
取「最后一轮」的方式（它遍历 user 消息取最后一个 `turn_id`）。
