### 1.2 取数从 `/relations` 换到 `/relations/board`

```
旧：relations.list({ limit: 200 })    ← 上限就是 200，拿到 200 条时无从判断后面还有没有（B-1）
新：relations.board({ ownership, limit: 2000 })
```

新增 `types/api.ts` 的 `RelationBoardCard`（9 字段）与 `lib/api/index.ts` 的 `relations.board()`。

**`BOARD_FETCH_LIMIT = 2000`，没有取满端点允许的 5000**：2000 行瘦卡片约 760 KB（gzip 后约 190 KB），再往上前端分组和 DOM 的成本增长快于收益，那时该上游标分页而不是继续抬数字。真取到 2000 条会在概况条下方**显式告警**「后面可能还有数据，计数不能当全量」——B-1 治的是**静默**，不是那个数字。

### 1.3 列映射（D1）：已成交独立成列

```
初步接触  recommended | interested | in_discussion
深度交流  due_diligence | agreement
已成交    deal_closed                              ← 独立成列
已关闭    paused（琥珀色，排最前）| not_interested | lost   ← 底部抽屉，默认收起
```

看板用自己的 `BUCKET_BY_STATUS`，**没有复用 `isRelationEnded`**——那个函数把 `deal_closed` 算已结束，复用会把成交卡冲进抽屉。`daysSince` / `isStaleRelation` / 状态标签与配色仍复用 `relationLabels.ts`（「已结束不预警」的语义两边一致）。

未知状态兜底进「初步接触」而不是丢卡；抽屉分节次序也做了兜底。**宁可摆错列，不能让卡片凭空消失**。

### 1.4 分组与排序

按施工单 B2-2 实现。两处值得记：

- **组内成员按「深的在前」排**，展开摞先看到推进最远的那条；摞头显示的代表状态也取这个。
- **尾巴块按组整体进退**：`deepest === recommended` 的组进尾巴块，否则留主区。一个组不会被拆到两块里——这是「折叠只是呈现、不改领域模型」的直接推论。

### 1.5 搜索刻意放在客户端

后端 `/relations/board` 有 `q` 参数，**没有用**。原因有两条，第二条是硬的：

1. 数据已整块在内存，按键即出结果，不用重新取数。
2. **交给后端 `q` 就拿不到筛前总数了**，D9 要求的「隐藏 N」就没法算——用户会以为数据丢了。

代价：只能匹配卡片上那三个名字（标的 / 买家 / 意向），匹配不到后端 `q` 额外覆盖的 `last_event_summary` 与 `status_reason`。已写进搜索框 placeholder：「在已加载的卡片里找标的/买家/意向」。

### 1.6 计数纪律（D9）与 URL

- 列头 `N条 · M个标的/意向`，筛选生效时显示**筛后数**并另起一行注明「筛选中，隐藏 N 条」。
- 折叠摞的 `×N` 是关系数，与列头主计数同口径。
- `view` / `ownership` / `sort` / `q` / `stale` 全部进 URL query（默认值不写进 URL，保持地址干净）；搜索防抖 300ms 后再同步，且相等时直接跳过——否则「写 URL → searchParams 变 → 再写」会绕成死循环。

### 1.7 渲染预算（B2-3）

三层挡量：同主体折叠、「已推荐」尾巴块默认收起、抽屉默认收起。剩下的用**纯前端切片**——每块首屏 40 个条目（一个条目 = 一张独立卡或一摞），「显示更多」只改切片长度，不发请求。三个主列 40 × 3 = 首屏 ≤120 个条目，满足 ≤150 的预算。

### 1.8 B3：`?relation=` 深链接已接通（施工单 §5）

卡片链接是 `/targets/{id}?tab=progress&relation={rid}` 与 `/buyer-intents/{id}?tab=progress&relation={rid}`。props 链：

```
TargetDetail        →                        ProgressPanel(initialOpenId)
BuyerIntentDetail   → BuyerIntentWorkspace → ProgressPanel(initialOpenId)
                        新增 progressOpenRelationId 透传一层
```

施工单 §5 标注「买家侧中间层尚未通读，落地时先确认 props 链」——已确认：`BuyerIntentWorkspace` 本来就在传 `activeTab`，照着加一个可选 prop 即可，没有别的中转。

`ProgressPanel` 里 `openId` 初值取 `initialOpenId`，另加一个只在 `initialOpenId` **变化**时才写的 effect——因为从看板换一张卡再进同一个实体时路由不会重挂。只认变化，所以手动关掉抽屉不会被重新弹开。

深链接指向的关系若不在已加载列表里（id 失效、或超出 §1.9 的 100 条上限），`openRelation` 为 null，抽屉不开，页面正常——**不会报错也不会白屏**。

### 1.9 `/relations` 截断提示（施工单 §3 B1-4 遗留的前端半边）

B1-4 说「前端发现返回条数 === limit 即提示数据可能不完整」，`le=200` 本身不必调大。看板改走新端点后，`/relations` 只剩 `ProgressPanel` 一个调用方（按实体查，limit 100，业务上一个标的一般 ≤10 个买家）。现在它在 `items.length >= 100` 时显示琥珀色提示条。

### 3.0 前置：生产数据规模

2026-07-26 B1 验收实测生产只有 **39 条有效关系**。这意味着**折叠摞、尾巴块、「显示更多」这些为规模设计的机制，很可能在真机上一个都触发不到**。要验它们必须造数据：找一个标的，给它挂 ≥2 条同列的关系（名称带「看板验收0726」）。造不出来就如实记「数据不足，未测」，别因为没看到就判缺陷、也别因为没报错就判通过。

- [ ] 响应头有 `content-encoding: gzip`。

## 4. 已知风险与观察项

1. **真机零验证**（§2.3）。布局、粘性列头、滚动容器高度 `calc(100vh-19rem)`、折叠交互，这些静态检查一个都盖不住。这是本轮**最该优先补**的事。
2. **为规模设计的机制在当前生产触发不到**（39 条关系）。折叠摞、尾巴块、「显示更多」、截断告警都要靠造数据才验得了，验收时别把「没看到」当成「没问题」。
3. **搜索口径变窄**（§1.5）。用户如果习惯了用动态摘要里的词搜，会搜不到。这是为「隐藏 N」换的，取舍是清醒的，但需要在真实使用里回收反馈。
4. **57 项断言不在 CI 里，且只覆盖 `boardBuckets.ts`**。仓库无前端测试基建，脚本留在 scratchpad，改这个文件时不会自动跑。建议单开一单引入 vitest 把这份断言收编——不在本单范围内，没有擅自动构建配置。
5. **`ProgressPanel` 被改动了**。它是标的侧和买家意向侧「推进」tab 共用的组件，本轮给它加了 `initialOpenId` 和截断提示。新 prop 可选、默认 `null`，理论上不传就是旧行为，但**这是本轮唯一动到既有业务组件的地方**，回归要真的翻一遍两侧「推进」tab（§3.9 最后两项 + §3.10）。
6. **时间戳解析**沿用 `relationLabels.daysSince` 的既有约定（后端 `::text` 时间戳直接交给 `new Date`），没有改动，但也没有额外加固。
