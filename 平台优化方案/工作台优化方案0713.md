# Match-MA 工作台优化方案（0713）

## 1. 优化目标

本轮优化将“工作台 + 集中复核队列”收敛为更直接的实体管理流程：

1. 删除低使用价值的工作台概览和全局复核入口。
2. 登录后直接进入标的管理，日常工作围绕标的、买家和买家意向展开。
3. AI 解析结果继续自动写入，不再要求用户逐条完成“待复核/已复核”流程。
4. 用户在自己权限范围内的实体详情页查看完整更新记录。
5. 更新记录说明“录入了什么、上传了什么、最终写入了什么、何时录入、由谁操作”。
6. 发现 AI 写入错误时，仅允许撤回该实体最近一次实际生效的更新。
7. 管理员继续通过任务中心处理系统级失败任务；普通用户无需接触任务中心和 Debug 信息。

本轮不删除 `extracted_action`、`action_application_log`、`business_update` 等审计数据，也不修改现有数据库状态枚举。

## 2. 最终产品逻辑

### 2.1 普通用户

- 登录后进入“标的管理”。
- 只能看到权限范围内的标的、买家和买家意向。
- 在列表中查看推荐状态和解析状态。
- 解析失败时，从列表进入详情页重新提交更新或手工补充信息。
- 在详情页“更新记录”查看该实体全部可见历史，不区分是否由本人提交。
- 仅当最近一次有效更新满足安全条件时，可以撤回该次更新。
- 不展示“待复核/已复核”、任务中心、Prompt、Trace、错误堆栈等技术概念。

### 2.2 管理员

- 拥有普通用户的全部实体操作能力。
- 可以查看所有负责人的实体及更新记录。
- 可以撤回任一实体最近一次满足安全条件的有效更新。
- 通过“任务中心”查看、筛选、重试或忽略后台失败任务。
- 从任务详情进入隐藏诊断页定位 Trace、Prompt、Schema 等技术问题。

### 2.3 AI 自动处理

- 用户提交文字和附件后，系统异步解析并自动写入结构化字段。
- 解析过程通过列表“解析状态”反馈。
- 解析成功后生成一条更新批次记录，并记录输入、附件、字段变化、操作账号和时间。
- 解析失败时不产生可撤回的数据变更；错误治理由普通用户重新提交或管理员在任务中心重试。
- 后端保留 extracted action 和 application log，作为审计、诊断和撤回依据，不再作为用户必须完成的复核流程。

- 删除所有仍指向 `/updates/...` 的前端链接。

  - 标的：`/targets/{id}?tab=history`

- 标的详情中写死的“自动更新待复核 / 暂无待复核项”区域

- `business_update` 及其处理接口
- `extracted_action` 及 review status 字段
- `action_application_log` / update log
- `field_value_source`、证据链、附件关系

- 管理员任务中心和隐藏诊断页

## 4. 标的列表状态拆分

原“状态”列同时混合了解析、生命周期和推荐状态。本轮拆成“推荐状态”和“解析状态”两列。

### 4.1 推荐状态

用户界面只展示三种明确状态：

| 判断顺序 | 数据条件 | 展示 |
| --- | --- | --- |
| 1 | `lifecycle_status = sold` | 已售出 |
| 2 | `lifecycle_status = off_market` | 已停售 |
| 3 | `lifecycle_status = active` 且 `recommendation_status = recommendable` | 可推荐 |
| 4 | 其他过渡情况 | `—` |

说明：

- “已售出”和“已停售”都代表不可进入推荐池。
- 新建后正在解析、解析失败或尚未形成推荐资格时，推荐状态显示 `—`，原因由独立的解析状态列表达。
- 后端可继续保留 `not_recommendable`，本轮不迁移、不删除数据库值。

### 4.2 解析状态

标的和买家意向使用相同的展示口径：

| 后台状态 | 展示 | 样式 |
| --- | --- | --- |
| `queued` | 排队中 | 蓝色 + 转圈 |
| `running` | 解析中 | 蓝色 + 转圈 |
| `retry_waiting` | 重试中 | 黄色 + 转圈 |
| `failed` / `parse_failed` | 解析失败 | 红色 |
| `succeeded` 或已有成功解析结果 | 已解析 | 绿色 |
| 从未提交解析 | 待解析 | 灰色 |

标的列表不再仅依赖 `information_status` 推断，应与买家意向一致，优先读取最新解析任务状态；没有任务时再根据实体字段和 `information_status` 回退判断。

## 6. 更新记录重新设计

### 6.1 展示单位

更新记录从“逐字段日志”改为“更新批次”。一条更新批次代表一次用户提交或一次明确的字段更新操作。

批次来源包括：

- 详情页“录入更新”提交的文字和附件
- 新建标的/意向时随创建表单提交的补充内容和附件
- 标的解析任务
- 买家意向解析任务
- 手动字段修改
- 撤回操作

同一批次内的多个 `action_application_log` 聚合展示，不再在列表中散成十几条记录。

### 6.2 每个批次展示的信息

- 录入时间，精确到分钟
- 操作账号姓名
- 操作来源：新建录入、文字更新、附件更新、文字 + 附件、手动修改、撤回
- 当前处理结果：解析中、解析失败、已写入、已撤回
- 用户录入文字摘要，支持展开查看完整内容
- 上传附件数量及文件名，支持下载
- 最终写入字段数量
- 最终字段变化：字段中文名、原值、新值
- 是否为当前最近一次有效更新
- 是否允许撤回及不可撤回原因

不展示：

- 待复核/已复核
- 置信度
- Prompt、Schema、Trace
- 普通用户无法理解的错误码和堆栈

### 6.3 权限规则

- 用户能看到自己权限范围内实体的全部更新记录，不强调“我提交的”。
- 负责人能看到其他账号、管理员和系统对该实体形成的更新记录。
- 管理员能看到全部实体的更新记录。
- 操作账号显示触发该次更新的真实用户；worker 执行写库不应在用户界面显示为操作人。
- 系统自动维护且没有明确用户触发者的记录显示“系统助手”。

## 7. 最近一次更新撤回规则

### 7.1 核心定义

“最近一次更新”定义为：该实体按生效时间排序，最近一笔实际写入了可回退字段、尚未撤回的更新批次。

以下记录不占用“最近一次有效更新”位置：

- 解析失败且没有写入字段
- 仍在排队或解析中
- 仅上传附件但没有写入字段
- 无结构化变化的空更新
- 已被完整撤回的更新

### 7.2 可撤回条件

仅同时满足以下条件时展示“撤回本次更新”：

1. 当前批次是该实体最近一次有效更新。
2. 批次至少包含一个 `can_rollback = true` 的字段变更。
3. 批次尚未撤回。
4. 各字段当前值仍等于该批次写入的新值。
5. 当前用户对该实体具有写权限，或当前用户是管理员。

只要实体之后发生过新的有效字段更新，更早批次均只读，不提供撤回。

### 7.3 撤回单位与结果

- 撤回单位是整个更新批次，不提供单字段撤回。
- 点击后先展示将恢复的字段清单。
- 用户确认后在一个数据库事务内完成全部字段恢复。
- 撤回成功后生成新的“撤回”记录，原更新批次标记为“已撤回”，不删除原日志。
- 撤回后触发搜索文档、embedding 或相关索引重建任务。
- 如果确认前发生并发更新，后端返回冲突，页面提示刷新后重新检查，不强制覆盖。

### 7.4 不可撤回提示

历史批次不显示操作按钮，悬停或展开时可显示简短原因：

- 仅最近一次有效更新可以撤回
- 本次更新未写入字段
- 本次更新已撤回
- 字段已发生后续变化，请手工修正
- 当前账号没有修改该实体的权限

## 12. 后端接口方案

### 12.1 更新批次查询

建议新增通用接口：

```http
GET /api/v1/update-logs/batches
    ?entity_type=seller_target
    &entity_id={entity_id}
    &limit=50
```

响应核心字段：

```json
{
  "items": [
    {
      "batch_key": "business_update:{uuid}",
      "entity_type": "seller_target",
      "entity_id": "uuid",
      "source_type": "business_update",
      "source_id": "uuid",
      "input_summary": "用户录入内容摘要",
      "raw_input": "完整录入文本",
      "attachments": [],
      "operator_user_id": "uuid",
      "operator_name": "张三",
      "submitted_at": "2026-07-13T10:26:00Z",
      "applied_at": "2026-07-13T10:27:00Z",
      "status": "applied",
      "changes": [],
      "changed_field_count": 6,
      "is_latest_effective_batch": true,
      "can_rollback": true,
      "rollback_block_reason": null
    }
  ],
  "total": 12
}
```

批次聚合键优先级：

1. 有 `business_update_id`：按 business update 聚合。
2. 直接解析任务：按 `source_type + source_id(background_job_id)` 聚合。
3. 手动字段修改：按同一请求生成的 operation id 聚合；若当前日志缺少 operation id，第一版可按单条日志展示。
4. 撤回：按 rollback operation id 聚合。

### 12.2 批次撤回

建议新增接口：

```http
POST /api/v1/update-logs/batches/{batch_key}/rollback
```

请求：

```json
{
  "entity_type": "seller_target",
  "entity_id": "uuid",
  "reason": "AI解析结果有误"
}
```

后端必须重新判断“是否为最近一次有效更新”和字段当前值，不能只依赖前端传入的 `can_rollback`。

### 12.3 解析状态

标的补齐与买家意向一致的最新解析状态接口消费方式：

- 列表优先批量返回最新任务摘要，避免每行单独请求造成 N+1。
- 若第一版暂不改列表接口，可先复用 `/seller-targets/{id}/parse-status`，但应尽快改成列表聚合。
- 仅对排队中、解析中、重试中的行轮询。
- 成功或失败后停止轮询并刷新当前行。

## 13. 数据与审计规则

- 不删除任何历史 business update、action、application log 或 attachment。
- 撤回只是写入反向变更和撤回标记，不删除原变更。
- “操作账号”取用户触发入口的账号，而不是执行任务的 worker/system user。
- 附件删除规则保持现状；撤回更新不删除附件。
- 附件下载权限跟随父实体可见性。
- 更新记录查询和撤回接口必须复用 owner scope 权限判断。
- 推荐豁免仅允许查看推荐关联实体，不自动赋予修改或撤回权限。

## 14. 异常与边界

### 14.1 一次更新影响多个实体

- 同一个 business update 同时更新多个实体时，每个实体详情只展示作用于自己的字段变化。
- 在每个实体中分别判断最近一次有效更新。
- 撤回某个实体的批次，只撤回该实体字段，不影响同批次中的其他实体。

### 14.2 更新只写入部分输入信息

- 不引入“部分应用”产品状态。
- 更新记录同时展示原始录入、附件和最终写入字段，用户可自行判断哪些内容未形成结构化字段。
- 未写入的内容不生成额外待复核任务。

### 14.3 解析失败

- 记录原始录入、附件、操作人、时间和“本次未写入字段”。
- 普通用户看到简短提示和“重新录入更新”。
- 管理员在任务中心查看错误码、原始错误和 Trace，并决定重试或忽略。

### 14.4 后续修改冲突

- 如果最近批次写入后又有任何字段变更，最新有效批次会随之变化，上一批次自动失去撤回资格。
- 并发情况下以数据库事务内的当前值校验为准。
- 不提供强制撤回给普通用户；管理员也默认不强制覆盖，必要时手工修正。
