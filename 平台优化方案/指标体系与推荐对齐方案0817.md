| 施工单 | 状态 | 证据 |
|---|---|---|
| 重构 0806（第一轮，标的侧四列） | **已执行** | `major_risk_flags_json` / `acceptable_transaction_structures_json` / `main_products_text` / `stock_code` 均在注册表且有闭集；`operation_stability_status` 已消失 |
| 二轮 0807 | **已执行** | 交易所 8 值闭集两侧就位；`GROUPS` 只剩 4 组（技术与团队已解散）；`management_retention_possible` 已归 `deal_terms` |

**开场白里有三处前提已经不成立**，后面的结论按实况重写：

1. **`earnout_dependency_status` 不再有 DB 列。** 它在迁移 `016_indicator_system_round_two.sql:118` 被 `drop column` 了（二轮施工单 §2.4 的四删之一，理由是「0% 且无买家对手方」）。所以对赌那一项不是「补进注册表」，而是「要不要新建一列」——成本完全不同。

2. **`transaction_types_json` 不是「补声明即可」。** 它有 27/44 的存量数据，而那些值**不在标的侧闭集的语义轴上**（详见 §4.2）。只补 `operator` 会让这 27 个需求全部筛空。

3. **`max_premium_rate` 已经是「条件类」字段。** 它的 `default_effect='preferred'` 是非空的，而 `_buyer_intent_field_contract()`（`buyer_intent_parse.py:472`）正是用 `default_effect is not None` 判断 `is_condition`。所以"不进筛选"不能只是"不给 operator"。

   > **落地时修正（0817）**：起初的结论是"把 `default_effect` 也清掉"。**那是错的**——`default_effect` 还在驱动需求单链路的规则打分（`recommendation_conditions.condition_effect()` 的兜底就是读它），清掉等于静默拆掉三个打分维度，`test_net_margin_and_ps_are_derived_from_revenue_and_valuation` 当场挂。正解是让两个标志各管一件事：`default_effect` = **需求单链路的打分强度**，`screening` = **进不进初筛 schema**，然后把 `is_condition` 从读前者改成读后者。详见施工单 §11.2。

## 三、两个必须先于三项硬阻塞解决的判决

### 3.1 `requirement_capability` 与「缺失即出局」直接矛盾，且 `unknown` 是多数派

框架 §4.2 把这个算子定义成 `t.<col> <> 'no'`，框架 §2 的铁律是「缺失即出局」。两条在 `unknown` 上冲突。

**SQL 三值逻辑救不了这一处**，因为这些列在 DB 里是 `not null default 'unknown'`（`001_baseline.sql:801-813`）——值不是 NULL，是字符串 `'unknown'`，`'unknown' <> 'no'` 为真，行照样通过。

生产实况（标的侧 71 个）：

| 标的列 | `unknown` | 占比 | `yes`+`likely` |
|---|---:|---:|---:|
| `accepts_relocation` | 71 | **100%** | 0 |
| `accepts_return_investment` | 71 | **100%** | 0 |
| `accepts_minority_investment` | 70 | 99% | 1 |
| `management_retention_possible` | 68 | 96% | 3 |
| `can_consolidate` | 42 | 59% | 23 |
| `can_control` | 40 | 56% | 25 |

按 `<> 'no'`：买家要求控股，40 个「不知道能不能控股」的标的照样进候选，另外四条则是**恒真条件**，一个都筛不掉。

**决定性的论据不是"谁更严"，是 `excluded_by_condition` 那个拆分。** 框架 §4.3 把它称作"这个设计的核心"——agent 靠「字段为空 N 家 / 确实不符 M 家」决定放宽哪一条。按 `<> 'no'`，`unknown` 的行**静默通过**，永远不会出现在"字段为空"那一桶里；agent 看到的只有「加了控股条件，89 → 65」，无从区分"条件太严"与"数据没录"。**放宽策略的唯一依据被这个算子悄悄抹掉了。**

**判决：算子改为 `t.<col> in ('yes','likely')`。** `unknown` 归入"字段为空"，进 `excluded_by_condition` 的空值桶。

配套是按数据把六条分成两组——**不是删字段**，列、成对关系、`target_column`、`operator`、`default_effect` 全留着，**只动买家侧的 `screening`**，等标的侧有数据了改回来是一行：

| 买家条件 | 标的侧可用（yes+likely） | 处置 |
|---|---:|---|
| `requires_control` → `can_control` | 25/71 | 保留 `screening=True` |
| `requires_consolidation` → `can_consolidate` | 23/71 | 保留 `screening=True` |
| `accepts_minority_investment` | 1/71 | 按 §4.3 置 `screening=True`，但施工单标注「今天一带只剩 1 家」 |
| `requires_relocation` → `accepts_relocation` | **0/71** | 降级：买家侧 `screening=False` |
| `requires_return_investment` → `accepts_return_investment` | **0/71** | 降级：同上 |
| `requires_team_retention` → `management_retention_possible` | 3/71 | 降级：同上 |

> **落地时修正（0817）**：**标的侧那三列的 `screening` 不能跟着关。** `recommendation_flow.py` 的需求单打分器仍在读它们（`_scorer_reads()` 证实），关掉会当场挂守卫。根因是 `screening` 在两侧本来就是两件事——标的侧答「有没有人比对我」（喂信息页角标），买家侧答「这一条进不进初筛 schema」。同名不同义但各自自洽；新守卫 `test_seller_screening_matches_who_points_at_it` 按这个定义两个方向都守。详见施工单 §11.1。

这三条降级正是二轮施工单 §六第 4 项（「两对空转指标的处置」）留的口子，现在有判据了：**它们不是"筛得太松"，是从来没筛掉过任何一家**，却占着信息页的位置和模型 schema 的槽位。

> 补数据可行吗？这六列的 `writable_by` 都是 `{parse, manual}`，**不含 research**——存量补不了，只能靠新解析质量和人工。这一条决定了它们短期内不会自己变好。

### 3.2 闭集"一一对应"是个错规则，正确的规则是三类

审计 ⑦ 报了 5 对不一致，逐条看只有一类是缺陷：

| 对 | 差异 | 判定 |
|---|---|---|
| `acceptable_listed_status_json`(3) → `listed_status`(4) | 标的多 `unknown` | ✅ **有意的子集**。缺失即出局下，买家不该能选"未知"；9/71 个 `listed_status='unknown'` 的标的筛不进任何上市状态条件，这是预期行为 |
| `requires_relocation` / `requires_return_investment` / `requires_team_retention` → 三个 `accepts_*` | 要求侧 `required/preferred/not_required/unknown` vs 能力侧 `yes/no/unknown/likely` | ✅ **有意的异轴**。框架 §4.2 已决定 schema 里只出布尔（"要求控股=是"），买家侧那个四值强度枚举**不进 SQL** |
| `unacceptable_risk_flags_json`(4) → `major_risk_flags_json`(5) | 标的多 `none` | ✅ **有意的子集**（见 §4.1） |

所以配对审计测试的规则应写成三档，而不是等号：

1. **相等**：`in` / `overlap` 类，两侧词表必须一致（现金流、盈利、控股、并表、少数股权、上市地）
2. **子集**：买家闭集 ⊂ 标的闭集，差集必须是 `unknown` 或状态值（上市状态、重大风险）——**差集里出现业务取值就是缺陷**
3. **异轴**：`requirement_capability` 类，两侧词表无关，只校验各自内部合法

不写这三档，测试一开就在有意为之的地方全红，然后被人关掉。

### 3.3 顺带查出两处口径缺陷（已在生产、静默失效）

审计查不出的第三类：声明齐备、算子正确、单位对不上。

**（a）`min_net_margin` 的 `target_column` 口径错了。**

```
买家 min_net_margin 存的是百分数：  8.0000 / 1.0000
标的侧 current_net_profit_yuan / current_revenue_yuan 算出来是分数：0.0164 / 0.1000 / 0.1692
```

`0.1692 >= 8` 永远为假——**这个条件今天筛出来必然是空集，且不报错**，正是开场白警告的那一类。修法是 SQL 模板乘 100，或把 `target_column` 写成带口径的表达式。

**（b）`desired_equity_ratio_min` 有一行单位污染。** 取值里混着 `0.2990`（其余是 `51 / 100 / 25 / 60`）。原话是「上市公司29.9%及以下」，被存成了分数。`gte` 比 `transfer_ratio_max`（60/80，百分数）时它通过一切。这是脏数据不是声明错，但同一个条件上并存两种口径，修声明修不掉它。

其余四对口径已核对一致：`max_debt_ratio`↔`current_debt_ratio`（都是百分数）、`max_pe`↔`pe_ratio`（都是倍数）、`desired_equity_ratio_*`↔`transfer_ratio_*`（都是百分数）、`max_valuation_yuan`↔`valuation_yuan`（都是元）。

**关于 `max_ps` 与 `min_net_margin` 的取舍，我的结论与框架 §7.5.4 不同。** 那里写的是"建议剔除两个：`min_net_margin`（靠现算）、`max_ps`（口径本身是坏的）"。实际是：

- `min_net_margin` **应当保留**。两个分母分子列填充率 77% / 82%，SQL 一行 `current_net_profit_yuan / nullif(current_revenue_yuan,0)`，现算完全成立——它的问题是口径写错了（上面的 a），不是不该算。
- `max_ps` **应当剔除**，但理由要说准：不是"现算"的问题，是 `market_cap_yuan` 只有上市公司有（11/71），非上市标的分子恒为 NULL。**PS 这个口径对非上市标的物理上不存在。** 买家侧 0/44 也印证了没人用。

## 四、三项硬阻塞的最终形态

### 4.1 买家侧重大风险容忍 → 新增 `unacceptable_risk_flags_json`

| 项 | 结论 |
|---|---|
| 指标名 / 列名 | 不接受的重大风险 / `unacceptable_risk_flags_json` |
| 归类 | 可枚举定性（多值闭集） |
| 枚举全集 | `litigation` 涉诉 / `equity_frozen` 股权冻结 / `enforcement` 被执行 / `violation` 违规违法 —— **4 值，不含 `none`** |
| 对手方 | `major_risk_flags_json` |
| 算子 | `not_overlap` |
| 缺失时 | `[]` = 未提及 = 不带这个条件 |

**为什么买家侧不含 `none`：** 标的侧的 `none`（已核查无重大风险）是**核查状态**不是**风险类型**，"不接受已核查无风险"讲不通。所以两侧是 §3.2 的第 2 档"子集"关系，差集恰是状态值，合规。

**三态由代码派生，SQL 只有一条路径**（按开场白的要求）：

```
未提及      → []
不接受全部  → ["litigation","equity_frozen","enforcement","violation"]   ← 落库时展开
不接受特定  → 其子集
```

**SQL 模板必须带前半段，通用 `not_overlap` 模板不够：**

```sql
t.major_risk_flags_json <> '[]'::jsonb
and not exists (
  select 1 from jsonb_array_elements_text(t.major_risk_flags_json) f
  where f.value = any(:vals)
)
```

没有第一行，`major_risk_flags_json = []`（**未核查**）的标的会通过——"没查过"被当成"干净"，方向恰好是危险的那一边。这与迁移 015 注释里定的三态语义（`[]` 未核查 / `["none"]` 已核查无风险 / 其余已核查有风险）一致，也是缺失即出局在这一条上的正确落法。

**现实提醒（必须写进施工单）：** 标的侧今天只有 **2/71** 有值。这个条件一带就只剩 2 家。所以：

- 它的 `writable_by` 已含 `research`（0806 §四已确认调研会自动接手），存量靠调研回填是唯一可行路径；
- 在存量补齐前，agent 侧应把它当 `preferred` 而非 `required`。

`major_risk_tolerance_summary` **保留为明细载体**，与 `risk_summary` ↔ `major_risk_flags_json` 完全同构。生产 10 条里 2 条就是枚举原话（"不接受标的公司有重大风险（涉诉、冻结、执行、违规违法）"）→ 直接落 4 值全集；其余 8 条是定性诉求（对赌、知识产权纠纷、环保税务、质量事故）→ 归深评。

### 4.2 `transaction_types_json` —— 需要迁移，不是补声明

存量 27/44 的取值里混着**三个正交轴**：

| 轴 | 实测取值 | 归属 |
|---|---|---|
| 交易结构 | 老股转让、定增、资产收购、吸收合并、借壳重组、并购 | ✅ 标的侧闭集就是这一轴 |
| **支付方式** | 现金、股份、现金+股份、全现金收购、现金+债务融资、资产换股、交叉持股 | ❌ 标的侧无对应列 |
| **控制权诉求** | 控股收购、少数股权、战略投资、战略参股、项目投资、成长股权投资 | ❌ 已由 `requires_control` / `accepts_minority_investment` 表达 |

只补 `operator='overlap'`：模型下一版会填闭集值，但**存量 27 条一条也匹配不上闭集**，带上这个条件的需求全部筛空。所以必须配存量重写。

| 项 | 结论 |
|---|---|
| 指标名 / 列名 | 可接受交易结构 / `transaction_types_json` |
| 归类 | 可枚举定性（多值闭集） |
| 枚举全集 | `equity_transfer` / `capital_increase` / `asset_purchase` / `merger` / `other`（与标的侧**完全相等**） |
| 对手方 | `acceptable_transaction_structures_json` |
| 算子 | `overlap` |
| 缺失时 | `[]` = 未提及 = 不带条件 |

**存量映射（写进迁移）：**

| 原值 | 映射 |
|---|---|
| 老股转让、股权转让 | `equity_transfer` |
| 定增、增资控股、增资扩股 | `capital_increase` |
| 资产收购 | `asset_purchase` |
| 吸收合并、并购、借壳重组 | `merger` |
| 支付方式与控制权诉求那两轴的全部取值 | 不进闭集 |

映得出结构码的约 **10/27**，其余 17 条重写后为 `[]`。

**这 17 条的信息不能静默丢。** 迁移把重写前的原数组按顿号 join 成中文原话，写进 `transaction_type`——那个正在退役的 text 标量列，从"兼容字段"改判为**「交易方式原文」**（解析溯源 + 深评读），与 `industry_primary` 的定位完全一致。零新列。

> **支付方式是真实的一票否决维度**（全现金 vs 换股在并购里差别巨大），但标的侧没有对手方列。按成对铁律，**本轮不建**，记进 §7 的"下一轮候选对"。不要只加买家侧——那正是开场白第一条铁律禁止的事。

**标的侧连带：** `acceptable_transaction_structures_json` 现在 `screening=False`（审计 ⑧），要改 `True`，否则信息页角标与实际不符。它今天 1/71，`writable_by` 是 `{parse, manual}`，**调研补不了**。

## 五、四项判断的结论

### 5.1 对赌 → **两侧都归深评**

- 标的侧 `earnout_dependency_status` 已在迁移 016 删除（删除前 **0/70**）。要接就是新建列，不是"补进注册表"。
- 买家侧 `earnout_requirement` 是 **43/44 `unknown`**，唯一一条真值是 `required`。
- 语义上它是**谈判条款**不是标的的既有属性——在 LOI 阶段定，不会写在标的材料里。这解释了为什么标的侧那一列建了之后 0 填充。
- 旁证：`major_risk_tolerance_summary` 的生产取值里出现"接受3年期业绩对赌与核心团队锁定"、"不强制业绩对赌"——**对赌正在被写成散文**，这是定性诉求的形状，不是枚举的形状。

**处置**：不新建标的列。`earnout_requirement` 保留列（NOT NULL、无成本），注册表标注「不参与匹配，供深评阅读」，值随定性诉求进深评载荷。

### 5.2 毛利率 → **降级为深评项**

- 买家侧 `min_gross_margin` **1/44（2%）**，唯一取值 25.0。
- 标的侧无毛利率列，也无营业成本列，**推算不出来**。
- 新建列意味着解析要能提毛利。参照实况：连"利润总额"这种财报常规项都只有 **6%**，新列的落地填充率会在 0–5% 之间。
- 缺失即出局下，2% 的买家条件比 ~0% 的标的列，那一个需求的候选池会被打成 0。

**处置**：清 `default_effect`，标注描述项。**不新建标的列。**

> 替代路径已经存在：`min_net_margin` 走的是同一个业务诉求（盈利能力门槛），两个来源列填充率 77%/82%，修好口径（§3.3a）就能用。真要做毛利率，必须**标的列 + 买家条件 + 解析提示词一次做齐**，不能只留买家侧。

### 5.3 主要产品 / 细分方向 → **这一对明确划给深评**

- 买家 `industry_focus_tags_json` **13/44（30%）**——填充率不低。
- 标的 `main_products_text` **2/71（3%）**，自由文本。
- 做受控字典不可行：实测取值的粒度天差地别——「能源/电力」（比一级行业还粗）与「车载智慧座舱/ADS芯片」「钙钛矿/异质结光伏组件材料」（比二级行业细两层）在同一个字段里。收敛成闭集要么丢义、要么把字典撑爆，而 L2 行业字典本身是有维护成本的资产。

**处置**：两侧都标注描述项，内容必须进深评载荷（`industry_focus_tags_json` 作为定性诉求逐条判定，`main_products_text` 进标的画像）。

> **但这里有一个真实的召回损失，属于解析质量而非 schema：** `industry_l2_json`（活条件，`op=overlap`）只有 **3/44**，而 `industry_focus_tags_json` 有 13/44。实测标签里「半导体」「储能系统」「医疗器械」「集成电路」这些**本来就在 L2 字典里**。解析器把它们直接倒进了自由标签，没有先过字典。修法是解析侧「先试 L2 字典，落不进再进标签」——这是一条活条件的召回提升，成本在提示词。

### 5.4 日期字段 → **要修，但不按原样修，且不在本轮**

- 两列 DB 类型都是 `text`（`001_baseline.sql:828-829`）。
- `valuation_date` **9/71**，九条全是 ISO。
- `asking_price_date` **3/71**，**三条里两条不是日期**：「2025年二季度」「2026年一季度」。

直接 `text → date` 会丢掉那两条的真实口径——"二季度"是顾问拿到的原话，转成 `2025-06-30` 是我们替他做的推断。

**正确形态是照抄 `financial_period_label` / `financial_period_end_date` 那一对**：text 列留原话，旁边加一个 `date` 列存换算值。

**但本轮不做**，三条理由：

1. 这两列**都不是买家条件**，两侧都没有对手方，也没人提议要建；
2. 真正需要日期比较的是「财务数据新鲜度」（框架 §7.5.3 的系统级过滤），而**那一列已经是 `date` 类型了**（`financial_period_end_date`）；
3. 填充率 13% / 4%，改造收益低于两次发版加全服务切读的风险（这也是 0806 §三对它的原判，理由未变）。

> **但 `financial_period_end_date` 有个必须本轮修的问题：它写得进、看不见。** 列在注册表、`writable_by` 含 parse+research、进了 `seller_target_fact_columns()` 的 SELECT，但**不在 `SellerTargetOut`**（`seller_targets.py:122` 只有 `financial_period_label`），也不在 `api.ts` 与 `fieldLabels.ts`。框架打算拿它做新鲜度过滤，而顾问在信息页上看不到、也改不了这个日期。这是三行的事，本轮补。

## 九、对推荐线的交付清单

四项声明定稿后，schema 生成器可以开工。要一并带走的**三条不能从注册表读出来的约定**：

1. **`requirement_capability` 的 SQL 是 `t.<col> in ('yes','likely')`**，不是 `<> 'no'`（§3.1）。
2. **`not_overlap` 用于重大风险时必须带"已核查"前置**：`t.major_risk_flags_json <> '[]'::jsonb and not exists(...)`（§4.1）。
3. **`min_net_margin` 的比较需要 ×100 归一**，因为买家侧存百分数、标的侧现算是分数（§3.3a）。**尚未修**——它在 SQL 模板侧，本轮没动那一层。

4. **`overlap` / `not_overlap` 有两种目标形状**：行业是 `{l1,l2}` 对象数组，重大风险与交易结构是扁平字符串数组。0817 落地时发现 `screening_sql.py` 把这两个算子写死成了行业路径，两个新字段因此**静默生成打在 `industry_pairs_json` 上的 SQL** —— `overlap` 恒不命中（候选池恒空）、`not_overlap` 恒命中（条件恒真），两个方向都不报错。已在 `_array_clause()` 里按 `target_column` 分派修好，并补了守卫 `test_every_clause_reads_the_column_it_declared`；**改坏它之前，21 个既有用例全绿**。详见施工单 §11.3。

以及一份"今天带上就几乎筛空"的清单，供 agent 的调用策略参考：
`min_total_profit_yuan`(6%)、`desired_equity_ratio_*`(1–3%)、`listing_market_region`(3%)、`unacceptable_risk_flags_json`(3%)、`transaction_types_json`(1%)、`accepts_minority_investment`(1/71)。
