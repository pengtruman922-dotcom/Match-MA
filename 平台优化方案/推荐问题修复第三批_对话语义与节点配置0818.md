## 一、中止轮进上下文（问题二）

### 1.1 现状是刻意设计，不是 bug

`_agent_history_turns` 只收同时有 user 与 `agent_answer` 的完整轮
（`backend/app/services/recommendation_flow.py:954`，docstring 明写整轮丢弃）。
生产 Prompt 也同步写死了：parser `v0.3.0`「最近 5 轮已经完成、未中止」；
Agent `v0.2.1`「最近 5 轮已完成对话」。节点目录里也写了
（`backend/app/registry/nodes.py:247`「中止的轮次不带」）。

用户现在要支持「停止 → 补充」，所以改设计。

### 1.2 改成什么

**只保留中止轮的用户原话，明确标记 AI 没有回答。**

```text
<aborted_user_turn>
<user>：江苏制造业，净利润1000万以上
<turn_note>用户主动中止了该轮，AI未作答；此输入仍属于当前需求，请与后续补充合并理解。</turn_note>
</aborted_user_turn>
```

- **不生成空的 `<AI>：`**
- **不带入已经流出的半截正文**

### 1.3 计数口径

- 中止轮算一轮，占最近 5 轮额度
- 「最近 5 轮」统一指：**已完成轮 + 主动中止轮**
- 后端真实失败、Writer 未完成但**未中止**的半轮 —— 仍不进历史
- 连续中止多次时最多保留最近 5 条，按时间顺序交给 parser；本轮消息仍单独传入
- 本轮说「前面都不要了 / 重来」时，仍由 parser 按现有重置语义处理

### 1.4 要发两个新 Prompt 版本

照 `scripts/publish_*_prompt.py` 的既有写法写发布脚本：

- **`recommendation_query_parser v0.3.1`**：明确中止轮属于需求的一部分；
  ⚠️ **补一句「若后续消息与中止轮原话冲突，以后续为准」** ——
  用户点停止可能是「跑太久不要了」，也可能是「我说错了」。这一句零 UI 成本地覆盖后者，
  不加的话「我说错了」那种停止会把错误需求带进后续所有轮。
- **`recommendation_agent_to_target v0.2.2`**：明确只能消费 parser 的完整快照，
  **不能把中止轮当成一个待单独回答的问题**。

顺序：**Prompt 可以先发布再部署代码**。旧代码不会产出 `<aborted_user_turn>` 标签，
新 Prompt 里描述该标签的段落在旧代码下是「描述了一个永不出现的输入」，安全。
（Prompt 走设置页或 `/model-config/prompts` API，即时生效，**不写 prompt seed 迁移**。）

同步改 `backend/app/registry/nodes.py:247` 那句「最近 5 轮已完成对话的原文（中止的轮次不带）」。

**不改公开 API、不迁移数据库。**

## 二、节点超时语义统一

### 2.1 现在有四层各自为政

| 层 | 当前值 | 真实含义 |
|---|---:|---|
| 前端轮询 | 361 秒 | **第二批已删除** |
| Agent 墙钟预算 | 240 秒 | 只在工具调用**之间**检查（`jobs/handlers/recommendation.py:67`） |
| 节点 `timeout_seconds` | 30~600 秒 | **socket 超时，不是总时长**（见下） |
| worker stale | 1800 秒 | 基础设施保护（`scripts/railway_start.py:22`） |

### 2.2 施工前必须理解的关键事实

`timeout_seconds` 被直接喂给 `urlopen(timeout=…)`
（`backend/app/ai/llm_client.py:89` 与 `:186`）。那是**每次 socket 操作**的超时：

- **非流式**：服务端生成完才发字节，读阻塞 ≈ 总时长，近似成立
- **流式**：**每来一个 token 计时器就重置**。配 180 秒的 Writer，
  只要 token 一直滴，跑 10 分钟也不超时

所以「把 `timeout_seconds` 重定义为节点整体超时」**不是改个文案就完事**，
流式路径必须自己算 deadline。

### 2.3 要做的

1. 把 `timeout_seconds` 重新定义为「**节点本次执行的整体超时**」，
   从节点真正开始执行计时，**不含队列等待**
2. **流式路径自己算 deadline**：`stream_openai_compatible_chat` 的循环里比对开始时间，
   超了主动断开并抛 `LlmCallError`。注意 `finally: response.close()` 仍要执行
3. 多次调用模型的 Agent：整个工具循环共用节点配置的总预算，
   每次请求的超时取 `min(节点配置值, 剩余时间)`，替换掉写死的
   `AGENT_WALL_CLOCK_BUDGET_SECONDS = 240`
4. ⚠️ **改语义必须同时改值。** 生产 Agent 节点现配 **600 秒**，而真实总预算是 240 秒。
   只改语义不改值 = 把一轮从 4 分钟**偷偷放宽到 10 分钟**，用户等待反而更差。
   **把 Agent 节点压到 240~300 秒。**
5. **需求解析节点：不要直接跳到 300 秒。**
   现在代码默认 30 秒（`nodes.py:309`）、生产也是 30。30 确实偏紧（带附件文本时），
   但这个节点**有降级路径** —— 超时后 `parser_status=fallback`，
   Agent 只能无条件初筛或提问（`jobs/handlers/recommendation.py:104`）。
   **超时越长，降级来得越晚**，而一轮总耗时中位数才 105 秒。
   → 设 **90~120 秒**；若坚持 300，必须配一道软预算（超 60 秒就走 fallback 继续）。
   **代码默认值和生产配置两处都要改** —— 已建配置不会继承新的代码默认值。
6. trace 记录：节点配置的超时值、实际耗时、是否超时、超时发生在第几次调用、是否采用降级结果
7. 各节点超时后的降级口径写清楚：
   - 需求解析 → 写 `fallback` 并继续
   - 深评 → 保留真实初筛候选，标记深评不可用
   - Agent → 用已获得的候选强制收口；完全没有可用结果时才失败
   - Writer → 规则兜底正文
8. worker 的 1800 秒 stale **不进 AI 节点设置**（它是基础设施保护），
   但设置页要写一句它与节点超时的区别
9. 第一批上线后若 heartbeat 已稳定运行一轮，可以考虑下调 `--stale-after`；
   **没观察过就不要动**

### 8.6 ⚠️ 本批留下的回归（0820 用户实测发现，已修）

**§2.3 那个「每次请求取 `min(节点配置值, 剩余时间)`」的写法，在预算耗尽时会把收尾
调用饿死。**

收尾调用是「预算已经用完」这件事的**产物** —— `_agent_early_stop` 正是在预算见底
时才发出「别再调工具了，拿现有候选给最终 JSON」。再用同一份见底的预算去算它的
超时，剩余时间必然接近 0，它就拿到下限（当时写的 5 秒）、必然超时、整轮硬失败。
**这条路径在生产上 100% 失败**，而且报出来的错是 `LLM request timed out or dropped
after 5s`，把真正的原因（预算用完了）盖得严严实实。

本批之前它拿的是节点配的 600 秒 socket 超时，所以收尾能跑完 —— 纯回归。

生产证据（会话 `eb82582d`，矿业+电子信息，连挂两轮）：

| turn | job | trace timeout |
| --- | --- | --- |
| `905effe3` | failed，`after 5s` | `configured 300 / elapsed 427.161 / exhausted true` |
| `828079b1` | failed，`after 5s` | `configured 300 / elapsed 341.735 / exhausted true` |

同时暴露出两件本批没算到的账：

1. **深评一次就要 200~250 秒**（实测 201s / 254s），占满 300 秒预算的三分之二以上。
   §2.3 把 600 压到 300 时没算这笔账 —— 多组需求跑完一次深评预算就见底，每一轮都
   得走强制收口。0820 已把 Agent 预算放回 **600 秒**（用户拍板）。真想压下来得先压
   深评的候选量或把深评分片，不是压 Agent 的总预算。
2. **§2.3 第 6 条那个 trace 摘要里的 `elapsed_seconds` 是错的**：成功路径传的是
   `loop.usage.latency_ms`，也就是**各次模型调用耗时之和**，不含工具执行 —— 而预算
   是墙钟。本批验收时看到的 `32.834` 就是这个数，看着合理所以没深究。修复后墙钟与
   模型耗时分开记（`elapsed_seconds` / `llm_seconds`），差值就是工具吃掉的时间。

修复提交 `7657af9`，同批还修了另外两个与本批无关的问题（三个子节点从不写 `ai_trace`、
加粗里的站内链接渲染不出来）。0820 复跑同一条矿业需求：`job_status=succeeded`，
正文 1340 字带 8 个可点链接，trace = `configured 600 / elapsed 351.082 /
llm_seconds 122.658 / wrapup_reserve 60 / exhausted false`。
