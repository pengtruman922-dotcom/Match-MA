# 买家信息字段改造施工单（2026-08-24）

## 一、这一单要解决什么

`buyer_party` 现在是「一个名字 + 一个负责人」。生产 39 条主体里
`industries_json` / `industry_l2_json` / `contact_*` **全部 0%**，
`GET /buyer-parties/{id}` 详情**不投影任何业务字段**（实测返回 15 个键，业务相关零个）。

后果是系统里没有任何地方能回答「这家买家自己是做什么的」，
而这正是「为标的找买家」推荐的第一判断依据。

本单把 `buyer_party` 改造成能承载推荐维度的信息载体。

### 维度与字段的对应（设计依据，不要自行增删）

| 维度 | 判断依据 | 字段 |
| --- | --- | --- |
| 产业协同度 | 买家主营 vs 标的业务 | `business_tags_json` + `business_summary` |
| 财务赋能度 | 企业性质 | `ownership_type` |
| 成本承担能力 | 体量与现金 | `market_cap_yuan` / `valuation_yuan` / `current_revenue_yuan` / `current_operating_cash_flow_yuan` |
| 决策审批效率 | 企业性质 | 同「财务赋能度」，共用一列 |
| 管理文化匹配 | 定性 | 本轮**不做**（已决定推迟） |

**真正参与判断的只有 6 个字段**：业务标签、业务说明、企业性质、市值/估值、营收、现金流。
其余新增列都是让「自动刷新」和「调研」成立的支撑列（时间戳、股票代码、上市地），
不是新的匹配维度。**不要借这一单把买家表做成宽表。**

## 三、字段设计

### 3.1 新增 17 列

#### 基本信息（8 列）

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `location_province` | text | nullable | 三级地区，复用标的侧口径 |
| `location_city` | text | nullable | |
| `location_district` | text | nullable | |
| `ownership_type` | text | **not null default `'unknown'`** + CHECK | 企业性质 |
| `listed_status` | text | **not null default `'unknown'`** + CHECK | 上市状态 |
| `stock_code` | text | nullable | 自动刷新的锚点 |
| `listing_exchange` | text | nullable + CHECK | 上市地（交易所） |
| `our_contact_name` | text | nullable | **我方**对接人。用 text 不用外键：对接人可能没有系统账号 |

> 现有的 `region_province` / `region_city` 由 `location_*` 取代。
> 迁移里先把存量值搬过去再删旧列（存量 14/39 有省份，别丢）。

#### 业务信息（2 列）

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `business_tags_json` | jsonb | not null default `'[]'::jsonb` + CHECK 是数组 | 业务标签，目标 ≤5 个（数量由解析侧控制，DB 不限） |
| `business_summary` | text | nullable | 业务说明，目标篇幅 200 字左右 |

#### 财务信息（7 列）

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `market_cap_yuan` | numeric(20,2) | nullable | 市值 |
| `market_cap_as_of` | **date** | nullable | 市值的行情日期 |
| `valuation_yuan` | numeric(20,2) | nullable | 估值 |
| `valuation_date` | **text** | nullable | 估值时点，与标的侧同名列同型（存中文标签如「2025年一季度」） |
| `current_revenue_yuan` | numeric(20,2) | nullable | 营收 |
| `current_operating_cash_flow_yuan` | numeric(20,2) | nullable | 经营现金流 |
| `financial_period_label` | text | nullable | 营收与现金流**共用**，同一份定期报告 |

**为什么 `market_cap_as_of` 是 date 而另两个是 text**：
期间标签是人写的中文（「2025年一季度」），行情日期是机器给的确定日子。
只有 date 才能判断「这个市值过没过 7 天」，而自动刷新要靠这个判断。
这个差异是刻意的，不要为了「统一」把它改成 text。

**四个财务列名与标的侧一字不差是刻意的**：
`MONEY_YUAN_FIELDS`（`jobs/handlers/common.py:48`）的万元/亿元归一、
`CORE_FINANCIAL_FIELDS`（`services/research_apply.py:42`）配套的
「核心财务事实必须带期间」守卫（迁移 `009`），都能直接复用。
**不要改名。**

#### 其他（1 列）

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `supplementary_summary` | text | nullable | 风险或其他可能影响并购的企业重要信息。**进推荐上下文** |

> 与现有 `notes` 的分工：`notes` 是运营备注（不进任何推荐上下文），保持原义不变。
> 两者不要合并，否则运营备注会被送进 LLM。

### 3.2 三个闭集

闭集与中文名**只在指标注册表声明一次**，DB CHECK 与前端下拉都从它派生，
不要在任何地方手写第二份。

```
ownership_type
  state_owned  国企      # 央企与地方国企合并为一档（用户 0824 决定）
  private      私企
  foreign      外企
  other        其他
  unknown      未知

listed_status                    # 与标的侧 _LISTED_STATUS 同集
  listed       上市
  unlisted     非上市
  pre_ipo      拟上市
  unknown      未知

listing_exchange                 # 复用标的侧 _LISTING_EXCHANGE
  sse 上交所 / szse 深交所 / bse 北交所 / hkex 港交所
  nyse 纽交所 / nasdaq 纳斯达克 / other 其他 / unknown 未知
```

三点必须遵守：

1. **`listed_status` 与 `listing_exchange` 直接复用注册表里已有的
   `_LISTED_STATUS` 与 `_LISTING_EXCHANGE` 常量**，不要复制一份。
   先例：`transaction_types_json` 的注释「与标的侧共用同一个
   `_TRANSACTION_STRUCTURES`，不要复制一份闭集」。
2. **新列名叫 `listing_exchange`，不叫 `listing_market_region`。**
   标的侧那个列名名不副实（闭集其实是交易所），注册表 `indicators.py:116`
   自己注明「改名要动 25 处所以没改」。新建的不要继承这个债。
3. **`ownership_type` 里没有「央企」。** 央企与地方国企的区别落到
   `business_summary` 表达。基金 / PE 不设独立取值，按其出资方性质选
   （国资背景基金选国企，市场化基金选私企），这条规则写进注册表注释。

### 3.3 删除 4 列

| 列 | 依据 |
| --- | --- |
| `industries_json` | 生产 0%；职责被 `business_tags_json` + `business_summary` 取代。行业字典只有 16 个一级行业，接不住买家的细分主业 |
| `industry_l2_json` | 同上 |
| `region_country` | **零消费者**：后端前端全库检索为空，默认 `'中国'`，API 连投影都没有 |
| `long_term_preference_json` | **零消费者**，未投影 |

外加 `region_province` / `region_city` 在搬运到 `location_*` 之后删除。

删 `industries_json` 会连带删掉 GIN 索引 `idx_buyer_party_industries`（PostgreSQL 自动）。
本单用 `business_tags_json` 的 GIN 索引替代它，访问模式相同（`filter-options` 聚合）。

## 四、迁移

**文件**：`database/migrations/020_buyer_party_facts.sql`
**Alembic**：`alembic/versions/20260824_0067_buyer_party_facts.py`，
`revision = "20260824_0067"`，`down_revision = "20260819_0066"`，
`upgrade()` 里 `run_migration_sql(op.get_bind(), "020_buyer_party_facts.sql")`。
照抄 `20260819_0066_recommendation_answer_draft.py` 的骨架。

### SQL 要点

1. 全部用 `add column if not exists` / `drop column if exists`
2. CHECK 约束命名 `chk_buyer_party_<column>`
3. `business_tags_json` 加 `jsonb_typeof(...) = 'array'` 的 CHECK，
   并建 GIN 索引 `idx_buyer_party_business_tags`（`where deleted_at is null`）
4. **顺序**：先加新列 → 搬运存量（`region_*` → `location_*`；`industries_json` /
   `industry_l2_json` 里万一存在的非空值并进 `business_tags_json`）→ 再删旧列。
   行业两列生产实测是 0%，但测试环境可能有零星数据，这几行很便宜。
5. `idx_buyer_party_scope` 里没有地区列，搬 `region_*` 不影响索引；
   但要确认没有别的索引引用被删的列。
6. **迁移注释里不要出现分号。** 自制 splitter（`backend/app/migration_sql.py`）
   按分号切语句，注释里的分号会切坏语句、部署直接挂。这是有过事故的（见 `AGENTS.md`）。
7. 迁移注释里写清楚两件事，防止下一个人再删一次：

   > 三个财务数值列都不进任何 `where`。它们成为列的理由不是「能被筛选」，
   > 而是「能被刷新」—— 一个带 as_of、会被定期覆盖的数必须有确定的落点，
   > 你没法去 update 一段文本里的某个数字。

   > 013 删掉 `listed_status` 是对的：那时它是没人维护、不进 where 的死列。
   > 现在重建的理由不同 —— 它决定「市值/估值该显示哪一个」以及
   > 「财务数据能不能自动刷新」。这是重建，不是恢复。

## 七、`buyer_name` 被 AI 改写时的两条保护

本单只建字段，解析/调研在下一单。但**保护逻辑要在本单一起实现**，
因为更新接口就是写入口：

1. **旧名自动进 `aliases_json`。** 顾问输入「北控」，AI 改成
   「北京控股集团有限公司」，若旧名不留，顾问下次搜「北控」就搜不到自己建的买家。
   `dedup-check`（`:328`）本来就查别名（精确名 → 别名 → ilike 三级），
   append 进去即可保住搜索路径。
2. **名称变更走复核，不自动采纳。** 其他字段可以「空值 + 来源明确 → 自动采纳」，
   名称不行：改错了影响所有关联需求、撮合关系和搜索，**而且不会报错**，
   只会让人找不到东西。本单先把「非人工来源的改名需要确认」这条路留出来
   （具体的复核 UI 可以在下一单补，但接口不能默认静默覆盖）。

## 十一、已知的坑

1. **迁移注释里的分号会切坏语句**（§四.6）。有过事故。
2. **`unknown` 不是 `null`。** `ownership_type` / `listed_status` 是
   `not null default 'unknown'`。任何判断「这个字段有没有值」的地方，
   两者必须等价处理。这个坑在总纲 §3.3 已经记过一次。
3. **删列必须和 §八 的两个函数同一批改**，否则部署后深评与买家解析直接报错。
4. **不要动 `screening` 标记，不要碰 `buyer_intent` 的任何列。**
5. **未经用户明确要求，不要 commit、不要 push。** 推 `main` 等于直接改生产。

## 十二、这一单之后是什么（供理解上下文，不要提前做）

1. `buyer_party_parser` —— 从买家需求原文里分流出买家自身事实。
   生产实测：35 条有实质正文的需求里 **19 条带买家自身线索**
   （「A股上市，市值约260亿元」「买家性质：央企医药龙头」
   「与企业现有业务有一定关联性」），这些信息一直进过系统，
   只是历史解析提示词明令「不要生成或修改买家主体资料」把它挡在门外。
2. `buyer_party_researcher` —— 联网补全与财务自动刷新。
3. 主体清洗 —— 合并重复主体、拆分代录主体、需求改挂。
