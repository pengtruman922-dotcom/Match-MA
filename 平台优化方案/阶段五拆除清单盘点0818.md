# 阶段五拆除清单盘点（2026-08-18）

> **这不是施工单，是施工单的输入。** 阶段五工单要等 4D 收口后再写（4D 正在改
> `recommendation_flow.py` 与 `recommendations.py`，恰好是最大的两个拆除目标）。
> 本文只回答一个问题：**到底有哪些东西是死的，各自死在什么程度。**
>
> 盘点基线 `ddf1815`（4C 生产发布后），工作树含 4D 未提交改动。

---

## 结论摘要

盘点后最重要的一条：**死区比"旧打分链路"大得多，而且不都该删。**

前端 `recommendations` 客户端定义了 **22 个方法，实际有调用方的只有 7 个**：

| 在用（7） | 无调用方（15） |
|---|---|
| `agentTurn` `abortTurn` `answerStream` `messages` `turnStatus` `page` `recentSessions` | `candidates` `createRerankJob` `bundle` `getSession` `sessions` `createMessage` `selectItem` `selectedItems` `sessionSelectedItems` `cancelSelectedItem` `createReport` `createReportJob` `reports` `getReport` `downloadReportDocx` |

这 15 个里，只有前两个属于"被新链路取代"。**其余 13 个是 v3 推荐页重写成纯对话时被顺带切断 UI 的独立业务功能**——选中、报告、docx 导出。它们不是旧打分链路的一部分，阶段五不该替产品决定它们的生死。

所以清单分三类：**A 确定可删 / B 无 UI 的业务功能（产品决定）/ C 误删高危**。

---

## 一、A 类：确定可删

### A1　`search_targets_for_agent`　·　全仓零引用

`recommendation_flow.py` 里唯一一处出现就是它自己的 `def` 行。backend 0、tests 0、文件内自引用 0。
阶段一把 handler 改成 `screen_targets` 之后就没人调了。**最干净的一条，可以单独先删。**

### A2　`/candidates` 端点与其下游打分簇

入口：`POST /recommendations/candidates`（`recommendations.py:502`），前端 `recommendations.candidates()` 有定义无调用方。

随它一起走的（全部只被这条路和彼此引用）：

```
_candidate_targets_for_intent      _candidate_intents_for_target
_rank_and_report                   _score_target_against_intent
_score_against_scenarios           _select_with_scenario_quota
_effective_scenarios               _load_intent_scenarios
_with_resolved_exclusions          _build_candidate_row
_semantic_query_terms              _apply_semantic_keyword_match
_region_constraint_matches         _target_industry_values
_excluded_industry_hit             condition_effect（recommendation_conditions.py）
```

> **2026-08-18 更正**：初稿把 `_candidate_score_breakdown` 也列在这里，**错了**。
> 它和 `_candidate_display_meta` / `_candidate_display_badges` /
> `_with_frontend_candidate_fields` / `_enrich_candidates_for_frontend` /
> `_normalize_candidates` / `_extract_recommendation_candidate_sets` 同属「候选渲染簇」，
> 干的是**读历史候选消息**（bundle / page-state），不是生成候选。
> 它们随 B 类（选中 / 报告 / bundle）一起决定去留，**不随 `/candidates` 走**。
> 这也是为什么 B 类的产品决定是 5B 分包的硬前置，而不是可选项。

⚠️ **两处要留意**：

- **测试量很大**：`_score_target_against_intent` 有 30 处测试引用、`_candidate_targets_for_intent` 9 处、`derive_route` 8 处。
  这些测试要**跟着一起删**，不要试图改造成"测新链路"——它们测的是打分语义，新链路里没有分数这个东西。
- **反向推荐只有这一条路**：`_candidate_intents_for_target` 是"为标的找买家"的唯一实现（走注册表 `sql_recall`）。
  前端该方向的单选框是 `disabled` 且标着「下一轮支持」，所以删了不影响现有用户；
  但要明确接受"反向将来在新架构上重建，旧实现不保留"。框架第九节本来就是这么写的。

### A3　rerank 全链

- 路由 `POST /sessions/{id}/rerank-jobs`，前端 `createRerankJob` 无调用方
- `_enqueue_recommendation_rerank_job` / `_build_rerank_query` / `_get_latest_recommendation_rerank_job` /
  `_build_recommendation_rerank_status` / `_get_rerank_anchor_for_session`
- `dispatch.py:82` 的 `{"recommendation_rerank", "recommendation_deep_eval"}` 分支
- `recommendation_reranker` 节点——`nodes.py:433` 已自注「随推荐 v3 退役，深评已取代它，专用 worker 已下线」

### A4　旧深评（分片版）

```
_run_recommendation_deep_eval      _run_deep_eval_shards
_interleave_shards                 _apply_deep_eval_results_to_candidates
_insert_recommendation_rerank_message               DEEP_EVAL_SHARD_SIZE
```

⚠️ 其中四个被 `jobs/handlers/__init__.py` re-export。**re-export 是测试依赖，删函数必须同步删 re-export 与对应测试**，否则 CI 会在一个和本次改动看不出关系的地方挂掉。

### A5　旧增量条件操作簇（`recommendation_conditions.py` 下半部分）

```
parse_recommendation_message       normalize_parse_result
fallback_parse_result              apply_condition_actions
merge_condition_overrides          conditions_snapshot
persist_session_overrides          derive_route
describe_condition_ops             apply_overrides_to_anchor
suppress_pending_confirmation_fields                confirmation_field_names
EMPTY_OVERRIDES                    coerce_condition_value
```

全部只被 `/candidates` 路由与彼此引用，随 A2 一起走。
**上半部分（阶段二的 `normalize_intent_parse_result` / `parse_recommendation_intent` 等）是新链路的核心，别碰。**
这个文件删完会从 1101 行掉到一半左右，建议顺手拆成两个模块。

## 二、B 类：无 UI 的业务功能——删不删是产品决定

**这一类不要写进阶段五工单，先问产品。** 它们没有引用不是因为被取代，是因为界面在 v3 重写时被拿掉了。

| 功能 | 后端 | 前端 |
|---|---|---|
| **选中（selected items）** | 4 个路由 | 4 个方法全无调用方 |
| **推荐报告 + docx 导出** | 4 个路由 + 3 个 report writer 节点 | 5 个方法全无调用方 |
| **会话读写旧入口** | `bundle` / `getSession` / `sessions` / `createMessage` | 4 个方法全无调用方 |

报告目前只在 DebugCenter / DebugEntity 里以计数形式露过面，正常用户路径上没有入口。

### 一个必须先修的前置（如果选中要接回来）

`_ensure_selected_item_allowed_from_session_candidates`（`recommendations.py:2105`）要求选中项
必须来自本会话生成的候选消息——它扫的是 `content.candidates` 形状的消息。
而新 agent 会话写的是 `agent_brief`（`recommended` / `runner_ups`），**根本不产生那种消息**。

结论：**非管理员一旦从新推荐页点"加入选中"，会直接 403。**
现在不暴露纯粹是因为没有 UI。接回去之前必须先换判据（改成认 `agent_brief` 的名单）。

## 三、C 类：误删高危

### C1　`recommendation_flow.py` 里的会话 / 消息 / 概览 CRUD

这个文件 3763 行、112 个顶层函数，**打分只占其中一部分**，其余全是新链路在用的地基：

`agent_turn_aborted`（13 处引用）、`_get_recommendation_session_or_404`（15 处）、
`_optional_uuid`（61 处）、`_insert_recommendation_message`（8 处）、`_json_safe`（13 处）、
`agent_history_context`、`target_facts_for_agent`、`find_agent_turn_*`、`insert_agent_*`……

**按函数拆，不要按文件拆。**

### C2　`normalize_scenario_fields` / `normalize_condition_effects`

看着像推荐的东西，实际主用户是 **`buyer_intents.py`（5 处）与 `buyer_intent_parse.py`（3 处）**——
买家需求的建单、改单、解析回填。这属于买家字段线，不属于阶段五。

（与之相对，`condition_effect`（单数）只被旧打分用，随 A2 走。）

### C3　`_annotate_candidate_relations` —— 删之前先做个产品决定

新链路的 `relation_status` 在 `recommendation_agent_tools.py:404` 是**硬编码 `None`**，
真正会算关系状态的 `_annotate_candidate_relations` 只挂在旧 `/candidates` 上。

也就是说 **brief v2 的 `already_in_progress` 字段永远不会有值**——
`recommendation_answer.py:461` 那段"已在推进"的兜底文案是死代码。
（同一组的 `other_buyer_in_deep_progress` 是好的，它走 `deep_progress_ids`，有真实来源。）

两条路选一条，**不能默认按"删"处理**：

- 要这个提示 → 把关系标注接进 agent 工具层，`_annotate_candidate_relations` 保留
- 不要 → 连同 brief 字段与兜底文案一起删掉，别留一个永远为空的字段

## 四、建议的拆除顺序

按"越先做越安全"排：

1. **A1** —— 零引用，单独一个提交，几分钟
2. **A3 + A4** —— rerank 与旧分片深评，边界清晰，只连着 dispatch 和 re-export
3. **A2 + A5** —— `/candidates` 与打分簇、旧条件操作簇，一次性删干净，测试同批删
4. **C3 的决定** —— 做完再决定 `_annotate_candidate_relations` 的去留
5. **B 类** —— 单独提出来问产品，不进阶段五

每一步之后跑全量 `python -m pytest -q` 与前端 `typecheck / build / lint`。
删除类改动的验收标准是"测试数量下降且无失败"，不是"全绿"——全绿也可能是把测试一起注释掉了。

## 五、这份盘点的有效期

以下情况需要复核：

- **4D 落地后**：§4D.5 第 3 条要改会话"进行中"的判据，动的是 `recommendation_flow.py` 的会话状态派生，
  可能新增对 C1 里若干函数的引用
- **指标线对 `condition_effects_json` 出结论后**：影响 C2 的归属
- **产品对 B 类表态后**：选中与报告若要接回来，A2/A3 里有部分函数需要保留或重写

盘点方法：对 `recommendation_flow.py` 全部顶层 `def` 做跨文件引用计数，
再从 `/candidates` 与 `dispatch` 两个入口正向追调用图，两边对齐。
复核时重跑同样的计数即可，不需要重新读全文件。
