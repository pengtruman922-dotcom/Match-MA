## 一、范围铁律

**做三件事：**

1. 买家侧补齐两个闭集（重大风险容忍新建、交易结构改造），打开一个标志位；
2. 把六条空转/口径错的声明修正或降级；
3. 买家侧兼容字段与说明性文本的定性归位（多为注释与标志位）。

**不做：**

- **不碰 `recommendation_flow.py` / `recommendation_agent_tools.py` / `recommendation_conditions.py`。** 现行打分链路一行不改——本轮改的 `screening` 今天零后端消费方（方案 §1），改它只影响信息页角标。
- **不写筛选 skill、不写 SQL 生成器、不改深评载荷。** 那是推荐线的活；本轮交付它要读的声明 + 方案 §9 的三条约定。
- **不删任何标的侧列。** `is_for_sale`、`gap_summary` 的牵连超出指标体系（`relation_flow.py` / `search_docs.py`），维持 0806 §三原判。

**验收原则同 0806 §五：做完之后推荐结果不应有任何变化。** 本轮产出只有两样——买家需求页能看能编这两个新闭集，解析能把它们填上。业务价值等推荐线接线才兑现。

## 二、迁移 `018_buyer_condition_closed_sets.sql`

对应 alembic 修订 `20260817_0065`，`down_revision = "20260814_0064"`。

```sql
-- ===== 一、新增：买家不接受的重大风险 =====
--
-- 标的侧 major_risk_flags_json 的 5 值里 none 是「核查状态」不是「风险类型」，
-- 「不接受已核查无风险」讲不通，所以买家侧是它的 4 值子集。
-- 三态全部由这一个字段表达，不加第二列：
--   []                      未提及（不带条件）
--   四值全集                 不接受全部（落库时由代码展开）
--   其余子集                 不接受特定类型

alter table buyer_intent
  add column if not exists unacceptable_risk_flags_json jsonb not null default '[]'::jsonb;

alter table buyer_intent
  drop constraint if exists chk_buyer_intent_unacceptable_risk_flags_json;

alter table buyer_intent
  add constraint chk_buyer_intent_unacceptable_risk_flags_json
  check (
    jsonb_typeof(unacceptable_risk_flags_json) = 'array'
    and unacceptable_risk_flags_json
        <@ '["litigation", "equity_frozen", "enforcement", "violation"]'::jsonb
  );

-- ===== 二、交易方式：先救原话，再重写闭集 =====
--
-- 存量 27/44 的取值混了三个正交轴：交易结构、支付方式、控制权诉求。
-- 只有第一轴对得上标的侧闭集，另两轴没有对手方列。
-- 顺序不能反：先把原数组存进原话列，再重写，否则映射不上的 17 条直接蒸发。
--
-- transaction_type 从「兼容标量」改判为「交易方式原文」，与 industry_primary 同定位。
-- 只在它为空时写入 —— 已有原话的行不覆盖。

update buyer_intent bi
set transaction_type = (
      select string_agg(t.value, '、' order by t.ord)
      from jsonb_array_elements_text(bi.transaction_types_json)
           with ordinality as t(value, ord)
    )
where jsonb_array_length(coalesce(bi.transaction_types_json, '[]'::jsonb)) > 0
  and coalesce(nullif(btrim(bi.transaction_type), ''), '') = '';

update buyer_intent bi
set transaction_types_json = coalesce(
      (
        select jsonb_agg(distinct m.code)
        from jsonb_array_elements_text(bi.transaction_types_json) as t(value)
        cross join lateral (
          select case
            when t.value in ('老股转让', '股权转让')             then 'equity_transfer'
            when t.value in ('定增', '增资控股', '增资扩股')      then 'capital_increase'
            when t.value in ('资产收购')                        then 'asset_purchase'
            when t.value in ('吸收合并', '并购', '借壳重组')      then 'merger'
            else null
          end as code
        ) as m
        where m.code is not null
      ),
      '[]'::jsonb
    )
where jsonb_array_length(coalesce(bi.transaction_types_json, '[]'::jsonb)) > 0;

alter table buyer_intent
  drop constraint if exists chk_buyer_intent_transaction_types_json;

alter table buyer_intent
  add constraint chk_buyer_intent_transaction_types_json
  check (
    jsonb_typeof(transaction_types_json) = 'array'
    and transaction_types_json
        <@ '["equity_transfer", "capital_increase", "asset_purchase", "merger", "other"]'::jsonb
  );

-- ===== 三、股比单位污染 =====
--
-- desired_equity_ratio_min 里混着一条 0.2990（原话「上市公司29.9%及以下」被存成分数），
-- 其余是 51 / 100 / 25 / 60 这样的百分数。同一个 gte 条件上并存两种口径，
-- 那一行会通过一切。阈值取 1：股比小于 1% 的收购诉求在业务上不存在。

update buyer_intent
set desired_equity_ratio_min = desired_equity_ratio_min * 100
where desired_equity_ratio_min is not null
  and desired_equity_ratio_min > 0
  and desired_equity_ratio_min < 1;

update buyer_intent
set desired_equity_ratio_max = desired_equity_ratio_max * 100
where desired_equity_ratio_max is not null
  and desired_equity_ratio_max > 0
  and desired_equity_ratio_max < 1;
```

**不加 GIN 索引**：框架 §9 已定「标的库规模千级，索引可后置」，买家表更小（44 行）。015 给标的侧加索引是因为那两列进 jsonb 展开的召回路径，本轮两列都只在初筛 skill 里被读，而 skill 还没落地。

**迁移写完立刻跑 `tests/test_migration_sql.py`** —— 参数化用例对全部迁移做 load + split 回归。本文件里有 `case ... when ... then` 和多个 `'、'` 字面量，正是 splitter 出过事故的形状。

### 6.1 `buyer_intent_parser` → 下一版

```
- unacceptable_risk_flags_json：买家**不接受**的重大风险类型，数组。
  · 材料说「不接受任何重大风险」「要求无涉诉无冻结」这类全称否定时，
    输出四值全集 ["litigation","equity_frozen","enforcement","violation"]。
  · 只否定其中几类时输出对应子集（如只说「不能有股权冻结」→ ["equity_frozen"]）。
  · 材料没有提到风险这件事时**整个字段省略**，不要输出空数组。
  · 注意方向：这一列存的是「不接受什么」，不是「能接受什么」。
  · 具体的容忍度描述（如「可接受历史诉讼但需已结案」）继续写进
    major_risk_tolerance_summary，两者并存：枚举用于筛选，摘要是明细。

- transaction_types_json：买家可接受的**交易结构**，数组，闭集见字段目录。
  · 只装结构这一个维度。以下两类**不要**放进来：
    · 支付方式（现金、股份、现金+股份、全现金、换股）→ 写进 transaction_type 原话；
    · 控制权诉求（控股收购、少数股权、战略投资）→ 已由 requires_control /
      accepts_minority_investment / desired_equity_ratio_* 表达，不要重复。
  · 借壳重组、吸收合并、并购 → merger；老股转让 → equity_transfer；
    定增、增资扩股 → capital_increase；资产收购 → asset_purchase。

- transaction_type：交易方式原文，照抄材料措辞（如「全现金收购」「控股收购或分阶段并购」）。
  它不参与匹配，作用是保住闭集装不下的信息。

- region_constraints_json 与 region_scope_summary 必须同时产出：
  前者是结构化省/市/区，后者是原话语气（「优先」「最好但非强制」「以…为主」）。
  只写摘要不写结构化，这条地域要求在推荐里完全不存在。
  「全国」「不限」「无地域限制」→ region_scope_summary 照写，
  region_constraints_json 留空（那正确地表示「无约束」）。

- industry_l2_json 与 industry_focus_tags_json 的分工：
  **先试二级行业字典**，能落进字典的一律进 industry_l2_json；
  只有字典里确实没有的细分方向才进 industry_focus_tags_json。
  「半导体」「储能系统」「医疗器械」「集成电路」这类字典里有的词
  不要直接倒进自由标签 —— 那会让它在推荐里失效。
```

### 7.2 新增守卫（本轮的核心防线）

def test_buyer_conditions_have_all_four_declarations() -> None:
    """审计 ②③④：条件类字段的四项声明必须齐备。

## 十、交给推荐线的三条约定

注册表读不出来、必须写进 SQL 生成器的（方案 §9）：

1. **`requirement_capability` 是 `t.<col> in ('yes','likely')`**，不是 `<> 'no'`。这些列是 `not null default 'unknown'`，三值逻辑救不了；按 `<> 'no'` 会让 40+ 个「不知道能不能控股」的标的静默通过，同时抹掉 `excluded_by_condition` 里的空值桶——agent 的放宽策略就没有依据了。
2. **重大风险的 `not_overlap` 必须带「已核查」前置**：
   `t.major_risk_flags_json <> '[]'::jsonb and not exists (...)`。
   缺前半段，「没查过」会被当成「干净」。
3. **`min_net_margin` 的比较要 ×100**：买家侧存百分数（8.0），标的侧现算是分数（0.1692）。今天这个条件筛出来必然是空集且不报错。

以及一份「今天带上就几乎筛空」的清单，供调用策略参考：
`min_total_profit_yuan` 6% / `desired_equity_ratio_*` 1–3% / `listing_market_region` 3% /
`unacceptable_risk_flags_json` 3% / `transaction_types_json` 1% / `accepts_minority_investment` 1 家。

**本方案对推荐线的唯一反向依赖**：方案 §5.1/5.2/5.3 把对赌、毛利率、细分方向、主要产品判给深评，前提是**深评能看到这些字段**。而今天深评载荷只有画像散文（0807 §1.5），结构化列一个都不进。这四项的"归深评"在深评载荷改造落地之前是**空头支票**，交接时必须说清。

## 十一、实际施工与本单的差异（2026-08-17 落地后回填）

施工中发现六处本单写错或写漏的地方，逐条记下来——**下一个人照本单做会踩到同样的坑**。

### 1. 标的侧只改 4 处，不是 5 处；「两侧同步降级」这条是错的

本单 §3.3 要求把 `accepts_relocation` / `accepts_return_investment` /
`management_retention_possible` 的 `screening` 一起关掉。**不能关**——
`recommendation_flow.py` 的需求单打分器仍在读这三列（`_scorer_reads()` 证实），
关掉会让 `test_registry_screening_covers_everything_the_scorer_reads` 直接挂。

根因是 `screening` 在两侧本来就是两件事：

| 实体 | `screening` 的含义 | 消费方 |
|---|---|---|
| 标的 | 「有没有人比对我」——买家条件或打分维度 | 信息页「筛」角标 |
| 买家 | 「这一条进不进初筛 schema」 | schema 生成器 |

同名不同义，但各自自洽。新守卫 `test_seller_screening_matches_who_points_at_it`
按这个定义两个方向都守（标了却没人读 / 有人读却没标）。

### 2. `default_effect` 不能清，改成让 `is_condition` 读 `screening`

本单 §3.2 要求清掉 `min_gross_margin` / `max_premium_rate` 的 `default_effect`，
理由是解析契约用它判 `is_condition`。**清了会静默拆掉需求单打分器的维度**——
`recommendation_conditions.condition_effect()` 的兜底就是读它，返回 `None` 等于
「不参与规则打分」。实测 `test_net_margin_and_ps_are_derived_from_revenue_and_valuation`
当场挂掉。

正解是让两个标志各管一件事：

- `default_effect` = **需求单链路的规则打分强度**（required / preferred）
- `screening` = **进不进初筛 schema**

然后把 `_buyer_intent_field_contract()` 的 `is_condition` 从
`default_effect is not None` 改成 `indicator.screening`。这样六个「只进打分不进初筛」
的字段（毛利率、PS、溢价上限、迁址/返投/留任）在解析契约里被正确标成描述项，
而需求单打分器一行不动。

### 3. **必须动 `screening_sql.py`**——两个新字段会静默生成错 SQL

本单 §一说「不写 SQL 生成器」。但推荐线已经把 `screening_schema.py` /
`screening_sql.py` 建在同一个工作树里，而它的 `overlap` / `not_overlap`
**写死了行业路径**（`industry_pairs_json` 的 `{l1,l2}` 对象数组）。
本轮接线的两个字段是扁平字符串数组，于是：

```
transaction_types_json  → 查 industry_pairs_json ->> 'acceptable_transaction_structures_json'
                          恒为 NULL → 候选池恒空
unacceptable_risk_flags_json → 拿行业对去比风险码 → 恒不重合 → 条件恒真
```

**两个方向都不报错**，正是「写错 target_column 筛出来必然为空且不报错」那一类。
改动三处，都在 `screening_sql.py`：

- 新增 `_flat_array_exists()`：走 `jsonb_array_elements_text`，不取键；
- `build_clause` 的 `overlap` / `not_overlap` 分派到 `_array_clause()`，按
  `target_column` 是不是 `industry_pairs_json` 选路径；
- `_missing_sql()` 认闭集多值列的空数组（DDL 是 `not null default '[]'`，
  `is null` 判不到），与 `unknown` 同处理。

扁平数组的 `not_overlap` 显式排掉缺失（`not <missing> and not <hit>`），
因为 `not exists(...)` 对空数组恒真，而 `major_risk_flags_json` 的空数组是
**未核查**。行业那条分支保持原样——排除行业不因行业为空而出局，两者语义确实不同。

### 4. 迁移 018 多了一段：三个既有买家闭集列压根没有元素级约束

`acceptable_listed_status_json` / `acceptable_cash_flow_status_json` /
`acceptable_profitability_status_json` 从迁移 011 起只有形状约束
（`jsonb_typeof = 'array'`），元素取值全靠应用层的 `_normalize_closed_list_values` 拦。
标的侧 015 建的两列一开始就是元素级 `<@`。

这个缺口是扩守卫时被照出来的（守卫查两侧，那三列当场报「迁移里没有元素级 check」）。
迁移 018 第三段补齐，生产现有取值全部在闭集内，零数据风险。

### 5. `financial_period_end_date` 只补出参，不补入参

本单 §八说「补进 `SellerTargetOut` + `api.ts` + `fieldLabels`」。实际还要少一处：
**不能进 `SellerTargetUpdate`**——注册表声明它 `writable_by = {parse, research}`，
放进人工编辑模型等于让手工写一列注册表说人工不能写的字段。

另外它 `fold_into="financial_period_label"`，而信息页过滤掉所有折叠列
（`infoGroups.ts:108`），光加出参界面上仍然看不见。所以 `formatValue` 加了一条
`financial_period_label` 的合并展示：「2024年度（截至 2024-12-31）」。

### 6. 守卫是 6 条不是 4 条，其中最要紧的一条本单没提

除本单 §7.2 的四条与 §7.1 的扩充，另加一条
`test_every_clause_reads_the_column_it_declared`（在 `tests/test_screening_sql.py`）：
**生成的 SQL 只许读它声明过的列**。

它是被 §3 那个缺陷逼出来的——把 `_array_clause` 改回写死行业路径，
`tests/test_screening_sql.py` 原有的 21 个用例**全绿**。一个能让候选池恒空的缺陷
没有任何测试挡得住，这条守卫补的就是那个洞。

判据写成「只读声明过的列」而不是「每一列都读到」：`region_any` 按 constraint
实际填到的层级展开，只给了省就只出省，那是设计使然。
