### 决策一：选中 / 推荐报告 / docx 导出——留还是删？

盘点发现前端 `recommendations` 客户端定义了 22 个方法，**实际有调用方的只有 7 个**。
无调用方的 15 个里，只有 `candidates` 和 `createRerankJob` 属于「被新链路取代」；
**其余 13 个是 v3 推荐页重写成纯对话时被顺带切断 UI 的独立业务功能**——
选中、推荐报告、docx 导出、会话读写旧入口。

它们不是旧打分链路的残骸，是掉了界面的功能。**阶段五不替产品做这个决定。**

| 选项 | 5B 的范围变化 |
|---|---|
| **A. 保留**（将来补 UI） | 「候选渲染簇」整体保留（见下），5B 只删打分与生成侧 |
| **B. 一并删除** | 候选渲染簇、4 个选中路由、4 个报告路由 + docx、3 个 report writer 节点、`recommendation_report` 相关表的读写一起走 |

⚠️ **候选渲染簇不随 `/candidates` 走**——这是盘点初稿里我写错、后来更正的一条：

```
_extract_recommendation_candidate_sets   _infer_recommendation_candidate_message_type

_enrich_candidates_for_frontend          _with_frontend_candidate_fields

```

它们干的是**读历史候选消息**（`bundle` / `page-state` 渲染），不是生成候选。
选 A 则全部保留，选 B 则全部删。**混着来会留下一半能编译但永远没数据的代码。**

> 补充：若选 A 且将来真要把选中接回新推荐页，还有一个前置 bug 要先修——

### 决策二：`already_in_progress`（已在推进）要不要接回来？

新链路的 `relation_status` 在 `recommendation_agent_tools.py:404` 是**硬编码 `None`**；
真正会算关系状态的 `_annotate_candidate_relations` 只挂在旧 `/candidates` 上。

结果是 **brief v2 的 `already_in_progress` 字段永远不会有值**，
`recommendation_answer.py` 里那段「已在推进」的兜底文案是死代码。
（同组的 `other_buyer_in_deep_progress` 是好的，走 `deep_progress_ids`，有真实来源。）

**为什么会是 `None`——不是漏接，是算不出来。**

`already_in_progress` 取自 `buyer_seller_relation` 表里 **(买家需求 × 标的) 这一对**的推进状态，
渲染成正文里的「这家已经在推进中」。查它需要一个 `buyer_intent_id`。

而新链路是**无买家主体**的：用户直接说「找江苏制造业标的」，会话里根本没有买家实体。
即使用「带入已有买家需求」入口，`attachIntent` 也只是把需求**转成文本**当附件塞进去
（`intentToRequirementText`），**不绑定 `buyer_intent_id`**。所以这个字段在语义上就不存在。

对比：`other_buyer_in_deep_progress`（这家标的正与其他买家深入推进）只需要 `target_id`，
不需要知道买家是谁——所以它是好的，有真实来源，**留着**。

三条路：

| 选项 | 代价 |
|---|---|
| **删掉字段与兜底文案**（建议） | 丢掉「这家你自己已经在谈了」这个提示 |
| 让会话可绑定买家主体，再查关系 | 这是**产品与架构变更**，不是接线：要给会话加买家实体、改带入入口、改 UI，属于另一条线 |
| 维持现状 | 最差——留一个永远为空的字段和一段永不触发的文案 |

**建议删。** 想要这个提示的话，真正要做的是「让推荐会话能绑定买家主体」，
那是一个独立议题，不该挂在阶段五上。

### 决策三：确认反向推荐旧实现可以删

## 一、做什么、不做什么

**做**：删掉已经被新链路取代、且确认无调用方的旧代码与旧配置。

**不做**：

- 不做任何行为变更、不做重构、不做性能优化——**这一阶段的正确产出是「代码变少，行为不变」**
- 不动新链路的四个节点：`recommendation_query_parser`、`recommendation_deep_eval_to_target`、
  `recommendation_agent_to_target`、`recommendation_answer_writer_to_target`
- 不动 Prompt，不写 prompt 迁移
- 不动数据库 schema。**旧表不在本轮删**——历史会话的消息还在里面，
  删表是不可逆的，且与代码删除不同步会让老会话读不出来
- 不实现反向推荐
- 不修 B 类里那个 403（不属于本阶段）

## 五、删除类改动的验收怎么算

**这一阶段的验收标准和前四个阶段不同，写清楚免得走形。**

| 指标 | 期望 |
|---|---|
| 后端测试 | **通过数下降、失败数为 0** |
| 前端 | typecheck / build / lint 全过 |
| 行为 | 一轮真实推荐的四段消息、黄点绿点、追问芯片、链接回填**完全不变** |
| 代码量 | 净减少（`git diff --stat` 里删除行远多于新增行） |

⚠️ **「全绿」不是合格标准。** 把测试连同代码一起注释掉也能全绿。
每个包结束时必须报告：删了哪些测试、为什么这些测试没有保留价值、通过数从多少变到多少。

⚠️ **新增行应当接近 0。** 如果某一批删除产生了大量新增代码，说明不是在删，
是在借拆除之名重构——停下来说明理由。
