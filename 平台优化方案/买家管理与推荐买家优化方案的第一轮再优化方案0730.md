# 买家管理与推荐买家优化方案的第一轮再优化方案（P0-0730）

版本：v0.2
日期：2026-07-30
状态：待产品最终确认
基线文档：《买家管理与推荐买家优化方案0729.md》

> 本文是 0729 P0 方案完成第一轮开发和试用后的再优化方案。0729 中未被本文修改的原则继续有效；如两份文档存在冲突，以本文为准。本文用于最终产品确认和后续开发，不代表当前系统已经全部实现。

## 一、第一轮反馈与再优化目标

第一轮实现已经建立“需求为最小管理单元、公共条件加多个方案、待确认字段隔离、正反向推荐共用配对语义”等基础能力，但实际试用暴露出四类问题：

1. 买家需求的行业、地区编辑器没有复用标的信息已有的字典选择和省市区级联能力。
2. 买家需求字段与标的字段缺少统一的对应契约，存在字段遗漏、枚举不一致和同义状态重复。
3. 页面将字段静态标记为“硬筛、软排、深评”，但条件的实际作用取决于具体表述和所在方案，页面标签与部分后端规则不一致。
4. 买家需求解析直接追求标准字段输出，需求理解、字典映射、枚举规范化和最终入库边界不够清晰。

本轮再优化目标是：

- 复用标的与需求的行业、行政区划基础组件和数据源。
- 建立需求条件到标的事实的一一对应关系。
- 将“必须、优先、仅深评”和“已生效、需要确认”拆成相互独立的属性。
- 将买家需求解析拆为需求语义解析、字段规范化、代码校验入库三个清晰环节。
- 保留正反向推荐的同一配对规则，同时拆分候选召回流程和 AI 深评 Prompt。
- 将“未知不淘汰、只有必须条件下的明确冲突才淘汰”固化为系统底线。

## 二、继续有效的产品边界

### 2.1 管理单元

需求仍是买家管理、推荐、选中和推进的最小单元：

```text
买家主体（轻量共享）
└─ 需求（列表一行、独立状态）
   ├─ 公共条件
   ├─ 方案 A
   ├─ 方案 B
   ├─ 仅深评内容
   └─ 待确认事项
```

同一买家的多项需求创建为多条需求并关联同一买家主体；P0 不强化买家主体配置。

### 2.2 单次创建边界

- 一次创建只处理一个买家的一项需求。
- 不检测、不拆分、不提示一份材料中是否包含多个买家或多个需求。
- AI 解析后自动写入可确定的内容，人工在详情页事后复核。
- 不保存或展示 AI 置信度。
- 含糊复合描述不强行生成数值筛选条件，保留为仅深评内容或需要确认事项。

### 2.3 需求与方案关系

```text
公共条件 AND（方案 A OR 方案 B OR 方案 C）
```

- 没有显式方案时，需求按一套公共条件匹配。
- 一个标的只要与任一启用方案不冲突，整个需求就可以保留。
- 推荐结果必须记录并显示最佳命中方案和其他可命中方案。

## 三、统一的需求条件模型

### 3.1 条件不是一个字段值

每条需求条件至少包含：

```text
作用范围：公共条件 / 方案
业务维度：行业、地区、营收、迁址等
对应字段：标准需求字段
运算关系：包含、不包含、不低于、不高于、等于等
标准值：枚举、数值、行业、地区等
单位口径：元、万元、百分比、倍数、年度等
匹配作用：必须满足 / 优先满足 / 仅深评
复核状态：已生效 / 需要确认
原文证据：支持该条件的材料片段
补充说明：无法结构化但需要保留的上下文
```

### 3.2 匹配作用与复核状态必须分离

条件的匹配作用：

| 作用 | 规则含义 |
|---|---|
| 必须满足 | 对方明确不满足时形成冲突并淘汰；对方未知时保留 |
| 优先满足 | 满足时加分，不满足时降序但不淘汰 |
| 仅深评 | 不进入 SQL 预筛和确定性排序，只进入 AI 深评上下文 |

条件的复核状态：

| 状态 | 规则含义 |
|---|---|
| 已生效 | 按条件的匹配作用参与规则 |
| 需要确认 | 暂不参加 SQL 预筛和确定性排序，但保留原文并进入 AI 深评 |

“需要确认”不是第四种匹配作用，也不是字段枚举值。

### 3.3 所有信息都会进入深评

“必须、优先、仅深评”不是“硬筛、软排、深评”三个互斥的信息集合：

- 必须条件同时进入确定性规则和 AI 深评。
- 优先条件同时进入确定性排序和 AI 深评。
- 只有“仅深评”条件不进入确定性规则。
- 待确认内容虽然暂不生效，但仍进入 AI 深评并明确标记为未确认。

需求页条件标签统一建议为：

```text
[必须] [优先] [仅深评] [需要确认]
```

不再把字段本身永久标记为硬筛或软排。

### 3.4 标的信息页的“筛”标签调整

标的事实本身没有“必须”或“优先”属性；同一个标的字段可能被不同需求以不同作用使用。

因此标的信息页现有“筛”标签应改为“匹配”或“规则匹配”，含义为：

> 该标的事实可被买家需求条件用于结构化比较。

它不表示该字段天然属于硬筛，也不表示一定在 SQL 阶段执行。

## 四、行业与地区基础组件复用

### 4.1 行业组件

标的与买家需求共用同一行业字典、搜索、父子关系和勾选组件：

```text
行业字典
   ↓
一级行业搜索与勾选
   ↓
根据一级行业过滤二级行业
   ↓
二级行业搜索与勾选
   ↓
返回标准行业组合 [{l1, l2?}]
```

基础组件复用，业务外壳不同：

| 使用位置 | 业务含义 | 保存目标 |
|---|---|---|
| 标的所属行业 | 企业客观所属行业 | 标的行业组合 |
| 需求可接受行业 | 买家接受的一级行业范围和二级关注方向 | 需求行业条件 |
| 需求排除行业 | 买家明确不接受的行业 | 排除条件 |

需求模式的默认规则：

- 明确选中的一级行业可作为必须条件，多个一级行业为 OR。
- 二级行业默认作为优先条件，不命中不淘汰。
- 二级行业的父级只用于导航、展示和字典关联；不得因为勾选二级行业就暗中生成一级行业必须条件，除非用户或 AI 明确设置了一级行业条件。
- 字典外的产品、技术、应用场景和细分方向进入仅深评内容。
- 无法唯一映射的行业进入需要确认。

### 4.2 地区组件

标的与买家需求共用同一行政区划列表和省市区级联逻辑：

- 根据省过滤城市。
- 根据城市过滤区县。
- 修改上级时清空无效下级。
- 共用标准省、市、区名称及行政区划代码映射。

业务外壳不同：

| 使用位置 | 组件形态 |
|---|---|
| 标的所在地 | 单组省、市、区 |
| 需求可接受地区 | 多组省、市、区，可分别设置必须、优先或排除 |

需求多选示意：

```text
可接受地区

已选：
[必须] 浙江省                         [删除]
[必须] 江苏省 / 苏州市                [删除]
[优先] 上海市                         [删除]

继续添加： [省] → [市] → [区/县]  [作用：必须/优先]
```

### 4.3 自然语言区域由 AI 展开

不额外建设严格的区域组配置。AI 负责理解自然语言区域并展开为标准省份，规范化环节负责校验省名和去重。

示例：

```text
全国
→ 明确表示不限地区，不生成地区筛选条件

长三角
→ 上海、江苏、浙江、安徽

华东
→ 上海、江苏、浙江、安徽、福建、江西、山东
```

“全国”是明确的不限地区，不是解析失败或信息缺失。可以保留展示摘要“全国”，但结构化地区约束为空：

```json
{
  "region_scope_summary": "全国",
  "region_constraints_json": []
}
```

区域组边界不要求通过代码硬编码到唯一版本；Prompt 提供常见示例，LLM 负责语义理解，代码只接受标准行政区划值。

## 五、需求字段与标的字段对应契约

### 5.1 对齐原则

“对齐”是指每个可结构化需求维度都有明确的标的对应事实、比较方式和未知处理，不要求买家字段名或枚举与标的完全相同。

```text
需求侧：要求、接受范围、上下限、优先级
标的侧：客观事实、能力、意愿、当前数值
配对层：字段映射 + 运算符 + 要求×能力矩阵
```

并非所有标的字段都需要变成买家条件。标的名称、信息状态、调研时间等没有明确需求语义的字段，只作为展示或深评上下文。

### 5.2 P0 结构化对应表

| 需求维度 | 需求字段/条件 | 标的对应事实 | 默认比较 |
|---|---|---|---|
| 一级行业 | 可接受一级行业 | 所属一级行业 | 任一命中；必须条件不命中冲突 |
| 二级行业 | 二级关注方向 | 所属二级行业 | 默认优先，不命中降序 |
| 排除行业 | 排除一级/二级行业 | 所属一级/二级行业 | 明确命中排除项时冲突 |
| 地区 | 可接受省市区 | 所在省市区 | 按条件作用判断必须或优先 |
| 上市状态 | 可接受上市状态集合 | 已上市/未上市/拟上市/未知 | 集合包含比较 |
| 上市地 | 境内/境外要求 | 上市地 | 枚举比较 |
| 最低营收 | 营收下限 | 当前营收 | 标的值不低于下限 |
| 最低净利润 | 净利润下限 | 当前净利润 | 标的值不低于下限 |
| 最低利润总额 | 利润总额下限 | 当前利润总额 | 标的值不低于下限 |
| 净利率 | 净利率下限 | 净利润÷营收派生 | 标的派生值不低于下限 |
| 估值 | 估值范围 | 非上市估值，必要时以市值补充 | 区间比较，口径必须一致 |
| 市值 | 市值范围 | 上市公司市值 | 区间比较 |
| PE | PE 上限 | 标的 PE | 标的值不高于上限 |
| PS | PS 上限 | 市值或估值÷营收派生 | 标的派生值不高于上限 |
| 负债率 | 负债率上限 | 当前资产负债率 | 标的值不高于上限 |
| 盈利状态 | 可接受盈利状态 | 盈利/亏损/盈亏平衡/未知 | 可接受集合比较 |
| 现金流状态 | 可接受现金流状态 | 稳定为正/为正/为负/不稳定/未知 | 可接受集合比较 |
| 控股 | 控股要求 | 可控股 | 要求×能力矩阵 |
| 并表 | 并表要求 | 可并表 | 要求×能力矩阵 |
| 少数股权 | 是否接受少数股权 | 接受少数股权、可转让比例 | 能力和比例综合比较 |
| 收购股比 | 期望股比区间 | 标的可转让比例区间 | 区间是否有交集 |
| 迁址 | 迁址要求 | 接受迁址 | 要求×意愿矩阵 |
| 返投 | 返投要求 | 接受返投 | 要求×意愿矩阵 |
| 团队留任 | 团队留任要求 | 团队可留任 | 要求×能力矩阵 |
| 对赌 | 对赌要求 | 对赌依赖/接受情况 | P0 先结构化并进入深评，明确对应后再启用硬规则 |
| 风险 | 排除项和风险容忍 | 风险摘要及结构化风险 | 明确排除项可冲突，其余进入深评 |

### 5.3 上市状态统一

标的事实闭集：

```text
已上市 / 未上市 / 拟上市 / 未知
```

买家需求选择的是可接受集合：

```text
已上市 / 未上市 / 拟上市
```

- 可多选。
- 空集合或“不限”表示不启用上市状态条件。
- 不再将“准备上市”和“Pre-IPO”拆成两个与标的无法一一对应的需求值，统一规范为“拟上市”。
- 买家侧的“未知”不作为有效要求；无法判断时进入需要确认。

### 5.4 要求×能力矩阵

控股、并表、迁址、返投、团队留任等维度统一使用以下语义。

需求侧条件作用：

```text
必须满足 / 优先满足 / 不作要求
```

标的侧能力或意愿：

```text
是 / 可能 / 否 / 未知
```

统一判断矩阵：

| 需求作用 | 标的是 | 标的可能 | 标的否 | 标的未知 |
|---|---|---|---|---|
| 不作要求 | 忽略 | 忽略 | 忽略 | 忽略 |
| 必须满足 | 明确满足 | 可能满足，保留 | 明确冲突，淘汰 | 信息缺失，保留 |
| 优先满足 | 明确加分 | 较低加分 | 软性不足，不淘汰 | 信息缺口，不淘汰 |

系统底线：

> 只有“必须满足 + 标的明确否”才淘汰；标的信息未知永远不因未知而淘汰。

“可能”和“未知”均不得在 SQL 预筛阶段被排除，但排序时应保证：

```text
明确满足 > 可能满足 > 信息未知 > 明确不满足
```

## 六、全字段需要确认机制

### 6.1 覆盖范围

所有由 AI 解析、可能进入需求画像的业务条件都必须支持需要确认，包括：

- 字段识别
- 条件值
- 运算符
- 金额或比例单位
- 必须/优先/仅深评作用
- 公共条件或方案范围
- 行业和地区映射
- 多值条件中的单个值

系统字段、审计字段和任务状态不属于业务条件，不需要套用此机制。

### 6.2 待确认数据结构

建议结构：

```json
{
  "scope": "非上市方案",
  "field": "min_revenue_yuan",
  "uncertain_part": "unit",
  "operator": "gte",
  "proposed_value": 5000000,
  "reason": "原文写500，未说明金额单位",
  "evidence": "营收要求500以上"
}
```

`uncertain_part` 可取：

```text
field / value / operator / unit / effect / scope / taxonomy_mapping
```

不保存置信度。

### 6.3 多值字段必须按条件项隔离

例如买家明确接受“医药与健康”，但“养老服务”是否属于接受范围不确定：

- 已确认的“医药与健康”继续参与匹配。
- 只有“养老服务”暂停生效并进入待确认。
- 不因一个值存疑而暂停整个行业字段。

行业、地区、上市状态集合等多值字段都遵循此规则。

### 6.4 复核动作

对每个待确认项支持：

- 采纳建议值并生效。
- 修改后生效。
- 确认不设置该条件。
- 改为仅深评。

编辑任何条件后应只清除该条件对应的待确认状态，不影响其他待确认项。

## 七、买家需求解析与规范化入库

### 7.1 完整流程

```text
（1）用户输入文字或上传买家需求材料
        ↓
    OCR、附件文本提取与材料合并
        ↓
（2）LLM 需求语义解析
        ↓
    原始需求条件 JSON
        ↓
（3）LLM 需求字段规范化
        ↓
    标准条件 + 需要确认 + 仅深评内容
        ↓
（4）代码确定性校验与事务写入
        ↓
    公共条件、方案、待确认事项、解析审计
```

第（3）步负责语义规范化和建议，不是最终可信校验；第（4）步代码才是最终入库权威。

### 7.2 第一阶段：LLM 需求语义解析

重心是理解和拆解需求，不加载完整行业字典，不要求直接猜数据库字段名或标准枚举。

主要任务：

- 识别公共条件和多个方案。
- 识别条件之间的 AND、OR。
- 提取原始业务维度、原始值、运算符和单位。
- 判断必须、优先、仅深评。
- 记录原文证据。
- 标记字段、值、作用或范围上的歧义。
- 含糊复合描述只作为仅深评内容，不擅自生成数值规则。

输出示例：

```json
{
  "intent_summary": "围绕医疗健康开展控股并购",
  "conditions": [
    {
      "scope": "公共条件",
      "raw_dimension": "行业",
      "raw_value": "医疗健康",
      "operator": "include",
      "effect": "required",
      "evidence": "主要考虑医疗健康行业"
    },
    {
      "scope": "公共条件",
      "raw_dimension": "地区",
      "raw_value": "长三角",
      "operator": "include",
      "effect": "preferred",
      "evidence": "长三角项目优先"
    }
  ],
  "scenarios": [],
  "ambiguous_statements": []
}
```

### 7.3 第二阶段：LLM 需求字段规范化

输入：

- 上一步原始需求 JSON
- 统一需求—标的字段契约
- 行业字典及别名
- 标准省市区列表
- 各枚举字段候选值
- 运算符、金额、比例和单位规则
- 公共条件与方案规则

主要任务：

- 将原始业务维度映射到标准需求字段。
- 将行业映射到标准一级、二级行业。
- 将“全国、长三角、华东”等地区语义展开为标准省份。
- 将同义枚举转换为标准候选值。
- 将万元、亿元、百分比和倍数换算为标准单位。
- 将无法唯一规范化的内容放入需要确认。
- 将字典外产品、技术和场景词放入仅深评内容。
- 不得补造原文没有的条件。

输出分组：

```json
{
  "normalized_conditions": [],
  "needs_confirmation": [],
  "deep_eval_only": [],
  "normalization_notes": []
}
```

行业规范化规则：

| 情况 | 处理 |
|---|---|
| 唯一命中字典或别名 | 写入标准行业 |
| 属于产品、技术、应用场景 | 进入仅深评 |
| 有多个合理字典映射 | 进入需要确认 |
| 完全无法理解 | 保留原文，进入需要确认或仅深评 |

枚举规范化规则：

| 情况 | 处理 |
|---|---|
| 明确同义词 | 自动转换 |
| 根据字段定义可唯一判断 | 自动转换 |
| 存在多个可能值 | 进入需要确认 |
| 用户没有提出该条件 | 不生成条件 |

### 7.4 第三阶段：代码校验与入库

代码负责：

- JSON 结构和字段白名单校验。
- 数据类型、枚举、数值范围和单位校验。
- 行业、行政区划值存在性校验。
- 条件作用、方案范围和运算符合法性校验。
- 待确认条件隔离。
- 多值条件逐项校验。
- 已确认条件、待确认事项和仅深评内容事务写入。
- 保存原始材料、语义解析输出、规范化输出、Prompt 版本、字典快照信息和实际写入差异。
- 触发需求匹配画像刷新。

AI 输出不得直接生成 SQL，也不得绕过代码校验写库。

字段级容错：

```text
10 个条件中 8 个合法
→ 正常写入 8 个

1 个无法唯一规范化
→ 写入需要确认

1 个只能用于语义判断
→ 写入仅深评
```

单个字段失败不得导致整项需求解析失败；如果没有任何结构化字段可写，仍保留原始材料和解析结果并提示人工复核。

### 7.5 Prompt 与节点边界

建议拆分为两个独立 Prompt 节点：

```text
buyer_intent_semantic_parser
buyer_intent_normalizer
```

- 买家新建解析和买家更新解析共用同一规范化节点和字段契约。
- Prompt 版本通过设置页「Prompt 版本管理」或 API 维护，不通过数据库迁移写入 Prompt。
- 两个节点分别留存输入、输出、Prompt 版本和错误信息，支持独立重试和回滚。

### 7.6 AI 管理模块同步改造

新增 LLM 节点不能只存在于后台任务代码中，必须同步进入设置页「AI 管理」并具备完整的可配置、可测试和可审计能力。

AI 管理模块新增或调整以下业务节点：

| 节点 | 设置页名称 | 主要职责 |
|---|---|---|
| `buyer_intent_semantic_parser` | 买家需求语义解析 | 理解原始材料，拆解公共条件、方案、作用、运算符、单位和证据 |
| `buyer_intent_normalizer` | 买家需求字段规范化 | 注入字段契约、行业字典、行政区划和枚举规则，输出标准条件、待确认和仅深评内容 |
| `recommendation_deep_eval_to_target` | 推荐深评·为买家找标的 | 固定买家需求，评价候选标的 |
| `recommendation_deep_eval_to_buyer` | 推荐深评·为标的找买家 | 固定标的画像，评价候选买家需求 |

AI 管理页面要求：

- 节点列表显示明确中文名称、业务说明、节点类型、当前模型和启用状态。
- 每个节点独立配置模型提供方、模型、温度、超时、最大输出和响应格式。
- 每个节点独立维护 Prompt 版本，支持新建版本、预览渲染、切换默认版本和回滚。
- Prompt 编辑器展示并校验该节点可使用的变量；语义解析节点不注入完整行业字典，规范化节点才提供行业、行政区划和字段候选值变量。
- 节点测试支持输入一份买家需求样例，并分别查看语义解析 JSON、规范化 JSON、校验问题和 Token/耗时。
- 深评测试按方向提供锚点与候选样例，避免用同一测试输入验证两个不同业务任务。
- 设置页显示最近测试结果、最近生产调用状态、Prompt 版本和错误摘要，便于判断问题发生在语义解析、规范化还是入库校验。
- 方向专属深评节点未配置时允许短期回退到公共 `recommendation_deep_eval`，但 AI 管理页面必须显示“正在使用兼容回退”，不得静默回退。
- 节点停用、Prompt 缺失或输出不合法时，不得绕过规范化或代码校验；任务应保留可复核错误信息。

Prompt 发布仍遵守平台规则：通过 AI 管理页面或 `/model-config/prompts` API 创建和切换版本，不新增 Prompt seed 数据库迁移。仅当新节点需要新的输出字段、变量或任务路由时随代码发版。

## 八、正向与反向推荐流程

### 8.1 一个配对语义，两套候选召回

正向与反向推荐始终回答同一个问题：

```text
Accept(需求, 标的) = 这项买家需求是否接受这个标的？
```

不维护两套相互独立的业务判断规则，以免同一需求—标的配对在两个方向得到不同结果。

```text
买家需求
   │
   └─ 正向 SQL：从标的事实中召回候选 ─┐
                                      │
                                      ▼
                           共用 PairEvaluator
                        需求是否接受这个标的？
                                      │
                                      ▼
                           正向排序 + Prompt A
                           为买家评价候选标的


标的画像
   │
   └─ 反向 SQL：从需求条件中反查候选 ─┐
                                      │
                                      ▼
                           共用 PairEvaluator
                        需求是否接受这个标的？
                                      │
                                      ▼
                           反向排序 + Prompt B
                           为标的评价候选买家
```

### 8.2 推荐阶段

```text
1. 方向专属 SQL 无损召回
2. 共用确定性配对判断
3. 方向专属排序
4. 方向专属 AI 深评
5. 结果解释与人工选中
```

SQL 层只做召回和已知硬冲突预筛：

- 没有设置该条件时保留。
- 条件处于需要确认时不得参加 SQL。
- 标的事实未知或可能时保留。
- 只有已生效的必须条件与标的明确事实冲突时才允许排除。
- SQL 是执行优化，不是产品规则的唯一实现位置。

### 8.3 正向召回：需求找标的

固定公共条件和每个启用方案，从标的事实中召回候选：

```text
标的满足公共必须条件
AND
标的至少满足一个方案的全部已知必须条件
```

对标的未知字段不做排除，进入确定性判断后标记为 `possible` 和信息缺口。

### 8.4 反向召回：标的找需求

固定标的事实，反向查询哪些需求或方案可能接受它。例如医药与健康、营收 800 万元、可控股的标的应保留：

```text
一级行业无必须限制 OR 包含医药与健康
AND
最低营收无要求 OR 最低营收 ≤ 800万元
AND
控股不作要求 OR 控股为优先 OR 标的可以/可能控股
AND
未命中明确排除行业
```

如果标的控股能力未知，不得淘汰要求控股的需求；如果标的明确不可控股，才淘汰“必须控股”的方案，控股为优先的方案只降低排序。

### 8.5 共用确定性判断输出

每个需求—标的—方案组合输出：

```text
compatible / possible / conflict
明确满足项
可能满足项
软性不足
信息未知项
明确冲突项
规则分
最佳命中方案
其他可命中方案
```

验收要求：对任意固定的需求—标的配对，从需求找标的和从标的找需求必须得到相同的兼容状态、冲突原因和方案判断。

## 九、方向专属 AI 深评 Prompt

### 9.1 必须拆成两套 Prompt

代码可以共用调用、分片、校验和结果写入，但业务 Prompt 分为：

```text
recommendation_deep_eval_to_target
recommendation_deep_eval_to_buyer
```

如果方向专属 Prompt 未配置，不应长期依赖公共 Prompt 回退；公共 Prompt 只作为短期兼容和故障恢复。

### 9.2 Prompt A：为买家找标的

固定买家需求，评价每个候选标的：

- 使用需求公共条件和实际相关方案。
- 使用标的完整结构化事实、画像、风险和信息缺口。
- 重点判断业务匹配、财务门槛、交易可行性和风险。
- 买家主体背景只作为协同性上下文，不得凭买家背景臆造需求条件。

### 9.3 Prompt B：为标的找买家

固定标的画像，评价每个候选买家需求：

- 使用标的完整事实和画像。
- 使用候选需求的公共条件、最佳命中方案和其他可命中方案。
- 重点判断该需求是否可能接受标的、哪些条件明确满足、哪些信息尚需补充以及联系价值。
- 买家主体作为辅助信息，不得取代明确需求条件或擅自扩大买家接受范围。

### 9.4 两个方向共用输出契约

```json
{
  "candidate_id": "...",
  "grade": "A|B|C",
  "best_scenario_id": "...",
  "matched_scenarios": [],
  "reason": "一句话综合判断",
  "risks": "主要风险",
  "info_gaps": "需要补充的信息"
}
```

最终排序可以使用 AI 档位，但规则冲突不能被 AI 改写为匹配；AI 只能在未冲突候选中做综合判断和排序。

推荐对话中的条件解析器可以继续共用一个 Prompt 和输出契约，通过 `mode` 区分方向；若后续实际效果证明有明显差异，再拆分方向节点。

- 方案编辑器不得维护一套独立的少量字段白名单，应读取统一需求条件契约。

推荐结果的主对象仍是需求，买家主体作为辅助信息。优先展示可解释事实，不以单一分数代替判断。

```text
+================================================================================+
| 北大健康 · 医疗健康产业并购                                             A档 |
| 最佳匹配方案：非上市公司控股并购                                          |

| ? 团队留任意愿未知                                                        |
| - 地区不在优先范围                                                        |
| AI判断：标的满足非上市方案的全部已知必须条件，建议优先联系并确认迁址与团队。|
|                                                        [完整对比] [选中]   |
+================================================================================+
```

完整对比至少显示：

- 条件作用和复核状态。
- 需求值、标的值和比较结果。
- 实际命中方案。
- 明确满足、可能满足、软性不足、未知和冲突。
- AI 深评理由、风险和补充信息建议。

## 十二、统一字段契约作为唯一事实源

后续不能继续在买家页面、解析器、方案白名单和推荐规则中分别手写字段集合。需建设统一字段契约，至少定义：

```text
需求字段
对应标的字段或派生表达式
字段类型和标准单位
允许的运算符
需求侧候选值
标的侧候选值
要求×能力比较规则
默认匹配作用
是否允许人工修改作用
是否允许进入方案
是否支持多值
未知值处理
行业/地区字典来源
是否进入 SQL 预筛
是否进入确定性排序
是否进入 AI 深评
```

以下消费者必须读取或由该契约校验：

- 买家公共条件编辑器
- 买家方案编辑器
- AI 语义解析输出校验
- AI 字段规范化
- 代码入库白名单
- 正反向 SQL 预筛
- 共用确定性配对判断
- 推荐结果逐字段对比
- 待确认字段中文名和编辑控件

## 十三、开发顺序

### P0-1：冻结统一字段契约

1. 完成需求—标的字段对应表。
2. 统一上市状态及其他枚举。
3. 定义要求×能力矩阵、运算符和未知处理。
4. 明确每个条件是否支持多值、方案和待确认。

### P0-2：重构编辑基础组件

1. 抽取行业字典勾选基础组件。
2. 抽取省市区级联基础组件。
3. 标的继续使用单值所在地和所属行业外壳。
4. 需求增加行业接受/排除和地区多选外壳。

### P0-3：补齐需求详情与字段编辑

1. 公共条件和方案读取统一字段契约。
2. 补齐团队留任、迁址、返投、现金流、盈利状态等已存在但当前编辑器缺失的条件。
3. 条件作用改为必须、优先、仅深评。
4. 待确认覆盖所有业务条件并支持逐项复核。

### P0-4：拆分买家需求解析链路

1. 建立需求语义解析节点和输出契约。
2. 建立字段规范化节点并注入行业字典、行政区划和枚举规则。
3. 建立代码确定性校验、字段级容错和事务写入。
4. 买家新建和更新共用规范化能力。
5. 将语义解析、字段规范化节点接入 AI 管理页面和节点测试。

### P0-5：统一正反向规则

1. SQL 仅排除已知必须冲突，未知不排除。
2. 正反向共用 PairEvaluator。
3. 按方案生成 compatible、possible、conflict 和解释。
4. 修正页面标签与后端实际规则不一致的问题。

### P0-6：拆分方向专属深评

1. 发布“为买家找标的”深评 Prompt。
2. 发布“为标的找买家”深评 Prompt。
3. 共用输出契约、校验、分片和结果展示。
4. 公共 Prompt 仅保留为兼容回退。
5. AI 管理页面显示两个方向节点及当前是否使用公共 Prompt 回退。

### P0-7：推荐解释与验收

1. 展示最佳方案和其他可命中方案。
2. 展示满足、可能、软性不足、未知和冲突。
3. 支持完整逐字段对比和最终选中。
4. 完成正反向一致性和 Prompt 效果验收。

## 十四、核心验收用例

### 14.1 行业与地区

1. 标的和需求行业编辑使用同一行业字典、搜索及一级二级勾选逻辑。
2. 标的和需求地区编辑使用同一省市区列表及级联逻辑。
3. 需求可以选择多个省市区；标的仍只保存一个实际所在地。
4. “全国”规范化为不限地区；“长三角”可规范化为上海、江苏、浙江、安徽。
5. 字典外产品词只进入仅深评，不污染结构化行业筛选。

### 14.2 字段对应

1. 买家“团队必须留任”正确对应标的“团队可留任”。
2. 买家上市要求只使用已上市、未上市、拟上市的可接受集合。
3. 控股、并表、迁址、返投和团队留任使用统一要求×能力矩阵。
4. 所有结构化需求字段都能找到对应标的事实或明确标记为仅深评。

### 14.3 必须、优先和未知

1. 必须迁址且标的明确不接受迁址时淘汰。
2. 必须迁址且标的迁址意愿未知时保留并标记信息缺口。
3. 优先迁址且标的明确不接受迁址时不淘汰，只降低排序。
4. 标的任何事实未知时都不能仅因未知被 SQL 淘汰。
5. 页面标签与实际确定性规则一致。

### 14.4 需要确认

1. 任一业务条件的字段、值、运算符、单位、作用和方案范围都能进入需要确认。
2. 待确认条件不参加 SQL 和确定性排序，但进入 AI 深评。
3. 多值字段中一个值待确认，不影响其他已确认值继续生效。
4. 逐项采纳、修改、不设置或改为仅深评后，只更新对应条件。

### 14.5 两阶段 AI 解析

1. 第一阶段不依赖完整行业字典，能输出原始需求条件、方案、作用和证据。
2. 第二阶段读取行业字典、行政区划和枚举规则，输出标准条件、待确认和仅深评内容。
3. 第二阶段无法唯一规范化时不得猜值入库。
4. 代码校验能拒绝非法字段和枚举，并保留其他合法字段。
5. 原始材料、两阶段输出、Prompt 版本和实际写入结果都可审计。
6. AI 管理页面可以分别配置、测试和查看语义解析与字段规范化节点。
7. 规范化节点测试能够看到实际注入的行业字典、行政区划和字段枚举变量，但不得泄露模型密钥。

### 14.6 正反向推荐

1. 营收 800 万元的标的保留最低营收 300 万、500 万和无营收要求的需求，淘汰必须最低营收 1000 万且标的营收已知的需求。
2. 同一个需求只要一个启用方案不冲突就保留，并显示实际命中方案。
3. 同一需求—标的配对从两个方向得到相同的兼容状态和冲突原因。
4. 两个方向分别调用各自深评 Prompt，但输出同一结果契约。
5. AI 不得将确定性规则判定的明确冲突改写为 A 档匹配。
6. AI 管理页面可以分别配置和测试两个方向的深评节点，并明确显示公共 Prompt 回退状态。

## 十五、最终确认清单

请在进入下一轮开发前确认以下原则：

- [ ] 行业和行政区划的基础数据、搜索、勾选、级联逻辑在标的与需求之间共用。
- [ ] 需求行业和地区使用多选业务外壳，标的继续使用客观归属和单一所在地外壳。
- [ ] “全国、长三角、华东”等自然语言由 AI 理解并规范化到标准省份，不建设严格区域组字典。
- [ ] 需求条件作用统一为必须满足、优先满足、仅深评；需要确认是独立复核状态。
- [ ] 所有 AI 解析出的业务条件都支持需要确认，多值字段按条件项隔离。
- [ ] 上市状态等维度与标的建立一一对应，需求侧“不限”不与“未知”混用。
- [ ] 控股、并表、迁址、返投和团队留任统一使用要求×能力矩阵。
- [ ] 只有“必须满足 + 标的明确不满足”才淘汰，标的未知永远不因未知淘汰。
- [ ] 买家需求处理拆为 LLM 语义解析、LLM 字段规范化、代码确定性校验入库。
- [ ] 行业字典、行政区划和枚举规则在规范化阶段注入，而不是要求第一阶段直接输出标准值。
- [ ] 正向和反向使用同一 PairEvaluator，但维护两套方向专属 SQL 召回和深评 Prompt。
- [ ] 新增语义解析、字段规范化和两个方向深评节点同步进入 AI 管理页面，支持独立配置、Prompt 版本、测试、状态和回退提示。
- [ ] Prompt 通过设置页或 API 维护，不通过数据库迁移写入。

全部确认后，本文件作为买家管理与推荐买家下一轮 P0 开发、测试和验收的正式基线。
