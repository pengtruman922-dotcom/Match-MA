## 〇、一页结论

| 判决 | 内容 |
|---|---|
| **A 字段** | 标的行业改成 `seller_target.business_tags_json`（自由标签，与 `buyer_party.business_tags_json` / `buyer_intent_scenario.business_tags_json` 同构、同一归一函数、同一契约文案）。`industry_taxonomy` 表、字典服务、设置页 tab、导入功能整体下线 |

## 二、四条判决与理由

### 判决 A：标的行业改自由标签，字典整体下线

**做什么**：`seller_target` 新增 `business_tags_json`（`jsonb not null default '[]'`，形状 CHECK，GIN 索引），
与买家两侧同构。`industry_pairs_json` 退役；`industry_taxonomy` 表与设置页整套下线。

**为什么标的侧也不需要字典**（与 0828 判决一同源，但依据是标的侧自己的数据）：

1. **字典没有在承担信息**。阿里云 94 个标的里 81 个只有一级行业，其中 52 个是「制造与工业」；
   Railway 好一些（66% 有二级），但二级行业只用了 29 个词，而字典维护着 156 个二级 + 26 个别名。
   `business_summary` 99% / 93% 有值 —— 真正描述「这家做什么」的一直是摘要，不是字典项。
2. **字典的唯一理由是跨侧匹配的共享词表，而那个契约 0828 已经解散了。** 买家侧说的是
   「薄膜电容器」「线控底盘」（方案标签），标的侧存的是「制造与工业」。今天没有任何一条 SQL 在比这两列，
   `industry_pairs_json` 的 `screening` 0828 就置了 `False`。留着字典，是在维护一个没有对手方的闭集。
3. **字典外的词会被静默丢掉**。`normalize_l2_values` 对不在字典里的二级词直接 drop（记一条
   `industry_l2_unmapped` note），`normalize_industry_pairs` 对 L1 也解不出的整对丢弃。
   模型写了「军用半导体分立器件」，落库变成「制造与工业」—— 这是信息损失，不是归一。
4. **外部 Agent 已经在按文本判断**。MCP 的 `INSTRUCTIONS` 与 `skills/match-ma-mcp/SKILL.md`
   都写着「库里没有行业筛选，业务是否对口由你读文本判断，行业只是辅助」。把「辅助」从 15 个粗桶
   换成 3~5 个赛道级自由标签，是给 Agent 更准的辅助，不是拿掉辅助。

**与 0828 的异同**（要么照抄、要么说清为什么不一样）：

| | 0828 买家需求侧 | 本单标的侧 |
|---|---|---|
| 自由标签 + 自由文本，不建字典 | ✔ | ✔ 照抄 |
| 退役 = 改注册表标志位，阶段 A 不删列 | ✔ | ✔ 照抄 |
| 退役字段保留 `manual` 可写，过渡期人工能修 | ✔ | ✘ **不同**：`industry_pairs_json` 的任何写入都要过字典，而字典服务阶段 A 就删。`writable_by` 直接清空（有先例：`_BI_RETIRED_READONLY`） |
| 有调研写入方 | ✘ 需求侧没有 research | ✔ **不同**：标签是 `research` 可写的，调研 mapper 契约与 `research_apply` 归一要跟着改 |
| 退役对象 | 列 | 列 + 兼容投影列 + 字典表 + 设置页 + 导入 + 过渡 skill |
| 消费者 | 反向 skill 的首轮召回 | 外部 Agent 的 `targets_scan` 载荷（正向首轮召回） |

### 判决 B：`targets_filter` 不加标签条件，也不留 `industry_l1`（回答问题 2）

三个候选逐一判：

| 候选 | 判决 | 理由（以「Agent 能不能筛得更准」衡量） |
|---|---|---|
| ① 彻底不设行业 / 标签条件（维持现状） | **采用** | 库 94 / 71 家，`targets_scan` 上限 300，**一页就是全库**。Agent 读 3~5 个标签 + 82 字摘要 + 主要产品做首轮判断，召回率只受材料质量限制，不受词表限制 |
| ② 标签包含匹配（`business_tags_json ?| array[...]`） | **不加** | 两侧标签都是自由词，由不同模型在不同材料上写出来，「汽车零部件」vs「汽车零部件制造」vs「商用车车架」是同一件事却不相等。漏掉的标的**不会出现在任何拆分里**（分不清「没录标签」与「标签不匹配」），Agent 看不见自己漏了什么。更糟的是它会诱使 Agent 跳过 `targets_scan` 直接 filter —— 买家侧 SKILL.md 已经在禁止同一种行为 |
| ③ 保留 `industry_l1` 做粗筛 | **不留** | 15 个桶，阿里云 55% 的标的在同一个桶里，筛不出任何东西。而为了这一个参数，字典表、归一服务、设置页都得活着 |

**触发条件写清楚，将来不用重新争论**：只有当 `targets_scan` 一页装不下全库（A–D 级标的 > 300）
或单页载荷超过 Agent 的上下文预算时，才考虑加标签条件，并且加的时候必须带 `missing`（没录标签）
与 `failed`（标签不匹配）的拆分。今天离这个阈值还有三倍空间。

### 判决 C：三列两阶段退役，最终真删（回答问题 3）

**阶段 A（本单第一次发版）**：注册表把 `industry_pairs_json` 标退役（`group=None`、`writable_by=frozenset()`、`screening=False`、`deep_eval=False`），
`industry_l1/l2` 留在 `_SELLER_TARGET_EXTRA_FACT_COLUMNS` 里继续被 SELECT 出来但没有任何读者渲染它。
**所有读写方在 A 就切到 `business_tags_json`**，三列变成纯粹的「还在库里」。

**阶段 B（A 在两套部署都跑稳、存量收敛完成、观察一周之后）**：一条迁移 drop 三列、四个索引、一个 CHECK、`industry_taxonomy` 表；
代码只删「这些列还存在」的声明（注册表退役条目、`_SELLER_TARGET_EXTRA_FACT_COLUMNS`、Pydantic 可选字段、TS 类型、fixture 键）。
**B 不碰任何业务逻辑** —— 这是 0828 定下的节奏：「阶段 B 的动作变成把注册表退役区那一块删掉」。

**为什么不一次删完**：本项目三次先例（0727、0814、0828）都是两阶段，理由没变 —— preDeploy 迁移跑完才发现某条投影漏改，
那时数据已经没了。行业三列在后端被 27 个文件引用（含测试与过渡 skill）、前端 19 个文件引用。

**为什么最终要真删而不是留死列**：三个列 + 一张表 + 四个索引留在库里，每个新人都会问一遍「这是活的吗」；
`test_sql_schema_consistency` 的 SCHEMA 重建不认 drop，死列会一直「存在」于测试的世界观里；
`_SELLER_TARGET_EXTRA_FACT_COLUMNS` 会一直把它们 SELECT 出来喂给解析上下文。死列有持续成本，删列是一次性成本。

### 判决 D：买家主体链不改 prompt，只改代码侧契约（回答问题 4）

实测两边默认版本：`buyer_party_parser v0.2`、`buyer_party_normalizer v0.2`、`buyer_party_researcher v0.3`，
正文里**没有任何行业字典契约**（没有 `industry_*` 变量、没有闭集清单）。标签规则今天在两处代码里：
`buyer_party_ingest.py:370` 的 `rules.business_tags` 与 `:1986` 的 `field_contract` note，文案都是
「自由文本，不过行业字典，5 个以内，写买家自己的细分主业」。

要改的是：

1. **标签契约文案抽成三侧共用常量**（`services/business_tags.py`），买家主体两处、方案侧
   `buyer_intent_parse.py`、标的侧解析 / 更新 / 调研映射契约都引用同一份。粒度与数量约定见 §3.3。
2. **`research_apply.normalize_structured_fact` 删掉 `industry_pairs_json` / `industry_l1` / `industry_l2` 三个分支**。
   它是实体无关的入口（`entity` 参数），买家主体的提案若叫 `industry_l1` 今天会走进标的侧的字典分支 —— 顺手关掉这个洞。
3. **`buyer_intent_parse.py:120-149` 删掉 `industry_l1_list` / `industry_l2_list` 传参与 `dictionary_snapshot`**。
   `nodes.py:138-141,167-171` 的注释说「线上可能正跑着引用它们的旧版本」，本次实测两边默认版本
   （normalizer v0.5.0 / parser v0.10.0 / semantic v0.2.0）都不引用，可以删。
4. **`business_update_extractor` 的上下文** `bound_buyer_parties` 不变；但该 prompt 要改版（它给标的侧列了 `industry_pairs_json`，见 §七）。

三个细节，漏一个就是一类静默 bug：

- `multi_value=True` **且没有** `enum_options`：`multi_value_enum_values()` 与 `SELLER_TARGET_CLOSED_LIST_FIELDS` 都按「有闭集」过滤，
  标签自动不进闭集校验；前端 `infoGroups.ts` 的 json 分支按 `multi_value` 用顿号串显示，找不到 enum label 就原样显示 —— 正是标签要的行为。
- `field_writer._normalize_value` 的 json 分支今天对「多值但无闭集」直接 `return value`，**不校验**。要加一个显式分支
  `if indicator.column == "business_tags_json": return normalize_business_tags(value)`，它同时覆盖买家主体的手动编辑路径（0827 那次「整串 JSON 变成唯一标签」的洞在写入口这一层也就关上了）。
- `tests/test_indicator_registry.py::test_every_indicator_is_a_real_seller_target_column` 要求 baseline 之后新增的列在 `post_baseline_columns` 里登记建列迁移，
  新列必须加一行 `"business_tags_json": (BUSINESS_TAGS_MIGRATION, "add column if not exists business_tags_json jsonb")`。

### 3.3 三侧业务标签契约（粒度与数量约定）

三列同构：`buyer_party.business_tags_json`（主体自己做什么）、`buyer_intent_scenario.business_tags_json`（这个方案要买什么）、
`seller_target.business_tags_json`（标的自己做什么）。**同一个归一函数、同一段契约文案、同一条 GIN 索引写法。**

| 约定 | 取值 | 依据 |
|---|---|---|
| 粒度 | **细分赛道或产品品类**，与买家方案标签同级：「汽车零部件」「PCB」「污水处理运营」「维生素原料药」「无人机管控系统」 | 买家说的就是这一级（0828 实测「薄膜电容器」「线控底盘」）；两侧同级 Agent 才能比 |
| 不写什么 | 一级大类（制造业 / 能源 / 医药）、公司名、地名、形容词（领先 / 优质）、**对方的需求**（标的不写买家要什么，买家不写想买什么） | 一级大类是本单要下线的东西；地名有 `location_*`；需求有方案层 |
| 形状 | 名词短语，2~10 个字 | 实测两边主体标签均长 5~6 字 |
| 数量 | **3~5 个，最多 8 个** | 两边主体与方案实测均 4.8 个；阿里云有一条 11 个（湖北联投）、方案最多 15 个，都是「把业务板块列表整个倒进来」，信息量不增 |
| 归一 | `normalize_business_tags`：去空白、去空值、去重、限长，**不过任何词表** | 0828 判决一 |
| 代码上限 | `MAX_BUSINESS_TAGS=50` 是防爆不是业务规则，**不改**；数量由契约文案控制 | 0824 决定「数量由解析侧控制，DB 不限」 |

文案落成一个函数，按实体换最后一句：

## 五、迁移与回填（回答问题 5）

### 5.1 阶段 A：`025_seller_target_business_tags.sql` + `alembic/versions/2026MMDD_0072_seller_target_business_tags.py`

alembic 壳照抄 `20260907_0071_api_keys.py`（`run_migration_sql`）。SQL 全文（**注释里不能出现分号**，splitter 会切坏）：

```sql
-- 标的行业改自由标签，与买家两侧同口径（方案 0908）。
-- 阿里云 94 个标的里 52 个的行业就是「制造与工业」四个字，字典没有在承担信息。
-- 唯一的跨侧契约（买家行业词 ↔ 标的 industry_pairs_json）0828 已解散，
-- 留着字典等于维护一个没有对手方的闭集。
--
-- 本文件只加列、回填、加索引。三个旧列与 industry_taxonomy 表的 drop 在阶段 B，
-- 等两套部署都跑上本轮代码并完成存量收敛之后另开迁移。
--
-- 注意：本文件的注释里不能出现分号，自制 splitter 按分号切语句。

alter table seller_target
  add column if not exists business_tags_json jsonb not null default '[]'::jsonb;

alter table seller_target
  drop constraint if exists chk_seller_target_business_tags_json;

alter table seller_target
  add constraint chk_seller_target_business_tags_json
  check (jsonb_typeof(business_tags_json) = 'array');

-- 回填只取二级行业。一级大类（制造与工业）不是业务标签，写进去会污染标签筛选下拉，
-- 而且对读摘要的 Agent 没有任何信息量。没有二级的标的留空，等重解析收敛。
update seller_target
set business_tags_json = (
  select coalesce(jsonb_agg(l2 order by l2), '[]'::jsonb)
  from (
    select distinct btrim(pair ->> 'l2') as l2
    from jsonb_array_elements(
      case when jsonb_typeof(seller_target.industry_pairs_json) = 'array'
           then seller_target.industry_pairs_json else '[]'::jsonb end
    ) as pair
    where nullif(btrim(pair ->> 'l2'), '') is not null
  ) as tags
)
where business_tags_json = '[]'::jsonb
  and exists (
    select 1
    from jsonb_array_elements(
      case when jsonb_typeof(industry_pairs_json) = 'array'
           then industry_pairs_json else '[]'::jsonb end
    ) as pair
    where nullif(btrim(pair ->> 'l2'), '') is not null
  );

create index if not exists idx_seller_target_business_tags
  on seller_target using gin (business_tags_json)
  where deleted_at is null;
```

`downgrade`：drop index、drop constraint、drop column。

### 5.2 回填规则与两边预期

| 规则 | 决定 | 理由 |
|---|---|---|
| L2 → 标签 | ✔ 逐个 distinct 并进数组 | 二级行业本来就是赛道粒度（汽车零部件 / 半导体 / 医疗器械），与买家标签同级 |
| L1 → 标签 | ✘ | 「制造与工业」不是标签；52 个标的会得到同一个无信息量的标签并把筛选下拉顶到第一位 |
| `main_products_text` → 标签 | ✘ 不在 SQL 里做 | 产品名（PVPK30、维生素K3）是另一个轴，切分规则也不统一（逗号 / 顿号 / 中文逗号混用）。交给重解析 |
| 字典同义词（食品 / 食品制造 / 食品加工） | 不合并 | 自由标签不做同义词治理，这是设计不是失真 |
| 只回填空数组 | ✔ | 幂等，重跑迁移不覆盖人工或解析写过的值 |

预期结果：阿里云 **13/94** 得到标签（81 个空着），Railway **47/71** 得到标签。
**回填不是收敛，只是不丢已有信息** —— 真正让标签覆盖全库的是 §5.3。

### 5.3 存量收敛：谁来跑、怎么跑

> **施工修正（2026-09-09）**：下面「整条重解析」的方案在阿里云试跑 5 条后停用 —— 它会把调研写的风险摘要压缩改写、
> 重新判所在地，财务数字虽是同值也会在审计链里刷出一串假改动。实际采用的是
> `scripts/backfill_target_business_tags_inplace.py`：在 api 容器里直接调标的解析节点的模型，
> 从名称 + 业务摘要 + 主要产品生成 3~5 个标签，经统一写入口**只写 `business_tags_json` 一列**；
> 摘要为空的跳过、不从公司名猜。`backfill_target_business_tags.py`（整条重解析）保留，只在确实要重抽全部字段时用。

`POST /seller-targets/{id}/parse` 已经存在（`seller_targets.py:1085`）：`raw_target_text` 可省略，省略时用
`_seller_target_parse_fallback_text` 把名称 + 主体 + 业务摘要 + 交易摘要 + 风险摘要拼成材料；`force=true` 跳过「已有解析任务」检查；
标的在调研中时返回 409。阿里云 99% 的标的有摘要（均 82 字），够模型写出 3~5 个标签。

**跑法**：新增 `scripts/backfill_target_business_tags.py`（跟 `match_ma_api_tools.py` 同一套鉴权，`--api-base` 指向 Railway 或 ECS）：

1. `GET /seller-targets?limit=200` 取 `business_tags_json = []` 且级别 A–D 的标的；
2. 逐个 `POST /{id}/parse`（`force=true`），每次间隔 3~5 秒（`worker-llm` 单队列，别把顾问的解析排到几十个补跑后面）；
3. 轮询 `/parse-status`，汇总成功 / 失败 / 409；
4. 结束后 `POST /search-docs/jobs/seller-targets/rebuild` 重建全部搜索文档（否则 `seller_target_search_doc.full_text` 里还是「一级行业：制造与工业」）。

**成本**：一条解析一次模型调用，阿里云约 81 次、Railway 约 24 次。

**副作用要知道**：重解析会把摘要里的其他字段也再抽一遍。级别不会被打回（§2.4 反模式①已修，AI 只能进 E 不能出 E、未提取不写），
但财务数字若摘要里有不同口径会走 `needs_confirmation` / 待复核。**先在阿里云跑 5 个看更新记录，再全量。**

**验收指标**：A–D 级标的 ≥ 90% 有 ≥ 3 个标签；抽 10 个看标签质量（没有「制造业 / 能源」这种大类词、没有公司名、没有地名）；
`targets_scan` 返回里「业务标签」非空比例同上。
