## 一、为什么做件〇

排查买家创建流程时顺手核了一条链，四个环节全部落空：

| 环节 | 事实 |
| --- | --- |
| 入口 | `RecommendationAgentTurnRequest` 只有 `mode / user_message / attachment_ids`，**没有任何买家 id —— 会话在结构上无法锚定** |
| 前端 | 「推荐标的」按钮带 `?intentId=`，但 [Recommend.tsx:600](../frontend/src/pages/Recommend.tsx:600) 的注释自己写着 *"prefill the box rather than to anchor the session"*，它只把需求转成文本 chip；而它手上的主体数据只有 `buyer_name` |
| 初筛闸门 | `screening_sql.py` 对 `buyer_party` **零引用** |
| 深评 | `buyer_party_fact_block()` 写好了、有 4 条测试、docstring 点名北控「与现有业务有关联性」与北京工控「强链补链」是它存在的理由 —— 但唯一调用点 `recommendation.py` 的 lambda **没传 `buyer_party_id`**，函数第一行 `if not buyer_party_id: return ""` |

**结论**：买家主体解析与调研链路产出的全部字段（性质/上市/市值/营收/业务标签/补充信息），此前唯一用途是在详情页上给人看。**推荐链路一个字都收不到。**

`run_recommendation_deep_eval` 的 docstring 自己承认了：「参数留着是为了锚定式调用（从买家需求详情页发起）**接上来时**不用改签名」——那条路一直没接。

## 二、改了什么

### 1. 会话记住锚点（`491c7d6`）

`agent-turn` 加可选 `buyer_intent_id`。**不传时行为与从前逐字节相同**（纯对话页仍是主场景）；传了才把需求与推导出的主体落进 `recommendation_session` 那两个一直写 `None` 的列。

三处刻意：

- **可见性按用户给的那条需求判**（`ensure_entity_visible` 在 `_get_buyer_party_id_for_intent` 之前）。不加这道检查，传一个别人的需求 id 就能把别人的买家资料读进自己这一轮。
- **锚定不改变会话形态**。`_recommendation_session_display` 里 agent 分支先于锚点分支返回，列表里它还是「N 轮对话」，`temporary_filter` 的关系创建保护照旧。
- **补写锚点只补空的**（`where buyer_intent_id is null`）。换锚点等于之前几轮的回答悄悄换了买家。

深评侧读取做成**惰性 + 记一次**：中止在深评之前的轮次一次都不查，一轮里深评跑两次（agent 自己跑或代码补跑）也不查两遍。

> 第一版把读取写在 handler 开头，挂了 8 条既有用例（它们的假 db 对所有查询返回同一个 `EmptyRows`）。惰性化之后中止类用例自然不再碰到这条查询——这个改动是被测试逼出来的，也确实更对。

### 2. 深评看得到候选自己那句业务说明（`15dd438`）

第一轮验收就撞到另一半：买方自身情况已到位，候选侧只有行业与财务数字，于是协同性诉求判成「无法判断」，理由写「画像为空」——**而那家标的的 `business_summary` 是有内容的，只是没人送进来**。

实测覆盖率：

```
画像（四栏 profile_section）  22/50   44%
business_summary             46/50   92%   中位数 38 字，最大 171 字
```

深评此前只读画像，于是对一多半候选，协同性这类诉求**结构上判不了**。反方向对称处理：候选是买家需求时这句话在它的主体上，所以走 `buyer_party`。上限 300 字纯防御。

## 四、发现的问题

### 问题 1：标的自己那句业务说明不进深评 —— 已修（`15dd438`）

第一轮两侧都判「无法判断」，`info_gaps` 写「画像为空，无法判断具体产品品类、客户渠道、产能布局与买家的协同点」。查下来：`build_deep_eval_candidates` 只读 `profile_section`（44% 覆盖），不读 `business_summary`（92% 覆盖）。

买家侧的业务说明已经在块里了，标的侧没有——协同性判断需要两边都有。第二轮验证有效。

### 问题 2：缓冲式模型调用没有墙钟，能跑成节点预算的五倍以上 —— 已修（`b386db4`）

**现象**：工控那条 1462 字需求，`buyer_intent_semantic_parser` 配 300 秒，实跑 **26 分钟仍未返回**。job 一直 `running`、`ai_trace` **一条没有**（trace 在调用返回后才写），前端一直停在「语义解析中」，**没有任何报错**——因为确实没超时。随后 stale 清扫器把它捞回来重试，`attempt=2` 最终成功了——**代价是 26 分钟的界面假象**。

同一时段匿名对照那轮的 `recommendation_agent` 也卡住了，只有一条 `query_parser` trace ——**同一个根因**。

**触发条件不是输入长度**：修复上线后同一条 1462 字需求 191 秒就解析完了（attempt 1）。那 26 分钟是**一次偶发的连接挂死**，而缺少墙钟让偶发挂死变成了「无声挂到 stale 窗口」。这也是它此前没被发现的原因——每次都会被 stale 清扫器兜住，最终 `succeeded`，只是慢得离谱且期间毫无信号。

**根因**：`urlopen(timeout=)` 只约束**单次 socket 操作**，服务端持续吐字节就永远不触发。这件事流式路径的 docstring 早就写明并自己量了墙钟：

> `timeout_seconds` is enforced **twice**, on purpose. `urlopen` applies it per socket operation, which on a stream resets with every token — a node configured for 180 seconds could run for ten minutes as long as the tokens kept dripping.

**但那道墙钟只加在流式那一支**，而所有非流式节点（解析、调研、深评、归一、编排 agent）都走缓冲式。

**改法**：分块读 + 每块前检查墙钟，与流式那个循环同一个形状，不引入新的并发面。超时抛 `LlmCallError` 而非裸 `TimeoutError`（后者会绕过调用方的 `except`，失败分支写 trace 的代码不执行，一次挂死什么记录都不留）。报错带「已读多少字节」，用来分辨「一个字节都没来」和「读到一半卡住」。

**影响面**：这是所有 LLM 节点共用的路径。改动附 4 条新用例，全量 1258 passed。

**诚实说明**：修复上线后的第三轮**没有真的触发这条墙钟**（那次解析 191 秒就正常返回了）。所以这个修复目前由单元测试钉住，**不是由生产运行验证的**——要在生产里看到它生效，得等下一次偶发挂死。

### 问题 3：方案拆分选错了轴，条件被收窄且不可见 —— **未修，需要你定**

盐业那条需求解析得相当好——正确拆成两个方案，还抓到了 `buyer_industry_advantage_summary = "买家拥有雷州、徐闻、阳江三个省属盐场，具备盐田资源协同优势"`：

```
方案A：并表控股    min_revenue_yuan=10亿  min_net_margin=5.0  requires_control=yes
                   requires_consolidation=yes  earnout_requirement=preferred
方案B：参股不并表  requires_control=no  accepts_minority_investment=yes
                   industry_focus_tags=["战新产业"]
```

但原文那句是：

> 营收：**上市要有10个亿，非上市要至少4-5亿**

而落库结果：

```
方案A  min_revenue_yuan         = 10亿
方案A  acceptable_listed_status = None      ← 不区分上市与否
需求顶层 acceptable_listed_status_json = ['listed', 'unlisted']
needs_confirmation 条数 = 0
```

**后果**：一个营收 5 亿的**非上市**标的会被方案A 排除，尽管买家明确说过 4-5 亿可以。原文有两条独立的轴——上市/非上市决定营收门槛，并表/参股决定股权结构——解析把它们塌成了一条轴，`10亿` 挂到了错的那条上，`4-5亿` 丢了。

而 `needs_confirmation = 0`，**这次收窄在界面上完全看不出来**。这正是《系统总纲》里那条「丢弃必须可见」。

对照第三轮：工控那条产出了 2 条待确认，理由写得很到位。**所以待确认机制是好的，问题是盐业这类「按 A 轴给了两个门槛、却按 B 轴拆方案」的情况没被它识别成需要确认。**

**为什么没动**：修法在提示词侧（要么按原文的轴拆方案，要么塌轴时必须产出一条待确认）。改提示词即时生效、影响全部买家的匹配结果，而你说过「需求方案后续我们再讨论怎么简化，先不急着动」。**建议并进那次方案讨论一起定。**

### 观察 A：标的画像覆盖率 44%

```
有画像内容的标的 22/50。无画像的包括 8 条 Mock测试- 前缀的种子数据，
以及南京贝诺生物、台州衡驱传动、嘉兴禾谷食品等真实标的。
```

`business_summary` 补上之后不再是「什么都没有」，但画像四栏（身份/产业优势/经营质量/交易属性）仍是深评最主要的信息源。这是数据录入问题，不是代码问题。

### 观察 B：长需求解析贴着预算跑

1462 字的需求正常解析要 **191 秒**，节点预算是 300 秒——余量只有 1.5 倍。表里还有更长的（第 12 行广州轻工 1623 字、第 10 行是 1462 字、第 27 行珠江实业 1382 字），一旦模型稍慢就会触到新加的墙钟并**干净失败**。

这比以前好（以前是无声挂到 stale 窗口），但用户看到的仍是失败。要不要把 `buyer_intent_semantic_parser` 的 `timeout_seconds` 从 300 提到 600（对齐 `buyer_party_researcher` 的 900 那个量级）**需要你决定**——设置页即时生效、不用发版，我不擅自改生产节点配置。

## 五、验收结论

| 项 | 结论 |
| --- | --- |
| 件〇 锚点落库 | ✅ 两轮均确认 `buyer_intent_id` 与 `buyer_party_id` 都写进会话行 |
