# 附件正文截断 与 调研失败静默 修复施工单（2026-08-01）

起因：新建标的「锋尚文化集团股份有限公司」上传 10 页年报摘要 PDF，解析后营收等
财务字段全部空白；随后对该标的发起调研，22 分钟才出结果。

真相与两个猜测都不同 —— 不是「AI 解析后写入格式不对」，写入侧一条没丢；也不只是
一处截断，而是**三处叠加**。调研也不慢，慢的是一次没人知道发生过的失败。

## 一、附件正文被截掉 86%

| 环节 | 字符数 | 剩余 |
| --- | --- | --- |
| PDF 全文（10 页） | 14,110 | 100% |
| `inspect_pdf_text_layer(page_limit=5)` 只采样前 5 页 | 4,658 | 33% |
| `evidence_span.text_excerpt` 截到 2,000 字 | 2,000 | **14%** |

「3、主要会计数据和财务指标」在前 5 页文本的第 **2,306** 字，截断点在 2,000 ——
**差 306 个字**。模型看到的最后一句是「……打造虚拟」，然后就没了。

三处成因：

1. `inspect_pdf_text_layer` 的职责是**判断有没有文字层**，为此只采样前 5 页。
   但 `attachment_ocr.py` 把这份判据的副产品 `extracted_text` 当**正文**落库了。
   更隐蔽的是 `parsed_document.page_count` 记的是 10，掩盖了里面只有 5 页。
2. `_insert_ocr_evidence_span` 硬截 2,000 字。这个上限对「证据摘录」（给人看的
   引文）是合理的，但下游把它当模型输入正文用了。
3. `_build_business_update_attachment_context` 读的是 `evidence_span.text_excerpt`，
   而不是已经存进 S3 的 `parsed_document` 全文。

另一个独立缺口：`_fetch_seller_targets` 只把 24 列放进 `context_json`，而提示词说的是
"use canonical seller_target fields **from context**"。对照 `writable_columns("parse")`：

```
parse 可写 42 列，context 只暴露 21 列 —— 21 个可写字段模型不知道它们存在
```

财务类缺席的有 `current_total_profit_yuan` `current_assets_yuan` `current_debt_ratio`
`current_operating_cash_flow_yuan` `financial_period_label` `market_cap_yuan`
`profitability_status` `cash_flow_status` `operation_stability_status`。

注意 `financial_period_end_date` 与 `listing_market_region` **不是 parse 可写**（只有
research 能写），不能加进 context —— 加了模型输出也会被写入层拒掉。

## 二、调研 22 分钟

| 时刻 | 事件 | 耗时 |
| --- | --- | --- |
| 13:21:07 | 入队 | |
| 13:21:09 | 第 1 次尝试开始 | |
| 13:36:58 | **第 1 次尝试失败** | **15分49秒** |
| 13:37:58 | 第 2 次尝试开始（固定退避 60s） | |
| 13:42:27 | 成功（4 次 LLM、6 次搜索、1 次抓页） | 4分29秒 |
| 13:43:22 | 映射完成，字段落库 | 54秒 |
| | 合计 | **22分15秒** |

第一次失败**没有留下任何痕迹**，只剩 `attempt_count=2`。两个原因叠加：

1. `urlopen` 的读超时抛裸 `TimeoutError`（`OSError` 子类，**不是** `URLError`），
   `llm_client` 只捕获 `HTTPError` / `URLError`，于是它绕过了 research handler 的
   `except LlmCallError` —— 那个分支里写 failed trace 的代码根本没执行。
2. `mark_job_succeeded` 会清空 `error_code` / `error_message` / `error_detail_json`，
   第二次成功把第一次的错误信息抹掉了。

时长是旁证：`seller_target_researcher` 节点超时 900 秒，第一次尝试跑了 949 秒。

另附一个观测性坑：`ai_trace.started_at` / `finished_at` 存的是 `now()`，而 Postgres 的
`now()` 是**事务开始时间**。两条 trace 的 started/finished 完全相等，只有 `latency_ms`
可信。本次未修，先记在这里。

## 六、第二批：两个遗留已清（`cfd64fd` / `388a3a0`）

原本考虑「像调研那样拆成解析 + 规范化两个 LLM 环节」来解决这两个遗留。查完代码，
**两个问题的修法都和拆分正交** —— 调研链路早就解决了它们，但用的不是拆分这个手段：

| 问题 | 调研链路怎么解决的 | 和拆分有关吗 |
| --- | --- | --- |
| 字段看不见 | `RESEARCH_STRUCTURED_FIELDS = writable_columns("research")` 从注册表派生 | 无关 |
| 一个错全批回滚 | `apply_research_claims` 逐条 claim，坏的记 `_mark_proposal_invalid` 后 `continue` | 无关，注释明说该函数**内联模式下也这么工作** |

于是照搬这两个做法，没有拆分：

- **字段词汇表改为注册表派生**（seller + buyer 双侧）。手写清单 seller 漏 21 个、
  buyer 漏 12 个。排除项收进具名集合，每条要有理由：`information_status` 由
  `mark_parse_completed` 维护；买家的 `status` / `pause_reason` 是人操作的，不是从材料
  里读出来的。两条 ratchet 用例锁死「只能故意排除，不能漏」。
- **`write_seller_target_fields` 增加可选 `rejected_fields` 收集器**。传了就逐字段收集
  失败并跳过，不传保持严格全有全无 —— 自己拼 changes 的 4 个调用方靠的就是那个保证。
  被拒字段写进 `extracted_action.metadata_json.rejected_fields`，复核页和 debug 可见：
  静默丢弃比整批失败更糟，所以是**记下来**而不是忽略。

### 买家侧同病（用户提出后排查）

- **截断：同一套代码，同一个缺陷。** 买家新建带附件时走
  `CreateIntentModal.tsx:142` → `/business-updates/upload(auto_parse_linked_objects=true,
  parse_entity_types=['buyer_intent'])` → `_enqueue_linked_parse_jobs_after_ocr` →
  `raw_requirement_text`。和标的**共用**被截断的那三段路径，第一批已一并修好。
  之所以没人发现：历史买家附件都很小（实测 298 字、819 字），够不着 2000 的线。
  一份 10 页并购需求说明书会在完全相同的位置被切断。
- **字段词汇表：`_fetch_buyer_intents` 漏 12 个**，已随本批修复。漏掉的包括
  `desired_equity_ratio_min/max`、`equity_ratio_summary`、`equity_requirement_type`
  —— **股权比例诉求整个维度**买家说了也听不见；还有 `min_total_profit_yuan`
  （卖方侧记着对应的 `current_total_profit_yuan`，买方却提不出这个门槛）。
- **但买家新建那条路（`buyer_intent_parser`）不吃 `_fetch_buyer_intents`。**
  它的字段词汇表**写死在提示词正文里**，会随注册表悄悄漂移。而两段式的
  normalizer 拿的是 `_buyer_intent_field_contract()` —— **注册表派生**，带 label、
  kind、operator、enum。也就是说两段式**已经把这个问题解对了**，只是没启用。
