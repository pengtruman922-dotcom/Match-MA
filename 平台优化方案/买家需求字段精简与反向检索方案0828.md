# 买家需求字段精简与反向检索方案（2026-08-28）

> 本单同时做两件互相咬合的事：**买家需求字段精简**（改 schema、注册表、解析提示词）
> 与 **反向检索 skill**（新建，供 wegent 等外部 Agent 调用）。
> 两者不能拆开做 —— 精简的依据正是「反向检索不需要这些结构化字段」，
> 而 skill 的返回契约又依赖精简后的字段表。
>
> 与《买家信息字段改造施工单0824》《买家信息解析与调研施工单0825》是同一条线的第三单：
> 前两单解决「买家自己是谁」，本单解决「买家的需求怎么被检索到」。

---

## 一、这一单要解决什么

总纲 §3.3 现在写着：

> 反向（为标的找买家）暂时不可用……真正要解决的是把一段出售需求描述解析成能驱动
> **买家侧硬筛**的标的画像，而买家需求的结构化字段空则筛不出东西 —— 这是重建时的第一道坎。

**这个判断被推翻了。** 这道坎不是要翻过去，是要绕开：买家库规模足够小，业务匹配可以
把全部买家的业务原文一次性交给 LLM 判断，根本不需要结构化字段参与。

### 实测依据（2026-08-27，生产库）

| 量 | 实测 |
|---|---|
| 买家主体 / 需求 | 42 / 52（预期增长到 200） |
| 买家 `business_summary` | 12/42 有值，**均 259 字** |
| 需求 `intent_summary` | 32/52 有值，均 94 字 |
| 业务卡片（当前，含大量空值） | 285 字/条 |
| **业务卡片（只算数据齐全的 9 条）** | **600 字/条 → 200 个买家 12 万字 ≈ 90k token** |
| 省略空字段后 | 业务卡片省 21%，全量档省 33% |

**90k token 一次调用装得下。** 这是整个方案成立的唯一前提，其余判决都从它推导。

⚠️ **不要用 285 字/条那个数做预算** —— 它低是因为 72% 的买家没填业务说明，
数据补齐后是 600 字/条。业务说明是判业务匹配的主材料，**不能为了压体积把它截短**。

### 精简的收益不在数据库，在解析提示词

| | 现在 | 精简后 |
|---|---|---|
| `field_contract_json`（每次解析都喂给模型） | 54 项 / 15,602 字符 | 约 24 项 / 约 8,000 字符 |
| `enum_contract_json` | 17 项 / 1,385 字符 | 约 8 项 / 约 550 字符 |
| `buyer_intent_normalizer` 规则正文 | 5,615 字符 | 约 3,600 字符 |
| `SCREENING_FIELDS`（正向初筛工具参数） | 24 项 | 约 13 项 |

`normalizer` 提示词里最长的几段，服务的恰恰是最空的字段：「百分比口径」那张表六行，
其中 `max_debt_ratio`(1/52)、`min_net_margin`(2/52)、`min_gross_margin`(1/52)、
`max_premium_rate`(0/52) 四行**合计只有 4 条真实数据**。
**每多一个字段，模型每次解析都要判一次「这里有没有这个信息」** —— 字段表越长，
它在真正重要的行业和金额上分到的注意力越少。精简换的是解析准确率。

## 二、边界

### 在范围内

1. 买家需求新建 5 列、回填、退役 32 个解析字段（阶段 A 不删旧列）
2. 删 4 个孤儿列（注册表根本没声明、解析却在写）
3. 指标注册表 `BUYER_INTENT_INDICATORS` 重写
4. `buyer_intent_normalizer` 提示词改版
5. 后端 API、前端需求信息页跟随字段变化
6. **正向初筛失去行业条件后的连带改造**（见 §十）
7. 新建 `skills/buyer-search/`：三个接口 + SKILL.md + tool.json

### 明确不在范围内（做了就是越界）

- **不动买家主体（`buyer_party`）的任何字段**。它 0824 刚定型，业务标签 + 业务说明的
  设计是本单要照抄的样板，不是要改的对象。
- **不动标的侧 `industry_pairs_json`**。总纲 §2.3「它是唯一的标的行业事实源」保持有效。
  标的侧 `business_summary` 平均只有 49 字，现在还撑不住纯文本匹配（见 §十）。
- **不做买家主体业务信息的数据补录**。那是运营动作不是代码改动，但它是本方案效果的
  最大变量（当前只有 28% 的主体有业务说明）。
- **不处理 Mock 测试数据**。库里 5 个主体 / 10 条需求是 `Mock测试-20260624-*`，
  用户已明确本单不管。**但 skill 上线前必须解决**，否则 Agent 会把它们当真买家推荐。
- 不动正向的深评、Writer、追问芯片。
- 不 commit、不 push。

## 三、三条设计判决

### 判决一：买家需求侧的行业字典下线

**做什么**：`industries_json` / `industry_l2_json` / `industry_primary` /
`industry_secondary` / `industry_focus_tags_json` / `excluded_industries_json`
六个字段合并成 `intent_business_tags_json`（自由标签）+ `intent_business_summary`（自由文本）
+ `excluded_business_text`（自由文本）。

**照抄的样板**：迁移 `020` 给买家主体做过同一件事 ——
`industries_json` + `industry_l2_json` → `business_tags_json`，理由写在总纲 §2.2：
「行业字典只有 16 个一级行业，接不住买家的细分主业」。

**必须知道的代价**：买家主体能用自由标签，是因为它**从来不跨侧匹配**
（注册表：`buyer_party` 的 `screening` 一律 `False`，「主体没有另一侧」）。
买家需求**有另一侧** —— `industries_json` 是正向初筛唯一的行业硬条件
（`sql_recall=True`、`default_effect="required"`），对手方是 `seller_target.industry_pairs_json.l1`。
**跨侧匹配需要共享词表，这是行业字典存在的唯一理由。**

所以本判决同时意味着：**正向初筛不再有行业条件**。这不是副作用，是同一个判断的必然结果。
连带改造见 §十。

**支持这么做的数据**：实测买家需求人均只填 1.25 个一级行业、二级行业只有 21% 有值，
而信息主要落在**不参与匹配的** `industry_primary`(92%) / `industry_secondary`(73%) 两个原文列里。
也就是说行业字典今天已经没在承担业务匹配，它只是把范围粗筛一下，判断照样得读文本。

### 判决二：地区结构简化为两个平铺数组，保留三级

**做什么**：`region_constraints_json`（`[{province, city, district, effect}]`，三级嵌套 + effect 三态，
实测只有 13% 有值）替换为：

```
acceptable_regions_json : [{"province":"广东省"}, {"province":"江苏省","city":"苏州市"}]
excluded_regions_json   : [{"province":"新疆维吾尔自治区"}]
```

- **省 / 市 / 区三级都支持筛选**，逐级独立生效：只填省 = 全省命中，填到市 = 只匹配那个市。
- **去掉 `effect` 三态**。`required` 与 `preferred` 的区别（「必须在广东」vs「优先广东」）
  交给 `region_scope_summary` 原话承载 —— 它是【召】类字段，12 个字，语气它表达得比枚举好。
- 排除地区从 `effect="excluded"` 拆成独立字段，语义写在字段名里。

**匹配 SQL（反向，给定标的的三级地区）**：

```sql
(
  jsonb_array_length(acceptable_regions_json) = 0
  or exists (
    select 1 from jsonb_array_elements(acceptable_regions_json) r
    where (r->>'province' is null or r->>'province' = :province)
      and (r->>'city'     is null or r->>'city'     = :city)
      and (r->>'district' is null or r->>'district' = :district)
  )
)
and not exists (
  select 1 from jsonb_array_elements(excluded_regions_json) r
  where (r->>'province' is null or r->>'province' = :province)
    and (r->>'city'     is null or r->>'city'     = :city)
    and (r->>'district' is null or r->>'district' = :district)
)
```

**⚠️ 大区展开是写入侧的事，不是接口的事。** skill 接口只认标准行政区划，
「长三角」「大湾区」由调用方 Agent 自行解析后传省市区 —— 这条写进 SKILL.md。
但 **`buyer_intent_normalizer` 解析买家材料时也必须展开**，否则
`acceptable_regions_json` 会和今天的 13% 一样空着，接口三的地区筛选**筛不到任何东西**。
展开表见 §八。

### 判决三：语气和强度归文本，阈值和枚举归字段

`condition_effects_json`（`{"min_revenue_yuan": "required"}`，标注条件是硬门槛还是只影响排序）
**整个退役**。

**它现在没有任何筛选消费方。** 注册表的注释写着「只服务需求单链路：`recommendation_flow.py`
用它把三道硬门槛按 effect 放宽」，但全仓库 grep 后 **`recommendation_flow.py` 里根本没有它** ——
那个消费方在阶段五 5B 拆旧链路时一起删了，**注释是过期的**。今天的活消费方只剩三个，
没有一个是筛选：

1. 前端角标（`features/buyers/presentation.tsx:362` + `BuyerIntentRequirements.tsx`）
2. 深评上下文（`search_docs.py:149` 的 `_kv("条件作用", ...)`）
3. 解析与业务更新的写入路径

生产里只有 5/52 有值。退役的损失是「界面上少一个从来不起作用的角标」。
将来若要让 Agent 知道某个门槛硬不硬，**那句话写进需求摘要正文，由 LLM 读** ——
与地区的「优先/必须」交给原话是同一个处理方式。这是本方案贯穿始终的一条原则：

> **语气和强度归文本，阈值和枚举归字段。**

## 四、字段设计

### 4.1 新建 5 列

| 列名 | 类型 | 说明 |
|---|---|---|
| `intent_business_tags_json` | `jsonb not null default '[]'` | 需求业务标签，**自由标签不过字典**。与 `buyer_party.business_tags_json` 同构 |
| `intent_business_summary` | `text` | 需求业务方向说明。**口径：必须写清「要买什么样的业务」**，这是首轮筛选唯一读的东西 |
| `excluded_business_text` | `text` | 明确排除的方向，自由文本 |
| `acceptable_regions_json` | `jsonb not null default '[]'` | `[{province, city?, district?}]`，空数组 = 不限 |
| `excluded_regions_json` | `jsonb not null default '[]'` | 同构 |

约束：三个 jsonb 列加 `jsonb_typeof(...) = 'array'` 形状约束。
`intent_business_tags_json` 加 GIN 索引（照抄 `idx_buyer_party_business_tags`）。

### 4.2 退役清单

**⚠️ 「退役」= 从注册表的 `writable_by` 去掉 `parse`、`screening` 置 `False`，
阶段 A 不删列。** 删列在阶段 B（见 §五）。

| 组 | 字段 | 处置 |
|---|---|---|
| 行业六件套 | `industries_json` `industry_l2_json` `industry_primary` `industry_secondary` `industry_focus_tags_json` `excluded_industries_json` | 合并进新的三个业务字段 |
| 地区 | `region_constraints_json` | 替换为两个新数组 |
| 摘要 | `intent_summary` | 并入 `intent_business_summary` |
| 条件强度 | `condition_effects_json` | 退役（判决三） |
| 股权冗余 | `accepts_minority_investment` `equity_requirement_type` | 退役。前者标的侧 70/71 是 unknown，带上它候选池只剩 1 家；后者是解析中间产物 |
| 上市派生 | `preferred_listed_status` | 退役。派生列，注册表已标不可手写 |
| 双侧皆空的比率与阈值 | `min_net_margin` `min_gross_margin` `max_ps` `max_debt_ratio` `max_premium_rate` `min_total_profit_yuan` | 退役。注册表注释已逐条写明理由 |
| 双侧皆空的枚举 | `acceptable_cash_flow_status_json` `acceptable_profitability_status_json` `listing_market_region` | 退役 |
| 交易能力五项 | `requires_relocation` `requires_return_investment` `return_investment_multiple` `requires_team_retention` `earnout_requirement` | 退役。标的侧对手方 71/71 unknown，或已在 016 删列 |
| 六段说明文字 | `equity_ratio_summary` `market_cap_range_summary` `listing_board_requirement_summary` `financing_stage_requirement_summary` `premium_tolerance_summary` `debt_ratio_requirement_summary` | 退役，内容改由**各模块「其他」**（`entity_profile_section`）承接 —— 那张表就是干这个的，且已进 `search_doc` |
| **孤儿列（阶段 A 直接删）** | `acceptable_control_paths_json` `budget_min_yuan` `budget_max_yuan` `relocation_target_regions_json` | **drop**。注册表根本没声明它们，前端不显示、初筛不用、深评不读，但 `buyer_intent_parse.py` 每次都在写 |

**降级不等于丢信息**：深评读的是 `buyer_intent_search_doc.full_text`，而它已经把
`profile_sections`（三个模块的「其他」）拼进去了（`search_docs.py:174`）。
normalizer 提示词也**已经**在教模型「装不进结构化字段的说法写进 profile_sections」。
所以这些字段从「独立结构化列」降级成「其他里的一句话」之后，**深评侧零损失**，
只损失「能被 SQL 筛」—— 而它们本来就筛不到任何东西。

顺带一个自动的好处：`_remove_structured_profile_duplicates` 会删掉与结构化字段重复的
「其他」句子；字段不再结构化之后，那句话就自动留下来了，不用另外处理。

这不是保守，是本项目的既有节奏（总纲 §2.4 记着 0727 和 0814 两次先例）：

> 阶段 A（加列、回填、加约束、换索引，**旧列保留**），删旧列另开迁移，

### 回填 SQL（阶段 A）

```sql
-- 业务标签：三个数组去重合并。照抄 020 给 buyer_party 做的那次。
update buyer_intent
set intent_business_tags_json = (
  select coalesce(jsonb_agg(tag order by tag), '[]'::jsonb)
  from (
    select distinct btrim(c.value) as tag
    from jsonb_array_elements_text(
      case when jsonb_typeof(industries_json) = 'array' then industries_json else '[]'::jsonb end
      || case when jsonb_typeof(industry_l2_json) = 'array' then industry_l2_json else '[]'::jsonb end
      || case when jsonb_typeof(industry_focus_tags_json) = 'array' then industry_focus_tags_json else '[]'::jsonb end
    ) as c(value)
    where nullif(btrim(c.value), '') is not null
  ) as t
)
where intent_business_tags_json = '[]'::jsonb;
```

业务说明用 `concat_ws` 把旧摘要与两个行业原文列拼成一段（换行分隔，
前缀「行业方向：」「细分方向：」），只在 `intent_business_summary is null` 时写入。

排除方向用 `string_agg` 把 `excluded_industries_json` 的元素拼成顿号分隔的文本。

地区拆成两个数组：遍历 `region_constraints_json`，`effect <> 'excluded'` 的进
`acceptable_regions_json`，`effect = 'excluded'` 的进 `excluded_regions_json`，
两边都用 `jsonb_strip_nulls(jsonb_build_object('province', ..., 'city', ..., 'district', ...))`
去掉空层级。

## 十、正向链路的连带改造（判决一的代价）

删掉行业条件之后，正向初筛只剩营收 / 地区 / 控股 / 并表几道。
**一条只写了「最低营收 1 亿」的需求会召回接近全库** —— 这不是 bug，是判决一的设计意图，
但它要求正向的流程跟着改成和反向同一个形状：

> SQL 收窄（收不窄也没关系）→ **全量标的业务摘要给 LLM 首轮筛** → 选出 10-20 家 → 深评 → Writer

标的库约 300 家 × 业务摘要平均 49 字 ≈ 1.5 万字，首轮全量塞得下。
但**深评那一步跑不了 300 家**，所以「LLM 首轮筛」是新加的一段，不是把现有哪一步改改。

⚠️ **标的侧的业务摘要只有 49 字，远薄于买家侧的 259 字**（target-search 的 README 自己写了
「这是当前语义判断准确率的主要瓶颈」）。所以正向这一段的效果**必须实测**，
不能假设它和买家侧一样好。

### 施工顺序（推荐）

1. **先用现有字段把反向 skill 做出来跑通**，验证「全量文本 + LLM 首轮筛」在买家侧的准确率
2. 验过了再做本单的字段改造，同一批把正向改成同一形状

**判决一的全部依据是「全文 LLM 首轮筛够用」，而这件事还没在生产上验证过。**
先在新建的、不影响任何人的反向 skill 上验，比在已上线的正向链路上验便宜得多。

## 十一、反向检索 skill（`skills/buyer-search/`）

格式照抄 `skills/target-search/`：`SKILL.md` + `tool.json` + `search_buyers.py` + `README.md`。

### 三个接口 —— 它们是三种返回形状，不是同一查询的三种筛法

| 接口 | 选谁 | 返回什么 | 规模 |
|---|---|---|---|
| ① `search_buyers_business` | 全库 | **只有业务字段**（薄） | 200 条 |
| ② `get_buyer` | 按名称/别名 | **全量**（厚） | 几条 |
| ③ `filter_buyers` | 条件组合 | **全量**（厚） | 上限 50 条 |

②③ 返回形状相同、选法不同。不合并的理由：按名称要做模糊匹配和同名候选消歧
（「北大健康」在库里有 3 个主体），那套逻辑塞进筛选工具会让它变脏。

#### 接口一 `search_buyers_business`

- **参数里没有业务/行业/关键词这一维** —— 这是刻意的。业务匹配 100% 由调用方 LLM 读文本完成。
  （同一手法：target-search 刻意不暴露 `q`，因为上游是 ilike 不是语义）
- 唯一参数 `detail`：`full`（默认，约 600 字/买家）/ `brief`（业务说明截 120、需求摘要截 80，约 280 字/买家）
- 返回字段 = §4.3 里全部【召】类 + 买家名 + id

#### 接口二 `get_buyer`

- 参数：`name`（模糊，认别名）或 `buyer_party_id`
- 名称命中多个时**返回全部候选让 Agent 消歧，不合并不丢弃**
- 返回：买家主体全部【筛】【召】【补】+ 名下全部需求的完整档案
- `raw_requirement_text` 要清洗：去掉解析指令原文（「解析要求：只提取买家意向字段…」）、
  去重复的附件 OCR 段落

#### 接口三 `filter_buyers`

- 买家自身条件：`ownership_type` `listed_status` `province` `city` `district`
  `min_market_cap_yuan` `min_revenue_yuan`（买家自己的）
- 需求条件（反查，给定标的事实）：`target_revenue_yuan` `target_net_profit_yuan`
  `target_pe` `target_market_cap_yuan` `target_valuation_yuan` `target_listed_status`
  `target_province` / `target_city` / `target_district`
- **硬上限 50 条**；超出时返回命中总数 + 「请收窄」提示，不静默截断
- **每条数值条件必须写成 `字段 IS NULL OR 条件成立`**（见下）
- 全量档实测 4,384 字/条（已省略空字段），50 条约 22 万字符 ——
  **仍然偏大，`raw_requirement_text` 必须清洗后再返回**

### ⚠️ 反向检索最大的陷阱：空值方向是反的

正向筛选里「买家没提这条」= 不带这个条件、天然无害。
**反向筛选里如果把 NULL 当成「不满足」，一半以上的买家会当场消失。**

所以：

1. 每条数值/枚举条件都是 `IS NULL OR 命中`
2. 返回里**如实区分「明确符合」与「买家没提过」** —— 这是两个结论
3. 带 marginal 说明（「去掉营收这条能多召回 8 家，其中 5 家只是没录数据」），
   照抄正向 `search_targets` 的做法。买家侧空值率比标的侧高得多，这句比标的侧更要紧

### ⚠️ 省略空字段的约定 —— 两类缺失含义相反

字段为空则连字段名也不返回（实测省 21%~33%）。**但必须在 SKILL.md 里分两类写清**：

- **买家自身的事实**（业务说明、市值、营收、企业性质）缺失 = **没录，未知**。
  不能当成「没有」。
- **买家需求的门槛**（要求最低营收、可接受地区、可接受上市状态）缺失 =
  **买家没提这个门槛 = 不构成障碍**，是**正面**信号。

写不清这一条，LLM 会把「没提营收门槛」读成「信息不足无法判断」，
然后**把库里最灵活的那批买家全漏掉** —— 而那批恰恰最该推。
标的侧那份 skill 只有前一类，**它的写法不能照抄**。

### 闸门

- 需求 `intent_grade = 'E'` 不返回（与标的侧同一口径，总纲 §2.4）
- 需求 `status = 'closed'` 不返回；`status = 'paused'` **返回但标注**
- 买家主体 `status <> 'active'` 不返回

⚠️ 总纲 §2.4 记着「闸门有五处独立实现，漏改一处不报错」。**本 skill 会是第六处。**
要么在总纲里如实加上，要么这一轮把闸门收回服务端。标的侧 skill 已经欠了同一笔债
（它的 README 自己写了「这是过渡实现」）。

### 认证

沿用 target-search 的方案：专用账号换 7 天 JWT，写进 skill 目录的 `auth.local.json`
（已被 `.gitignore` 的 `skills/**/auth.local.json` 排除）。
**不要用仓库里 `.match-ma-local-auth.json` 的 `effective_admin_token`** ——
它静态、不过期、权限全开，还是登录系统的恢复通道。

⚠️ 买家侧比标的侧多一层风险：`contact_info_json` 是联系方式。
**skill 层永不返回联系人三件套和运营备注**（§4.3 的 ⛔ 类）。

## 附：本方案的一条贯穿原则

> **语气和强度归文本，阈值和枚举归字段。**

- 地域的「优先 / 必须」→ `region_scope_summary` 原话，不做 effect 枚举
- 条件的硬软 → 写进需求摘要正文，不做 `condition_effects_json`
- 业务方向的细分 → 自由标签 + 自由文本，不做行业字典
- 而营收、市值、PE、股比、上市状态 → 老老实实是字段，因为它们**可比较**

判断一个新字段该不该建，就问一句：**它是可比较的量，还是一句话？**
