## 五个容易做错的地方，先打预防针

1. **`timeout_seconds` 现在是 socket 超时，不是总时长。**
   它被直接喂给 `urlopen(timeout=…)`（`backend/app/ai/llm_client.py:89` 与 `:186`）。
   非流式还近似成立（服务端生成完才发字节）；**流式每来一个 token 计时器就重置**，
   配 180 秒的 Writer 只要 token 一直滴就能跑 10 分钟。
   所以「重定义为节点整体超时」**必须在流式循环里自己算 deadline**，改文案没用。
2. **改语义必须同时改值。** 生产 Agent 节点现配 **600 秒**，而真实总预算是写死的 240 秒。
   只把 600 升格成「整轮总预算」= 把一轮从 4 分钟**偷偷放宽到 10 分钟**，
   用户等待反而更差。**把它压到 240~300。**
3. **需求解析不要直接从 30 秒跳到 300 秒。** 这个节点**有降级路径** ——
   超时后 `parser_status=fallback`，Agent 只能无条件初筛或提问。
   **超时越长，降级来得越晚**，而一轮总耗时中位数才 105 秒，
   300 秒的死等会显著恶化尾部延迟。设 **90~120 秒**，
   或者配 300 但加一道软预算（超 60 秒就走 fallback 继续）。
   **代码默认值和生产配置两处都要改** —— 已建配置不会继承新默认值。
4. **退役节点要标 `lifecycle="retired"`，不是删 `NodeSpec` 定义。**
   `nodes.py:361` 的注释自己写了：删定义会让它变成「未登记节点」重新出现在设置页 ——
   5A/5B 直接删定义正是这次设置页脏掉的原因。而 `NodeList.tsx:42` 已经过滤 retired，
   标 retired 就达成了「前端不展示」。
5. **删节点前先拆三颗雷：**
   - `backend/app/api/routes/meta.py:232` **硬编码**查 `recommendation_deep_eval`
     是否有启用的默认配置，并并进**系统整体就绪**布尔（`meta.py:308`）。
     停用它 → **系统自检直接报「未就绪」**。要改成查 `recommendation_deep_eval_to_target`。
   - `nodes.py:217` / `:234` 的 `understudy="recommendation_deep_eval"` 指针要摘掉。
   - `background_jobs.py:1640` 的中文名映射**保留**，否则历史 job 详情掉标签。

## 验收标准

| 项 | 期望 |
|---|---|
| 中止轮 | 停止一轮 → 补充一句 → 新一轮的 `history_context` 里有 `<aborted_user_turn>`，模型把两段合并理解，**不把它当成待回答的问题** |
| 中止冲突 | 停止后说一句与原话冲突的需求，parser 以后续为准 |
| 就绪自检 | 停用共用深评后，系统自检**仍为就绪** |
| 设置页 | AI 节点 → 推荐**只剩 4 行**，都显示「已配置」 |
| 流式超时 | 本地 mock 慢速 chunk，Writer 能在节点配置的秒数上主动断开 |
| 解析降级 | 解析节点超时后走 fallback，整轮继续 |
| 测试 | `python -m pytest -q` 全绿；`npm run typecheck && npm run build && npm run lint` 全过 |

本机是 Python 3.14、无后端 venv，直接 `python -m pytest` 即可。
