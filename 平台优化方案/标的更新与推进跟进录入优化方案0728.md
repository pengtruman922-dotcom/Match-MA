# 标的更新与推进跟进录入优化方案 0728

> 状态：代码与独立提交树验收已完成；生产 Prompt 已按上线顺序配置；跟进功能独立发布中。

## 1. 已定稿决策

1. 标的列表、买家意向列表及两侧详情页统一使用「录入」入口，展开三个选项：更新基本信息、记录跟进、基本信息和跟进都更新。
2. 用户选择处理范围，代码据此调用固定 AI 节点；不再让通用 Agent 判断是信息还是跟进。
3. 跟进录入前必须由用户选择既有的「买家意向 × 标的」撮合关系。没有关系时先走现有「关联对手方」流程，AI 不识别、不创建关系。
4. 跟进 AI 只把原始材料整理为 `content`（沟通内容）和 `next_step`（下一步）草稿。关系、推进状态、动态类型仍由用户沿现有路径选择。
5. AI 草稿不直接写库；用户可修改，确认后仍调用现有关系动态接口创建 `relation_event`。
6. 「两者都更新」只保存一份原始文字和附件，信息解析与跟进草稿解析作为两个独立后台任务读取同一来源。
7. 删除两侧「跟进记录」Tab，旧 `target_follow_up`、`buyer_intent_follow_up` 数据无需迁移，直接删除。
8. 原标的列表「最近跟进」改读撮合关系事件并更名为「最近推进」；工作台「跟进记录」统计改为「推进动态」。

## 2. 目标交互

### 2.1 统一入口

```text
[ 录入 ▾ ]
┌──────────────────────────────┐
│ 更新基本信息                 │
│ 解析文字或附件，更新实体字段 │
├──────────────────────────────┤
│ 记录跟进                     │
│ 选择推进关系，AI 整理沟通草稿│
├──────────────────────────────┤
│ 基本信息和跟进都更新         │
│ 同一份材料分别进入两个节点   │
└──────────────────────────────┘
```

列表使用点击式下拉菜单；详情页主按钮根据当前 Tab 显示「更新基本信息」或「记录跟进」，右侧下拉仍提供三个选项。悬浮只显示提示，不以 hover 作为唯一操作方式。

### 2.2 跟进草稿

```text
推进关系 *  [买家 · 意向 × 标的 ▾]
当前状态    深入沟通（在推进页按现有方式修改）
动态类型 *  [会议沟通 ▾]（用户选择）

原始记录    [粘贴聊天记录、会议速记或上传附件]
                                      [AI 整理]
沟通内容    [AI 回填，可编辑]
下一步      [AI 回填，可编辑]
                                      [记录动态]
```

只有一个关系时可自动选中但必须展示；多个关系必须显式选择；没有关系时不调用跟进节点。

## 3. AI 节点与输出契约

新增共用节点 `relation_followup_draft_parser`（设置页名称「推进跟进整理」）。输入变量：

- `relation_context_json`：用户已选择的关系、买家、意向、标的名称，仅作语义上下文；
- `raw_text`：原始文字与已完成 OCR 的附件文本。

严格输出：

```json
{
  "content": "买方希望进一步查看标的近三年财务报表。",
  "next_step": "本周五前发送近三年财务报表。"
}
```

规则：不得输出或修改关系 ID、状态、动态类型、实体字段；不得创建关系；未明确下一步时返回 `null`；保留原文金额、日期、比例、条件和否定语义。该结果只存为业务更新草稿并进入 `ai_trace`，不新增 `extracted_action.action_type`。

现有 Prompt 调整（通过设置页/API 发布，不写 seed 迁移）：

- `seller_target_update_parser`：只允许标的当前事实更新，不再输出 `target_follow_up`/`seller_event`；
- `buyer_intent_update_parser`：只允许买家意向当前事实更新，不再输出 `buyer_intent_follow_up`；
- `business_update_extractor`：不再作为新 UI 的文本路由 fallback；保留到旧任务兼容结束；
- `seller_target_parser`、`buyer_intent_parser`：保持新建实体的 `fields` 契约，补强「忽略沟通过程、只提取当前事实」边界。

## 4. 后端流程

业务更新请求新增显式 `processing_scope`：

- `basic_info`
- `follow_up`
- `both`

`follow_up`/`both` 必须同时传 `bound_relation_id`，后端校验该关系存在、可见，且绑定标的/意向与关系两侧一致。处理范围和关系 ID 记录在 `business_update.metadata_json`，避免新增只为路由服务的宽表列。

任务分发：

- `basic_info` → 现有 `business_update_extract_actions`；
- `follow_up` → 新增 `relation_followup_draft_parse`；
- `both` → 两个独立任务并行，失败互不回滚。

附件继续复用现有上传、图片多模态和 OCR 流程；OCR 完成后按同一 `processing_scope` 补发对应任务。跟进草稿状态与结果写入 `business_update.metadata_json`，前端轮询后回填表单。

## 7. 已实现范围与关键保护

- 后端新增 `processing_scope`、`bound_relation_id`、`relation_followup_draft_parse` 和独立 handler；文字、OCR 文本、图片均复用既有附件证据链。
- `POST /business-updates/{id}/process` 支持 `branch=follow_up`，只重试失败的跟进分支；`both` 不会因为单独重试把全局状态永久留在 processing。
- 跟进草稿严格拒绝 `content/next_step` 以外的字段，空内容视为 schema 失败；长度与事件接口一致，分别限制为 4000/1000 字。
- handler 最终失败会写 `followup_draft_status/error`；关系在排队后被删除、附件上下文读取失败等前置异常也不会让前端永久等待。
- 前端轮询把「任务明确失败」与「读取/等待超时」分开：超时只能继续读取既有任务，不直接触发重复解析；明确失败才显示「仅重试跟进整理」。
- AI 成功只把草稿写入 `business_update.metadata_json`，handler 没有任何 `relation_event` 写入；最终事件仍由顾问确认后调用现有关系事件接口。
- 两侧旧跟进 Tab、API、类型、解析 action、apply/rollback 和统计读取均已清理；列表最近推进与工作台推进动态统一读取 `relation_event`。

### 8.2 新节点 Prompt

system prompt：

```text
你是投资撮合平台的推进跟进整理助手。用户已经选择了一条确定的“买家意向 × 标的”关系。你只整理本次原始材料，不负责识别或创建关系，不修改推进状态，不选择动态类型，不更新标的或买家基本信息。只输出一个 JSON 对象，且只能包含 content 和 next_step 两个键，不要输出 Markdown。content 必须是非空字符串；没有明确下一步时 next_step 必须为 null。保留原文中的金额、日期、比例、条件、主体和否定语义，不补充材料中没有的事实。
```

user prompt template（few-shot 必须保留在正文，不能只写 `few_shot_examples_json`）：

```text
已选关系上下文：
{{ relation_context_json }}

本次原始材料：
{{ raw_text }}

输出格式：
{"content":"本次已经发生的沟通与反馈，使用简洁完整的中文。","next_step":"材料中明确约定的下一步；没有则为null"}

示例1
输入：买方看完简介后希望再看近三年财务，本周五前发给他。
输出：{"content":"买方已查看项目简介，并希望进一步查看近三年财务资料。","next_step":"本周五前发送近三年财务资料。"}

示例2
输入：电话沟通，对方说目前估值太高，暂时不继续谈。
输出：{"content":"电话沟通中，对方反馈当前估值过高，暂时不继续推进。","next_step":null}

再次确认：禁止输出 relation_id、status、event_type、实体字段或任何第三个键。
```

output schema：

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["content", "next_step"],
  "properties": {
    "content": {"type": "string", "minLength": 1, "maxLength": 4000},
    "next_step": {"type": ["string", "null"], "maxLength": 1000}
  }
}
```

variables：`["relation_context_json", "raw_text"]`。

### 8.3 现有基础信息 Prompt 边界

不要覆盖生产当前 Prompt 的其他字段规则；从当前默认版本复制新版本后，增加下面的硬边界，并删掉旧正文中对 `seller_event`、`target_follow_up`、`buyer_intent_follow_up`、关系进展的输出示例或允许列表：

- `seller_target_update_parser` / `seller_target_parser`：`只提取标的当前有效的企业事实、交易诉求和画像信息。沟通过程、已推荐给谁、对方反馈、等待动作和下一步不属于标的基本信息，必须忽略，不得写入任何摘要字段，也不得输出跟进或关系 action。`
- `buyer_intent_update_parser` / `buyer_intent_parser`：`只提取买家主体和买家意向当前有效的信息。与某个标的的沟通过程、反馈、推进状态和下一步必须忽略，不得写入意向摘要，也不得输出跟进或关系 action。`
- 若仍保留 `business_update_extractor` 供旧任务兼容，也要移除上述三个旧 action 和关系进展自动应用规则；新 UI 不再把它作为自由路由 Agent。

发布每个版本后检查它是该 `node_name` 唯一的 active + default 版本，并分别跑一条“纯基本信息”和一条“夹杂沟通记录”的节点测试，确认基本信息节点不会产出跟进内容。
