# 撮合看板改版施工单 0726

图纸：`docs/系统总纲.md`。本单只改**撮合看板的呈现与取数**，不改撮合领域模型（关系仍是「买家意向 × 标的」）、不改状态取值、不涉及迁移。做完把结论合并回总纲 §3.4 后归档。

批次顺序：**B1 后端瘦端点 → B2 前端看板改版 → B3 深链接与顺手项**。B1 可独立发版验证。

## 0. 起因：现状的三个体验问题 + 两个既有缺陷

体验问题（用户提出）：

1. 没有买家/标的视角，只有一条状态流水线。
2. 状态列过细（9 个），且 90% 的卡堆在早期列，其余列常年空着。
3. 看板定位不清——它应该是**概览 + 跳转**，卡上不该堆明细。

排查中发现的既有缺陷（**本单必须一并处理**）：

- **B-1 静默截断**：[`relations.py:141`](../backend/app/api/routes/relations.py) 的 `limit` 上限 `le=200`，而 [`Board.tsx:27`](../frontend/src/pages/Board.tsx) 正好要 200。生产关系数已达几千，**看板只显示按最近活动排序的前 200 条，其余无声消失，列头计数是假的**。客户端拿到 200 条无从判断后面还有多少。
- **B-2 列表接口过重**：[`_relation_select_columns()`](../backend/app/api/routes/relations.py) 每行跑 **4 个关联子查询**（3 次回捞 `relation_event` 取 type/content/next_step + 1 次 `exists` 扫 `buyer_seller_relation`），并返回 `last_event_summary`/`last_event_content`/`metadata_json` 等不定长文本。单行约 1 KB。**看板这 4 个子查询的结果一个都不用。**

结论：单纯把 `le=200` 调大到 10000 不可行——10000 行意味着 40000 次子查询 + 8~15 MB 未压缩 JSON，等于把"静默丢数据"换成"静默卡死"。正确解法是**瘦字段集**（下见 B1）。

## 1. 已定稿的设计决策

| # | 决策 | 备注 |
|---|---|---|
| D1 | 状态收敛为 **3 主列 + 1 抽屉** | 见下表 |
| D2 | **卡片 = 一条关系**（1 标的 × 1 意向），落在自己真实状态所属的列 | 同一标的可同时出现在多列，这是正确的信息 |
| D3 | 卡片固定 **4 行**，不展示其他明细 | 看板只做概览 |
| D4 | 双视角 tab：**按标的 / 按意向** | 聚合到 `buyer_intent` 而非 `buyer_party`——意向才是撮合单元且有独立详情页 |
| D5 | 同列内同主体 **≥2 张时折叠成一摞，默认收起**，用户手动展开 | 折叠只是呈现，展开后每张仍是独立关系卡、独立跳转 |
| D6 | 责任范围改为**三态选择器**，默认「我参与的」 | 见 D6 说明 |
| D7 | 「已推荐」尾巴块**默认收起** | 「推了还没回音」池，天生最长、最不需要天天翻 |
| D8 | 看板**只读 + 跳转**，不做状态编辑/记动态 | 编辑归详情页，避免误操作 |
| D9 | 列头**双计数**：`N条 · M个标的/意向` | 两个数都能在屏幕上自己数出来 |

**D1 状态映射**（`recommended`…`lost` 九个取值不变，只改看板分组）：

```
初步接触   recommended | interested | in_discussion      主列
深度交流   due_diligence | agreement                     主列
已成交     deal_closed                                   主列（独立成列：唯一产出，不埋进抽屉）
已关闭     paused（单独分组，琥珀色）| not_interested | lost   底部折叠抽屉
```

> ⚠ **不要复用 `isRelationEnded`** 做列映射：[`relationLabels.ts:26`](../frontend/src/features/relations/relationLabels.ts) 的 `ENDED_STATUSES` 把 `deal_closed` 算作已结束，直接复用会把成交卡冲进抽屉。看板需要自己的映射（见 B2 `boardBuckets.ts`）。标签、`daysSince`、`STALE_RELATION_DAYS` 照旧复用该文件。

**D6 三态责任范围**，与现有权限模型的关系：

现有可见性 [`relation_visible_sql`](../backend/app/api/routes/utils.py) 是 **OR**（标的负责人 ∨ 意向负责人 ∨ 买家负责人）。若看板筛选取 **AND**（标的与买家均归我），会出现孤儿卡——标的归我、意向归同事的关系，在我和同事的看板上**都不显示**。而撮合业务里「一人持卖方、一人持买方」很可能是常态。故做成三态，AND 作为可选档而非默认：

```
责任范围： 全部  |〔我参与的〕|  我全权的
            ↑         ↑            ↑
      权限内全看   OR（默认）   AND：标的+买家都归我
```

## 3. B1 后端：瘦端点（约 40 行，无迁移）

### B1-1 瘦字段集 + 新路由

看板只需 9 个字段，**零子查询**：

```python
def _relation_board_columns() -> str:
    return """
      r.id, r.seller_target_id, r.buyer_intent_id, r.status,
      r.last_event_at::text as last_event_at,
      coalesce(r.last_event_at, r.updated_at, r.created_at)::text as last_activity_at,
      st.target_name as seller_target_name,
      bi.intent_name as buyer_intent_name,
      bp.buyer_name
    """

@router.get("/relations/board", response_model=list[RelationBoardCardOut])
def list_relations_board(
    current_user: CurrentUser,
    db: Session = Depends(get_db),
    ownership: str = Query(default="involved", pattern="^(all|involved|sole)$"),
    q: str | None = Query(default=None, max_length=200),
    limit: int = Query(default=2000, ge=1, le=5000),
    offset: int = Query(default=0, ge=0),
) -> list[dict[str, Any]]:
    ...
```

join 与排序沿用 `list_relations`（三张表 join，`order by coalesce(r.last_event_at, r.updated_at, r.created_at) desc`）。**不做服务端分组**——一次拉完整块数据就没有分页边界，分组交给前端。

`last_activity_at` 与上述 `order by` 表达式同源，是稳定排序键；无事件关系的 `last_event_at` 为 `null`，但 `last_activity_at` 仍会回退到更新时间/创建时间。`last_event_at` 单独保留，继续服务「N 天无动态」语义。

载荷对比：

| | 现有字段集 | 瘦字段集 |
|---|---|---|
| 单行 JSON | ~1 KB | **~400 B**（目标 ≤500 B） |
| 每行子查询 | 4 次 | **0 次** |
| 1000 条 | ~1 MB | **~400 KB**（gzip 后 ~100 KB） |
| 3000 条 | ~3 MB + 12000 次子查询 | ~1.2 MB（gzip 后 ~300 KB） |

几千行对 Postgres 是小数据，**先不要为此加索引**；本端点解决的是浏览器载荷与计数正确性，不是 DB 性能。

### B1-2 `ownership` 三态

```sql
all       -- 不加额外条件（仍受 owner_scope_enforced 下的 relation_visible_sql 约束）
involved  -- relation_visible_sql('r')                     现有 OR，默认档
sole      -- st.owner_user_id = :scope_user_id
          -- and (bi.owner_user_id = :scope_user_id or bp.owner_user_id = :scope_user_id)
```

### B1-3 抽公共 where

把 `list_relations` 里的 where 拼装抽成 `_relation_where(...)`，两条路由共用，避免筛选/可见性逻辑分叉。**这是本批次唯一需要动既有代码的地方，改完既有 `/relations` 行为必须完全不变。**

### B1-4 顺手两件

- **启用 GZip**：[`main.py:84`](../backend/app/main.py) 一带只有 `Utf8JsonMiddleware` / `AdminAuthMiddleware` / CORS，**没有 `GZipMiddleware`**。加 2 行，JSON 压缩率约 75%，全站接口受益。注意与 `Utf8JsonMiddleware` 的顺序，加完回归中文响应。
- **`/relations` 截断信号**（治 B-1）：不改信封，前端发现「返回条数 === limit」即在顶部提示"数据可能不完整"。`le=200` 本身**不必调大**——看板走新端点后，`/relations` 的其余调用方（`ProgressPanel` 按标的查，≤10 行）都不需要大 limit。

> ⚠ 命名陷阱：[`relations.py:468`](../backend/app/api/routes/relations.py) 的 `deep_progress_elsewhere` 判的是 `status in (已推荐…协议阶段)` 五个状态，**语义是「另有其他活跃买家」，与 `recommendation_flow` 里只算尽调/协议/成交的同名概念不同**。新端点不返回该字段，也别照抄这个命名。

## 4. B2 前端：看板改版

### B2-1 组件拆分

```
pages/Board.tsx              tab / 筛选 / URL 同步 / 取数编排
features/board/
  boardBuckets.ts            状态→列映射、深度排名、排序键、stale 判定   ← 纯函数
  useBoardData.ts            取数 + 分组 + 截断检测
  BoardSummary.tsx           顶部概况条
  BoardFilters.tsx           搜索 / 责任范围三态 / 隐藏无动态 / 排序
  BoardColumn.tsx            粘性列头、独立滚动、卡片流式排布、已推荐尾巴块、显示更多
  RelationCard.tsx           4 行独立卡（view 决定行序）
  RelationGroupCard.tsx      折叠摞（≥2 才折、默认收起）
```

### B2-2 分组与排序算法

```
1. 按 D1 映射把关系分进 4 个桶
2. 每桶内按 view 的主体键分组：
     view=target → seller_target_id ；view=intent → buyer_intent_id
3. 组的 deepest = 成员状态里最深的一个
     初步接触 in_discussion(3) > interested(2) > recommended(1)
     深度交流 agreement(2) > due_diligence(1)
4. 初步接触列切两块（一个组只出现在一块里，不碎）：
     主区   deepest ∈ {沟通中, 有意向}
     尾部块 deepest == 已推荐   → 默认收起（D7）
5. 块内排序：sort=activity 按组内最新 last_activity_at desc（默认）
             sort=stale    按无动态天数 desc（催办视角）
6. 渲染：relation_count == 1 → RelationCard
        relation_count >= 2 → RelationGroupCard（收起态，D5）
```

### B2-3 渲染预算

网络解决后 DOM 成为新瓶颈。三层各挡一部分：**同主体折叠**（单标的业务上 ≤10 买家 → 压成 1 摞）、**已推荐尾巴默认收起**、**「显示更多」纯前端切片不发请求**（数据已在内存）。目标：**初始渲染 ≤150 张卡**。

### B2-4 筛选与计数纪律

- 列头按 D9 双计数；**筛选生效时显示筛后数并注明 `(隐藏 N)`**，别让人以为数据丢了。
- 折叠摞的 `×N` 是关系数，与列头主计数同口径。
- tab / 责任范围 / 排序进 URL query，刷新与分享保持视图。
