## 一、给接手 Agent 的开场白

你好，接下来我们一起重构 Match-MA 的**标的信息指标体系**。

**为什么做这件事。** 平台的核心能力是「买家需求 → 标的推荐」。这条链路上有两个消费者在读标的指标，它们对指标的要求完全不同：

1. **SQL 初筛**——把买家的定量门槛和可枚举条件直接翻译成 `where` 子句，决定「谁有资格出现在候选里」。这一段必须精确、可索引、零歧义，因为它一票否决。
2. **LLM 深度评估**——读标的的自然语言画像，判断「具备地区产业优势」「有成熟海外仓」「产业链上下游能协同」这类**没有固定枚举值**的诉求。这一段负责细排和推荐理由。

所以指标体系的第一性问题不是「字段够不够全」，而是**每个指标该归到哪个消费者名下**：

- **定量指标**（营收、净利、估值、PE、股比…）→ 进 SQL，`gte/lte` 比较
- **可枚举定性指标**（是否上市、上市交易所、可否并表、盈利状态…）→ 进 SQL，`eq/in` 比较，**枚举值必须封闭且穷尽**
- **不可枚举定性指标**（产业优势、团队特点、协同想象空间…）→ **不进 SQL**，进画像正文交给 LLM 判断

判错一类的代价是不对称的：把不可枚举的硬塞进枚举（比如给「产业优势」定义 8 个选项），会逼着解析环节在 8 个都不合适时乱选一个，污染的是筛选结果；把可枚举的留在自由文本里，则是白白放弃了精确筛选能力，还让 LLM 去做本该 SQL 做的事。

**一条贯穿全局的硬约束：指标必须成对。** 标的侧的每个筛选指标，买家侧都要有对应的诉求字段，反之亦然。平台已经用 `registry/indicators.py` 的 `target_column` + `operator` 把这个配对关系显式声明了——买家的 `min_net_profit_yuan` 声明了 `operator='gte'`、`target_column='current_net_profit_yuan'`。**只在一侧加字段等于没加**：买家能填但标的没有对应列，筛出来全是空；标的有数据但买家无从表达，这个数据永远用不上。所以后面每提一个新增指标，都要同时回答「买家侧怎么表达」。

**当前状态。** 下面第二节是标的侧现有指标的完整清单（77 项，含已识别的缺口），按画像栏目分类，标注了定量/可枚举定性/不可枚举定性和现有枚举值。它是从三处真源合并出来的：

- `backend/app/registry/indicators.py` —— 指标注册表（46 项，带 `screening`/`operator`/`target_column`/`deep_eval` 等标志位）
- `database/migrations/001_baseline.sql` + `002_target_information_model.sql` —— 实际 DB 列与 check 约束
- `backend/app/services/profile_sections.py` —— 5 个画像栏目，不可枚举定性内容的载体

**已知需要处理的问题**（详见第三节），按优先级：上市信息只有「境内/境外」两值不够用、缺主要产品与产业链方向、缺投资并购形式、毛利率/净利率买家能提要求但标的侧没有列、日期类字段存成了 text。

**需要你产出什么。** 逐项过一遍这张表，给出增/减/改的结论，每一条都要落到：指标名、归类（定量/可枚举定性/不可枚举定性）、枚举值全集（如果是可枚举）、买家侧对手方字段、以及「这个指标缺失时筛选该怎么办」。**注意：改动会连带影响标的信息页和标的解析流程**（新增枚举值意味着解析提示词要能识别它、录入界面要能选它），这部分的施工范围也请一并评估。

推荐链路那侧（筛选器 skill、SQL 生成、深评接入）由另一条线在做，不用管；你只要保证指标体系本身自洽、成对、且三类归属清晰。

先读 `docs/系统总纲.md` 了解全局，再看本文件第二节。

## 三、已识别的问题清单

按处理优先级排列。每条都需要在重构中给出结论。

### P0 上市信息表达能力不足（序号 42/43/44/45）

`listing_market_region` 只有「境内/境外/未知」三值，check 约束写死在 DB 里。业务实际需要区分 A股（还要细到主板/科创板/创业板/北交所）、新三板、港股、美股——这直接影响「只看 A 股上市公司」「要港股壳」这类高频诉求。

需要决定：是扩展现有字段的枚举，还是新增「上市交易所」作为独立指标、原字段降级为派生值？买家侧对应的 `listing_market_region` 和纯文本的 `listing_board_requirement_summary` 要怎么合并？

### P0 缺主要产品与产业链方向（序号 21/22）

行业只到二级，但实务里「做锂电池正极材料的」和「做锂电池 PACK 的」是两回事，都归在同一个二级行业下。买家侧已有 `industry_focus_tags_json`（字典外细分方向，自由标签）在承接这类表达，但标的侧没有对手方——**等于买家能提，系统永远匹配不上**。

需要决定：走「受控标签字典」还是「自由标签 + 语义匹配」？前者能进 SQL 但要持续维护字典，后者只能交给 LLM。

### P1 投资并购形式与现有交易字段语义重叠（序号 70）

新提的「接受股权投资 / 接受并购 / 两者皆可」，和已有的 `transfer_flexibility_type`（转让灵活度，7 值）、`can_control`、`can_consolidate`、`accepts_minority_investment` 覆盖同一片语义。直接新增会造成同一件事有两处记录、两处可能打架。

需要决定：是新增独立指标并把老字段改为派生，还是它本就是 `transfer_flexibility_type` 的一个视图？

### P1 毛利率 / 净利率买卖两侧不对称（序号 39/40）

买家侧有 `min_gross_margin`、`min_net_margin` 两个条件字段，标的侧**没有对应列**。净利率还能用净利/营收现算，毛利率完全无解——买家填了这个条件，筛选时只能当作「未知」放行。

需要决定：标的侧补列（需要解析环节能提取毛利），还是把买家侧这两个条件降级为深评项？

### P1 三个字段有 DB 列和 check 约束，却没进指标注册表（序号 37/57/64）

`operation_stability_status`（经营稳定性）、`transfer_flexibility_type`（转让灵活度）、
`earnout_dependency_status`（对赌依赖）三列在 `001_baseline.sql` 里有列定义、有 check 约束、
枚举值明确，但 **`registry/indicators.py` 里一条都没声明**。

后果：前端指标体系不展示、筛选用不了、规则打分不参与、解析环节大概率也不填。
全后端只有 `api/routes/update_logs.py` 引用过它们（变更日志的字段名映射）。

其中「转让灵活度」和「对赌依赖」业务价值不低——前者直接回答「这家能不能控股/并表」，
后者正是买家侧 `earnout_requirement`（对赌要求）的天然对手方。**建议优先补进注册表**：
不需要新增迁移，只是声明缺失。

### P2 日期字段存成 text（序号 48/50）

`valuation_date`、`asking_price_date` 在注册表里声明是 `date`，DB 里是 `text`。后果是无法比较、无法排序、无法回答「估值是半年内的吗」这类新鲜度问题——而估值和报价的新鲜度对撮合判断相当关键。

### P2 行业原文字段已被取代但仍在（序号 17/18）

`industry_primary` / `industry_secondary` 是结构化行业之前的遗留，现在双轨并存。需要确认能否退役，或明确它只作为解析溯源留存、不参与任何匹配。

### P2 财务期间未规范化（序号 33）

`financial_period_label` 是自由文本。不同标的写「2024年」「2024年度」「24全年」，无法判断两个标的的财务数据是否同期可比。
