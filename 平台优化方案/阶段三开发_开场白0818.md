## 这个阶段在做什么

阶段二把用户的话拆成了两半：能翻译成 SQL 的进 `condition_groups`，

你要给它一个消费者：一次干净上下文的 LLM 调用，拿到全部候选的完整画像，
**逐条判定每个定性诉求，然后按匹配程度重排序**。

节点已经存在（`recommendation_deep_eval_to_target`，有生产配置），

你要做的是改造输入输出形态并发布 prompt v0.2.0。

## 和上一版深评最大的三处不同

1. **不评级、不打分，只排序。** 分档是绝对判断（要求模型心里有一把看不见的标尺），
   排序是相对判断（两两比较），LLM 对后者稳定得多。
2. **不分片。** 这是取消分档的必然结果——分档时两片能靠绝对标尺合并，
   纯排序时 A 片的 rank 1 和 B 片的 rank 1 谁靠前**没有任何依据**。整体提交，
   40 家 ×800 字符 ≈ 3.2 万字，放得下。
3. **定性诉求是独立输入变量，不是塞进 `anchor_context` 的一段文本。**
   它是深评的主要工作对象，要能在提示词里明确指令「逐条判定这些」。

## 三个容易做错的地方，先打预防针

1. **不要复用 `_get_deep_eval_node_config()` 的 understudy 回落。**
   它在方向节点未配置时会回落共用节点，而新形态提示词只装在 `_to_target` 上——
   回落会拿到旧形态提示词，模型返回的东西对不上新代码，**而且不会报错**。
   取不到配置就按「深评不可用」降级，不要悄悄换个节点跑。
2. **旧深评函数一个字都不改**（`_run_recommendation_deep_eval` / `_run_deep_eval_shards` /
   `_interleave_shards` / `_apply_deep_eval_results_to_candidates`）。
   它们服务 `/candidates` 旧链路，阶段五整体拆除。你新建一个叶子模块
   `services/recommendation_deep_eval.py`，两条路并存——阶段二也是这么做的。
3. **`load_profile_sections` 传错实体类型不会报错**，只会返回空画像，
   然后深评在没有画像的情况下照常给出排序，**看起来完全正常**。正向是 `seller_target`。

## 四条必须过的验收

施工单第六节有 11 条用例，这四条是硬要求：

- **用例 7** 模型返回 `{"foo": 1}` —— `deep_eval_status` 必须是 `schema_mismatch`，
  不抛异常也不伪造排序
- **用例 8** LLM 调用抛错 —— `deep_eval_status = "unavailable"`，**本轮不中断**，
  agent 的原始名单照常输出
- **用例 10** 同一标的被两次筛选命中 —— `candidate_hit_counts` 为 2 且进了深评输入。
  这是本阶段唯一的新数据流，漏了不会报错，只会让深评永远看不到「强候选」信号
- **用例 11** 节点未配置 —— **不得回落共用节点**

7 和 8 是在复刻上一轮的真实事故：v0.1.0 提示词把变量写成了单花括号，
模型收到字面量，输出全错但**全链路零报错**，只能靠人读对话记录才发现。
两种失败都必须有名字。

## 本阶段只产出、不改最终答案

深评结果写成一条 `agent_deep_eval` 消息落库，**素材包 `answer_brief_json` 保持原样**，
写作节点看不到它。把深评接进最终名单是阶段四。

这样切是有意的：深评的质量要在真实数据上看了才知道，
而在它稳定之前就让它决定用户看到的名单，出了问题连对照组都没有。
阶段二就是这么做的（快照落库、接进 agent 提示词留给阶段四），效果很好。
