## 一、为什么这次要对齐

推荐功能正在重构成两段式：**SQL 硬筛负责「谁有资格出现」，LLM 深评负责「谁排在前面」**。

关键在于——**SQL 侧的字段契约完全由 `backend/app/registry/indicators.py` 生成，不再手写**。
筛选工具暴露给模型的 JSON Schema，它的字段清单、算子、枚举取值，全部读自注册表的四项声明：

| 声明 | 作用 |
|---|---|
| `screening` | 这个字段能不能用于筛选 |
| `operator` | 生成什么 SQL（`gte` / `lte` / `in` / `eq` / `overlap` / `not_overlap` / `region_any` / `requirement_capability`） |
| `target_column` | 买家条件比对标的的哪一列 |
| `enum_options` | 闭集取值，直接进 schema 的 `enum`，模型物理上填不出集合外的值 |

**结论：指标注册表的声明质量，直接就是推荐能力的上限。** 少声明一个 `operator`，
那个条件在推荐里就完全不存在；写错一个 `target_column`，筛出来必然为空且不报错。

### 一条贯穿全局的硬约束：指标必须成对

买家侧的每个筛选条件，标的侧必须有对应的列，反之亦然。**只在一侧加字段等于没加**——
买家能填但标的没有对应列，筛出来全是空；标的有数据但买家无从表达，这个数据永远用不上。

所以后面每提一个新增或改动，都要同时回答「另一侧怎么表达」。

## 三、推荐线需要你交付的三项（硬阻塞，做完推荐才能开工）

标的侧的闭集都已就绪，**卡点全部在买家侧**。

### 1. 买家侧「重大风险容忍」——需要新增字段

标的侧 `major_risk_flags_json` 已是闭集：
`litigation`（涉诉）/ `equity_frozen`（股权冻结）/ `enforcement`（被执行）/ `violation`（违规违法）/ `none`（已核查无重大风险）

买家侧目前只有自由文本 `major_risk_tolerance_summary`，**筛不了**。

业务方明确的语义是三态：**未提及 / 不接受全部风险 / 不接受特定风险**（特定风险与标的侧的类型一一对应）。

实现建议（最终形态由你定，但要满足两个要求）：

- **SQL 只读一个列表字段**。建议 `unacceptable_risk_flags_json`，存"不接受的风险类型"数组，
  算子 `not_overlap` 对 `major_risk_flags_json`——标的命中任一买家不接受的风险即出局。
- **三态语义由代码派生，不要让 SQL 去判三态**。"不接受全部"落库时自动展开成全部风险类型；
  "未提及"落成空数组。这样筛选逻辑只有一条，不需要分支。

### 2. `transaction_types_json`（交易方式）——补声明即可

标的侧 `acceptable_transaction_structures_json` 已是闭集：
`equity_transfer` / `capital_increase` / `asset_purchase` / `merger` / `other`

买家侧字段已存在，但缺 `operator` 与 `target_column`，且 `screening=False`。
**两侧枚举值必须严格对应**，请核对后补声明。

### 3. `accepts_minority_investment`（接受少数股权）——只差一个标志位

买家侧的 `operator='requirement_capability'` 和 `target_column='accepts_minority_investment'`
**都已经声明好了**，只差 `screening=True`。这是成本最低的一项。

## 四、明确不要做的三件事

- **溢价上限（`max_premium_rate`）不进筛选。** 业务方判断：可接受溢价范围是与买家预算、
  标的估值/报价挂钩的计算值，与标的侧 `premium_rate` 不同轴，硬比会得出错误结论。
  它归深评，注册表里不要给它 `operator`。
- **不要复活「经营稳定性」。** `operation_stability_status` 已在 `8e14c718` 被判为伪枚举删除，
  这个判断是对的，不要因为它在旧文档里出现过就补回来。
- **`is_for_sale` 不要接进筛选。** 它与 `target_grade='E'` 语义重叠
  （E ⟺ 已售出/已停售，由 `services/entity_grade.py` 单点派生），属于待清理项而非待启用项。

## 五、还需要你判断的四项

这些我给不出结论，需要你结合业务判断：

1. **对赌**：买家侧有 `earnout_requirement`（required/preferred/not_required/unknown），
   标的侧 `earnout_dependency_status` 有 DB 列和 check 约束，但**未进注册表**。

## 七、产出要求

一份更新后的方案 + 一份可施工的施工单。每个字段的结论都要落到：

| 项 | 说明 |
|---|---|
| 指标名与列名 | |

**关于「缺失时怎么办」**：推荐新方案采用 **缺失即出局**——条件字段为空的标的不进候选。
这是 agent「先按完整条件搜、召回不足再减条件重筛」这套策略成立的前提。
所以每个字段都要明确：它为空是否可接受、是否需要在解析或调研环节兜底。

**注意连带影响**：新增或改动枚举值会连带影响标的信息页展示、录入交互、
以及解析提示词（模型要能识别新枚举）。这部分施工范围请一并评估进施工单。
