## 你要修的三件事

1. **Writer 归 worker**（问题四根治）。现在 agent job 刻意停在 brief，正文由前端调
   `/answer-stream` 时在 API 里生成，`persist()` 在流循环之后 —— 用户关页签就整段丢失，
   会话永远停在黄点，重开会话又会重新生成、**重新付费一次**。
   改成：job 写完 brief 继续把正文写完，节流落草稿，`/answer-stream` 退化成订阅。
2. **worker 优雅退出 + heartbeat**。`backend/app/worker.py` 全文没有信号处理，
   Railway 部署一重启，手上的 job 就消失，只能等 1800 秒 stale 扫描。
   生产那 3 个 `stale_running_job` 基本可以确定是部署打断，不是模型慢。
3. **吞异常处补 savepoint**。`_emit_step` 和 `tool_loop.py` 里 `except Exception: pass`
   之后继续用同一个 session，session 已经中毒，下一次查询才报 `InFailedSqlTransaction`，
   最初的真实错误永远丢失。

## 五个容易做错的地方，先打预防针

1. **不要在 API 侧做 lease + 生产者线程。** 这是被明确否决的方案：API 会重启会多副本，
   进程内生产者跟着死；没有 Redis，跨进程协调只能靠 DB，最后就是把 job 表的原子领取和
   stale 回收在 API 里重新发明一遍。**服务端所有者用现成的 worker job。**
2. **草稿必须独立 commit 才可见，但不要因此把 handler 改成大事务。**
   `session_scope` 退出时才 commit（`backend/app/db.py:53`），可 handler 本来就是
   inline commit 模式（`jobs/handlers/recommendation.py` 有 8 处裸 `db.commit()`）。
   沿用它直接 commit 即可。**改成一个大事务会让所有进度消息在 job 结束前都看不见**，
   等于把现在能用的进度回显也弄坏。
3. **`max_attempts=1`。** agent job 只有一次机会。任何「把 job 放回 queued」的路径
   都必须确认**不消耗 attempts**，否则优雅退出反而在制造失败。
   也别顺手触发 `run_once` 失败分支里的 `_finalize_attachment_job_failure` 和
   `_mark_related_business_update_failed_if_final` —— 释放不是失败。
4. **绝不把半截草稿升格成 answer。** 只有上游正常收尾、或已生成完整规则兜底文案，
   才写 `agent_answer`。中止优先这条不变式必须保住：每次 flush 前查 abort，
   最终写入仍走现有 advisory lock，**在锁内同时复查 answer 与 abort 都不存在**。
5. **迁移会阻断整个部署。** 从 `002_` 起编号，加完**必须**跑 `tests/test_migration_sql.py`
   （历史事故：注释里的分号把语句切坏）。Railway preDeploy 跑 `alembic upgrade head`，挂了整个部署停。
