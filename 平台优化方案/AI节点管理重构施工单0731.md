# AI 节点目录规范化与设置页重构施工单（0731）

## 总原则

> **节点集合、节点类型、节点职责由代码目录固定；设置页只管理固定节点的运行配置（模型 / Prompt / 参数 / 测试），不创建也不删除节点。**
> **数据库中的停用/退役记录是历史配置，不等同于节点从系统中消失。**
> **模型配置与节点配置生命周期不同**：模型是管理员资产，可停用；节点是代码目录，只有配置状态，没有存在与否。

对应代码：`backend/app/api/routes/model_config.py`（2079 行）、`frontend/src/pages/Settings.tsx`（961 行单文件）、新增 `backend/app/registry/nodes.py`。

本单**不改任何 AI 运行时行为**（handler、回退逻辑、prompt 渲染一行不动），**不加数据库迁移**，**不改 prompt 内容**。

# 第一部分：后端目录契约

## 1.1 新建 `backend/app/registry/nodes.py`

与既有 `registry/indicators.py` 同构：frozen dataclass + 元组常量 + 查询函数，**无 SQL、无传输代码**。

```python
@dataclass(frozen=True)
class NodeSpec:
    node_name: str
    label: str                          # 中文名，唯一真源
    domain: str                         # target | buyer | recommendation | common
    node_type: str                      # 照抄 §0.1，代码目录声明，DB 只是副本
    description: str                    # 一句话用途
    runtime_inputs: tuple[str, ...] = ()    # handler 实际喂进来的业务数据
    prompt_variables: tuple[str, ...] = ()  # 模板里的 {{ var }}
    prompt_required: bool = True        # OCR 为 False
    understudy: str | None = None       # 代跑节点（原 fallback）
    understudy_kind: str | None = None  # "and" | "solo"，见 §0.2
    lifecycle: str = "active"           # active | retired
    sort_order: int = 0
```

**`runtime_inputs` 与 `prompt_variables` 必须分开。** 节点抽屉要回答的是「这个节点运行时吃什么」，不是「模板里写了哪些变量」—— OCR 就是反例：没有 Prompt，但有附件输入。原稿把两者混为一谈，是错的。

`PROMPT_VARIABLE_DESCRIPTIONS`（`Settings.tsx:509`）一并迁入本模块，通过接口下发。

- 不接受调用方传 `node_type`。

`POST /model-config/nodes` 保留（通用 API，其他调用方可能用），但**设置页不再调用它**。

### 规则

1. **一个节点一行，永不重复出现。** 「买家需求与推荐节点」卡片区整块删除。
2. **只有两种状态**：已配置 / 未配置。**没有「停用」，没有「删除」。** 行内不提供任何生命周期操作。
3. **主操作只有一个「配置」**，进单节点抽屉。测试、查看测试记录都在抽屉里。
4. **retired 节点完全不显示**（不是折叠）。它们即将被《退役 AI 节点与代码清除》单删掉，没必要让管理员看见。唯一的隐藏依据是注册表 `lifecycle=retired`。
5. **不再按 `node_type` 过滤** —— 这是 OCR 节点消失的根因。
6. **未登记节点照常显示**：DB 里有、注册表没有的 `node_name` 仍渲染，`label` 回落到 `node_name`，`domain` 归入 common，标「未登记」。**装饰，不是过滤。**
7. **代跑提示按 `understudy_kind` 分两种文案**（§0.2），不能套同一个模板：
   - `and` → `未启用 · 需与「XXX」同时就绪才生效`
   - `solo` → `未启用 · 当前由「XXX」代跑`
8. **「回退」一词从设置页彻底移除。**

# 第三部分：坑（已探明）

### 坑 1：代跑的两种语义不能套同一个文案

见 §0.2。**最容易做错的一条。** 只配 `buyer_intent_semantic_parser` 而不配 `buyer_intent_normalizer`，运行时行为**完全不变**；而方向深评配一个就生效一个。旧 UI 把四个节点渲染成四张同构卡片，把这个差异彻底抹平。

### 坑 2：注册表不能变成新的隐式过滤器

OCR 节点消失的根源是白名单式过滤（`Settings.tsx:135`）。注册表必须是**装饰**而非**过滤**。复核时重点看有没有被实现成 `filter(n => REGISTRY[n.node_name])`。唯一允许的隐藏是 `lifecycle=retired`。

### 坑 3：`node_type` 决定的能力不能被 domain 顶掉

`prompt_editable`、`test_supported`、`show_sampling_options` 仍由后端按 `node_type` 下发（`_settings_node_summary` 的 `ui` 块）。domain 只管**分组显示**，不参与能力判断。OCR 节点进列表后必须仍然没有 Prompt 编辑入口。

### 坑 4：`_latest_production_calls` 的 test-trace 排除条件必须原样保留

现有 SQL 排除 `metadata_json->>'source' in ('model_node_test','model_config_node_test')`。扩到全部节点后如果漏掉，「最近生产调用」列会被业务测试记录污染 —— 而管理员正是靠这一列判断节点在真实链路里是否健康。

### 坑 5：修 `meta.py` 的两个健康指标会让数值跳变

`default_llm_nodes` 与 `default_prompts` 修复后从 8 变 11。**这是修正不是回归。** 如果有告警阈值绑在这两个指标上，需要同步调整。

### 坑 6：`node_type` 不是装饰，它会落进 `ai_trace.trace_type`

```python
# traces.py:415 _insert_model_node_test_trace
trace_type = "llm" if node_config["node_type"] == "llm" else str(node_config["node_type"])
```

而业务路径的 `_insert_llm_trace` 等硬编码 `'llm'`（`traces.py:49,134,218,301`）。于是 `recommendation_query_parser`（`parser`）在业务链路写 `trace_type='llm'`、在节点测试写 `trace_type='parser'`。**这是不动 `node_type` 现值（方案 A）的直接理由** —— 归一会造成历史 trace 与新 trace 的 `trace_type` 断层，值得单独评估。
