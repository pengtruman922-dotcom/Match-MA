## 0. 诊断与总目标

### 0.1 系统现状（实测）

后端 36,612 行 / 前端 13,279 行 / 38 张表 / 41 个迁移 / 7 个 LLM 节点。按职责归类后端代码：

| 板块 | 行数 | 占比 |
|---|---|---|
| AI 抽取管线（OCR、解析、抽取动作、业务更新） | ~11,800 | 32% |
| AI 运维与可观测（debug、model_config、background_jobs、update_logs） | ~8,200 | 22% |
| 推荐 | ~5,800 | 16% |
| 核心业务 CRUD（标的、买家、意向、关系、字典） | ~5,900 | 16% |

**54% 的代码在服务"把材料变成数据"和"观察 AI 有没有干活"，16% 在服务撮合业务本身。**
前端对比更明显：调试 AI 有 2 个独立页面（DebugCenter + DebugEntity，889 行）；跟进管理 0 个独立页面。

### 0.2 根因判断

原始设计是**档案思维**：把标的当成一份要填完整的档案（`seller_target` 建表即 74 列，现 77 列；`buyer_intent` 52 列），所有投入都在"填得更全、更自动、更有据可查"。

但撮合的实质是**比较**。比较需要的不是"字段填得全"，是"维度可对照"。这就是"越来越复杂却达不到期望"的来源：**投入全在输入侧，判断侧那一层从来没建过。**

**结论：不重写。** 理由三条——代码结构不是瓶颈（上月刚重构完，有 CI）；重写要把迁移 splitter/任务队列/OCR/证据链/权限全部重踩一遍；最关键的是**重写之后库里还是没有匹配需要的信息**，这是数据问题不是代码问题。

正确动作是**补一层 + 冻两块 + 转重心**（见 §11）。

### 0.3 已发现的两个生产级错筛（静默发生中）

**Bug ①：价格口径串味。** `_score_target_against_intent` 中：

```
target_price = 标的报价 or 标的估值 or 标的市值
if target_price > 买家.max_valuation_yuan → 硬失配沉底
```

北控需求"预算 10–15 亿、控股 25–30%"，对应标的整体估值 33–60 亿，但系统拿 15 亿去比标的整体估值/市值，**33–60 亿的标的全部沉底**。专杀"大标的+小比例"——正是国资买家最典型的形态（北大健康 29.9%、黄河、北控 25–30% 全中招）。

**Bug ②：排除项被压平到 L1。** 黄河"排除风电"，"风电"是 L2，录入解析归一化后变成"能源"，`_excluded_industry_hit` 拿它比标的 `industry_l1` → **整个能源行业被排除**，而黄河本该保留光伏储能类高科技标的。

两个 bug 同源：**口径不对应**，且完全静默。

### 0.4 产品取向与规模（已确认）

- 取向：**更怕漏**（recall 优先）；
- 规模：标的 500–1000，买家意向 100–500 → 全库扫描无性能压力；
- 填充率：一级行业/地区 ≈99%，利润/营收 ≈60%；
- 两个方向（为买家找标的 / 为标的找买家）频率相当。

## 1. 核心架构

```
全局条件 AND（方案A OR 方案B OR 方案C）
  → 扫描全部有效对象（不再 200 截断）
  → 结构化三态判断（compatible / possible / conflict）
  → 深评队列（乐观分 + 已知条件数二级排序 + 方案保底名额）
  → 一次性 LLM 深评（分片并发、同一标准、按 ID 回写）
  → 合并去重、按 (grade, 乐观分) 排序展示
  → 漏斗数字全程可见（scan / eligible / deep_eval / display）
```

三条不可动摇的原则：

- **结构化规则只负责识别"明确冲突"和组织方案**，信息缺失不出局；
- **LLM 只做无法结构化的业务判断**，结果通过实体 ID + 方案 ID 确定性回写；
- **会话内条件调整默认只对本次会话生效**，只有显式"保存回买家需求"才修改正式意向。

### 1.1 统一评判轴

无论哪个方向，唯一评判轴是 **"标的满足买家采购需求的程度"**：

- 推标的（buyer_to_target）：固定买家，问所有标的；
- 推买家（target_to_buyer）：固定标的，问所有买家意向。

因此**指标体系一律从买家采购需求倒推**，标的侧字段是它的对照面。

## 2. 指标体系（MECE 九轴）

### 2.1 设计原则

1. 指标来源：从买家真实需求倒推（7 份样本：北控/北京工控/北物/荆州城建/北大健康/黄河/广州城投）；
2. **两侧一一对应**：每个维度，要么两侧都是结构化字段（走 SQL），要么两侧都是画像栏目（走语义）。**不允许一侧结构化、另一侧散落自由文本**；
3. 不重不漏互相独立。

### 2.3 MECE 自查

- **C1 整体价值 vs C2 交易对价**：是**依赖**不是重叠，必须分开——合并就是 Bug ①；
- **D1 比例 vs D2 控股 vs D3 并表**：语义上有重叠（51% 蕴含控股），但业务上"能否控制"还取决于股东结构与交易方式（30% 也可能控制）。规则：**比例是事实，控股/并表是结论，结论不由比例自动推导**；
- **F2 经营状态（枚举）vs F3 经营质量（语义）**：划界规则——**枚举装得下的一律不进画像**；
- **D5 交易方式 vs D1–D4**：交易方式 = 结果（控股/参股）× 路径（协议转让/增资/借壳）。结果部分已被 D1–D4 完整覆盖，做成独立维度会重复计分 → 因此 D5 不进 SQL。

## 3. 价格轴（两条独立的轴）

**报价 ≠ 市值。** 报价是"卖方对所售那部分股权的要价"，市值/估值是"100% 股权的价值"。必须拆成两条同口径的轴：

| 轴 | 买家侧 | 标的侧 | 口径 | 判定 |
|---|---|---|---|---|
| **C-a 整体价值** | min/max_valuation、min/max_market_cap | 上市比 market_cap_yuan，非上市比 valuation_yuan | 100% 股权 | 硬筛 |
| **C-b 交易对价** | budget_min/max_yuan（新增） | asking_price_yuan | 本次交易 | 硬筛 |

### 3.1 必须废除的 fallback 链

现有 `报价 or 估值 or 市值` 三选一混成一个变量的写法**整体删除**。上市公司比市值、非上市比估值，报价只与预算比，不跨轴。

### 3.2 预算的定位（降级）

`budget_min/max_yuan` **不作为独立筛选标准**。唯一用途：当买家**没写**市值/估值要求但写了预算和比例时，反推 `隐含估值 = 预算 / 比例`，且该推算值**只用于排序参考，不判 conflict**。理由：比例本身经常不确定（"要控制"不等于某个具体数）。

### 3.3 股权比例（D1）的判定边界

买家常常只写"要控股/要并表"而不写比例，且"能否控制"取决于标的股权结构与交易方式。因此 **D1 只在买家明确写了比例区间时才启用 conflict 判定**，否则不参与。控股/并表走 D2/D3 的独立枚举。

## 4. 两条通用判定规则

这是整套体系的工程收益所在：**打分器从"223 行、每维一段定制代码 + 每维一个权重 + 各种 cap"，变成"两条通用规则 + 一张字段元数据表"。新增维度 = 元数据表加一行，不改代码。**

### 4.1 规则一：要求 × 意愿（覆盖 D2 D3 D4 E2 E3 H2 H3 共 7 维）

两侧枚举**不同名不同值**——买家侧是"要求强度"，标的侧是"能力/意愿"（标的侧 schema 已统一为 yes/likely/no/unknown）：

| 买家＼标的 | yes | likely | no | unknown |
|---|---|---|---|---|
| **required** | compatible | possible | **conflict** | possible |
| **preferred** | compatible | compatible | compatible（扣分） | possible |
| **not_required / unknown** | compatible | compatible | compatible | compatible |

买家侧统一值域：`required / preferred / not_required / unknown`。

### 4.2 规则二：数值区间（覆盖 B1 B2 B3 B4 C1 C2 C3 C4 D1 F1 共 10 维）

- 标的值已知 且 在买家区间内 → `compatible`
- 标的值已知 且 越界 → `conflict`
- 标的值未知 → `possible`（乐观分按"假定满足"计）

### 4.3 三条定制逻辑（仅此三条）

- **行业**：字典分层匹配（§6）；
- **地域**：行政层级 + REGION_GROUPS 展开；
- **风险**：severity 系统级降权（§5.3）。

### 4.4 三段式维度模式

一个维度可以同时有闭集部分和描述部分，分层落到不同引擎：

| 层 | 存法 | 用在哪 |
|---|---|---|
| 枚举 | required/preferred/not_required/unknown ↔ yes/likely/no/unknown | **SQL 判 conflict** |
| 数值 | numeric（如返投倍数、留任年限） | 深评（买家明确时可进 SQL） |
| 描述 | text | 深评 / 画像 |

适用：返投、迁址、团队留任、对赌。
**通用规则：一个维度只要存在"明确不接受"这个状态，枚举部分就值得进 SQL；程度和条件永远留深评。**

## 5. 闭集设计

### 5.1 判据（严格执行）

> 闭集的**唯一**目的是让 SQL 能判 conflict。必须同时满足：
> **①买家会在需求里明确表达该项**（须有样本证据）；**②标的侧能稳定拿到对应事实**；**③不与已有维度重叠**。
> 三条缺一 → 保持自由文本，只进深评。

补充两条硬要求：

- 项数 ≤ 20（超过 LLM 归类准确率明显下降）；
- **每个闭集必须带 `unknown` 和 `other`**，`other` 配自由文本。否则 LLM 会把不认识的东西强行归到最近一项——制造看起来干净、实际错误的数据，比留空危害大得多。

### 5.2 样本证据复核

| 候选闭集 | 样本命中 | 证据 | 判定 |
|---|---|---|---|
| 行业 L2 | 7/7 | 全部样本都写细分方向 | ✅ 做 |
| 经营状态（现金流/盈利） | 3/7 | 北控"现金流稳定是首要"、工控"小而美现金流好"、荆州"微利也行" | ✅ 做 |
| 迁址·招商落地 | 2/7 | 荆州"迁址加分"、广州城投"可招商落地" | ✅ 做 |
| 境内/境外上市 | 1/7 | 黄河"只投**境内**上市公司" | ✅ 做（轻量） |
| 团队留任 | 1/7 | 北控"保留核心团队" | ✅ 做 |
| 对赌接受度 | 1/7 | 北控"不强制对赌" | ✅ 做 |
| 返投 | 0/7 | 与迁址同源，成本近零 | ⚠️ 跟迁址一起做 |
| 风险类型 | **0/7** | 无人枚举具体风险 | ❌ 不做 |
| 交易方式 | 1/7 | 广州城投"控股或借壳重组"，但与 D1–D4 重叠 | ❌ 不做 |
| 控制路径 / 支付方式 / 上市板块 | 0/7 | — | ❌ 不做 |
| 买家类型 | — | 标的侧数据为空 | ⏸ 后置 |

### 5.3 三处关键决定

**风险：一个新枚举都不建。** 买家对风险的表达永远是"不接受重大风险"或不提，无法枚举 → `excluded_risk_types_json` 无 SQL 价值。正确形式是复用**已存在**的 `seller_target_risk.severity`（low/medium/high/critical/unknown）做**系统级默认规则**：critical 风险标的降权并在卡片标注，不需要买家提任何条件。`risk_type` 保持自由文本进深评。

**交易方式/控制路径/支付方式：不做 SQL。** 真问题不是频率低，是违反 MECE（见 §2.3）。原文交给深评读足够。

**上市板块换成上市地。** 样本 0 人提板块，但有人提"境内上市"。新增极轻的 `listing_market_region`（境内/境外/unknown），标的侧由已有 `listing_board` 直接推导（main_board/gem/star_market/bse → 境内；hkex/nasdaq/nyse → 境外），**零新增采集成本**。板块字段标的侧继续保留供展示，买家侧不建。

### 5.4 新增字段定案（共 9 项）

| # | 内容 | 侧 | 备注 |
|---|---|---|---|
| 1 | `industry_l2` / `industry_l2_json` | 两侧 | 字典 110 个 L2 现成 |
| 2 | `excluded_industries_json` 改为带 level 分层存储 | 买家 | 修 Bug ② |
| 3 | `requires_cash_flow_status` / `requires_profitability_status` | 买家 | 复用标的侧闭集 |
| 4 | `requires_relocation` + 目标地区 | 买家 | 拆自 `buyer_industry_advantage_summary` |
| 5 | `requires_return_investment` + 倍数 | 买家 | 三段式，枚举进 SQL |
| 6 | `requires_team_retention` | 买家 | 对 `management_retention_possible` |
| 7 | `earnout_requirement` | 买家 | 对 `earnout_dependency_status` |
| 8 | `listing_market_region` | 两侧 | 标的侧由 listing_board 推导 |
| 9 | `budget_min/max_yuan` | 买家 | 只做推算，不判 conflict |

3–7 全部走**规则一**同一条判定逻辑，零新增分支代码。真正的新值域只有 `listing_market_region`（3 值）。

**废弃**：`financing_stage_requirement_summary`（并购撮合场景用不到，样本 0 次出现）。

**保持文本、只进深评**：risk_type、交易方式、控制路径、支付方式、上市板块、买家类型（后置）、全部 `_summary` 类字段、`business_summary`、`transaction_summary`、`management_team_summary`、`consolidation_path_summary`。

## 6. 行业字典（三层分工）

### 6.1 现状

15 个 L1 + 110 个 L2 + 73 个 alias，表结构合理（`industry_taxonomy`: term / level / l1_name / parent_id / canonical_term_id）。`industry_l1_prompt_list` 注入 prompt，`resolve_l1` 归一化。

L1 清单：能源、金融、信息技术与通信、房地产与建筑、交通与物流、文化与传媒、制造与工业、商贸与消费、医药与健康、教育与科研、环保与公用事业、农林牧渔、军工、商务与专业服务、其他。

三个问题：① 排除项被压平到 L1（Bug ②）；② 110 个 L2 已录好但完全没用于筛选，`resolve_l1` 只拿它反查 L1 就丢掉；③ 15 个 L1 做初筛几乎等于没筛（"制造与工业"一类可能占库里 30%）。

### 6.2 三层分工（不改 L1 定义，避免全库重跑归一化）

| 层 | 数量 | 存储 | 作用 |
|---|---|---|---|
| **L1** | 15 | `industries_json` / `industry_l1` | 粗筛"必须属于"，粒度粗、宽松 |
| **L2** | 110（可扩至 ~200） | **新增** `industry_l2_json` / `industry_l2` | **筛选主力**：聚焦 + 精确排除 |
| **alias** | 73 | 不存储 | 仅录入时归一化输入 |
| **细分赛道** | 不入字典 | 画像① | 深评语义匹配 |

### 6.3 排除项分层存储（修 Bug ②）

`excluded_industries_json` **必须按原始层级存**，禁止压平：

```json
[{"term":"风电","level":"l2"}, {"term":"房地产与建筑","level":"l1"}]
```

判定时：L1 排除比 `industry_l1`，L2 排除比 `industry_l2`。

### 6.4 字典边界（守住这条线）

样本里的"醋酸下游""PVA""偏光膜""聚丙烯"细到产品级，**不要往字典里塞**——无法稳定枚举，塞进去只会让字典膨胀且归类不准。

> **字典边界：L2 = 可稳定归类的产业环节；再细一律交给深评。** 与 A2（SQL）/ A3（语义）的分工一致。

### 6.5 字典本身的两项小优化

- L2 补到覆盖样本高频词（北斗、物联网、集成电路目前挂在 alias→L1，应提升为 L2）；
- 允许 alias 挂到 L2 而非只挂 L1（迁移 040 已加 `parent_id`，具备条件）。

## 7. 多方案条件模型

### 7.1 结构

```
buyer_intent
├─ 全局条件：所有方案共同满足（共同排除项、总体偏好、原始需求、联系人）
└─ condition_scenarios（方案，组间 OR）
   ├─ 方案A（组内 AND，自包含完整字段集）
   ├─ 方案B
   └─ 方案C
```

- **全局 + 自包含方案**：方案之间不互相继承，但执行时自动与全局条件组合（避免改一个全局排除项时方案间漂移）；
- **不做 hard/preferred/stretch 三档强度**。"市值最好 50 亿以内、可放宽至 100 亿"本质是**带附加条件的另一个完整分支**（放宽通常伴随更高的利润/排名/技术要求），应解析成两个方案；
- 第一版**只支持析取范式**，方案内不再嵌套 OR。真实需求基本都能转成这个形式；
- 方案标签由录入解析 LLM 生成（"上市方案""非上市控股方案""大营收微利型"）。

### 7.2 示例（北大健康）

```
全局：医药健康行业；排除纯贸易企业
方案A：已上市 + 市值≤50亿 + 净利≥1000万 + 股比≤29.9%
方案B：已上市 + 市值≤100亿 + 行业排名前三 + 净利≥3000万 + 核心技术
方案C：未上市 + PE≤13 + 净利≥2000万 + 可取得控制权
```

（荆州"营收几百亿+微利 OR 营收三五十亿+几亿利润"同理拆两个方案。）

### 7.3 存量兼容（硬规则）

**所有现有意向自动视为"1 个默认方案"，`scenario_count=1` 时行为与现状逐字节一致。** 多方案上线是纯增量，迁移零风险。

### 7.4 会话覆盖与保存回

- 会话中"先只看非上市方案"→ 只产生 session override（`condition_overrides_json` 体系内），**不改原始意向**；另设显式「保存回买家需求」操作；
- 方案级操作进现有 `condition_actions` 词汇：新增 `disable_scenario` / `enable_scenario`，不另开机制；
- **对话新增的结构化条件默认作用于全部方案**（等价临时全局条件），除非用户点名方案；「从对话新建方案」必须是显式动作（否则"再看看 100 亿以内的"是放宽方案 A 还是新建方案 B，模型会随机猜）。

## 8. 召回与三态判断

### 8.1 三态

每个候选 × 每个方案产生一个状态：

| 状态 | 定义 |
|---|---|
| `compatible` | 已知结构化字段均满足该方案 |
| `possible` | 无明确冲突，但部分字段缺失 |
| `conflict` | 至少一个已知结构化条件不满足 |

- 候选只要有**一个方案不是 conflict** 就进入候选池；
- `conflict` 即出局，**废除"沉底到 45 分"的软处理**（HARD_MISMATCH_CAP 机制退役）；
- 信息缺失永远不导致出局。

### 8.2 判定时记录（每候选）

可进入哪些方案（及各方案三态）／已知条件中满足了哪些／哪些字段缺失（→ 缺失维度清单，§9）／哪些方案明确冲突及原因。

### 8.3 漏斗拆分与可见性

废除混在一起的 limit，拆成四个独立数字并**在页面/会话中展示**（不是 debug 信息，是"该收紧条件了"的业务信号）：

```
scan_count      实际扫描数（当前规模 = 全库）
eligible_count  无明确结构化冲突数
deep_eval_count 实际送入深评数（预算上限）
display_count   最终展示数
```

eligible 超预算时明确告知覆盖率（"符合基础条件 312 个，本轮深评 50 个"），引导顾问收紧条件；**禁止静默截断**。

### 8.4 深评队列排序（替代 0.3 折扣）

`UNKNOWN_DIMENSION_CREDIT = 0.3` 退役。排队规则：

1. **乐观分**：未知字段按"假定满足"计分（保证缺数据的标的不被挤出队列）；
2. **同分二级排序：已知条件数降序**（全已知且满足 > 全未知；信息空白的候选只在没有更好选择时才占名额）；
3. `conflict` 不占名额（已出局）；
4. **方案保底名额**：每个方案保底 `min(5, 该方案 eligible 数)`，剩余名额全局按乐观分分配（防宽方案挤掉用户亲口写的窄方案）；
5. **风险降权**：`severity=critical` 的标的降权并标注（系统级规则，不需买家提条件）。

不做"顾问显式动作过的候选无条件优先"（避免自我实现回路污染推荐与评测）。

## 9. 信息缺失与匹配度拆分

- 打分不再把"满足"与"未知"揉进同一标量（80 分可能全已知满足、也可能一半靠未知——对怕漏的产品意义相反）；
- **最小实现：缺失维度清单，不做百分比**。清单在三态判定时现算（本次意向引用的结构化字段 + 语义维度中，该候选未知的部分），不建独立存储字段；
- 三个消费者：① 候选卡片风险提示；② 调研任务清单（§12 的输入）；③ 评测时区分"漏是规则错"还是"漏是数据缺"。

卡片示意：

```
│ ▸ 杭州XX生物   深评A ·「方案B」                │
│   同时满足：方案C                              │
│   待确认：净利润、技术团队、行业地位            │
```

## 10. 深评协议

### 10.1 单次深评 + 分片并发

坚持**一次评估、一套绝对标准**（不做两阶段 LLM、不做候选间相对比较），实现上允许分片：

- 分片只切候选清单，**不切上下文**：每片带完整意向 + 全部方案 + 同一套评级标准；
- **候选按排名 round-robin 交错分片**（1,4,7→片一；2,5,8→片二…），不按分数切段——若片间标准漂移，交错可避免漂移与候选质量相关；附带自检信号：各片 A 档比例应接近，明显偏离说明模型不稳定；
- 合并 = 按 `candidate_id` 拼接（绝对标准，无需跨片归一化）；合并后按 `(grade, 乐观分)` 排序；
- **失败按片重试**：某片校验不过只重发该片，其余照常回写；
- 分片并发，延迟低于单请求大批量。

容量：不再固定 20 条，按输入 token 预算动态计算，默认以 40–60 条起步验证。

### 10.2 输出协议

一个 JSON 数组，每元素 = **少量机器字段 + 一个自由文本理由字段**（理由放 JSON 字符串内不压制表达，且保住 ID 对应关系）：

```json
{"results": [
  {
    "candidate_id": "<seller-target-uuid 或 buyer-intent-uuid>",
    "grade": "A",
    "matched_scenarios": ["<scenario-uuid>"],
    "reason": "自由文本推荐理由，可写数百字：细分赛道契合点、链位判断、信息缺口、风险……"
  }
]}
```

机器字段仅三个：`candidate_id`（回写/加载卡片）、`grade`（评级与 only_grade 筛选）、`matched_scenarios`（多方案命中展示）。

### 10.3 校验（代码侧，不用 json_schema）

现有 LLM 客户端仅支持 `response_format=json_object`（`backend/app/ai/llm_client.py:52`），各兼容端点对 json_schema 支持参差，**不绑 json_schema**，校验全部落代码：

- `candidate_id` 必须来自本片输入集合、不重复、每个输入候选有且只有一个结果；
- `matched_scenarios` 必须来自该意向的方案集合；`grade` 枚举合法；
- 校验失败 → **只把缺失/非法的候选定向重发一次**（附校验错误反馈），不整批重发；
- 回写按 UUID，不按数组位置/名称。

### 10.4 深评快照（可解释性）

每次深评保存：意向与方案快照、候选画像快照、prompt 版本、模型版本、输入候选 ID 集合——日后意向/画像变化仍能解释当时为何这样推荐。

### 10.5 双向两版 prompt

深评节点分**两个独立可编辑 prompt 节点**（经设置页维护，不写 seed 迁移）：

- **推标的版**（buyer_to_target）：锚点=买家意向（含方案），候选=标的画像；判断"标的满足买家哪个方案 + 语义诉求"，同时校验标的出售诉求与该买家的相容性；
- **推买家版**（target_to_buyer）：锚点=标的（属性 + 出售诉求），候选=买家意向；判断双向——买家方案是否容纳该标的 + 标的诉求是否接受该买家。

去重粒度在**意向**不在方案：同一买家多方案命中合并一张卡，显示"最佳命中：非上市控股方案｜同时满足：大营收微利方案"。深评预算按意向数计。

target 模式的会话条件调整语义是"对候选买家集合的过滤"，**不是修改锚点条件**，不与 buyer 模式的 condition_overrides 共用结构；「保存回」在 target 模式无意义，不提供。

## 11. 匹配画像

### 11.1 三层职责

**规范事实层**（结构化字段 + 标签，唯一事实来源，含期间/来源/证据/确认状态）→ **匹配画像层**（下述 6 栏，高信号定性视图，不重复维护财务数字）→ **精炼上下文层**（发给 LLM 的文本，由前两层自动生成，按栏目分配字符预算，**不允许人工另行维护**）。

### 11.2 存储：独立表，不是新列（关键决定）

**画像绝不做成 `seller_target` 的新列。** 现已 77 列，加 6 栏就是 83 列，且调研 Agent 要写的"内容 + 来源 + 证据原文 + 时点 + 置信度"塞不进一个 text 列。

```
entity_profile_section
  id
  team_id / workspace_id
  entity_type    -- 'seller_target' | 'buyer_intent'
  entity_id
  section_code   -- 6 栏闭集
  content_text
  source_type / source_url / source_excerpt / as_of_date / confidence
  review_status  -- 复用现有复核状态语义
  updated_by / updated_at
```

收益是连锁的：加一个画像栏目 = 加一个枚举值（2 处，不是 11 处）；调研 Agent 的产物形状天然就是这张表的一行；同期冲突（§12.3）= 同 section 多行 + `as_of_date`，有地方落；两侧对称，intent 侧共用同一张表；精炼上下文按栏目分配预算 = 一次按 section 查询。

> 这条同时是对"加一个字段要动 11 处"（迁移→pydantic→CRUD→search_doc→抽取 prompt→抽取 handler→apply→types/api.ts→fieldLabels→详情页→打分器）的结构性解法。

### 11.3 六个栏目（由 §2.2 指标表倒推）

| 栏目 | 内容 | 对应样本诉求 |
|---|---|---|
| ① 业务与产品 | 核心产品服务、商业模式、下游行业、收入结构 | 北控"与现有业务关联（非单纯燃气）"、北物醋酸/PVA/偏光膜上下游 |
| ② 产业链位置与行业地位 | 上中下游+环节、链上角色、市场地位、细分排名、竞争壁垒 | 北物"链主"、北京工控"行业前三/强链补链" |
| ③ 技术与团队能力 | 核心技术、知识产权资质、研发、核心团队、产能关键资产 | 北物"有团队有技术"、北控"保留核心团队" |
| ④ 经营质量（只写定性） | 增长特征、盈利质量、客户集中度、周期性 | 北控"现金流稳定首要"、工控"小而美现金流好" |
| ⑤ 交易属性与配合度 | 可交易比例、控股并表可能、交易灵活性（先参股后控/对赌/迁址/招商配合） | 北物"先参股后控"、荆州"迁址加分"、广州城投"可招商" |
| ⑥ 出售诉求与风险缺口 | **出售诉求**（拟售比例、接受的买家类型、迁址意愿、团队安排、对赌接受度）+ 已知风险、待核实事实、数据新鲜度 | 反向匹配的筛选依据 |

规则：

- 原"产业链位置"与"市场竞争力"合并为②（业务语境里"链主"与"细分前三"是同一判断）；
- ④只留定性，数字全在事实层；**枚举装得下的一律不进画像**（与 F2/F3 划界一致）；
- **每栏必须有显式"无信息"取值，不用空字符串**（深评须分清"没查到"与"不适用"，与三态原则一致）；
- 不在标的画像存"与某买家协同度高"（协同取决于具体买家，由深评动态判断）。

### 11.4 标的出售诉求（正式维度）

挂在画像⑥，**不用于 SQL，只用于深评**：

- 推标的时：深评校验"该买家是否满足标的诉求"（如标的只接受产业买家）；
- 推买家时：标的诉求是锚点侧的**主动筛选依据**（不只验证"买家要不要它"，还验证"它要不要这个买家"）。

### 11.5 买家侧

- 画像挂在 **intent**（本次需求 + 方案），不给买家母体做完整画像；
- 保留一个**极小的买家母体事实块**：现有主业、产业布局、历史投资方向（三五行）。不参与筛选，仅深评时注入，供"协同性/强链补链"类判断使用（I1）；
- 公开调研得到的买家战略信息不自动当作正式投资需求。

### 11.6 深评上下文生成

- 精炼上下文按栏目预算截断（如 业务产品 400 / 链位地位 400 / 技术团队 300 / 经营质量 300 / 交易属性 300 / 风险缺口 200 字），**不再从 full_text 开头截 1200 字**；
- 送深评的画像文本**剔除结构化数字复述**（数字已在 candidate 的结构化字段与 matches/gaps 里）；
- **时序提醒**：现 `full_text`（`services/search_docs.py`）= 结构化摘要 + 业务摘要 + 财务 + 交易 + 风险，**根本没有画像类内容**。因此**画像建成之前，单纯把 1200 放宽到 2500 几乎拿不到新信息**——放宽字数是画像的配套动作，不是独立优化。

## 12. 调研 Agent

### 12.1 定位与触发

- 职责收敛两项：**补画像栏目** + **提议新的基础事实/标签**；不生成推荐结论，不静默覆盖已有事实；
- **需求驱动，不做全库无差别调研**。触发：顾问手工勾选批量调研 / 推荐中发现关键字段缺失（§9 清单直接生成任务）/ 语义需求无法据现有画像判断 / 信息超期未更新；
- 技术路线：**搜索 API/网页抓取 + 自己的 LLM 编排**（保引用、可重放、控成本），不用黑盒联网模型。

现状：「批量调研」按钮为纯占位（`frontend/src/pages/Targets.tsx:291` 无事件绑定，后端无路由），从零建。

### 12.2 调研产物（每条事实）

```
entity_id / dimension·field / proposed_value / period·as_of_date
source_url / source_title / source_type / source_excerpt
confidence / researched_at
```

定性结论（排名/壁垒/链主）必须带支持原文证据。

### 12.3 冲突处理（四分类）

| 类型 | 处理 |
|---|---|
| 一致 | 自动增加证据与更新时间 |
| 补充（原字段空/新维度） | 高权威来源可自动写入（留审计可撤回）；普通网页 → 待确认建议 |
| 时序更新（不同期间） | 两期都保留，最新期更新当前快照，不互相覆盖 |
| 同期冲突（同期同口径不同值） | 生成冲突项，**必须人工处理** |

来源优先级（综合权威度/时间/口径/用户确认/原始文件，非简单新覆盖旧）：

```
审计报告·监管披露 > 用户确认一手材料 > 公司公告·官网
> 权威行业报告 > 主流媒体 > 聚合数据库 > LLM 推断
```

用户确认的信息也可能过期，仍需 `as_of_date`。定性标签（"行业龙头"）默认为带证据候选标签；**LLM 推断只能进画像建议，不能写规范事实层**。复用现有 `field_value_source` / `evidence_span` / `extracted_action` / 应用日志审计体系，不另建。

### 12.4 两个实操杀手（必须设计进去）

1. **同名实体污染**（最高频失败，比幻觉更常见）：必须有实体锚点（统一社会信用代码/官网域名/注册地/法人），**证据原文须包含锚点特征才采信**。不做这条，调研越勤数据越脏且脏得隐蔽。
2. **无痕标的**：非上市中小标的公网信息近零。记录"已调研·无有效信息·下次重试时间"，避免反复烧钱。（ROI 侧写：只要上市/知名企业的需求恰是公网信息最全的一段。）

## 13. Golden Set（评测底座）

口径由用户另行设计。已讨论的框架供参考：

- 区分**顾问判断**（匹配/可能匹配/不匹配/信息不足）与**业务结果**（已推荐/拒绝/沟通/见面/尽调/成交 + 拒因）——业务结果受价格/关系/时机影响，不等于算法匹配好坏；
- 轻量 v0：30–50 个"系统必须召回"的历史正样本测 `recall@20/50`；10 条典型需求 × 人工判 20–30 个候选，测排序质量与误推荐率；
- 应在正式调整推荐阈值前完成；漏斗四数（§8.3）同时记录，用于区分"漏在规则层还是 LLM 层"。

## 14. 重心转移（非推荐链路，但同属本次结论）

**冻结两块**（不删、不下线，但不再投入迭代）：

- AI 运维面（debug 两页、model_config 深度功能、update_logs 精细化、background_jobs 治理）——8,200 行后端 + 889 行前端，对顾问零直接价值，现在够用；

**补一块**：跟进管理。定位里的三大职责之一，目前投入接近于零（4 张表齐备，0 个独立页面，`relations.py` 仅 362 行）。缺的是顾问视角的 pipeline 视图。不依赖任何数据补全，纯粹是没做界面；且与推荐闭环——推荐结果 → 推进记录 → 反馈，正是 Golden Set 的天然来源。
