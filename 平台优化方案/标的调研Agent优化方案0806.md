## 一、先看实测：哪些老问题已经不存在了

| 指标 | 实测 | 读数 |
|---|---|---|
| 调研任务 | 49 次：成功 42 / 失败 7 | 成功率 86% |
| **失败时间分布** | **全部 7 次都在 2026-07-29 及之前** | **0801 那批修复之后零失败** |
| 映射任务 | 38 次：成功 37 / 失败 1（07-29） | 同上 |
| 结论分布 | found 27 / no_public_information 15 | 36% 查不到 |
| 建议产出 | 481 条：自动采纳 404 / 待确认 72 / 忽略 5 | 自动采纳率 84% |
| LLM 调用 | 中位 4 次，p90 8 次，最多 13 次 | 迭代上限只触发过 1 次 |
| prompt_tokens | 中位 57,923，p90 195,718，最大 340,132 | 单次调研的累计输入 |
| completion_tokens | 中位 8,778，最大 17,667 | |

**结论一：可靠性问题已经解决，本轮不要再修它。** 历史失败里 3 次是日期序列化、1 次是 `st.website` 不存在的列、1 次是模型输出非 JSON、1 次是供应商内容审核拦截。前两类分别由 0728 的 `_json_safe_value` 和 `e28ea00` 修掉，此后 5 天 42 次调研零失败。**0728 验收单 §4 的「零真机验证」这条风险可以关闭了。**

**结论二：本轮该修的是「产出被静默丢弃」和「提示词本身是坏的」，不是稳定性。**

## 二、P0：两个谁都没发现的生产缺陷

### 2.1 两个调研提示词的尾段都是问号

生产上正在生效的 `seller_target_researcher` **v0.5.0**，最后一节实测：

```
长度 321 字符 | '?' 199 个 | 中文字符 0 个
'## ???????????????\n\n`current_operating_cash_flow_yuan` ????????????????...'
```

`seller_target_research_mapper` **v0.3.0** 的第 13、14 条规则同样：整段中文被替换成 `?`。

两处坏的都是**最后追加的那一节**，特征一致——某次通过非 UTF-8 的管道保存，中文被逐字替换成问号。后果：

- 经营现金流的口径规则（「每股经营现金流不是这个字段，不得按股本倒推」）**从未真正送达模型**；
- 每次调研白白发送 321 个问号，映射再发一遍；
- 更糟的是它掩盖了自己：`research_map.py:250-254` 在**代码里**给 `current_operating_cash_flow_yuan` 补了一段中文 note——有人在下游打补丁，没人回头看上游的提示词已经烂了。

**判决：重发两个提示词版本。** 顺带把内容按下面几节一并更新，不必为了修编码单发一版。

**配套规矩**：提示词保存后必须回读一次确认中文没被替换。这条写进施工单验收项。

### 2.2 映射节点被告知买家的栏目码是合法的

`research_map.py:260` 用的是 `PROFILE_SECTION_LABELS`，而它是**买卖两侧合成的一张表**（`profile_sections.py:59` 的注释写得很清楚：「两侧的栏目码不重叠，所以展示用的标签表可以合成一张」）。于是标的调研的映射节点收到的 `profile_section_catalog` 里带着 `intent_scope` / `intent_financial` / `intent_deal`。

模型照做了。下游 `normalize_profile_section_items` 按实体取合法码，把它们丢掉：

```
5x  not_found:unknown_section:intent_scope
5x  not_found:unknown_section:intent_deal
4x  not_found:unknown_section:intent_financial
```

**14 次输出被丢弃**，模型为它们花的 token 全白付，且顾问在界面上看不到任何提示。

**开发中发现：同一个错误在 agent 那边也有，而且那才是源头。** `research.py:91` 的 `PROFILE_SECTION_CATALOG` 用的是同一张合成表，喂进 `research_context_json.profile_section_catalog`。也就是说买家栏目码是 **agent 先写进报告的**，映射节点只是原样转发——只修映射不修 agent，报告里照样带着 `intent_*`。它还让 `_current_profiles_for_prompt` 给 agent 多列 3 个永远「missing」的栏目，反过来诱导它去填。

**判决：两处都按实体取栏目目录**（`profile_sections_for("seller_target")`）。展示用的合成表继续合成，喂模型的目录必须分实体。

### 2.3 agent 被告知可以写两个它写了会被丢掉的字段

`research.py:313` 把 `allowed_structured_fields` 设成 `RESEARCH_STRUCTURED_FIELDS`（27 个），而 `normalize_research_output` 按 `RESEARCH_AGENT_STRUCTURED_FIELDS`（25 个）过滤。差的两个是 `financial_period_end_date` 与 `financial_period_label` —— 它们是**内部字段**，由代码从每条 claim 的 `period_label` 派生，故意不给 agent。

后果是提示词规则 1 说得斩钉截铁（「`field_path` must come from the lists supplied in the context」），agent 照做，写了这两个字段，然后被静默丢弃并记 `unsupported_field`。

这大概率还和 §3.1 的财务期间问题互为因果：agent 把期间当成一个**独立字段**输出（然后被丢），而不是挂在每条财务 claim 的 `period_label` 上——于是那一批财务数字就成了「没有期间的数字」。

**判决：改用 `RESEARCH_AGENT_STRUCTURED_FIELDS`。** 「你可以写的字段」和「写了会被收下的字段」必须是同一份，这条加测试锁死。

## 三、P1：产出被规则挡掉

### 3.1 核心财务缺一个 ISO 日期，六个字段一起作废

`research.py:594-598`：核心财务字段的 claim 必须带合法 ISO `as_of_date`，否则记 `validation_error` 丢弃。实测一次调研里 4 个财务字段同时因此报废：

```
current_revenue_yuan: 缺少合法财务期间截止日。
current_net_profit_yuan: 缺少合法财务期间截止日。
current_operating_cash_flow_yuan: 缺少合法财务期间截止日。
current_debt_ratio: 缺少合法财务期间截止日。
```

而模型明明给了 `period_label`——两个提示词都强制要求它（researcher 规则 3「每个数字必须同时给出 period_label」，mapper 规则 4「A number without a period_label must not be emitted」）。

**代码里已经有现成的换算器**：`_financial_period_from_label`，用于把库里历史行的 `financial_period_label` 折算成可比日期。它只用在**当前值**上，没用在**新 claim** 上。

**判决：`as_of_date` 缺失或非法时，用同一条 claim 的 `period_label` 回退推导。** 推不出来才丢。这是把已有的兼容逻辑用在它本来就该用的地方，不是新机制。

注意「同批核心财务期间必须一致」这条校验（`research.py:602-614`）**保持不变**——回退推导发生在它之前，推出来的日期照样参与一致性检查。

### 3.2 调研 Agent 看到的标的是 12 列手写清单

`_get_research_target` 手写 12 列喂给 agent，而 agent 可见可写的结构化字段有 **25 个**。

这正是 0801 在解析侧修过的那个病（`_fetch_seller_targets` 手写 24 列、漏 21 个可写字段），**调研侧漏改了**。后果：

- agent 不知道库里已经有什么，重复检索已知信息（token 白花）；
- agent 不知道库里缺什么，无法把检索预算投在缺口上；
- 本轮新增的三个字段它一个都看不见。

**判决：改为注册表派生。** 与 `seller_target_context_columns()` 同一个做法。

### 3.3 本轮新增的三个字段，提示词没同步

`major_risk_flags_json` / `main_products_text` / `stock_code` 已经**自动**进了 agent 的 `allowed_structured_fields` 与 mapper 的 `writable_fields`（两处都是注册表派生，零代码）。但提示词的检索模块还停在旧字段集上：

| 模块 | 现状 | 要改 |
|---|---|---|
| M0 主体锚定 | 有「上市/挂牌状态与上市地」 | 加**股票代码** |
| M1 业务与行业 | 有主营业务、收入构成 | 加**主要产品/产品线**，明确它与 `business_summary` 的分工 |
| M2 财务与经营质量 | 提到「**经营稳定性**」 | **删**——该字段已随迁移 `015` 判死 |
| M5 风险与合规 | 「汇总进 `risk_summary`」 | 改为**同时**输出 `major_risk_flags_json` 闭集枚举 + `risk_summary` 明细 |

**M5 是本轮价值最高的一处。** 重大风险闭集当初就是照着「调研 Agent 能自动核工商公开信息」设计的（施工单 0806 §四）；字段建好了、调研可写、目录自动生成，唯独没人告诉模型去查。

**「未核查」与「已核查无风险」必须分开**这条要写进提示词：查过确认干净 → 输出 `["none"]`；根本没查到风险类信息 → **整个字段省略**，不要输出空数组。空数组的含义是「尚未核查」，那是系统的默认状态，不是模型能得出的结论。

### 3.4 多值闭集字段的输出形状没告诉映射节点

`_mapping_context` 给 `kind == "yuan"` 配了 note（怎么给数字和单位），给多值 json 列什么都没给。模型看到 `allowed_values` 很容易输出单值字符串而不是数组。

`research_apply.normalize_structured_fact` 我已经加了 `str → [str]` 的兜底，但显式说清楚更省一次返工。

**判决：`multi_value` 列自动带 note，说明输出数组、取值来自 `allowed_values`。** 由代码从注册表生成，不写进提示词正文——新增闭集列时自动生效。

## 四、P2：看得见但本轮不做

### 4.1 36% 的调研得出「查不到」

15 次 `no_public_information` 里，12 次报告正文是同一段 234 字的模板，3 次报告为空。看 `llm_calls`：多数是 3 次就收尾——这与提示词的设计一致（「M0 锚定不上就停下」）。

**这大概率是对的行为**，不是缺陷：非上市中小标的在公开渠道确实查不到。但顾问看到的只有一个「未查到公开信息」的状态，**不知道是在哪一步停的**——是主体没锚定上，还是锚定上了但后面几个模块都空。

**本轮不改检索策略。** 只做一件配套的事：让 `coverage` 与停止原因进入报告（见 4.2）。检索策略要改必须先有分层数据，现在没有。

### 4.2 报告对顾问不可见（0728 遗留，仍未做）

报告全文躺在 `background_job.result_json.report_text` 里，只有 `/background-jobs/{id}` 能看到。九模块里装不进 5 栏画像的内容——诉讼细节、访谈问题清单、检索覆盖情况——**对顾问是完全不可见的**。

这是本轮清单里**用户可见价值最高**的一项，但它是一个新的界面入口（API + 前端抽屉），与其余六项的性质不同。**需要你拍板本轮做不做**，默认不做。

### 4.3 token 成本

中位 58K prompt tokens/次，p90 196K。agent 循环每轮把全部工具结果累加进 messages，输入量随轮数二次增长。

0728 定的判据是「超过模型窗口 60% 就做上下文外置」。qwen3.7-plus 的窗口下，p90 已经接近这条线，但**只有 1/42 触发过迭代上限**，说明还没有实际卡住。

**本轮不做上下文外置**（0728 的 B-7 继续挂着）。先把上面六项便宜的修完，再拿新的 token 数据决定。

## 五、否决清单（不重开）
