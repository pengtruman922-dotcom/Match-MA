## 1. 主要改动

四个文件，**无迁移、无 schema 变更、无 prompt 变更**。

### 1.1 新增 `GET /api/v1/relations/board`（`backend/app/api/routes/relations.py`）

看板专用取数端点。与 `/relations` 并存，互不影响。

```
GET /api/v1/relations/board
  ?ownership=all|involved|sole   默认 involved
  &q=<关键词>                    可选，最长 200
  &limit=2000                    默认 2000，范围 1~5000
  &offset=0
→ [{ id, seller_target_id, buyer_intent_id, status,
     last_event_at, last_activity_at,
     seller_target_name, buyer_intent_name, buyer_name }]
```

**为什么不复用 `/relations`**：`_relation_select_columns()` 每行要跑 **4 个关联子查询**（3 次回捞 `relation_event` 取 type/content/next_step + 1 次 `exists` 扫 `buyer_seller_relation`），外加 `last_event_summary`/`metadata_json` 等不定长文本，单行约 1 KB。而看板 4 行卡片这些字段**一个都不用**。

新的 `_relation_board_columns()` 是 **9 字段、零关联子查询**：

| | `/relations` | `/relations/board` |
|---|---|---|
| 单行 JSON | ~1 KB | **~380 B** |
| 每行关联子查询 | 4 | **0** |
| limit 上限 | 200 | **5000** |

> **`last_activity_at` 是第 9 个字段**。原因：没有事件的关系 `last_event_at` 为 `null`，前端拿它排序会把新建关系沉到底部。该字段等于 `coalesce(r.last_event_at, r.updated_at, r.created_at)`，**与 `order by` 表达式同源**，前端按它排序才不会和后端顺序打架。`last_event_at` 仍单独保留，供「N 天无动态」预警使用（无事件即不预警，语义与现状一致）。施工单 §3、§6 与 B2 排序口径已同步为 9 字段。

### 1.2 责任范围三态 `ownership`（`utils.py` 新增 `relation_sole_owner_sql`）

```
all       仅受权限地板约束
involved  任一方归我 —— 复用 relation_visible_sql（默认档）
sole      标的归我 AND（意向归我 OR 买家归我）—— 新增 relation_sole_owner_sql
```

**这是视图筛选，不是权限收紧。** 权限地板仍由 `owner_scope_required()` + `relation_visible_sql` 在 `OWNER_SCOPE_ENFORCED` 打开时负责；两者同为 AND 追加，因 `sole ⊆ involved` 不会互相矛盾（代码里对同一谓词做了去重）。

`sole` 默认**不开**，因为它会造孤儿卡：标的归我、意向归同事的关系，在双方看板上都不显示。默认 `involved` 规避这一点。

### 1.3 抽出公共 `_relation_base_where()`

`/relations` 与 `/relations/board` 共用过滤谓词（team/workspace/deleted + 各 id 过滤 + status + q），避免筛选逻辑分叉。**`/relations` 的行为完全不变**——原逻辑逐条搬入，负责人范围仍由各路由自己追加。

### 1.4 启用 GZip（`backend/app/main.py`）

```python
app.add_middleware(GZipMiddleware, minimum_size=500)
```

中间件层序（外→内）：**CORS > GZip > AdminAuth > Utf8Json**。GZip 必须在 `Utf8JsonMiddleware` 之外——content-type 先定好，再压缩体。

**全站接口受益**，不只看板。已核对 Starlette 1.3.1 实现：非流式响应压缩后会**重写 `Content-Length`**（`gzip.py:78`），流式则删除该头（`gzip.py:91`），所以 `attachments.py:481` 手工设置 `Content-Length` 的附件下载不会坏。

### 1.5 新增测试 `tests/test_relations_board.py`（19 个）

守护字段集不回胖、精确 9 字段与路由优先级、参数 422、权限地板开/关 × ownership 三态的完整 SQL/bind、SQLite 数据夹具上的 `sole ⊂ involved`、两路由实际共用 where、改动前后 32 种过滤组合等价、排序表达式同源、旧 `/relations` 完整字段，以及完整中间件栈下 JSON/PDF/中文 CSV 的 GZip 无损往返。

### 3.4 责任范围三态


## 4. 已知风险与观察项

1. **GZip 会压已压缩的二进制**（PDF/JPEG 附件），浪费 CPU 但不影响正确性。若附件下载量大，后续可给 `GZipMiddleware` 加 content-type 排除；当前不做。
2. **`limit` 上限 5000 最初没有测算依据**。2026-07-26 生产仅 39 条，当前余量很大；B2 仍必须在 `len == limit` 时提示截断，并持续记录总量、raw/gzip 大小与 P95。若接近 5000，应评估 `has_more`/游标分页或服务端分组，而不是继续抬上限。
3. **`sole` 的判别性验证需要普通顾问账号**。只有管理员 token 时 §3.4 做不出结论，别把「三个数相等」当成通过。
4. **本地无 Postgres**，自动化仍以 SQLite 语义夹具和 SQL 拼装为主；真实 PostgreSQL 已由生产 §3.1 验证。后续应补同构 PostgreSQL CI，避免每次都把语法风险推迟到部署后。
