# 买家需求页重构 施工单（2026-08-02）

> 定稿于 0802 的设计讨论。目标：买家需求页在结构上和标的信息页对齐，
> 同时保住买家独有的东西 —— 规则标签（必须/优先）、待确认内联处置、多方案。

## 一、不动的部分（先说清楚，免得改着改着漂了）

**多方案沿用「公共条件 + 分支方案」。** 讨论中我提过「分档依据」的抽象，
被例子否掉了：市值/盈利那个例子里分档依据是市值，上市/非上市那个是上市状态，
医药10亿/AI 5亿那个是行业 —— 它不是一类稳定的字段，就是「两套组合标准」。
方案是完整的替代条件集，`merge_scenario_into_anchor` 已经支持任意字段整体覆盖，
存储和匹配逻辑都不用动。方案的创建与展示也沿用现设计。

**深评不按字段设。** 已核实：深评上下文是 `anchor_context = "\n\n".join([query,
json.dumps(anchor), profile_text, doc_text, party_facts])`（`recommendation.py:344`），
整个 anchor 一个 JSON 甩进去，没有任何按 `condition_effect == deep_eval` 的分流。
那个标签今天只干一件事 —— `recommendation_flow.py:2118` 让该字段跳过规则打分。
它的真实含义是「不参与规则打分」，被起名叫「深评」。本单取消这个取值。

## 二、四件事

### 1. 字段级来源与证据

`/field-sources?entity_type=buyer_intent` 已经通（路由正则里就有 `buyer_intent`），
生产上真实需求有 15~42 条记录，部分带 `evidence_id` 可直跳附件原文。
前端一行没接（三个买家组件里 `fieldSources` 出现 0 次）。复用标的的
`ResearchEvidenceDrawer`。**纯前端接线，后端不动。**

### 2. 模块化 + 折叠 + 每模块一块「其他」

`intent_notes`（15 个字段的杂物间）解散，字段重分配；三个模块各带一块自由文本。

| 模块 | section_code | 条件字段 | 「其他」吸收 |
| --- | --- | --- | --- |
| 行业与地区 | `intent_scope` | 行业、二级行业、地区 | 字典外细分方向、地域摘要、产业优势 |
| 经营与财务 | `intent_financial` | 营收/利润/利润率/PE/PS/估值/市值/负债率/现金流/盈利状态 | 市值范围说明、负债率说明、风险容忍 |
| 交易与能力要求 | `intent_deal` | 控股/并表/股比/上市状态/上市地/迁址/返投/团队留任 | 股权比例说明、上市板块、融资阶段、溢价要求、交易方式 |

`intent_summary`（需求摘要）保留在页面顶部，不进模块。

**`entity_profile_section` 表的 check 约束里已经写着 `buyer_intent`**，
API 的 `ENTITY_TYPES` 也已经是两个实体 —— 缺的只有 `section_code` 的取值扩展，
以及 `profile_sections.py` 里那个写死成卖方 5 栏的 `PROFILE_SECTIONS` 要按实体拆。

### 3. 排除放到值级

字段级标签收成 **必须 / 优先** 两态。「排除」不是字段级三态 —— 阈值字段没有「排除」，
它只对集合型字段成立，落在**值**上：

| 行 | ✓ 写进 | ✕ 写进 |
| --- | --- | --- |
| 行业 | `industries_json` / `industry_l2_json` | `excluded_industries_json` |
| 地区 | `region_constraints_json` effect=required/preferred | 同列 effect=`excluded`（**已支持**，`region_dictionary.py:127` 别名表里就有） |
| 上市状态 | `acceptable_listed_status_json` | 白名单外即排除，三个 chip 渲染三态 |
| 交易方式 | `transaction_types_json` | 同上 |

### 4. 方案字段强制硬门槛（本单唯一的匹配行为变更）

分档字段的注册表默认值实测：

```
industries_json                default_effect = required    ← 硬
acceptable_listed_status_json  default_effect = preferred   ← 软
min_market_cap_yuan            default_effect = preferred   ← 软
```

而 `_score_against_scenarios` 取**各档中最好的一档**。推演一个
**5亿市值、1500万盈利**的标的，面对「市值≥10亿→盈利≥1000万 / 市值<10亿→盈利≥1亿」：

| | 判定 |
| --- | --- |
| 方案A | 市值不达标，但是「优先」→ 只扣分不冲突；盈利 1500万 ≥ 1000万 ✓ → **不冲突** |
| 方案B | 市值 ✓；盈利 1500万 < 1亿，「必须」→ 冲突 |

取最好的一档 → 它从方案A 混进来了，而买家的本意是它走方案B、不达标。

**规则：同一字段在两个及以上方案里取了不同的值，它在方案内按硬门槛判。**
只在单个方案出现的字段不受影响；顾问在某方案显式标了规则的，显式优先。

注册表默认值不能直接改硬 —— 单方案时买家说「市值最好10亿以上」，那儿它确实该是软的。
所以作用域必须是「在这一档内」。

钩子已经埋好但没接：`recommendation_flow.py:1580` 每次打分都写
`"_scenario_fields": set(scenario["fields"])`，全文件搜下来再没有第二处读它。

## 三、存量数据处理

生产 37 条需求，四个待删列的非空数量：

| 列 | 非空 | 去向 |
| --- | --- | --- |
| `preference_summary` | 26 | → 「经营与财务」的其他，带 `【其他偏好】` 标签 |
| `negative_summary` | 12 | → 「行业与地区」的其他，带 `【排除项】` 标签 |
| `priority_summary` | 11 | → 「行业与地区」的其他，带 `【优先条件】` 标签 |
| `unknown_summary` | 3 | **直接丢弃** |

`unknown_summary` 丢弃的理由：内容是「市值/估值区间、溢价容忍度、负债率要求未明确」
这类元信息，和 `needs_confirmation_json` 完全重复，而后者有自己的界面和处置流程。

内容跨模块、自动分不了，所以按列整体归到一个模块并打来源标签，
顾问事后可以自己剪切到别的模块。这是有损的（归错模块），但不丢字。

**迁移里有 `drop column`，不可逆。推送前单独确认。**
