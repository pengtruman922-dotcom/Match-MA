# 智能推荐 Agent 化改造 施工单（2026-08-04）

> **状态：六个阶段已全部落地，本地测试与构建通过，等设置页配置两个新节点后做 UAT。**
> 施工记录见第十二节。
> 来源：2026-08-04 与种子用户（投资撮合客户经理）沟通后的逐条拍板。

## 一、为什么做

种子用户的原话是「来了一个并购需求或者一个出售需求，**不是先建标的或者建买家**，而是直接
在输入框输入客户需求，然后看到结果，把清单推给客户」。资料录入和跟进录入交给助理，
不该出现在推荐环节。

对着现状核了一遍，这条路今天走不通：

1. **「直接输入就出结果」的能力其实已经有了** —— 就是 `temporary_input` 临时筛选：free text
   进来由 `parse_recommendation_message` 同步解析成结构化条件，再走正常初筛。但它被设计成
   **只读死路**：`recommendations.py:1185 / 1337 / 1436` 的 `_ensure_session_is_not_temporary_filter`
   把「加入推荐列表」和「生成报告」全拦死。直接输入得到的结果，**一个字都导不出去**。
2. **入口藏着**。默认路径是「搜索选择已有对象」，临时筛选是一行灰色小字链接。
3. **重点不突出**。结果出来前首屏就有 5 条工具栏；每张候选卡最多叠 7 行摘要 + 5 类徽标，
   还混着漏斗四数、轮次、方案、条件覆盖/停用这些工程语言。
4. **卡片没有硬数据**。`recommendation_flow.py:1141` 的 SQL 已经把净利、地区、PE、控股查出来了，
   在 `_candidate_row`（同文件 ~1615）组装时全被丢弃。客户经理最先要看的几个数，卡上一个没有。

从零到把清单发给客户，今天要走 12+ 次交互、3 次等待。

## 二、目标形态：一个对话页

推荐页 = **一个输入框 + 一段 AI 输出的文本**。参考 Claude 的对话界面，不再有卡片、条件面板、
已选抽屉、报告弹窗。用户可以直接复制 AI 的回答发给客户。

用户对等待的耐心是 **2–5 分钟**，前提是过程可见。

## 三、不动的部分（先说清楚，免得改着改着漂了）

- **初筛与打分必须代码化**（`AGENTS.md` 硬规则）。Agent 只负责**编排**：澄清 / 整理 / 决定筛几次 /
  解读结果 / 写话。初筛工具本身仍是 SQL，Agent 看到的永远是每次筛选返回的候选摘要，
  **绝不允许把全库打包给 LLM**。这条是本单的红线。
- 多方案 OR / 三态判断 / 条件冲突排除等既有匹配语义**全部保留**，只是改由 Agent 通过工具参数驱动。
- 推荐召回继续跨负责人。
- 撮合关系仍然只由「开始推进」和手动「关联对手方」两条确定性路径创建，**Agent 不写任何业务数据**。

## 四、Agent 架构

### 4.1 复用现成的工具循环

`backend/app/ai/tool_loop.py` 的 `run_tool_loop` 是通用、与模型无关的 agent 循环（调研 Agent 在用），
自带工具预算、超限强制收尾（`final_turn_instruction`）、工具报错回喂给模型不中断运行。
推荐 Agent 不用新搭框架，供一套工具 + 一份 prompt 即可。

### 4.2 工具集（v1 三个，正向）

下表是「为买家找标的」方向的工具。反向是另一套（`search_intents` / `get_intent_detail`），
本轮不做，见 4.4。

| 工具 | 职责 | 预算 |
| --- | --- | --- |
| `search_targets(filters, count_only?)` | 参数化初筛。由 `_candidate_targets_for_intent` 拆出参数化版本。返回候选摘要 + 漏斗计数。`count_only=true` 只返回计数，供 Agent 低成本试探条件宽窄 | 每会话 ≤6 次，每次返回 ≤30 条 |
| `get_target_detail(ids[])` | 取少数候选的完整画像（含各业务分组的「其他」长文本、最近调研结论）。**这个替代掉现在的深评分片 rerank job** | 每会话 ≤12 个 |
| `ask_user(questions[])` | 澄清。做成工具而非让模型自由发挥，是为了前端能把问题渲染成**可点选项** —— 客户经理不想打字 | 全程 ≤1 次 |

`run_tool_loop` 的 `max_iterations` 取 12（默认值）。

### 4.3 澄清策略：默认不问，先给结果

**默认不主动提问。** 拿到需求就先筛先答，在回答末尾追一句「补充 XX 我能筛得更准」。

只有条件空到无法收敛时（例如行业、地区、规模全缺，初筛命中数超过阈值）才真的挡下来调
`ask_user`，且：

- 最多一轮，一次最多 3 题
- 每题必须给可点选项
- 必须有「跳过，先看结果」的逃生口

理由：种子用户反复强调的是「快」，反问本身就是变慢。

### 4.4 两个方向是两套流程，不是一个流程的参数

这条是本单的结构性前提，写在前面免得被当成"加个 mode 变量"糊过去。

| 层 | 正向（为买家找标的） | 反向（为标的找买家） |
| --- | --- | --- |
| SQL | `_candidate_targets_for_intent` | `_candidate_intents_for_target`，过滤维度完全不同 |
| 工具集 | `search_targets` / `get_target_detail` | `search_intents` / `get_intent_detail` |
| Agent prompt | 从买家需求出发找公司 | 从公司画像出发找买家 |
| 会话 | `recommendation_session.mode`，**后端已强制会话内不可变**（`recommendations.py:476` 拦 mode 不匹配 → 400） |

**不设通用兜底节点。** 现有 `recommendation_deep_eval` 有个通用节点替两个方向代跑，是因为深评
只是评价文本、工具没差别。推荐 Agent 不一样 —— **工具集本身就不同**，一份 prompt 换个变量兜不住。
所以方向专属节点必须各自配置，没配就是没有，不代跑。

### 4.5 AI 节点（每个方向两个）

在 `backend/app/registry/nodes.py` 新增，`recommendation_mode` 字段照现有约定填：

| 节点 | 方向 | 类型 | 说明 | 本轮 |
| --- | --- | --- | --- | --- |
| `recommendation_agent_to_target` | buyer_to_target | llm（带工具） | 编排：理解需求 → 决定筛几次 → 解读 → 产出「写作素材包」。跑在 worker | **做** |
| `recommendation_answer_writer_to_target` | buyer_to_target | llm（无工具，流式） | 拿素材包生成最终回答正文。跑在 API 的 SSE 端点 | **做** |
| `recommendation_agent_to_buyer` | target_to_buyer | llm（带工具） | 反向编排 | 下一轮 |
| `recommendation_answer_writer_to_buyer` | target_to_buyer | llm（无工具，流式） | 反向写作 | 下一轮 |

**为什么每个方向还要拆成 agent + writer 两个**：最终写作是单次、无工具、纯生成，所以它可以放在
API 侧做流式，而 `llm_client` 只需要加一个**独立的**流式函数，完全不用碰现有的 tool_calls 解析逻辑
（OpenAI 兼容协议里 tool_call 的 arguments 是逐片下发、要按 index 累积的，那是最脏的一块，
本方案直接绕开）。这个拆分是 5.2 时序的前提，不要合并回去。

Prompt 按惯例走设置页版本管理发布，**不写 prompt seed 迁移**。

## 五、流式：走「末段 SSE」

### 5.1 现状核查

| 层 | 现状 | 结论 |
| --- | --- | --- |
| LLM 客户端 | `llm_client.py:88` 用标准库 `urllib.request.urlopen`，一次性读完 body | 零流式支持，要新增流式函数 |
| worker→API 通道 | **没有 Redis**。队列是 Postgres `background_job` 表 + `claim_next_job` SQL 抢占 | worker 内部的流式无法实时推到浏览器 |
| 代理层 | 自建 `deploy/Caddyfile` 开着 `encode gzip`，会缓冲 SSE；Railway 前端与 API 是独立服务，前端直连 API 域名不过 Caddy | 两套部署都要单独验 |

因此**不做全程 SSE**（一个 HTTP 请求活 2–5 分钟、违背「重活进队列」、断线即丢、且必须重写
tool_calls 流式解析）。只给最后一段做。

### 5.2 时序

```
1. 前端 POST /recommendations/agent-turn
       → 创建或复用 session，入队 recommendation_agent job（llm 队列）
       → 立即返回 {session_id, turn_id}

2. worker 跑 tool loop，每完成一个阶段写一条 recommendation_message
       （role=tool, message_type=agent_step）
       最后写一条 writer_brief（写作素材包）

3. 前端轮询 bundle（1s）→ 渲染「过程折叠行」

4. 看到 writer_brief ready 后，前端发起
       GET /recommendations/sessions/{id}/turns/{turn_id}/answer-stream   (SSE)
       → API 读素材包 → 调流式 LLM → 逐 token 推送

5. 流结束时 API 把完整正文落成一条 recommendation_message（role=assistant），
   并在落库这一步做标的名 → 链接的确定性回填（见 6.2）

6. 断线重连：正文已落库则直接返回完整消息（幂等），未落库则重新生成
```

**流式过程中前端拿到的是纯文本（无链接）；流结束后重新拉一次那条消息，拿到带链接版本。**
这样避免在流式增量里做回填的复杂度。

### 5.3 两套部署都要处理

- 自建：`deploy/Caddyfile` 给 SSE 路径关掉 gzip 缓冲
- Railway：实测一次长连接行为，确认边缘代理不缓冲

### 6.2 标的名 → 链接：确定性回填，不让模型生成

**绝不能让 LLM 输出 `[名称](/targets/<id>)`** —— 它会编 ID，编出来的链接指向别人的标的，
这种错很难被发现。

做法：Agent 与 writer 都只输出**纯文本**；后端在消息落库时，拿本轮候选的 `(name, id)` 表做
**精确字符串匹配**的替换。匹配不上的名字保持纯文本，不猜、不模糊匹配。

### 6.3 附件上传

`POST /attachments/upload` 的 `entity_type` / `entity_id` 本就是可选的（`attachments.py:259`），
配 `auto_start_ocr=true` + `auto_parse_linked_objects=false` 即可「上传 → 提取正文 → 不碰任何实体」。

两个要改的点：

- `temporary_input` 上限 4000 字（`recommendations.py:145`）→ 提到 20000，前端显示「已读取 N 字」
- 前端要分段进度提示（读取文件 → 理解需求 → 筛选 → 细看资料），不能只转一个圈。
  扫描件走外部 Doc2X，可能顶到 2–5 分钟上限

### 6.4 一个顺带要修的限制

`frontend/src/features/recommend/TinyMarkdown.tsx:113` **硬限制表格最多 4 列**（为报告的受限
markdown 定的）。7 列的候选表会被整个丢弃，放宽到 8。

## 七、拆除清单

「下线」= 代码不再调用，节点定义与数据表**先留着**，后续走死表判决流程再删。

| 对象 | 处理 |
| --- | --- |

## 九、验收

1. 打开推荐页，粘一段需求，回车 → 2–5 分钟内拿到一段可复制的推荐文本，**全程没有建任何实体**。
2. 过程行如实反映 Agent 实际做了什么：筛了几次、每次什么条件、命中多少、放宽过什么。
3. 正文里的标的名可点，链接指向正确的标的（抽查 10 条，ID 必须与候选表一致）。
4. 追问「只看江苏」「利润提到 3000 万」能正确改条件并重筛。
5. 条件空到无法收敛时才出现澄清提问，且有「跳过」逃生口；条件充分时**不提问**。
6. 上传一份需求文档，能走通同一条链路。
7. 「列出全部」输出的 7 列表格能正常渲染。
8. 流式：最终回答逐字出现；断线刷新后能拿到完整正文，不重复计费。
9. 两套部署都验流式（Railway + 自建 Caddy）。
10. Agent 全程不写任何业务数据；「开始推进」在推荐页不存在。
11. `ai_trace` 留下完整工具调用链。
12. 方向锁定：发出第一条消息后方向选择器变成不可交互标签；构造请求强行改 mode 会被后端 400 拦掉。
13. 反向 tab 置灰不可选，且没有任何路径能进到一个跑不通的反向会话。

### 反向的处置：本轮暂时不可用（有代价，需知情）

**反向没法"半保留"。** 它今天依赖的深评 / rerank 链路正是本单要下线的东西，所以只有两个选择：
要么反向也一起 Agent 化，要么本轮暂时下线。本单按后者做。

**代价说清楚**：反向双向展示是 2026-08-03 刚落地的（`智能推荐双向展示与负责人操作边界优化方案0803.md`），
本单会让它暂时不可用。种子用户提的「来了个**出售需求**」正是这个方向，所以下一轮要尽快补。

界面上反向 tab **保留但置灰**，标注「下一轮支持」—— 不是删掉，是占位，下一轮补上 4.5 表里那两个
反向节点就自然亮起来。

**下一轮补反向时真正要解决的**：`recommendations.py:554` 现在把反向解析出的结构化条件全部丢弃、
只降级成语义偏好，而 `_candidate_intents_for_target` 的 SQL 初筛完全依赖标的的结构化字段 ——
自由文本描述的标的这些字段全空，**初筛等于不生效，退化成全量买家需求走语义排序**。
反向 Agent 化的核心工作量就在这里：把「一段出售需求描述」解析成能驱动初筛的标的画像。
