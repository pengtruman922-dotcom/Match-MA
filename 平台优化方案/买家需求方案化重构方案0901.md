# 买家需求方案化重构方案（2026-09-01）

> 承接 `买家需求字段精简与反向检索方案0828.md`（已上生产，commit `12ee8b5`）。
> 那一单把买家需求从 54 个字段砍到 23 个；这一单解决剩下的结构问题：
> **需求不是一组字段，是一组并列的方案。**

---

## 一、这一单要解决什么

0828 精简之后，需求信息 tab 仍然难用。逐条查下来，问题不在字段数量，在结构：

1. **公共层是错误的来源，不是共享的便利。** 一条需求分「公共条件」和 N 个「方案」，
   解析器遇到一条约束时必须猜它属于哪一层，猜错就把某一档的约束强加给全部档。
2. **必须/优先是假的。** 角标写着「优先」，`screening_sql.py` 照硬筛。
3. **门槛藏在第二次调用后面。** 全库买家的业务+门槛加起来才 5,848 token，
   分两次取纯属浪费；真正贵的是原文（37,693 token），它却和门槛捆在一起。
4. **方案里的数据没人读。** 推荐链路、搜索文档、反向检索 skill 三处都只读 intent 表，
   方案表的条件从未进入任何判断。

### 实测依据（2026-09-01，生产库 `12ee8b5`）

库存：**71 条标的 / 47 个买方主体 / 48 条真实需求**（另有 10 条 Mock）。

**公共层与方案层的取值冲突 11 个格子：**

## 三、四条设计判决

### 判决一：取消公共层，需求 = N 个完整并列的方案

一条买家需求不再有「公共条件 + 方案覆盖」两层。它是一个**容器**，
下面挂 1..N 个**互相独立、各自完整**的方案。命中任意一个方案即算命中这条需求。

容器层只保留：需求名称、级别、状态、暂停原因、归属主体，
以及附件 / 推进 / 更新记录 / 原始需求材料。

**保留容器的唯一理由**：级别、状态、附件、推进记录、原始材料来自同一次沟通，共享。
拆成 N 条独立需求要复制 N 份，推进记录也会分裂。

### 判决二：拆分标准是「取值必须成套对应」，不是「有多个值」

> 把这条需求的各维度取值列出来 —— 业务、地区、上市状态、营收、净利、市值、估值、PE。
> **如果任意组合都成立，就是一个方案；如果存在「A 维度取了这个值，B 维度就必须取那个值」
> 的绑定，就按绑定拆。**

**单个字段多值不算绑定。** 湖北农发的十来个农业赛道 + 「规模灵活，从四五亿估值、
年营收三四千万到五十亿都看」—— 任一赛道配任一规模都成立，**一个方案**。

岭南商旅的酒店 / 旅游 / 粮油食品 —— 拿酒店的业务配粮油食品的财务门槛不成立，**拆 3 个**。

**轴不固定。** 生产数据里的轴各不相同：北大健康是上市状态、广晟是业务板块、
盐业是交易结构、广百是业务方向。代码和提示词都不得预设「按上市/非上市拆」。

**默认倾向：拿不准就拆。** 两个方向的代价不对称 ——
拆多了每个方案门槛更少、召回更宽，损失有限；
该拆没拆，不兼容的条件被 AND 在一起（上市 AND 非上市 = 空集），直接筛出零条。

### 判决三：方案没有名称，摘要就是标题

方案不设 `label`。每个方案由它的**摘要**开头，摘要同时承担三个职责：

1. 界面上是这个方案的标题；
2. 反向检索 skill 第一层扫描读的就是它；
3. 业务匹配判断的主材料。

摘要口径：**一段话说清这个方案要买什么业务、什么地域、什么规模。**

> 收购文商旅、食品、调味品类企业，广东和珠三角优先；收入 5-50 亿、
> 净利润 1000 万以上、估值不超 50 亿。

**不再单设「业务说明」字段。** 0828 之后 `intent_business_summary` 中位只有 54 字，
跟标签列表差不多长；再设一个跨业务与门槛的摘要，两个文本字段必然互相抄。

内部引用用 `sort_order` 序号，不用名称。

### 判决四：强度归文本，缺失策略归字段

**删掉「必须/优先」。** 它在 `screening_sql.py` 里从来不生效（那里是一组纯 AND），
角标是在骗人。买家说的「优先大湾区」「上市公司优先」一律进「其他要求」文本。

**但保留一条按字段定死的缺失策略** —— 这是另一个问题，不要和上面那条混淆：

| 问题 | 答案在哪 |
|---|---|
| 这个买家有多想要？ | 模型判不准，SQL 也从来没用它 → **删掉** |
| 标的没录这个数时算不算不达标？ | 纯工程问题，有确定答案 → **按字段定死** |

| 字段 | 标的侧录入率 | 缺失策略 |
|---|---|---|
| 最低营收 / 最低净利润 / 上市状态 / 要求地区 | 77% / 82% / 87% / 97% | **缺失即出局**（缺的是真缺） |
| PE 上限 / 最低最高市值 / 最低最高估值 | 56% / 11% / 38% | **缺失不出局**，通过但标记「未知」 |

后一组按现行语义会贡献约 1,250 次误杀。改了之后，买家填了这些字段时它们在有数的
标的上照常生效，没数的标的不再被误杀。

## 四、字段设计

### 4.1 方案（`buyer_intent_scenario`）= 13 个字段

| 类 | 列 | 类型 | 说明 |
|---|---|---|---|
| 文本 | `scenario_summary` | text | **摘要**：要买什么业务 + 地域 + 规模。界面标题、skill 扫描层 |
| 文本 | `excluded_business_text` | text | 排除方向：买家明说不要的 |
| 文本 | `other_requirements_text` | text | **其他要求**：AI 归纳，保留全部约束、去掉冗余表达 |
| 可筛 | `business_tags_json` | jsonb | 业务标签，多值 |
| 可筛 | `required_regions_json` | jsonb | **要求地区**，省/市/区三级、多值、硬筛 |
| 可筛 | `acceptable_listed_status_json` | jsonb | 上市状态闭集 |
| 可筛 | `min_revenue_yuan` | numeric | 最低营收 |
| 可筛 | `min_net_profit_yuan` | numeric | 最低净利润 |
| 可筛 | `max_pe` | numeric | PE 上限 |
| 可筛 | `min_market_cap_yuan` `max_market_cap_yuan` | numeric | 市值区间 |
| 可筛 | `min_valuation_yuan` `max_valuation_yuan` | numeric | 估值区间 |

复用现有的 `id / buyer_intent_id / sort_order / active / source / 审计列`；
`label` 保留列但停止写入（判决三），`fields_json` 停止写入。

### 4.2 需求容器（`buyer_intent`）保留的字段

`intent_name` · `intent_grade` · `status` · `pause_reason` · `buyer_party_id`
· `raw_requirement_text` · `parsed_requirement_json` · `needs_confirmation_json`
· `processing_state` · 审计列。

**全部 23 个现役业务/门槛列在这一单退役**（阶段 A：停写、停筛、下界面，列还在）。

### 4.3 「优先大湾区」这类偏好的归宿

| 买家原话 | 落在哪 |
|---|---|
| 「标的地址：广东优先、珠三角优先」 | `other_requirements_text` |
| 「标的地址不限」 | 哪都不落（`required_regions_json` 留空即表达） |
| 「必须是江苏省内」 | `required_regions_json = [{"province":"江苏省"}]` |
| 「上市公司优先」 | `other_requirements_text` |
| 「非上市公司暂不考虑」 | `acceptable_listed_status_json = ["listed"]` |
| 「市值 50 亿以内，可适当放宽到 100 亿」 | `max_market_cap_yuan = 5e9` + 原话进 `other_requirements_text` |
| 「近三年净利润均在 1000 万以上」 | `min_net_profit_yuan = 1e7` + 「近三年均需，非单年」进 `other_requirements_text` |

**规则：能落进闭集或数字的落进去，落不进去或带弹性口径的落文本，两者可以同时出现。**

## 五、迁移（`023`，阶段 A）

### 5.1 做什么

1. `buyer_intent_scenario` 加 13 列 + 形状 CHECK + 业务标签 GIN 索引。
2. **为每条没有方案的需求生成一个方案行**（40/48 条），字段从 intent 直接搬。
3. 有方案的 8 条：每个方案 = `fields_json` 的值优先，intent 公共值补空。
   这等价于现行 `公共 AND 方案` 的效果，11 个冲突格子自动取到较严的那个。
4. `label` 的现有取值并进 `scenario_summary` 开头（重跑后会被覆盖，只是不丢）。
5. `fields_json` 里那 25 个退役列的取值 → 拼进 `other_requirements_text`。

**不删任何列**（阶段 B 另开一单，参照 0727/0814/0828 的先例）。

### 5.2 回填只是保底，正解是重跑

生产库 0 处人工修改，所以**重跑解析比机械回填准**：解析器面对的是原文，
不需要猜「公共层的这条约束属于哪个方案」—— 因为公共层不再存在。

回填只服务两种情况：重跑失败的、以及重跑前的那段窗口。

### 5.3 那 88 条业务更新采纳的保护

它们是顾问确认过的、可能比原始需求更新的信息。重跑结果与现值冲突时
**不直接覆盖，进 `needs_confirmation_json`**，界面上就是顶部那个「N 项需要确认」。
顾问在一个地方成批点，不逐字段翻 —— 这就是批量复核，机制现成。

### 5.4 迁移文件硬规则（AGENTS.md 已记录的坑）

- **注释里不能有分号**（自制 splitter 会切坏语句，历史事故）。
- 多列 CHECK 必须在**同一条 UPDATE** 内满足。
- 新增迁移后必跑 `tests/test_migration_sql.py`。
- alembic 修订：`20260901_0070`，`down_revision = "20260828_0069"`。
- `jsonb_array_elements` 前必须加 `jsonb_typeof(...) = 'array'` 守卫
  （生产有非数组脏数据，一条就能把迁移打挂）。

## 七、解析节点

**这是本单最大的改动：从「抽一组字段」变成「先切方案、再对每个方案抽一组字段」。**

三个节点都要改：

| 节点 | 现版本 | 新版本 | 改什么 |
|---|---|---|---|
| `buyer_intent_parser` | v0.9.0 | v0.10.0 | 输出 `scenarios: [...]` 数组 |
| `buyer_intent_normalizer` | v0.4.0 | v0.5.0 | 同上；v0.5.0 从未发布过，直接建在 v0.4.0 上 |
| `buyer_intent_update_parser` | v0.3.0 | v0.4.0 | 更新要能指名改哪个方案 |

提示词必须写进去的三条：

1. **拆分标准**（判决二原文），带湖北农发「不拆」与岭南商旅「拆 3」两个反差示例。
2. **轴不固定**，不得预设按上市/非上市拆。
3. **摘要口径**：一段话说清业务 + 地域 + 规模；不写成条目列表。

大区（长三角/大湾区）继续由代码侧 `REGION_GROUPS` 展开，提示词只说「原样写，系统会展开」。
