# 买家附件内容读取与 AI 解析状态一致性完整修复方案（P0-0730）

版本：v1.0  
日期：2026-07-30  
状态：待在新对话中实施  
范围：附件内容读取、买家需求 AI 解析、规范化写入、解析状态聚合、失败收口、历史异常数据恢复  

> 本方案针对新建买家需求并上传 Word 附件后出现的状态矛盾与任务卡死问题。本文是后续开发、测试、上线和生产恢复的实施基线；本轮仅制定方案，不修改业务代码。

## 一、问题结论

### 1.1 生产问题样本

买家需求：`北大健康2-并购需求（2026-07）`  
买家需求 ID：`3d3a30cb-b850-4849-a6e3-a8d589af0257`  
业务更新 ID：`c9bd2798-ed51-41dd-8255-72b6b4b5e25b`  
附件：`投资收购要素表-北大健康.docx`  
附件 ID：`37d34f41-2631-4231-8648-6ae27668860a`  
失败任务 ID：`1fe8ac5b-2523-48c7-9f31-2b29b47d0386`

生产数据的真实状态如下：

- Word 文件已上传并保存在对象存储中，附件没有丢失。
- Word 走的是本地 `office_text_layer` 文档文字提取，不是 PDF OCR，也没有调用扫描件 OCR 服务。
- 附件处理任务启动后失败，错误为：`Object of type UUID is not JSON serializable`。
- 异常导致当前事务回滚，已提取的文档内容、解析文档、证据、后续业务更新任务和 AI Trace 均未成功提交。
- 买家需求语义解析任务没有创建，因此 `latest_job`、`latest_trace` 为空，结构化需求字段没有写入。
- 后台任务虽然已是 `failed`，但附件仍为 `parsing`、业务更新仍为 `processing`，形成永久“解析中”。
- 列表页因为把默认值 `preferred_listed_status = any` 当成结构化结果，错误显示“已解析”；详情页使用另一套字段判断，显示“未解析”。

### 1.2 这是三个问题叠加，而不是一个显示问题

1. **附件处理成功路径存在 JSON 序列化错误**：带 UUID 的嵌套任务结果被直接写入 JSONB/AI Trace。
2. **附件任务异常后缺少失败收口**：事务回滚后，没有在新事务中把附件和业务更新同步标记为失败。
3. **页面没有统一状态来源**：列表、详情、附件和更新记录各自读取或推断不同状态。

因此不能只改一个前端标签，也不能只把当前记录的 `parsing` 手工改成 `failed`。必须同时修复任务执行、状态模型、接口聚合、页面展示和存量恢复。

## 二、修复目标与非目标

### 2.1 P0 修复目标

- Word、Excel、PPT、文本型 PDF、扫描型 PDF、图片和纯文本输入走正确的内容获取策略。
- 产品界面不再把所有附件内容提取统称为“OCR”。
- 附件内容读取状态与买家需求 AI 解析状态分开管理。
- 列表页与详情页顶部共用同一个后端整体处理状态。
- 附件 Tab 显示每个附件的内容读取状态，更新记录显示本批次的处理状态，二者可以粒度不同但不得互相矛盾。
- 任何最终失败的后台任务都必须将关联业务对象收口到终态，不允许无限停留在“解析中”。
- 修复现有“北大健康2”记录，并安全扫描、修复其他同类历史卡死记录。
- 修复后使用原附件重试即可继续处理，不要求用户重新上传。

### 2.2 本次非目标

- 不修改买家需求字段、筛选规则和推荐算法。
- 不修改买家需求语义解析及规范化 Prompt 的业务含义。
- 不把“待确认字段”混入解析状态；它继续属于人工复核状态。
- P0 不强制重命名数据库中既有 `attachment_ocr_parse` job_type，以免扩大兼容改造范围；界面和接口先使用准确的产品名称。
- 除非实施过程中确认现有表无法表达必要状态，否则不新增数据库字段或迁移。

## 三、统一术语

### 3.1 附件内容读取

“附件内容读取”是产品层总称，根据附件类型选择不同策略：

```text
附件内容读取
├── text_upload             TXT/Markdown/CSV 等直接读取
├── office_text_layer       Word/Excel/PPT 本地解析
├── pdf_text_layer          文本型 PDF 本地提取文字层
├── doc2x_ocr               扫描型 PDF OCR
├── multimodal_image        图片多模态理解
└── unsupported             不支持或无需读取
```

内部为了兼容，P0 可以继续使用 `attachment_ocr_parse` 和 `ocr` 队列，但用户可见名称必须改为“附件内容读取”或“文档读取”。只有实际使用 `doc2x_ocr` 等图像文字识别策略时，才在详情或调试信息中出现“OCR”。

### 3.2 AI 需求解析

AI 需求解析只负责将可用的原文变成结构化买家需求，内部包含：

1. LLM 语义解析；
2. LLM 规范化校验；
3. 代码校验与写库。

AI 解析不能与附件读取混为同一个状态。用户直接输入文字时可以跳过附件读取，直接进入 AI 解析。

### 3.3 人工复核

人工复核是解析完成后的独立状态域：

- 待复核；
- 存在需要确认的字段；
- 已复核。

“需要确认”不是解析失败，也不是解析中的一种状态。AI 已成功解析但存在待确认字段时，应显示“已解析 · N 项待确认”。

## 四、目标处理流程

```text
用户输入文字和/或上传附件
             |
             v
       创建买家与需求
             |
             v
  附件内容读取（无附件则跳过）
             |
             +---- 失败且无其他可用原文 ----> 整体解析失败
             |
             v
       汇总可用原文与证据
             |
             v
       LLM 语义解析需求
             |
             v
       LLM 规范化与校验
             |
             v
       代码校验并写入表
             |
             v
       已解析 / 存在待确认字段
             |
             v
          人工复核
```

关键约束：

- 有多个附件时，必须等待本批次所有附件进入终态后再决定是否进入 AI 解析，避免每个附件各自触发一遍重复解析。
- 至少存在一份可用原文时，可以继续 AI 解析；部分附件失败时记录警告，不应因为一个非关键附件失败而丢弃其他成功内容。
- 所有附件均失败且用户输入也不包含有效需求原文时，整体状态为失败，AI 解析状态为未开始。
- 用户输入本身已有有效需求原文时，即使某个附件失败，也可以使用现有原文继续解析，并展示附件失败警告。

## 五、状态模型

### 5.1 附件内容读取状态

继续兼容附件表当前值，但在接口层转换为明确语义：

| 存储状态 | 产品状态 | 页面文案 |
|---|---|---|
| `pending` | `pending` | 等待读取 |
| `parsing` | `processing` | 读取中 |
| `parsed` | `succeeded` | 读取成功 |
| `failed` | `failed` | 读取失败 |
| `skipped` | `skipped` | 无需读取 |

附件还应返回 `extraction_strategy`，用于解释实际采用的是 Office 本地解析、PDF 文字层、OCR 还是图片多模态，但该字段不参与总体成功与否判断。

### 5.2 AI 解析状态

| 状态 | 含义 | 页面文案 |
|---|---|---|
| `not_started` | 尚未创建 AI 解析任务 | 未开始 |
| `queued` | 已创建任务但尚未执行 | 排队中 |
| `semantic_parsing` | 正在执行需求语义解析 | 语义解析中 |
| `normalizing` | 正在执行规范化校验 | 规范化中 |
| `writing` | 正在代码校验并写库 | 写入中 |
| `succeeded` | 解析、规范化和写入均完成 | 已解析 |
| `failed` | 当前最新一次 AI 解析失败 | 解析失败 |

P0 不一定需要新增数据库列。可以在 `background_job.metadata_json` 中更新当前 `processing_stage`，并结合 job、AI Trace 和写入日志生成状态。

### 5.3 人工复核状态

| 状态 | 判断依据 | 页面文案 |
|---|---|---|
| `pending` | 已解析且 `reviewed_at` 为空 | 待复核 |
| `needs_confirmation` | `needs_confirmation_json` 非空 | N 项待确认 |
| `reviewed` | `reviewed_at` 非空 | 已人工复核 |

复核状态与解析状态正交，不用于覆盖失败或处理中状态。

### 5.4 整体处理状态

列表页和详情页顶部只使用后端返回的整体状态，不再从字段内容猜测：

| 状态 | 成立条件 | 页面主文案 |
|---|---|---|
| `not_started` | 没有处理任务，也没有可靠的历史解析完成证据 | 未解析 |
| `processing` | 当前最新处理链中存在排队或运行中的阶段 | 解析中 |
| `succeeded` | AI 解析、规范化和写入完成 | 已解析 |
| `failed` | 当前最新处理链已失败且没有更新的活动或成功重试 | 解析失败 |

整体状态必须针对“最新一次处理链”计算，不能让旧失败覆盖后续重试，也不能让历史成功掩盖当前正在重新解析的任务。

推荐状态优先级：

```text
最新处理链的活动任务
    > 最新处理链的最终失败
    > 最新处理链的成功写入
    > 可靠的历史解析完成证据
    > 未开始
```

“可靠的历史解析完成证据”包括成功的买家需求解析任务、成功 AI Trace 或来源为买家需求解析的写入日志，不包括默认枚举值、买家名称、创建时的模板文字或人工录入的任意一个结构化字段。

## 六、统一接口契约

### 6.1 完整状态对象

买家需求详情和解析状态接口统一返回：

```json
{
  "processing_state": {
    "overall_status": "failed",
    "current_stage": "attachment_extraction",
    "status_label": "解析失败",
    "stage_label": "附件读取失败",
    "attachment_summary": {
      "total": 1,
      "pending": 0,
      "processing": 0,
      "succeeded": 0,
      "failed": 1,
      "skipped": 0
    },
    "ai_parse_status": "not_started",
    "semantic_parse_status": "not_started",
    "normalization_status": "not_started",
    "write_status": "not_started",
    "review_status": "pending",
    "needs_confirmation_count": 0,
    "source_business_update_id": "...",
    "latest_job_id": "...",
    "error_code": "job_failed",
    "error_message": "Object of type UUID is not JSON serializable",
    "recoverable": true,
    "started_at": "...",
    "finished_at": "..."
  }
}
```

字段名在开发时可以根据现有类型风格微调，但含义必须保持一致。

### 6.2 列表接口

`GET /buyer-intents` 应直接返回精简版 `processing_state`，至少包含：

- `overall_status`；
- `current_stage`；
- `status_label`；
- `needs_confirmation_count`；
- `review_status`；
- `error_message` 的短摘要。

列表不应继续为每一行单独请求 `/parse-status`，避免 N+1 请求和加载期间状态跳动。列表与详情必须调用同一个后端状态聚合函数。

### 6.3 附件接口

附件接口保留原始 `parse_status` 兼容现有调用，同时增加或映射：

- `content_extraction_status`；
- `extraction_strategy`；
- `latest_job_status`；
- `error_message`；
- `recoverable`。

读取侧必须具备兜底规则：如果附件存储状态仍是 `parsing`，但最新关联任务已经最终失败且没有更新的活动任务，对外状态必须返回 `failed`，不能继续返回“读取中”。

### 6.4 更新记录接口

更新记录的批次状态不能只读取 `business_update.processing_status`。聚合时需要参考本批次关联任务：

- 有最新活动任务：处理中，并显示当前阶段；
- 最新相关任务最终失败且没有活动后继任务：处理失败；
- AI 写入完成：处理完成；
- 部分附件失败但仍基于其他有效原文完成 AI 写入：处理完成并带警告。

## 七、后端修复项

### 7.1 修复嵌套 UUID 序列化

根因是 `_enqueue_business_update_process_job` 返回的任务字典包含 UUID，且新流程还包含嵌套 `jobs` 列表；附件处理器将该对象直接写入 AI Trace 的 JSONB，触发序列化异常。

实施要求：

1. 把现有递归 JSON 安全转换能力下沉到无循环依赖的公共模块。
2. UUID 转字符串，Decimal、日期时间等也统一转换为 JSON 可序列化值。
3. `_enqueue_business_update_process_after_ocr` 返回前执行递归转换。
4. `_insert_ocr_trace` 在写入 `input_json`、`parsed_output_json` 等 JSONB 前再次执行递归转换。
5. 后台任务最终写入 `result_json` 前增加全局 JSON 安全转换，形成最后一道防线。
6. 不允许仅针对当前一个 UUID 字段手工 `str()`；必须覆盖嵌套字典和列表。

该修复应覆盖 Office 文档、文本型 PDF、OCR 完成回调以及通用附件解析成功路径。

### 7.2 增加附件任务失败收口

`attachment_ocr_parse` 和 `attachment_ocr_poll` 需要统一异常边界：

```text
处理器异常
   |
   v
回滚失败事务
   |
   v
判断是否为当前任务最终失败
   |
   +-- 尚可重试 --> 保持处理中/重试中
   |
   +-- 最终失败 --> 使用新事务写入：
                     attachment = failed
                     metadata.last_ocr_status = failed
                     metadata.last_ocr_error = 错误摘要
                     business_update = failed（满足收口条件时）
                     记录失败时间与 job_id
```

业务更新只有在以下条件同时成立时才收口为失败：

- 当前任务已经最终失败；
- 没有更新的活动附件读取任务或业务更新任务；
- 本批次没有足够的其他可用原文继续处理，或后续 AI 处理没有成功启动。

不能因为一次旧失败把已经重试中的新任务改成失败。

### 7.3 防止事务回滚吞掉终态

成功路径的内容提取、parsed_document、evidence、后续任务和 AI Trace 应在同一事务中保持原子性；但失败状态更新必须在主事务回滚之后使用新的可提交事务执行。

需要新增回归测试证明：即使异常发生在“已经读取 Word 文本、准备写 AI Trace”阶段，最终也能看到：

- 后台任务 `failed`；
- 附件 `failed`；
- 业务更新 `failed` 或按多来源规则继续处理；
- 页面不再无限显示处理中。

### 7.4 建立统一买家需求状态聚合服务

建议新增独立服务，例如 `buyer_intent_processing_state.py`，由以下位置共同调用：

- 买家需求列表；
- 买家需求详情；
- `/buyer-intents/{id}/parse-status`；
- 更新记录批次聚合；
- 必要的调试接口。

聚合服务读取：

- 最新业务更新及其 correlation/source 信息；
- 关联附件和最新附件任务；
- 最新买家需求解析任务；
- 语义解析与规范化 AI Trace；
- 写入日志；
- `needs_confirmation_json` 和 `reviewed_at`。

列表批量查询时必须一次性加载当前页所需状态，禁止逐行查库或逐行调用接口。

### 7.5 记录 AI 解析内部阶段

买家需求解析任务开始各节点前，在任务元数据中记录当前阶段：

- `semantic_parsing`；
- `normalizing`；
- `writing`。

节点成功或失败时记录完成时间、对应 Trace ID 和错误摘要。AI 管理模块继续负责管理语义解析与规范化节点配置；本次不修改 Prompt 内容，但应保证后台任务状态能关联到具体节点和 Trace，方便排障。

## 八、前端修复项

### 8.1 列表页

- 删除使用 `hasStructuredIntentFields()` 推断“已解析”的逻辑。
- 删除默认枚举值导致的“已解析”误判。
- 直接使用列表接口返回的 `processing_state`。
- 主状态展示：未解析、解析中、已解析、解析失败。
- 处理中或失败时显示阶段提示，例如“正在读取附件”“附件读取失败”“规范化失败”。
- 待确认和人工复核作为独立附加标签展示。

### 8.2 详情页顶部

- 与列表页复用同一个状态展示组件和同一份状态对象。
- 不再维护另一套 `hasStructuredIntentFields()`。
- 对当前样本应显示“解析失败 · 附件读取失败”，而不是“未解析”或“解析中”。
- 失败时提供明确的“重新处理”入口；重试应复用现有附件。

### 8.3 附件 Tab

- 文案由“解析状态”调整为“内容读取状态”。
- Word 显示“Word 内容读取中/成功/失败”，不显示“PDF OCR”。
- 失败时展示可读错误摘要和重试入口。
- 每个附件独立显示状态，多附件情况下允许部分成功、部分失败。

### 8.4 更新记录 Tab

- 展示整批处理状态及当前阶段。
- 当前样本应显示“处理失败 · 附件内容读取失败”。
- 不能因为 `business_update.processing_status` 的历史残值而永久显示“解析中”。
- 部分附件失败但业务更新最终完成时，显示“处理完成 · 1 个附件读取失败”，而不是整体失败。

### 8.5 建议的页面文案

```text
列表/详情顶部：
[解析失败] 附件读取失败

附件 Tab：
投资收购要素表-北大健康.docx
[读取失败] Word 文档内容处理失败    [重新处理]

更新记录：
[处理失败] 2026-07-30 上传附件
失败阶段：附件内容读取
```

## 九、历史卡死数据修复

### 9.1 扫描条件

提供可预览、可审计的修复脚本或管理接口，先 dry-run，再执行。候选记录包括：

- 附件状态为 `pending/parsing`，但最新附件任务已经 `failed/cancelled`，且不存在更新的活动任务；
- 业务更新状态为 `processing`，但所有相关任务都已终止且至少一个关键任务失败；
- 买家需求列表被默认字段误判为“已解析”，但没有成功解析任务、成功 Trace 或解析写入日志。

## 十一、生产验收场景

### 场景 A：Word 文档正常处理

- 上传 `.docx`；
- 附件显示“Word 内容读取中”，不显示扫描件 OCR；
- 内容读取成功；
- AI 依次进入语义解析、规范化、写入；
- 列表和详情最终一致显示已解析。

### 场景 B：Word 处理发生程序异常

- 后台任务最终失败；
- 附件、业务更新和详情顶部在一个轮询周期内进入失败终态；
- 不得持续显示解析中；
- 页面可使用原附件重试。

### 场景 C：纯文本新建需求

- 附件读取阶段为无需执行；
- 直接进入 AI 需求解析；
- 整体状态正常流转，不依赖附件状态。

### 场景 D：扫描型 PDF

- 明确显示使用 OCR；
- OCR 状态只属于附件读取阶段；
- OCR 成功后才进入 AI 需求解析。

### 场景 E：多个附件部分失败

- 每个附件显示真实状态；
- 有足够原文时继续 AI 解析；
- 整体完成后显示成功并带附件警告；
- 不因为一个失败附件让整批永久卡住。

### 场景 F：失败后重试成功

- 新重试任务优先于旧失败任务；
- 整体状态依次为失败、处理中、已解析；
- 旧失败记录保留用于审计，但不再覆盖当前状态。
