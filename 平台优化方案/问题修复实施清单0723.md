## 0. 本轮已定稿的决定

### 0.1 标的所在地与行业字段

- 标的只保留一个「所在地」概念，结构化为：`location_province`、`location_city`、`location_district`。
- LLM 直接按证据判断并填写省、市、区；无法确定的层级为空，前端统一显示 `-`。筛选按用户填写到的层级进行，不再引入别名字典或地区粒度。
- 废弃：`registered_province`、`registered_city`、`headquarter_province`、`headquarter_city`、`raw_region_text`、`region_granularity`。
- 废弃标的宽表中的 `industry_primary`、`industry_secondary`；行业原文仅保留在 `business_update`、附件、证据和解析审计中，不再作为标的事实字段。
- `industry_l1`、`industry_l2` 是唯一用于筛选和展示的标准行业字段。解析出的二级行业必须经行业字典归一化；无法归一化时不得偷偷写入原文列，应留下可诊断的解析/字典缺口信息。

### 0.2 标的信息页与「其他」补充栏

- 信息页保留七组：身份与地区、业务与产品、产业链位置、技术与团队、经营质量、交易属性、出售诉求。
- 原「匹配画像（仅用于深评）」改为各组一个「其他」补充栏；它用于承载无法进入结构化字段的定性内容，不再另起“匹配画像”概念。
- 每组都可有「其他」：为 `entity_profile_section` 增加 `identity` 分组，原有六个业务分组沿用同名 section code。
- 取消「画像待补」及其覆盖率/缺口提示。结构化字段与“其他”共同构成完整信息，不再人为分成“画像”和“非画像”。
- 所有未知、空值、未填写的页面字段统一显示 `-`；不再将数据库枚举 `unknown` 显示成“未知”。
- 保留来源和截止时间（`as_of_date`）；前端不显示、后端也不再生成或存储 `confidence`。`research_proposal.confidence` 与 `entity_profile_section.confidence` 应通过迁移删除，并从 API、模型、prompt、测试中移除。

### 0.3 手动编辑

- 信息页中所有**展示型结构化指标**与各组「其他」都支持编辑。
- 系统运行状态字段（例如 `information_status`、`recommendation_status`）不属于信息页编辑对象，继续由既有流程维护；本条“所有字段”指信息页展示的业务事实。
- 手动编辑必须走统一写入通道，记录：新值、`source_type=manual_edit`、来源标签“手动编辑”、操作者、操作时间、更新记录和字段来源记录。
- 注册表的 `writable_by` 增加 `manual`；写入服务必须按来源验证权限、按字段 `kind`/枚举校验与归一化，不能只验证“列名存在”。

### 0.4 关系动态

- 仅手工动态可编辑、软删除；系统生成的推荐开局、状态变更、解析生成事件不可编辑或删除，保持审计历史。
- 手工记录动态时，仅选择事件类型即可保存；服务端生成默认文案（例如“已记录：电话沟通”）。填写标题、内容、下一步仍是可选增强信息。
- 关系卡片与看板卡片必须显式区分双方：`买家（主体 / 意向）` 和 `标的`。
- 推荐结果“已在推进 / 新候选”分区按当前决定**暂不处理**；已有关系状态仍可作为卡片提示。

### 0.5 明确延期

以下事项仅记录问题，不在本施工单实施：

1. 同一条录入如何同时产生「当前事实更新」「实体跟进」「关系动态/状态」；
2. 从自由文本自动识别对手方并自动挂接关系。

后续讨论时以“事实是当前状态、跟进是实体事件、关系是双边事件；同一来源可扇出多个结果且共享证据”为候选原则，但在决定前不得借本轮改动改变现行路由。

   - 将“事实更新与跟进记录扇出”保留为未决项。
2. 新建 `database/migrations/002_*.sql`，不得修改已部署的 `001_baseline.sql`：

**完成标准**：不存在对废弃列的运行时代码引用；全新库 `001` + `002...head` 可建成；迁移 splitter 回归通过。

### R4b · 指标注册表和 AI 写入通道补全（P1）

**现状缺口（代码验收发现）**：

- `seller_target_parse.py` 和 `buyer_intent_parse.py` 仍各自维护解析白名单、枚举、UPDATE、审计、field source、search-doc rebuild；未走注册表或 `field_writer`。
- `field_writer` 只校验列是否在注册表，未校验该来源是否被 `writable_by` 授权；`extracted_action_apply.py` 仍有第二份 seller 字段白名单。

**实施步骤**：

1. 重写 `backend/app/registry/indicators.py`：
   - 指标覆盖所有仍允许解析/调研/手工编辑的 seller target 与 buyer intent 业务事实；
   - 以结构化 `enum_options=(code, label)` 取代仅有 code 的 `enum_values`，令中文枚举展示、写入校验同源；
   - 明确 `writable_by` 为 `parse`、`research`、`manual` 的集合；
   - 分组、字段中文名、筛选角色、折叠关系均只能在此声明。
2. 将 `seller_target_parse.py` 的字段白名单、枚举、写入及审计逻辑下沉：
   - 解析专有的行业字典归一化、金额/日期处理可以保留为调用前 normalization；
   - 实际 diff、UPDATE、action log、field value source、search-doc rebuild 必须调用 `write_seller_target_fields`；
   - 保持既有 source 标识（如 `seller_target_parse`）和自动采纳语义，避免破坏历史查询。
3. 将 `buyer_intent_parse.py` 的白名单和枚举从注册表派生；如需统一其写入器，单独建立 buyer intent 对等写入服务，不能把 seller target SQL 复用到错误实体。
4. `field_writer` 增加来源参数（业务来源与审计 `source_type` 分离）：
   - 拒绝未声明指标；
   - 拒绝来源无权写入的指标；
   - 校验/归一化 enum、金额、比例、日期、文本长度和 JSON；
   - 所有字段来源记录使用真实操作者，而不是固定管理员。
5. 删除或改为派生 `_allowed_seller_target_changes` 等重复白名单；确因系统字段保留的例外必须有命名清晰的单独集合和测试说明。
6. 前端 `fieldLabels.ts` 中与指标相关的中文字段名、枚举中文名改由 `/meta/indicators` 返回；它只保留纯格式化，不再是第二份业务字典。

**新增守护测试**：

- 注册表与 seller 初始解析、buyer 初始解析、business-update 解析、research 的白名单/枚举逐项一致；
- 任一 `writable_by` 外的字段被写入器拒绝；
- 任一解析路径均经过统一 writer（可对函数调用或副作用做测试）；
- 解析、研究、手动编辑对同一字段的审计、来源、索引重建行为一致；
- 保留原有 apply 行为测试，并新增 `applied_by`、真实 actor、no-op 的断言。

### R4c · 标的信息页、手动编辑与来源展示（P1）

1. `/meta/indicators` 仅返回 seller target 信息页所需的七组、字段、中文 label、中文枚举、kind、筛选标记、编辑权限和“其他”section 映射。
2. `TargetInfoPanel`：
   - 按 API 运行时渲染七组；每组结构化字段后紧接一个标题为“其他”的补充栏；
   - 不显示“匹配画像”“画像待补”“置信度”；
   - 未知/空值一律显示 `-`；
   - 金额、比例、日期、枚举中文值在统一 formatter 中处理；
   - 保持来源和截止时间可查看。
3. 新增/扩展手动编辑 API：
   - 结构化字段接受单字段或批量修改，并调用统一 writer；
   - “其他”通过 `profile_sections` 的版本化写入服务修改；
   - 成功后刷新字段、来源和更新记录；失败信息必须指出字段与校验原因。
4. 前端对手工编辑做按 kind 的控件和校验：金额/比例/日期/枚举不使用自由文本；文本显示必要的长度提示。
5. 旧 `PATCH /seller-targets` 中负责人、生命周期等非信息页业务操作保持原路径，不与本轮字段编辑混合。

### R4f · 排他提示修复与权限回归（P1）

**根因**：`_annotate_candidate_relations` 查询同时以候选 buyer intent 集和 target 集限制 relation；在“买家 A 正对标的 T 尽调、买家 B 正推荐 T”的真实场景下，A 的 relation 被过滤，故 `deep_progress_elsewhere` 不会置真。现有单测 stub 直接伪造了 SQL 条件实际不可能返回的行，属于假阳性。

1. 将“候选与本对的既有关系”和“候选标的是否被其他买家深入推进”拆成两次语义独立的查询/集合：
   - 精确关系：按 `(buyer_intent_id, seller_target_id)` 对匹配；
   - 深入推进：按候选标的集合查询所有其他 buyer intent 的 `due_diligence`、`agreement`、`deal_closed` 关系；仅输出布尔值，不输出对方 ID、名称、状态详情。
2. 双向推荐均使用“标的是否与其他买家深入推进”的同一语义，不能在 `target_to_buyer` 模式错误地改为“候选意向自身是否深入推进”。
3. 重写测试为能检查执行参数/SQL 语义的测试，禁止 mock 返回被 WHERE 条件排除的 relation。
4. 补充可见性回归矩阵：标的负责人、买家意向负责人、买家主体负责人、管理员可见；无关顾问不可见；提示本身不得泄露对方信息。

**TC-09 验收**：

1. A-T 状态设为尽调或协议；
2. 对 B 发起推荐并使 T 成为候选；
3. T 显示“正与其他买家深入推进”；
4. 页面、接口响应、浏览器网络包均不得包含 A 的姓名、意向名、relation id 或状态细节。
