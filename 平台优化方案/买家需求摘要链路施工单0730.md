# 买家需求摘要（intent_summary）链路施工单（0730）

**状态：待实施。** 与《买家需求列表改造施工单0730.md》拆分，两者无代码耦合（列表不展示需求摘要）。拆分理由：本单要改 4 个 prompt，需要单独跑一轮解析验证。

## 一、问题

需求摘要的内容与详情页下方的结构化条件重复。查证后是**两个独立成因**：

### 成因 A：写入者是规范化节点，不是语义解析节点

两阶段流水线（`backend/app/jobs/handlers/buyer_intent_parse.py`）：

```text
raw_requirement_text
   ↓
buyer_intent_semantic_parser  →  semantic_output_json
   ↓                                 ↓
buyer_intent_normalizer          仅写进 parsed_requirement_json.semantic_output（存档，不落字段）
   ↓
parsed_output_json → _normalize_buyer_intent_parse_changes() → 落库（含 intent_summary）
```

落库的 `intent_summary` **只来自 normalizer 的输出**。normalizer 的职责是把语义结果映射成结构化字段，让它顺带写摘要，产出必然是结构化条件的复述。语义阶段的叙述性理解被丢进存档 blob，从未落到字段上。

### 成因 B：详情页把同一字段渲染了两次

- `frontend/src/components/BuyerIntentRequirements.tsx` 顶部独立只读区块（「需求摘要」标题 + 正文）。
- `intent_summary` 在契约里 `group = "intent_scope"`（`indicators.py`），而 `conditionRows()` 只跳过「无 group」和 `industry_l2_json`，因此它**又**作为一个可编辑 textarea 行渲染进「公共条件 → 需求方向」分组。

## 二、目标

需求摘要表达**需求的整体形态与分方案理由**，不复述已结构化的行业、地区、财务门槛数值。对齐 0730 方案 §10.1 的范例：

> 围绕医疗健康产业开展控股并购，上市和非上市标的采用不同要求。

## 三、不能删的理由（先记录，避免后续误判为死字段）

`intent_summary` 是承重字段：
- 推荐深评上下文注入：`backend/app/jobs/handlers/recommendation.py`、`backend/app/services/recommendation_flow.py`
- 检索文档正文：`backend/app/services/search_docs.py`
- 全局搜索摘要：`backend/app/api/routes/global_search.py`
- 列表搜索字段之一：`BUYER_INTENT_SEARCH_COLUMNS`

## 四、改动面

| 环节 | 改动 | 是否占发版 |
|---|---|---|
| `buyer_intent_semantic_parser` prompt | 输出中新增明确的「需求形态摘要」字段：整体逻辑 + 为什么分方案，不含具体数值 | 否（prompt 版本管理） |
| `buyer_intent_normalizer` prompt | **关键**。要求透传语义阶段的摘要到 `intent_summary`，禁止自行复述结构化条件 | 否 |
| `buyer_intent_parser` prompt（单阶段兜底） | 同样的内容约束。两个新节点未同时配置时会走它，**漏改等于留了条产出旧风格的回退路径** | 否 |
| 跟进/业务更新 extractor prompt | 同样的内容约束。`extracted_action_apply.py` 的 `_allowed_buyer_intent_changes` 允许写 `intent_summary`，一次跟进录入即可把摘要覆盖回旧风格 | 否 |
| `_normalize_buyer_intent_parse_changes` | normalizer 未给摘要时，从 `semantic_output` 兜底取 | **是** |
| `BuyerIntentRequirements.tsx` | `conditionRows()` 排除 `intent_summary`，只保留顶部独立区块 | **是** |
| `BUYER_INTENT_PARSE_FIELDS` / `_allowed_buyer_intent_changes` | 不改 —— 只是字段白名单，不约束内容 | — |
| 推荐深评注入 | 不改 —— 摘要变叙述性后与结构化条件不再重复，是纯收益 | — |
| 检索 | 不改 —— `raw_requirement_text` 与 `intent_summary` 同在检索文档中，按数值检索由前者兜底 | — |

合计：**4 个 prompt + 1 处代码兜底 + 1 处前端去重**。

## 五、验收用例

1. 新建一条含多方案的需求并解析，`intent_summary` 描述形态与分方案理由，不含具体行业名、省份名、金额数字。
2. 详情页「需求摘要」只出现一次，「公共条件 → 需求方向」分组里不再有需求摘要行。
3. 两阶段节点只配置其一时走单阶段兜底，产出的摘要风格与两阶段一致。
4. 对已解析需求追加一条跟进材料并 apply，摘要不被改写回条件复述风格。
5. normalizer 输出中缺 `intent_summary` 时，落库值取自 `semantic_output`，不为空。
6. 改造后重跑一条历史需求的推荐，深评上下文中摘要与结构化条件无重复内容。

## 六、风险

- 摘要变叙述性后，「按需求摘要检索」的命中内容改变（不再能按金额数字命中摘要）。`raw_requirement_text` 仍在检索范围内，功能不丢，但需在验收时确认搜索建议的表现。
- 存量数据的摘要仍是旧风格，除非重跑解析。**需要决定是否批量重解析**，本单默认不重跑。
