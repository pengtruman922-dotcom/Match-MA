# 智能推荐双向展示与负责人操作边界优化方案

> 状态：已实施并完成本地验收
> 日期：2026-08-03
> 范围：智能推荐结果卡片、推荐会话恢复、推荐列表、撮合关系创建及相关权限提示

## 一、背景与总原则

智能推荐需要扫描全库，跨负责人候选仍应参与推荐，避免把“负责人范围”错误地变成推荐召回范围。但顾问从推荐结果继续查看或操作业务对象时，必须遵守负责人边界。

本轮统一采用以下原则：

1. **推荐可跨负责人展示，业务操作受负责人限制。**
2. **评分继续服务内部排序与调试，用户端不展示难以解释的具体分数或多套评级。**
3. **“加入推荐列表”只是收藏候选，不创建撮合关系、不写推进事件。**
4. **只有“开始推进”才创建 `buyer_seller_relation`。**
5. **前端负责及时、清楚地阻止误操作；后端负责不可绕过的权限兜底。**
6. **管理员保留全局操作能力，但页面仍展示对象的实际负责人。**

## 二、为买家找标的

### 2.1 已确认的问题

当前页面同时展示规则分数、推荐等级和深评 A/B/C 档，用户看到类似“强推荐 85”“A 档”的两套评级，解释成本高。

推荐候选来自全库标的，其中可能包含非当前用户负责或未指派的标的。当前候选响应没有完整的实时负责人信息，卡片也没有负责人边界提示；“详情”“加入推荐列表”“开始推进”“查看推进”均没有统一的前端拦截。

此外，当前“加入推荐列表”会同步创建或复用撮合关系，并写入一条“加入推荐列表”关系事件。这与“收藏候选”的按钮语义不一致，也使用户在尚未决定推进时提前产生业务关系。

### 2.2 用户端评分展示

用户端只保留一个定性推荐标签，例如：

- 优先推荐
- 推荐
- 可关注
- 谨慎考虑

不再展示：

- 具体数字分数；
- A/B/C 档；
- rule score、rerank score、boost 等内部评分信息。

匹配理由、信息缺口、风险和完整对比继续展示。后端继续保留原始评分、深评档位和分数明细，用于排序、报告生成、调试中心与审计，不改变推荐算法。

前端不得再从 `candidate.score` 拼接“强推荐 85”一类文案。最终定性标签应由一个统一映射产生，避免规则等级与深评档位同时出现在卡片上。

### 2.3 负责人信息与卡片标识

候选响应补充当前标的的实时负责人信息与操作判定，建议字段为：

```json
{
  "seller_target_owner_user_id": "uuid-or-null",
  "seller_target_owner_name": "张三",
  "seller_target_operation_allowed": false
}
```

`seller_target_operation_allowed` 的规则：

- 管理员：`true`；
- 顾问且 `seller_target.owner_user_id == current_user.user_id`：`true`；
- 其他负责人或未指派：`false`。

负责人信息必须在候选首次生成、深评完成、推荐会话恢复和轮询刷新时重新按当前数据库状态叠加，不能只依赖生成推荐时保存的快照。标的发生转交后，旧会话必须在下一次刷新中更新标识与操作权限。

卡片统一展示负责人：

- 本人负责：绿色弱提示“我负责”；
- 他人负责：醒目的琥珀色锁标识“其他用户负责 · 张三”；
- 未指派：琥珀色锁标识“未指派”。

管理员可以操作所有候选，但仍展示“负责人 · 张三”或“未指派”，不伪装成“我负责”。

### 2.4 统一操作拦截

对 `seller_target_operation_allowed = false` 的候选，以下入口必须统一拦截：

- 详情；
- 加入推荐列表；
- 开始推进；
- 查看推进。

点击后不得跳转、不得打开新窗口、不得调用对应 API，统一弹窗提示：

> 该标的由其他用户负责，如需操作请联系管理员

入口保持可点击外观，以便用户点击后得到明确原因；不能简单置灰且不给解释。所有入口复用同一个 guard 和同一个提示弹窗，禁止四处分散复制判断与文案。

“详情”和“查看推进”的限制只作用于智能推荐卡片入口。本轮不收紧系统既有的跨负责人关系可见规则，不影响撮合看板、关系时间线及其他已授权入口。

后端必须为会产生状态变化的接口增加权限兜底：

- 加入推荐列表：普通顾问只能收藏本人负责的标的；
- 开始推进：普通顾问只能以本人负责的标的创建关系；
- 管理员不受该限制；
- 绕过前端直接请求时返回 `403`，不得创建收藏、关系或事件。

### 2.5 “只看我负责的”筛选

在“为买家找标的”的结果对话框顶部增加切换按钮：

> 只看我负责的

交互规则：

- 默认关闭；
- 仅做前端展示过滤，不重新执行 SQL 初筛、LLM 深评或生成新推荐轮次；
- 开启后只展示 `seller_target.owner_user_id == current_user.user_id` 的候选；
- 管理员开启后也只看管理员本人名下标的，而不是“全部可操作”；
- 建议显示数量，例如“只看我负责的 6/20”；
- 与“仅看某推荐等级”“前 N 项”等展示筛选取交集；先过滤负责人，再在本人候选中应用前 N 项；
- 对当前会话的所有推荐轮次生效，历史轮次仍保留原始总数；
- 无结果时显示“当前推荐结果中没有你负责的标的”，不得只展示空白区域；
- 该开关是页面显示偏好，不写入推荐会话条件、不影响报告和服务端推荐快照。

### 2.6 推荐列表与开始推进解耦

“加入推荐列表”改为纯收藏：

1. 只写 `recommendation_selected_item`；
2. 不创建或复用 `buyer_seller_relation`；
3. 不写 `relation_event`；
4. 不使候选自动切换成“已在推进”；
5. 允许用户从推荐列表移出自己的收藏，不产生关系事件；
6. 推荐报告继续从有效的 `recommendation_selected_item` 生成，不依赖关系存在。

“开始推进”保持唯一的推荐转推进动作：

1. 创建或复用 `buyer_seller_relation`；
2. 初始状态为 `recommended`；
3. 写入系统开局事件；
4. 候选刷新后显示“已在推进 · 已推荐”，操作切换为“查看推进”。

为兼容历史数据，不删除已有收藏关联的关系和事件；新逻辑上线后只停止继续自动创建。旧收藏是否已经关联关系，仍由实时 `relation_id/relation_status` 独立表达。

### 2.7 验收要点

1. 普通顾问能看到全库推荐候选，但卡片明确区分本人、他人和未指派标的。
2. 他人负责或未指派标的的四个入口均只弹统一提示，无跳转、无 API 请求、无状态变化。
3. 管理员可操作全部候选，负责人标识仍准确。
4. 标的负责人转交后，已打开或恢复的推荐会话在刷新后更新权限状态。
5. 卡片不再出现数字分数和 A/B/C 档，只保留统一定性标签与文字理由。
6. “只看我负责的”不触发新推荐，数量、空状态和其他展示筛选组合正确。
7. 加入推荐列表后只新增收藏，不新增关系和关系事件；移出收藏同样不写关系事件。
8. 点击开始推进后才创建关系，刷新与轮询不会回退为“开始推进”。
9. 直接调用收藏或关系创建接口操作他人负责的标的时返回 `403`。

## 三、为标的找买家

### 3.1 现状审计结论

“为标的找买家”与“为买家找标的”共用同一套候选卡片和推荐会话，因此数字评分、A/B/C 档、收藏副作用及无负责人拦截等问题完全相同。

反向候选查询读取的是 `buyer_intent`，但当前候选响应没有返回该买家需求的 `owner_user_id/owner_name`，前端无法标识负责人，也无法实现“只看我负责的买家需求”。这里必须以 **`buyer_intent.owner_user_id`** 为准，不能使用共享买家主体 `buyer_party.owner_user_id` 代替；一个买家主体下的不同需求可以由不同顾问负责。

“深入推进”还存在方向性错误：

1. 推荐卡片把提示文案写死为“正与其他买家深入推进”；
2. 后端 `deep_progress_elsewhere` 在两个推荐方向都只检查“同一标的是否还有其他买家关系”；
3. `/relations` 返回的同名字段也只检查“同一标的 × 其他买家”，没有表达“同一买家需求 × 其他标的”；
4. 买家需求「推进」Tab 复用该字段并写死同一文案，因此数据含义和页面文案同时错误；
5. 当前关系接口把“已推荐、有意向、沟通中”也算作“深入推进”，与看板中“尽调中/协议阶段”的深度交流口径不一致。

因此第 4 点不能只改一行中文，必须拆分双向布尔语义并修正 SQL 判断维度。

### 3.2 用户端评分展示

与 §2.2 完全一致：反向推荐不展示具体数字、A/B/C 档或内部 score breakdown，只展示一套统一的定性推荐标签、匹配理由、信息缺口、风险和完整对比。

两个推荐方向必须共用同一个展示映射，不能分别维护标签口径。

### 3.3 买家需求负责人标识与操作拦截

反向候选响应补充当前买家需求的实时负责人信息与操作判定，建议字段为：

```json
{
  "buyer_intent_owner_user_id": "uuid-or-null",
  "buyer_intent_owner_name": "李四",
  "buyer_intent_operation_allowed": false
}
```

`buyer_intent_operation_allowed` 的规则：

- 管理员：`true`；
- 顾问且 `buyer_intent.owner_user_id == current_user.user_id`：`true`；
- 其他负责人或未指派：`false`。

与标的一侧相同，负责人信息必须在候选生成、深评完成、会话恢复和轮询刷新时实时叠加，不能依赖旧快照。

卡片标识：

- 本人负责：绿色弱提示“我负责”；
- 他人负责：琥珀色锁标识“其他用户负责 · 李四”；
- 未指派：琥珀色锁标识“未指派”；
- 管理员可以操作全部候选，但仍显示实际负责人。

对 `buyer_intent_operation_allowed = false` 的候选，统一拦截：

- 详情；
- 加入推荐列表；
- 开始推进；
- 查看推进。

点击后不跳转、不打开新窗口、不调用 API，弹窗提示：

> 该买家需求由其他用户负责，如需操作请联系管理员

四个入口复用与正向推荐相同的 guard 组件，只根据候选主实体类型切换提示文案。

### 3.4 “只看我负责的”筛选

在“为标的找买家”的结果对话框顶部展示同一个“只看我负责的”切换按钮。开启后只展示：

```text
buyer_intent.owner_user_id == current_user.user_id
```

其余规则与 §2.5 一致：只做本地显示过滤、不重跑推荐、显示“本人数量/全部数量”、与其他展示筛选取交集、无结果时显示明确空状态。

建议根据当前方向动态补充辅助说明：

- 为买家找标的：只看我负责的标的；
- 为标的找买家：只看我负责的买家需求。

### 3.5 双向“正在深入推进”语义

#### 3.5.1 统一状态口径

“正在深入推进”只认仍在进行中的深度阶段：

```text
due_diligence（尽调中）
agreement（协议阶段）
```

以下状态不触发该提示：

- `recommended / interested / in_discussion`：仍属早期接触；
- `deal_closed`：已经成交，不应显示“正在”；
- `not_interested / paused / lost`：非活跃深入推进。

后端、推荐卡片和两侧详情「推进」Tab 必须共用一份状态常量或同一服务函数，禁止再次各写一套列表。

#### 3.5.2 拆分两个明确布尔值

废弃含义模糊的单一 `deep_progress_elsewhere` 展示契约，改为两个明确字段：

```json
{
  "seller_target_has_other_deep_progress": false,
  "buyer_intent_has_other_deep_progress": true
}
```

语义分别为：

- `seller_target_has_other_deep_progress`：同一标的存在与**其他买家需求**的尽调中/协议阶段关系；
- `buyer_intent_has_other_deep_progress`：同一买家需求存在与**其他标的**的尽调中/协议阶段关系。

两项判断都必须排除当前候选对本身，只返回布尔值，不返回其他关系的 ID、对象名称或具体状态。

为避免上线切换期间前后端错配，可以短期保留旧字段作为兼容字段，但新页面不得再消费旧字段；完成生产切换后删除兼容字段与旧常量。

#### 3.5.3 推荐卡片使用规则

| 推荐方向 | 候选实体 | 使用字段 | 展示文案 |
| --- | --- | --- | --- |
| 为买家找标的 | 标的 | `seller_target_has_other_deep_progress` | 正与其他买家深入推进 |
| 为标的找买家 | 买家需求 | `buyer_intent_has_other_deep_progress` | 正与其他标的深入推进 |

反向场景的正确判断示例：固定标的 T1，为其推荐买家需求 I1；如果 I1 正与 T2 尽调，则 I1 卡片显示“正与其他标的深入推进”。T1 是否还与 I2 推进，不得影响 I1 这张候选卡。

#### 3.5.4 两侧详情「推进」Tab 使用规则

| 页面 | 每张关系卡的对手方 | 使用字段 | 展示文案 |
| --- | --- | --- | --- |
| 标的详情「推进」Tab | 买家需求 | `seller_target_has_other_deep_progress` | 正与其他买家深入推进 |
| 买家需求详情「推进」Tab | 标的 | `buyer_intent_has_other_deep_progress` | 正与其他标的深入推进 |

由后端同时返回两个布尔值，`ProgressPanel` 根据 `side` 明确选择，不允许再用一个字段配固定文案。

### 3.6 收藏、推进与权限的一致性

§2.6 的“收藏与推进解耦”同时适用于反向推荐：加入买家需求到推荐列表只写 `recommendation_selected_item`，不创建关系、不写关系事件；只有“开始推进”创建关系。

普通顾问从任一推荐方向开始推进时，买家需求和标的都必须归本人负责：

- 为买家找标的：会话锚点买家需求归本人，候选标的也必须归本人；
- 为标的找买家：会话锚点标的归本人，候选买家需求也必须归本人；
- 管理员可以跨负责人创建关系。

因此关系创建服务的权限地板应校验关系两端的 `owner_user_id`，不能继续沿用“能看见任一侧即可创建”。该规则也会约束详情页的“关联对手方”入口，确保用户不能绕过推荐页 guard 操作他人对象。

已有跨负责人关系不删除、不改负责人，仍按现行规则对双方负责人和管理员可见；新的跨负责人关系由管理员协调创建，或先完成负责人调整后再由顾问创建。

推荐收藏接口按当前 `mode` 校验候选主实体负责人：正向校验标的，反向校验买家需求。移出由当前用户创建的收藏不受对象后续转交影响，并且不再写关系事件。

### 3.7 验收要点

1. 反向候选卡准确展示买家需求负责人，判断依据是 `buyer_intent.owner_user_id`，不是买家主体负责人。
2. 他人负责或未指派买家需求的四个入口均只弹提示，无跳转、无 API 请求、无状态变化。
3. “只看我负责的”只保留本人负责的买家需求，不重跑推荐。
4. I1 与 T2 处于尽调中/协议阶段时，为 T1 推荐 I1 会显示“正与其他标的深入推进”。
5. T1 与 I2 深入推进但 I1 没有其他深入关系时，为 T1 推荐 I1 不得误标。
6. 标的详情推进 Tab 只显示“正与其他买家深入推进”；买家需求详情推进 Tab 只显示“正与其他标的深入推进”。
7. 早期状态、已成交和已关闭状态均不触发“正在深入推进”。
8. Network 响应和页面均不泄露其他关系的对象名称、ID 或具体阶段。
9. 正反向加入推荐列表都只写收藏；开始推进才创建关系。
10. 普通顾问直接调用 API 关联任一端由他人负责的对象时返回 `403`；管理员成功。

## 四、实施边界

- 不改推荐初筛、代码打分、深评排序和报告算法；
- 不修改数据库 schema，无需迁移；
- 不修改 Prompt；
- 不改变推荐结果跨负责人召回原则；
- 不在本轮重做全局实体可见性或关系可见性模型；
- 收紧关系**创建**权限为“两端均归本人或管理员”，但不收紧已有关系的可见性；
- 实施完成后，把双向推荐的最终展示、负责人操作边界和推荐列表语义合并回 `docs/系统总纲.md`。

## 五、实施与验收记录

2026-08-03 已按本方案完成实施，未修改数据库 schema、Prompt、推荐初筛、代码打分、深评排序或报告算法。

落地结果：
