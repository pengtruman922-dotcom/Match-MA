# 买家需求列表改造施工单（0730）

对应页面：买家管理（`/buyers`）→ `frontend/src/features/buyers/IntentsList.tsx`（渲染的是**并购需求列表**，`PartiesList.tsx` 当前未挂载）。

## 一、目标与根因

三个问题，按重要性排序：

1. **「关键需求」列消费的是影子字段。** `compactRequirementNotes()`（`presentation.tsx`）读的是 `industry_primary` / `industry_secondary` / `region_scope_summary` / `preferred_listed_status`。前三个不在需求字段契约（`backend/app/registry/indicators.py` 的 BUYER_INDICATORS）里，详情页的 registry 驱动编辑器**不渲染它们，用户改不了**；`region_scope_summary` 在契约里但标注「地域摘要（兼容）」且 `default_effect=deep_eval`。
2. **顶部筛选器同样查影子列**，「行业」「上市要求」两个筛选器的口径已经和详情页断开。
3. **操作列必然换行。** colgroup 声明 112px，最大屏实得约 122px，减去 `px-4` 只剩 90px；`录入⌄`(76) + `✨推荐标的`(80) + gap = 160px。且该 flex 容器缺 `whitespace-nowrap`。同时缺单条删除。

## 二、范围

**做**：关键需求列重建、筛选器切到契约字段、操作列加宽 + 冻结列 + 单条删除、多方案角标。

**不做**（本单明确排除）：
- 需求摘要（`intent_summary`）链路 —— 见《买家需求摘要链路施工单0730.md》，本次不实施。
- `budget_min_yuan` / `budget_max_yuan` 的归属判定。
- `industry_primary` / `industry_secondary` / `preferred_listed_status` 三个影子列的清理（本次只停止在列表消费，列和写入链路保留）。
- 「推荐状态」表头不改名。

## 三、后端改动（`backend/app/api/routes/buyer_intents.py`）

无 schema 变更，**不需要迁移**。

### 3.1 `BUYER_INTENT_OUT_COLUMNS` 增加方案信息

```sql
(select coalesce(jsonb_agg(s.label order by s.sort_order, s.created_at), '[]'::jsonb)
   from buyer_intent_scenario s
  where s.buyer_intent_id = bi.id
    and s.team_id = bi.team_id
    and s.workspace_id = bi.workspace_id
    and s.active
    and s.deleted_at is null) as scenario_labels
```

`BuyerIntentOut` 增加 `scenario_labels: list[str] = []`。数量由前端取 `length`，不另加字段。

### 3.2 `list_buyer_intents` 筛选条件换列

| 筛选器 | 原条件 | 新条件 |
|---|---|---|
| industry | `concat_ws(' / ', industry_primary, industry_secondary) = :industry` | `bi.industries_json ? :industry` |
| region | `bi.region_scope_summary = :region` | `exists (select 1 from jsonb_array_elements(bi.region_constraints_json) rc where rc->>'province' = :region and coalesce(rc->>'effect','preferred') <> 'excluded')` |
| listed_status | `bi.preferred_listed_status = :listed_status` | `bi.acceptable_listed_status_json ? :listed_status` |
| requires_consolidation | 不变 | 不变（`requires_consolidation` 本就在契约内，非影子列） |

> **实施偏离 1**：原计划把 `listed_status` 收敛为 `Literal["listed","unlisted","pre_ipo"]`，实施时放弃。原因：过期书签里的旧值（`any` / `unknown`）会触发 422，而前端 `fetchData` 的 `.catch(() => {})` 会把错误吞掉，表现为列表永久空白且无提示。保持 `str` 时未知值经 `?` 运算自然匹配 0 行，用户能看到「暂无匹配」并自行清除筛选。

> **实施偏离 2**：所有 `jsonb_array_elements*` 展开前统一套 `_JSONB_ARRAY` 守卫
> （`case when jsonb_typeof(col) = 'array' then col else '[]'::jsonb end`）。
> 这些函数遇到非数组值会在运行时报错，单条脏数据即可把列表或筛选项接口打成 500。

### 3.3 `buyer_intent_filter_options` 选项来源换列

- **industries**：`jsonb_array_elements_text(industries_json)` 聚合计数，只出一级行业。
- **regions**：`jsonb_array_elements(region_constraints_json)` 取 `->>'province'`，过滤 `effect <> 'excluded'`，按省聚合。
- **listed_statuses**：`jsonb_array_elements_text(acceptable_listed_status_json)` 聚合，labels 用 `{listed:已上市, unlisted:未上市, pre_ipo:拟上市}`。
- statuses / consolidation_requirements / owners 不变。

## 四、前端改动

### 4.1 `types/api.ts`
- `BuyerIntent` 增加 `scenario_labels?: string[]`。
- 补 `acceptable_control_paths_json?: string[]`（后端一直在返回，TS 类型漏了）。

### 4.2 `features/buyers/presentation.tsx`

删除 `compactRequirementNotes()`、`listingRequirementLabel()`、`marketCapRangeLabel()`（仅此处使用），新增：

```ts
export type RequirementChip = { key: string; label: string; effect: 'required' | 'preferred' };
export function requirementChips(item: BuyerIntent): { industry: RequirementChip[]; conditions: RequirementChip[] };
```

**5 个维度、2 行：**

| 行 | 维度 | 来源列 | 默认作用 |
|---|---|---|---|
| 1 | 一级行业 | `industries_json` | required |
| 1 | 二级行业 | `industry_l2_json` | preferred |
| 2 | 上市状态 | `acceptable_listed_status_json` | preferred |
| 2 | 营收下限 | `min_revenue_yuan` | required |
| 2 | 净利下限 | `min_net_profit_yuan` | required |
| 2 | 地区 | `region_constraints_json`（省级去重，排除 `effect=excluded`） | preferred |

**三条硬规则：**
1. 作用取 `condition_effects_json[列名]`，缺省时用上表默认值（默认值是对 `indicators.py` 的**有意复制**，改契约默认值时需同步，代码里留注释指回）。
2. **`effect === 'deep_eval'` 的维度一律不渲染。**
3. 多值维度「前 2 个 + `+N`」收敛，`title` 挂全量。

**视觉**：`required` 实心（`bg-gray-100 text-gray-700`），`preferred` 描边（`border border-gray-200 bg-white text-gray-500`）。

**未解析兜底**：`processing_state.overall_status !== 'succeeded'` 且无任何 chip 时，整列显示 `raw_requirement_text` 摘录（斜体灰，`line-clamp-2`）。

## 五、验收用例

1. 关键需求列不再出现 `region_scope_summary` / `major_risk_tolerance_summary` / `premium_tolerance_summary` 的内容。
2. 一条需求有 3 个一级行业时，「行业」筛选器选其中任意一个都能命中该行；筛选前后行内行业 chip 与筛选值一致。
3. `condition_effects_json` 把 `min_net_profit_yuan` 设为 `deep_eval` 后，该 chip 从列表消失；设为 `preferred` 时变描边。
4. 1280 宽窗口下横向滚动时，需求名称、买家名称、操作三列保持可见且背景不透明。
5. 操作列三个按钮在 1280 和 1440 两种宽度下都单行显示。
6. admin 点「🗑删除」→ 确认 → 行消失、总数减 1、筛选项计数更新；非 admin 不显示该按钮。
7. 有方案的需求显示角标，hover 出方案列表；无方案的不显示。
8. 未解析的需求，关键需求列显示原始需求文本摘录。

## 六、实施结果与存量数据实测

前端已实施并对生产 API（35 条需求）实测，契约字段填充率：

| 维度 | 契约字段 | 填充率 | 列表表现 |
|---|---|---|---|
| 一级行业 | `industries_json` | **32/35** | 正常 |
| 二级行业 | `industry_l2_json` | **0/35** | chip 永不出现 |
| 上市状态 | `acceptable_listed_status_json` | 13/35 | 部分出现 |
| 营收下限 | `min_revenue_yuan` | 19/35 | 部分出现 |
| 净利下限 | `min_net_profit_yuan` | 20/35 | 部分出现 |
| 地区 | `region_constraints_json` | **2/35** | chip 几乎不出现 |
| （对照）旧地区列 | `region_scope_summary` | 29/35 | 已停止消费 |
| 条件作用 | `condition_effects_json` | **0/35** | 实心/描边全部走默认值 |

**结论：地区维度在存量数据上实际不可用。** 结构化地区只有 2/35，而被停用的自由文本旧列有 29/35 —— 说明存量需求绝大多数没走过新解析链路。这不是实现缺陷，是数据缺口。

**不采用的补救方案**：让地区回退读 `region_scope_summary`。该列 `default_effect = deep_eval`，回退等于违反本单第 4.2 节的规则 2（deep_eval 不进列表），也把刚拆掉的影子列消费又装回去。

**建议的补救**：对存量需求批量重跑解析，填充 `region_constraints_json` 与 `industry_l2_json`。**待决策，本单未实施。**

## 七、风险
